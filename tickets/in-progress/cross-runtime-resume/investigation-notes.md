## Findings

| ID | Finding | How established |
| --- | --- | --- |
| F-01 | The Work Journal is derived from raw traces, rendered with no model, rebuilt on demand (`WorkJournalService.ensureCurrent`); one file per raw-trace file; the manifest has ONE `runtime_kind` per run, which selects the per-runtime tool translation. `docs/modules/agent_work_journal.md`, `work-journal-models.ts`. | Read |
| F-02 | The journal omits model reasoning, shortens outputs over 40 lines (first and last 20), shows a compaction only as the boundary between files, and has no result for an open tool call (`Tool result (call not in this file)` only for results). Same doc § Rendering. | Read |
| F-03 | Journals are large: largest per runtime in the user's data: Codex 22.6 MB (118 files), Antigravity 4.1 MB (13), Claude 9.2 MB (5), AutoByteus 1.4 MB (7); 4,083 journals (Codex 2,476; Claude 652; AutoByteus 537; no runtime recorded 345; Antigravity 72; Grok 1). A whole journal cannot be handed to a new runtime. | Measured (manifests, read-only) |
| F-04 | **No raw-trace record exists for a failed turn.** Across 713 run folders the trace types are only tool_call, tool_result, assistant, reasoning, user, tool_continuation, system_instruction, operation_boundary, system_task_notification, provider_compaction_boundary, llm_request_recovery; source events include only TURN_COMPLETED (549), AgentTurnInterruptedEvent (120), TURN_INTERRUPTED (3), TOOL_EXECUTION_FAILED (373). A run that ends on a usage limit, sign-out or unavailable model leaves nothing saying so; the journal cannot say why a run stopped. The reason exists only in the live ERROR event (`AgentRunEventType.ERROR`; Codex/Claude converters), which `AgentRunInputLifecycle` turns into a command failure. | Measured (scan of 713 `raw_traces_active.jsonl`) + Read (event converters) |
| F-05 | The journal updater runs on TURN_COMPLETED, TURN_INTERRUPTED and COMPACTION_STATUS only. A failed turn probably triggers none of them, so the journal lags until the next `ensureCurrent`; but raw traces are written as events arrive, and `ensureCurrent` re-renders the open file on every call, so a resume can regenerate the journal first. | Read (doc § Keeping It Current); the failed-turn trigger is `Unclear` (U-1) |
| F-06 | An external-runtime run restores from ONE durable provider session ID (`platformAgentRunId`) of ITS runtime (`buildAgentRunRestoreRuntimeContext`: Codex thread, Claude session, AGY conversation, Grok/ACP). The stopped-run settings update keeps "runtime kind ... fixed". A different runtime cannot reload the old session; it must start a new provider session. | Read (`agent-run-restore-context-factory.ts`, `docs/modules/agent_execution.md`) |
| F-07 | Putting a second runtime's work into the same run folder would mix runtimes in one raw-trace stream while the journal manifest and translation assume one runtime (F-01), and the run's identity, token usage and history rows are per run. So "same run, runtime changed" needs changes to the journal and identity; "a new linked run" needs none of them. | Read (inference from F-01, F-06; not run) |
| F-08 | Run end state in real data: of 485 runs with at least 5 records, 393 end on an assistant reply; 92 end on something else; 18 have a tool call without a result in the last turn. These are proxies for "stopped mid-work" (a user stop or a restart looks the same). | Measured |
| F-09 | A fact-based hand-over note (no model) is 1.7–3.3 KB for journals of 178–690 KB (76–400 times smaller) and holds: original request, latest user messages, last turn's tool use, last agent reply, open tool calls, files changed, path to the journal. | Reproduced on 4 isolated copies (Claude, Codex, Antigravity, AutoByteus) with `probes/handover_note_probe.py` |
| F-10 | Weaknesses of the fact-based note, shown by the probe: (a) the "original request" can be a finished old topic (the AutoByteus copy starts with "write a short poem" and ends on VPN work), so a long multi-topic run needs "latest requests", not the first; (b) `file_changes.json` exists for only 142 of 713 runs, and a Codex copy edited files only through shell commands (`python3` heredoc, `sed`), so the journal shows no `Edit file:` lines for them; changed files must be read from the workspace (`git status`/diff), not from notes; (c) all 4 copies were finished runs, so "mid-work" quality is not yet shown (U-4). | Reproduced / Measured |
| F-11 | A run's way to look earlier work up exists: tool `search_memory` returns pointers (journal file, lines, day) and the agent opens the lines with a file tool (`docs/modules/memory_search.md`). Whether each runtime's sandbox lets its file tool read another run's memory folder is not yet shown (U-2). | Read |
| F-12 | Memory layers today: raw traces (all runtimes); Work Journal (derived, neutral); memory search (journals); native compaction summary (agent's own model, inside the native `working_context_snapshot.json`, native runtime only); episodic/semantic summaries retired (5 runs, newest 2026-08-15; library code left, FU-003 of autobyteus-185). **No runtime-neutral summary of "what this run did / where it stands" exists.** autobyteus-185 measured model-written summaries from the journal skeleton with a local model (Qwen3.6-35B-A3B): good quality, small search gain (#1 hit 22 vs 20–21 on 234 runs), backlog ~4 days of GPU then ~40 min/day; the user then said "we don't generate a summarize for now" (FU-005, not sent). | Read (`agent_memory.md`, `tickets/done/work-journal-search/follow-ups.md`) |
| F-13 | Creating a run of an agent definition on a chosen runtime/model with a first message already exists (`AgentRunService.createAgentRun`/`prepareAgentRun`, launch configuration with runtime and model); no "continue in a new run" or fork exists. | Read (grep) |
| F-14 | The restart-and-resume chain (autobyteus-283 to 289) restores the same run on the same runtime and sends a restart notice from a system sender (decisions DEC-1…DEC-8 of that Task, requirements Approved SR-002). Its record of mid-turn runs and its notice are reusable by this design; this ticket must not change them. | Read (own Task documents) |
