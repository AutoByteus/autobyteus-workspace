## Current Implementation Summary

The implementation replaces the append-only token ledger runtime with an awaited, transactional, one-row-per-canonical-run fold. Current token services, repositories, statistics, GraphQL, activation, and bootstrap use only `token_usage_run_records`. Historical table knowledge is confined to registered app-data migrations. Incomplete consolidation gates historical reads and every pre-existing-run restore before provider construction while permitting unrelated capabilities and newly allocated current-only runs. Consolidation rejects any source/target run-ID intersection before mutation and otherwise imports, validates, and deletes source rows in one SQLite transaction. Both released 20260730 source-shaping migrations are repaired in place with bounded keyset/CAS/scalar work. Settings copy and typed errors describe run-created-range/lifetime-total semantics and degraded migration state truthfully. `IR-002` through `IR-007` preserve the reviewed BigInt/public boundary, focused pricing ownership, mixed-currency explanation, cache-state reduction, released unknown-input transformation, latest-base restore lifecycle, and deterministic nullable Prisma/SQLite scalar transport. `IR-008` implements the SR-009 audit envelope: every current migration-record read SQL-projects an absent, exact bounded, omitted-details, or counts-unavailable summary before Node materialization. Ordinary startup `runPending()` reaches a registered, startup-only, non-gating compactor that owns only the two terminal 20260730 audit records and their regular logs, preserves the original outcome tuple/counts, compacts valid row-linear evidence to at most 64 KiB, leaves unsupported sources intact with bounded warnings, and retries only nonterminal partial progress. `IR-009` makes the public retry capability execution-policy-aware: startup-only definitions never advertise a manual Retry action, while failed or stale-running attempts still retry on the next ordinary startup and terminal warnings remain skipped.

## Important Assumptions

- Migration execution has one writer, stable normal SQLite behavior, sufficient permissions/resources, and the existing runner's ordinary retry semantics, as approved by `data-migration-conventions.md`.
- Quit, kill, shutdown, and power loss are one ordinary incomplete SQLite attempt; no cause-specific recovery machinery is required.
- The canonical run allocator remains the new-run uniqueness authority. Consolidation independently enforces zero legacy/current `run_id` intersection before mutation, so allocator correctness is not the only safety check.
- Legacy numeric IDs and public numeric conversions must satisfy explicit safe-integer boundaries. Durable token totals remain BigInt/SQLite integer values until an API boundary deliberately narrows them.
- SQLite semantic type, computed-expression affinity, Prisma result metadata, and JavaScript runtime representation are separate contracts. Migration-derived scalars require a deterministic SQL transport and exact validation rather than a TypeScript raw-query annotation.
- Terminal audit compaction assumes the closed two-ID source set, one migration writer, stable ordinary filesystem/SQLite behavior, and runner retry. A stored log is writable only when its resolved regular-file path remains inside the configured app-data-migration log directory.
- No hostile tampering, arbitrary corruption, compromised/adversarial writers, or kernel/device/syscall recovery contract is in scope.
