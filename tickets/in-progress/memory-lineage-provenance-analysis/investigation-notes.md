## Request Context

The user asks how compaction should transform raw traces/work evidence into episodic and semantic memory while retaining explicit source and time provenance across runtimes. The user specifically asks exactly who creates a supporting pointer, whether the LLM needs internal storage metadata, and whether detailed per-entry citations during large compaction would impose excessive work. On 2026-07-22 the user authorized formal ticket work and requested a detailed foundation contract covering every use case. On 2026-07-27 the user requested an explicit previous-versus-target implementation statement. The user then rejected duplicated evidence/prompt content and artificial locator or generation/activity identities. After seeing `Assistant work notes` in the proposed compactor input, the user asked why it exists and directed omission of separate reasoning. The user then requested one XML-style outer boundary, but corrected the first proposal because separating “current memory to revise” from work evidence exposed application mechanics. The final direction is that compaction should look like compacting the logical conversation context sent to the working LLM: the planner includes the projected compacted-memory user region plus selected later units as one ordered prefix, and the renderer encloses that natural User/Assistant/Tool transcript in one `<conversation_history>` boundary. The user clarified that both native compaction and generated Work Evidence should use one general core `CondensedToolCallRenderer`. Source adapters own selection and call/result correlation; the renderer accepts only `name`, `arguments`, a discriminated `result`, `error`, or `no_outcome(status)`, and the per-value bound, then returns only the condensed body. Normal Work Evidence has a correlated terminal outcome; if no terminal record genuinely exists, the same renderer preserves the truthful status and emits `result: not available`. The consumers do not share source selection, timestamps, envelopes, files, or orchestration. Internal metadata alone preserves exact prior-memory origin versus R(n) raw-ref ownership. After API-REV-006, the user rejected the fixed one-to-three-episode/twenty-fact policy in both prompt layers and clarified the quality objective: compacted memory is good when the agent can continue correctly after the context refresh. The prompt must ask for the smallest sufficient semantic structure, preserve distinct phases only when that distinction matters, remove chatter/repetition/obsolete state, and prioritize continuation-critical constraints, decisions, unresolved work, preferences, and artifacts. The user later clarified that no ticket-specific token ceiling is permitted; the LLM chooses the natural number of episodes and facts under unchanged launch/provider behavior. ## Findings From Code / Docs / Data / Logs

Complete synthesis is in `provenance-methodology-analysis.md`.

Key conclusions:

1. Direct artifact/activity lineage must be persisted during compaction, not reconstructed later.
2. Raw leaf IDs already exist, but current episode/semantic models lose them.
3. The implemented SR-004 planner includes the compacted-memory message-local constituent in the natural compactable prefix while collecting archive membership only from newly selected raw-backed natural units. `MemoryManager` separately captures the current lineage tail outside the strategy and maps that unchanged baseline to `previousCompactionId`; absent/empty lineage means no current memory and a null predecessor.
4. The target recurrence is `M(n) = compact(M(n-1) + R(n))`; output is one complete bounded successor, not a delta.
5. Only the newest successful compaction output bundle is current; older outputs remain immutable/inactive history.
6. One `CompactionLineageRecord` stores only the existing successful `compactionId`, optional `previousCompactionId`, one completed raw-trace archive file's existing run-relative `file_name`, and produced episode/semantic IDs—not a parallel activity/generation ID, raw membership/content, fabricated segment ID, internal boundary key, rendered prompt, or copied transitive closure. Success requires non-empty newly selected raw-backed R(n); M(n-1) alone is not eligible and is never re-archived.
7. Recursive origin accepts run/member scope plus explicit artifact kind and ID, distinguishes direct inputs from ultimate raw roots, uses cycle protection/deduplication, and may use rebuildable indexes without changing authority.
8. Unknown typed artifact IDs return `not_found`; a missing/inconsistent relation inside a referenced current-format chain is an integrity error. No resolver reads discarded row files.
9. The directly referenced raw-trace archive file's source interval, recursive root interval, derivation time, and lineage append/derivation ordering are distinct.
10. Every episode and accepted semantic fact in the model-decided complete replacement shares one direct recurrent-input pointer; detailed localization/fine citations remain outside scope. No application layer may discard a valid item solely because it is fourth or twenty-first.
11. The strategy returns an IDless proposal containing selected new raw IDs, retained messages, normalized content, and execution metadata; it carries no prior compaction or output identity. `MemoryManager` reuses the pending `compactionId`, validates the separately captured baseline lineage tail, assigns episode/semantic IDs, constructs/validates the accepted candidate, and maps the baseline head to `previousCompactionId`.
12. Current compacted-memory/current-user adjacency is not a safe provider-neutral assumption; WorkingContext finalization owns natural composition and typed constituent provenance.
13. Raw IDs/content remain immutable across archive movement, and prior-memory ancestry is never re-archived as new raw activity.
14. Derived compaction outputs do not belong in raw traces; Event Monitor remains active-activity only.
15. Runner/parser failure leaves the lineage tail and baseline installed/snapshotted WorkingContext unchanged while retaining the pending `compactionId`; no staged publication journal is introduced.
16. Valid schema-v5 snapshot remains normal resume authority for finalized messages, media/tool structures, and message-local constituent ranges only. It contains no compaction/output/current-state identity. Separately, absent/empty lineage means no current compacted memory; otherwise its last valid record lists the exact current output IDs. One required startup app-data migration deletes pre-lineage episodic/semantic JSONL, WorkingContext snapshots, and compacted-memory manifests while preserving raw traces/manifests. Normal runtime contains no historical decoder or fallback.
17. After one thousand compactions, WorkingContext contains only M1000 rather than an accumulation of M1..M1000; the LLM chooses M1000's natural item count, while durable older outputs/provenance may grow separately.
18. SR-004 already removed the historical `Assistant work notes` formatting and implemented one reasoning-free XML-bounded User/Assistant/Tool history containing projected M(n-1) plus R(n). The remaining rendering defect is narrower: internal constituent expansion can split one canonical user turn; SR-010 reuses the existing finalizer before labels.
19. SR-004 already implemented the tight shared core Tool/value renderer and explicit head/tail omission for both compaction and generated Work Evidence while preserving separate source/envelope ownership. SR-010 leaves that boundary unchanged.
20. Normal accepted publication has one order: archive R(n), persist output rows, append the validated successful lineage record as the new current head, install finalized context, persist message-only v5, then clear pending state. Strategy/LLM cannot assign produced IDs or publish any of those artifacts.
21. `compaction_lineage.jsonl` is the only persisted compaction-history/current-state authority: successful records only, absent/empty means no current compaction, and the last valid record is current. Appending requires a unique `compactionId` and `previousCompactionId` equal to the prior tail. No `compaction_state.json`, snapshot-level output IDs, replacement manifest, or activation field is added.
22. The reset migration, migration runner, and `startConfiguredServer` have separate responsibilities. The reset returns `FAILED` for any discovery/deletion failure; the runner persists all attempted required results and throws after detecting any non-startable status; the real caller logs and rethrows before bootstrap/build/listen. Existing `SUCCEEDED` and `SUCCEEDED_WITH_WARNINGS` remain startable.
23. Semantic sizing has four relevant owners: `agent.md` owns the concise origin/personal-style natural task and stable quality/schema policy; the operation user message owns only renderer-produced canonical history turns; parser/normalizer own structural/per-entry validation and cleanup without count caps; acceptance owns non-empty/application identity invariants. The LLM chooses the natural item count. Internal message constituent ranges remain available for planning but do not create artificial model-visible turns. Launch/provider output-token configuration is unchanged. This is a bounded local extension to DF-L02/DF-L08, not a new primary spine or persistence model.
24. Lineage normalization is a fifth relevant structural gate in the accepted path. Its 3/20 maximum is not a provenance invariant and must be removed, while non-empty episode, uniqueness, safe archive filename, scope, predecessor, timestamps, execution metadata, and integrity validation remain.
25. `promptContractVersion` audits the producing LLM contract, not the lineage JSON shape. Existing value `1` truthfully means the implemented SR-004 fixed-count/system-plus-duplicated-operation contract. New value `2` means the approved natural system prompt, history-only operation payload, and canonical-turn contract. Mixed `1 -> 2` current-schema chains are direct-use and require no rewrite.
26. Message-local constituent metadata contains only local kind/range and raw-backed natural references. `MemoryManager` separately captures the lineage tail and maps it to `previousCompactionId`; neither rendering nor snapshot carries that ID.

## Constraints / Dependencies / Compatibility Facts

- Raw trace file paths and `active` source labels are not stable logical identities.
- The active file has mutable membership; completed archived original rows remain historical evidence. Neither active nor archive raw rows are current-context snapshots.
- Raw trace `seq` is per turn, not a run-global order.
- Work trace summary hash covers visible/redacted rendered content and deliberately excludes separate reasoning; it is not a complete raw-corpus fingerprint or evidence-selection record.
- Current work trace files are overwritten in place and can no longer reproduce an old input snapshot by path alone.
- Generated Work Evidence Markdown is not a native compaction input. Its reasoning omission and combined `tool:` body inform the contract, but native compaction renders planner-selected WorkingContext without raw timestamps or the file/manifest wrapper. Both paths may reuse the core visible-value/Tool-body/head-tail capability with different bounds.
- The implemented compactor already omits `reasoning_content` and uses shared per-value head/tail bounds. Provider-required reasoning may remain in WorkingContext. SR-010 changes only canonical turn reconstruction and prompt-layer text ownership.
- Cross-runtime normalization must not erase run/runtime/provider context needed for audit.
- Provenance must not force retention of provider-private reasoning or transport envelopes.
- Provider transport behavior is not uniform: current Anthropic combines adjacent turns, current tested OpenAI/DeepSeek/Grok endpoints accept them, Gemini guidance expects alternation, and Mistral templates may reject non-alternation.
- Multiple successful provider probes do not make adjacent-user transport a stable cross-provider contract.
- Canonical `WorkingContext` finalization, not provider rendering, owns memory/current-request semantic combination.
- Active membership may change after originals are archived, but original raw event IDs/content remain unchanged and no derived compacted-memory row is labeled as observed evidence.
- Implemented accepted compaction persists archive/output/lineage/context/snapshot through separate ordered writes, with the appended successful lineage position serving as current. No supported crash premise justifies a new journal in this ticket.
- Implemented snapshot bootstrap is current-only: it accepts strict v5, verifies the message-local memory region against the independent lineage head, and has no semantic schema gate, global manifest authority, or old-schema restore branch. Historical-file deletion belongs only to the startup migration before runtime.
- A compacted-memory constituent is message-local structure only: `kind` plus character range inside a finalized user message. Projector/finalizer/serializer/planner preserve that boundary without compaction/output IDs. `MemoryManager` alone reads the lineage baseline and maps its tail to `previousCompactionId`; the current-output loader alone resolves the tail's output IDs.
- Compactor output-token configuration is an existing provider/launch concern, not a semantic item-count policy or memory-schema field. SR-006 leaves it unchanged.
- Existing non-cardinality parser/lineage safeguards remain. SR-010 removes episode, total-fact, per-category, and lineage-membership count truncation/rejection and adds no numeric token ceiling. Prompt audit versioning changes from new-write value `1` to `2`; the reader preserves supported values `1 | 2`.
