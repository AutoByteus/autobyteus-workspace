# Requirements Doc

## Status (`Draft`/`Design-ready`/`Refined`)

Refined and approved as the design basis on 2026-07-30 — SR-004 incorporates the user's separation-of-concerns clarification and the architecture round-3 corrections. The append-only lineage tail is the sole current-compaction authority; `working_context_snapshot.json` owns finalized messages and message-local constituent structure only; no `compaction_state.json` or replacement manifest exists. The required clean reset remains fail-closed on the real `startConfiguredServer` path.

## Goal / Problem Statement

Define and then implement a unified, evidence-grounded memory contract in which:

- raw traces remain original runtime activity evidence;
- work evidence is the earliest memory-ready view, resolved from referenced authoritative raw records rather than persisted as copied content;
- every successful compaction retains explicit direct lineage to the preceding successful compaction whose output influenced it and to newly selected original work;
- WorkingContext and its persisted snapshot represent what the LLM currently sees/remembers;
- recurrent compaction consumes the current compaction output plus newly selected settled activity and produces one bounded complete replacement output;
- the compactable logical WorkingContext prefix—including the existing compacted-memory user region when present—is supplied to the compactor as one naturally ordered conversation history that omits private reasoning;
- native compaction and generated Work Evidence reuse one core-owned, deterministic readable-tool/text presentation policy for redaction, serialization, and explicit head/tail omission while retaining separate sources, envelopes, and consumer bounds;
- Event Monitor projection remains an active-raw-activity view rather than a memory/context view; and
- cross-runtime source identity and higher-memory provenance remain truthful.

The detailed intended behavior is normative in `memory-context-and-lineage-contract.md`, and `use-case-data-flow-spine-map.md` makes every use case traceable through its complete production or approved target-production path. This stage establishes the requirements basis; implementation design begins after approval of those normative artifacts and this document.

This is a bounded change to native AutoByteus structured memory compaction, compactor conversation-history rendering, shared readable-tool/text presentation used by generated Work Evidence, lineage lookup, canonical `WorkingContext` finalization, snapshot persistence/restore, and one startup app-data reset. It is not a general memory-evolution or external-runtime compaction project.

### Explicitly unchanged

- Raw trace records remain original user/assistant/tool/runtime activities; their IDs and content are not rewritten into summaries.
- Successful compaction may move newly selected natural raw records from active storage to archive exactly as today; prior-memory ancestry is never re-archived as though newly selected.
- Event Monitor continues to read and page active raw traces only.
- Readable server work-trace Markdown remains a separate generated presentation artifact and is not read as the native compactor input. Its source enumeration, timestamps, Markdown/file/manifest contract, reasoning omission, and generated-artifact ownership remain; only visible-value serialization/redaction and oversized-field presentation move to the shared core policy, replacing silent prefix-only loss with explicit head/tail omission.
- Storage-only external runtimes continue recording normalized raw activity and provider/session boundaries; this ticket does not add AutoByteus episodic/semantic compaction to them.
- There is no separate tool-result condenser: settled tool-call/result groups continue to be rendered directly into normal compaction input, while live/incomplete groups remain protected. Each selected group appears as one `Tool` block with `name`, `status`, `arguments`, and `result` or `error`; rendering changes from whole-item prefix-only clamping to explicit bounded variable-field head/tail omission.
- A one-time app-data reset intentionally discards pre-lineage episodic/semantic rows, the pre-v5 WorkingContext snapshot, and the obsolete compacted-memory manifest. Raw traces and raw-trace manifests remain untouched. No current runtime reader recognizes or projects the removed derived state.
- Current runner/parser failure and retry behavior remains: no candidate output or lineage record is published, the lineage head remains unchanged, and the same pending `compactionId` is retried on the next normal request.

## Investigation Findings

- At the latest 2026-07-30 validation point, the tracked base is `origin/personal@34f3fe97a281a9b85e02409bd753ad132df13d20`; the task branch is based exactly on it.
- Current Event Monitor/run-history projection is active-only. Initial projection uses `includeArchive: false`; earlier paging reads the active snapshot and never opens archive segments.
- Shared work-trace projection is a separate use case and still reads complete archive segments plus active traces.
- Working context, raw activity traces, and durable compacted memory are already distinct concerns in the canonical memory design.
- A valid working-context snapshot is already the normal restore source. It persists provider-neutral messages, structured media/tool data, and neutral metadata.
- The repository has an established startup app-data migration registry and runner invoked before built-in-agent bootstrap. Aggregate local persisted-state evidence includes 200 schema-v3 snapshots and sparse episodic/semantic usage, while the user's dominant Codex runtime does not use native structured memory. This makes an explicit destructive reset of derived memory low-risk and gives it a real pre-runtime product path.
- Current server memory-view parsing of snapshots drops media/provenance and assigns no message timestamps, confirming that it is not an Event Monitor event source.
- Current compaction plans from `WorkingContext`, excludes an existing synthetic memory unit, maps selected natural-message provenance to raw IDs for archive/prune, appends new memory rows, and restores one bounded mixed projection plus retained messages. The target instead consumes the current successful compaction's output as recurrent input and activates only the complete output of the new successful `compactionId`.
- Current compactor rendering exposes `reasoning_content` as `Assistant work notes:` and applies prefix-only whole-line truncation, while the planner excludes the compacted-memory user unit. Generated Work Evidence omits reasoning and already correlates each raw call/result into a readable `tool:` block with `name`, `status`, `arguments`, and `result` or `error`, but its redactor silently keeps only the first 20,000 characters of each cleaned value. The target keeps the sources/envelopes separate while reusing one core readable-tool/text presentation policy with configurable explicit head/tail omission.
- Current request assembly still permits adjacent compacted-memory/current-user messages. Provider live probes succeeded for OpenAI, Anthropic, DeepSeek, and Grok, but Gemini/Mistral contracts show that same-role adjacency is not a safe cross-provider assumption.
- Current compactor-runner/response-parser failure is product-reachable and retries on the next normal user request while preserving the pending operation and producing no memory/archive output. By contrast, no supported current product path was found for interrupted filesystem publication or an invalid built-in projected context; those premises cannot justify a transaction journal in this ticket.
- Standard provenance practice supports explicit application-owned artifact/activity edges and recursive derivation chains. The target records the prior-memory plus completed raw-trace archive-file relation automatically; it still does not require LLM-authored fine citations.

## Recommendations

- Adopt the complete foundation contract without introducing a raw-memory persisted alias.
- Use a recurrent compaction lineage chain with direct `previousCompactionId`/raw-trace-archive-file inputs, cycle-safe traversal, and rebuildable transitive closures.
- Use one reference-only `CompactionLineageRecord` per success: existing `compactionId` + optional `previousCompactionId` + run-relative native-compaction archive `file_name` + produced episode/semantic IDs.
- Bound each complete replacement result to one through three coarse episodes and at most twenty accepted semantic facts so the current output never grows with compaction count.
- Record already-known input/output IDs automatically; retain prompt/selection policy versions and optional integrity hashes, but do not duplicate rendered task or evidence content and do not ask the LLM for citations or storage IDs.
- Add a run-scoped resolver that reports direct inputs and recursive roots for current-format outputs; unknown IDs return `not_found`, and broken current-format chains fail integrity validation.
- Make the output listed by the lineage head a required recurrent compactor seed, append only a successful new record whose `previousCompactionId` matches that head, and finalize its natural memory/current-user composition inside WorkingContext before snapshot/render.
- Keep Event Monitor active-raw only and keep work-evidence/archive access separate.
- Add one required startup app-data migration that removes pre-lineage episodic/semantic rows, WorkingContext snapshots, and compacted-memory manifests while preserving every raw trace and raw-trace manifest. Keep all historical-format knowledge inside that migration and make normal restore current-schema-only.
- Preserve the reachable current pre-write failure behavior: a compactor-runner failure or invalid compactor response leaves baseline context and storage unchanged, and the next normal request retries the same pending in-memory operation.
- Render the planner-selected recurrent WorkingContext prefix as one natural `<conversation_history>` block: projected M(n-1) in its model-visible user-role position followed by selected R(n), with reasoning/backend metadata omitted and each settled call/result represented as a straightforward `Tool` block containing `name`, `status`, `arguments`, and `result` or `error`.
- Extract only the genuinely shared readable presentation core—visible-value serialization/redaction, the tight Tool-body shape, and configurable explicit head/tail omission—into `autobyteus-ts`. Keep WorkingContext planning/XML prompt construction and raw historical replay/timestamped Markdown generation in their current authoritative subsystems.

## Out Of Scope

- Work-evidence chunking and intra-file localization within one work-evidence file.
- Default per-token/per-sentence/raw-row citations for every episode.
- Fine LLM-selected evidence labels/citations; the selected complete compaction input is the only sourcing granularity in this ticket.
- Changes to generated Work Evidence source enumeration, timestamp/order semantics, Markdown filename/manifest contract, or its improvement-flow caller. Replacing silent prefix-only value clipping with the shared explicit head/tail omission policy is in scope.
- A new frontend provenance/origin screen; this ticket supplies the run-scoped backend/core resolver only.
- AutoByteus episodic/semantic compaction or WorkingContext snapshots for storage-only external runtimes.
- A separate tool-result condenser or second LLM summarization pass for tool output.
- Cross-run extraction or one compaction combining independent prior-compaction outputs from multiple runs; the recurrent input is exactly one preceding successful run-local compaction output plus one newly selected run-local natural prefix.
- Separate fact-level correction APIs, invalidation/deletion/redaction tombstones, and reverse-impact traversal. The compactor may consolidate changed understanding, and previous-output projection supersession is part of the approved recurrent behavior.
- Successful compaction with an empty durable-memory projection; the current structured parser requires a non-empty episode.
- Interrupted filesystem publication, crash recovery, staged-file journals, and retry deduplication for partially written compaction state; no supported operational path was established.
- Replacing Event Monitor with a WorkingContext view.
- Adding archived history to Event Monitor paging.
- Persisting provider-private chain-of-thought or unnormalized transport envelopes. Provider-required reasoning may remain in WorkingContext/provider history, but it is excluded from the compactor's work-evidence view.
- Duplicating raw-message, prior-memory, output-memory, tool/media, or rendered-prompt content inside lineage records.
- Byte-for-byte historical compactor-prompt replay.
- Replacing the design's run-local file-backed lineage with a centralized or synchronized lineage database before measured volume and synchronization requirements exist.
- A new “raw memory” storage type separate from work evidence.

## Functional Requirements

- `REQ-001`: The solution package must maintain an evidence-backed current production map for raw activity, active/archive storage, Event Monitor projection, WorkingContext/snapshot, native compaction, episodic/semantic memory, and external-runtime recording.
- `REQ-002`: The implementation contract must preserve the terminology and authority boundaries in the foundation contract: raw traces are original activity/content; work evidence is a reference-resolved memory-ready view rather than another content store; WorkingContext/snapshot is current model context; Event Monitor is active activity; durable memory is derived.
- `REQ-003`: The lineage contract must model one immutable derivation record per successful compaction, keyed only by the existing `compactionId`, with explicit reference-only inputs/outputs and stable run/member scope independent of absolute paths or timestamps. The record must not add parallel activity or generation identities for the same one-to-one successful operation/output bundle.
- `REQ-004`: Every successful native structured compaction must archive exactly its selected raw records in one immutable native-compaction raw-trace archive file and publish exactly one immutable `CompactionLineageRecord` containing the existing successful `compactionId`, optional `previousCompactionId`, the archive manifest entry's existing run-relative `file_name`, produced episode/semantic IDs, derivation/execution metadata, schema/prompt/selection-policy versions, and optional integrity hashes. The strategy returns an IDless content/selection/execution proposal. `MemoryManager` acceptance reuses the pending `compactionId`, verifies that the captured baseline lineage head is unchanged, assigns output IDs, builds and validates the accepted candidate, and its internal committer performs the normal sequence: complete exact raw archive -> persist output rows -> append lineage as the new head -> install finalized context -> persist v5 snapshot -> clear pending. The lineage store must accept only a unique next record whose `previousCompactionId` equals the existing head, or `null` when the file is absent/empty. The record must not repeat raw IDs/content, copy prior-memory content, copy rendered compactor-prompt content, flatten ancestral refs, add a separate activity/generation ID, fabricate a segment ID, or expose the internal archive boundary key. The resolver obtains selected raw membership and direct source interval from the referenced completed file/manifest entry. An absolute filesystem path is forbidden.
- `REQ-005`: The structured compactor must receive one naturally ordered conversation-history rendering of the compactable logical WorkingContext prefix—projected prior memory when present followed by selected new natural history—and return a self-contained replacement output bundle, not a delta: one through three coarse episodes plus at most twenty accepted semantic facts across existing categories and within existing per-entry bounds. The proposal carries content, selected new raw IDs, retained continuation, and execution metadata but no compaction/output IDs or persistence objects. `MemoryManager` retains the application-owned baseline lineage head outside the LLM strategy, reuses the pending `compactionId`, assigns episode/semantic IDs during acceptance, and appends their reference-only lineage only after the output rows exist. The appended tail is the sole current-compaction authority. The LLM emits no evidence citations, compaction IDs, or storage identifiers.
- `REQ-006`: A cycle-safe run-scoped resolver must accept a typed `MemoryArtifactRef` containing `kind: "episode" | "semantic"` plus `id`, locate its producing `CompactionLineageRecord` in the matching output list, validate and read the directly referenced raw-trace archive `file_name` through the archive manifest, and return its selected raw records/interval plus optional direct `previousCompactionId`, derivation time, and recursively deduplicated original raw roots/root interval. Unknown artifacts return `not_found`; a missing or inconsistent record/file in a referenced current-format chain is an integrity error. The implementation must not guess the artifact kind, guess sources, or claim transitive roots were direct inputs.
- `REQ-007`: Repeated compaction must implement `M(n) = compact(M(n-1) + R(n))`: consume the output listed by the last successful lineage record as a direct seed, set that head ID as the new record's `previousCompactionId`, require a non-empty newly selected raw-backed natural prefix R(n), archive only that eligible new activity, generate one complete bounded successor, and keep older compaction outputs immutable/inactive. Appending the successful new record makes it the sole new lineage head; no separate activation pointer exists. M(n-1) alone never makes a new compaction eligible and is never re-archived. Canonical provider-neutral `WorkingContext` finalization before snapshot/render must preserve typed memory/retained/current sections, system/media, and complete tool protocol. Renderers must not own semantic repair.
- `REQ-008`: Raw activity and current model context must remain separate. Event Monitor reads active raw only; newly selected original records archive unchanged; a valid current-schema snapshot is the normal resume source. Before the new runtime is available, one required idempotent startup app-data migration must scan standalone and team-member run directories and remove any pre-lineage `episodic.jsonl`, `semantic.jsonl`, `working_context_snapshot.json`, and `compacted_memory_manifest.json`, while preserving active/archive raw traces and raw-trace manifests. Missing target files are a successful no-op. Any discovery/deletion failure must produce `FAILED`, not `SUCCEEDED_WITH_WARNINGS`; the runner must persist every attempted required result and then throw when a required result is non-startable. `startConfiguredServer` must log and rethrow that failure before `bootstrapBuiltInAgents`, `buildApp`, or `app.listen`; its programmatic promise rejects and the existing CLI rejection handler terminates the process. `SUCCEEDED` and existing `SUCCEEDED_WITH_WARNINGS` remain startable for the existing migration contract. Snapshot schema v5 must persist finalized provider-neutral messages, media/tool structures, and message-local constituent ranges needed to preserve compacted-memory versus retained/current-user boundaries. It must contain no compaction ID, episode ID, semantic ID, lineage object, or current-state field. The lineage file is absent/empty before the first successful current-format compaction; otherwise its last valid record is the current head and lists the exact episode/semantic output IDs. No durable-memory fallback is allowed when lineage is absent. The current semantic schema gate, global compacted-memory manifest, old snapshot fallback, old-row tolerant reader, and every historical-format runtime branch must be removed. Archived compacted inputs must not replay as new activity. Arbitrary corruption and infrastructure loss remain outside the reachability basis.
- `REQ-009`: New lineage fields must use runtime-neutral run/member scope, and native compaction records must retain runtime/provider/model context. Storage-only external runtimes remain raw-evidence providers in this ticket; AutoByteus compaction and snapshot semantics must not be attributed to them.
- `REQ-010`: The compactor task must present one natural rendered conversation history derived from the compactable logical WorkingContext prefix. When M(n-1) exists, its already projected user-role compacted-memory region appears in its actual first non-system position, followed by selected settled R(n) user/assistant units and settled tool-call/result groups in their logical order; it must not be extracted into a separate “current memory” or “memory to revise” section. Exactly one application-generated `<conversation_history>` opening tag and matching `</conversation_history>` closing tag must wrap the complete rendered prefix, with source-originated reserved boundary sequences escaped so content cannot imitate or prematurely close it. Inside the boundary, visible user/assistant content is rendered as `User`/`Assistant`; every selected settled call/result group is rendered as one `Tool` block containing `name`, `status`, `arguments`, and exactly one outcome section, `result` or `error`. The prompt must not add an `Assistant tool call` label. `Message.reasoning_content`, raw reasoning events, `Assistant work notes`, raw/turn/tool-call/backend IDs, generated Work Evidence Markdown, and synthetic occurrence timestamps not present in WorkingContext are excluded. The compactor-specific bound must apply deterministically and independently to each variable message, argument, result, or error value with explicit head-and-tail omission. Internal planning/provenance must still separately identify the producing `previousCompactionId` and only R(n)'s newly selected raw refs for archival, even though the LLM-facing history is continuous.
- `REQ-011`: One general core-owned `CondensedToolCallRenderer` must be used by native compaction and generated Work Evidence. Its input must contain only tool `name`, `arguments`, one discriminated outcome—`result(value)`, `error(value)`, or `no_outcome(status)`—and a consumer-selected per-value character bound. It must provide deterministic visible-value serialization compatible with generated Work Evidence (strings unchanged, nullish values as `null`, JSON-serializable non-strings as indented JSON, stable string fallback), sensitive/backend-text redaction, and configurable head/tail omission using an explicit `… [N characters omitted] …` marker. The renderer must derive `status: success` for `result`, derive `status: error` for `error`, and for `no_outcome` render the supplied truthful status plus the literal line `result: not available`; terminal status must not be accepted independently in a way that permits contradictory status/outcome combinations. Its output must be only the consumer-neutral body containing `name`, derived/supplied `status`, `arguments`, and `result` or `error`, with no `Tool:` header, timestamp, XML/Markdown envelope, source ID, or file metadata. Native compaction may pass only settled `result`/`error` variants. Raw-backed Work Evidence must normally correlate a terminal result/error before rendering and may pass `no_outcome` only when no terminal record genuinely exists. Waiting/correlation remains the source adapter's responsibility; the renderer performs no trace lookup or lifecycle coordination. The omission count must be deterministic for the redacted serialized value, and values at or below the configured consumer limit must remain complete. Native compaction must retain compaction-owned XML/task/budget policy; generated Work Evidence must retain server-owned timestamps, Markdown/file/manifest/source policy. `autobyteus-ts` must not import `autobyteus-server-ts`; neither consumer may read the other's generated output or use one broad mostly-optional event type that mixes WorkingContext, raw replay, timestamps, or file metadata.

## Acceptance Criteria

- `AC-001`: A reviewer can follow current production code from runtime event through active/archive raw storage, active-only Event Monitor, WorkingContext/snapshot, native compaction, and durable episodic/semantic memory without rediscovery.
- `AC-002`: Event Monitor initial and earlier-page scenarios prove that only active raw traces are read, active rewrite expires the cursor, and no archive/snapshot fallback occurs.
- `AC-003`: Successful normal native compaction archives exactly the selected raw records in one complete immutable raw-trace archive file and publishes exactly one immutable/versioned reference-only lineage record containing the existing `compactionId`, optional `previousCompactionId`, that file's run-relative `file_name`, produced episode/semantic IDs, execution/version metadata, and optional hashes. The record repeats no raw IDs/content, memory content, rendered prompt, activity/generation ID, fabricated segment ID, or archive boundary key. The referenced file/manifest entry supplies membership/count/time bounds. Runner/parser failure publishes neither output lineage nor a new compaction archive file.
- `AC-004`: Given run scope plus explicit artifact kind and ID, the resolver can answer “why does this artifact exist?”, “which compaction produced it?”, “which previous compaction and raw-trace archive file were direct inputs?”, and “which selected or recursively deduplicated raw records ultimately influenced it?” while preserving direct-versus-transitive distinction.
- `AC-005`: The directly referenced raw-trace archive file's source interval, recursively derived root interval/completeness status, derivation time, and append/derivation ordering remain distinct.
- `AC-006`: A successful response is a complete replacement output containing one through three episodes and no more than twenty accepted semantic facts; all outputs resolve through the same reference-only lineage record without per-entry LLM citations.
- `AC-007`: Context scenarios cover user/assistant/tool/media composition and recurrent compaction. For C2 the compactor receives M1 plus non-empty raw-backed R2 and only complete bounded M2 becomes current; M1 alone does not create C2. After one thousand successes the renderer receives only bounded M1000, while M1..M999 remain immutable/inactive and recursively sourceable. Archive movement includes only each operation's newly selected natural raw refs.
- `AC-008`: A valid schema-v5 working-context snapshot restores the same logical messages, message-local constituent ranges, media, and tool structures without raw-history reconstruction. It contains no compaction/output IDs. Separately, an absent/empty lineage file means no current compacted memory; otherwise the last valid lineage record is the current compaction and its episode/semantic IDs load the exact current derived output.
- `AC-009`: Through the real `startConfiguredServer -> AppDataMigrationRunner.runPending` product path, a fixture containing pre-lineage episodic/semantic JSONL, a v1-v4 WorkingContext snapshot, an obsolete compacted-memory manifest, active raw traces, completed raw archives, and raw-trace manifests loses exactly the four obsolete derived-state files and retains the raw evidence files byte-for-byte. Missing targets are idempotent no-ops. A discovery/deletion failure is durably recorded as `FAILED`, remains retryable, causes `startConfiguredServer` to reject/rethrow, and proves that `bootstrapBuiltInAgents`, `buildApp`, and `app.listen` were not called. Existing `SUCCEEDED`/`SUCCEEDED_WITH_WARNINGS` results still allow startup. After a successful reset the run starts with no lineage records and no compacted-memory constituent; the first successful native compaction creates C1 with `previousCompactionId: null`. No normal runtime component contains an old-schema reader, compatibility fallback, or inferred provenance.
- `AC-010`: External-runtime scenarios preserve normalized evidence and provider/session boundaries without claiming AutoByteus semantic compaction/snapshot authority.
- `AC-011`: A runner failure or invalid response leaves the lineage head, baseline WorkingContext/snapshot, memory, and raw active/archive state unchanged; the next normal request retries the same pending `compactionId`.
- `AC-012`: The resolver returns recorded direct and recursive origin/time lineage for current-format output IDs. Unknown IDs return `not_found`; broken referenced current-format chains fail integrity validation. No resolver or runtime store queries discarded pre-lineage rows.
- `AC-013`: Methodology/design evidence uses primary standards/specifications/research where external authority is material, current repository code/tests for production behavior, and an explicit reachability classification for every required scenario and rejected premise.
- `AC-014`: A recurrent-compaction prompt scenario containing M1 followed by selected visible user/assistant content, separate assistant reasoning, a settled multi-call tool group, an error outcome, oversized command/output fields, and literal source-provided `<conversation_history>`/`</conversation_history>` text proves that the compactor receives exactly one naturally ordered `<conversation_history>...</conversation_history>` block. M1 appears as the compacted-memory user region that the working LLM actually saw—not in a separate mechanical section—and selected R2 follows in logical order. Source-provided boundary-like text is escaped; no `Assistant work notes`, `Assistant tool call`, reasoning content, synthetic timestamp, raw/backend/tool-call ID, or silent prefix-only clipping appears. Every selected call/result is represented as a `Tool` block with `name`, `status`, `arguments`, and exactly one `result` or `error`; secrets are redacted; and each oversized variable field preserves deterministic head and tail around an explicit omitted-character count.
- `AC-015`: A supported Work Evidence projection containing an oversized tool argument, oversized result, oversized error, redactable values, ordinary short values, and one truthfully outcome-less tool call proves that raw historical replay still produces the same timestamped Markdown/file/manifest/source ordering and `tool:` grammar through the same `CondensedToolCallRenderer` used by compaction. Every oversized variable value preserves deterministic head and tail around the same explicit omitted-character marker/count; short values remain byte-for-byte complete after redaction; the outcome-less call preserves its supplied status and renders `result: not available`; reasoning remains absent; and the native compactor remains sourced from WorkingContext rather than the generated Markdown.

## Constraints / Dependencies

- Current raw `seq` is per turn; exact trace-ID sets remain the safe locator until a stable run-global position/index exists.
- Current Event Monitor active-only behavior is approved delivered product behavior and must not regress.
- Current work-trace projection reads archive plus active and produces mutable timestamped Markdown views. Native compaction must remain sourced from planner-selected WorkingContext and must not import server-only work-trace orchestration or inject raw-trace timestamps into the logical conversation rendering. Both paths may depend on the tight core-owned visible-value/Tool-body presentation capability; each remains responsible for adapting its own source and composing its own envelope.
- Current WorkingContext snapshot schema is version 4 and includes neutral metadata/media/tool payloads. The implementation introduces snapshot schema v5 only for finalized message-local constituent ranges; the startup reset removes v1-v4 files before normal runtime rather than teaching the serializer/bootstrapper to decode them.
- Current `CompactedMemorySchemaGate` and global compacted-memory manifest are removed with no replacement in the runtime. The startup migration owns the only knowledge of the four obsolete filenames and deletes them before agent runtime starts.
- Target `EpisodicItem` writes no `turnIds`; target `SemanticItem` writes no `reference`/`tags`. Because pre-lineage row files are reset, current models require only the current schema and contain no ignored historical fields.
- Current durable memory has no producing-compaction grouping. The target lineage tail supplies that run-local current-output lookup so normal projection cannot select a mixture of outputs from different compactions, without adding a second persisted pointer.
- Current server memory-view parsing of snapshot content is not a complete event projection and must not be reused as such accidentally.
- Provider message and tool contracts differ; common semantic composition belongs before rendering while genuine wire/tool differences remain provider-owned. Reasoning required for provider continuation may remain in WorkingContext but is not evidence supplied to the compactor.
- Current compactor runner/parser failure occurs before memory/archive writes and is the failure boundary preserved by this ticket. Interrupted filesystem publication and invalid built-in projected-context premises are excluded unless a supported operational path is later established.
- Cross-workspace/tenant authorization and redaction apply during evidence selection and lineage traversal.

## Persisted Data Outcome (When Applicable)

- Stored subject/location: active/archive raw JSONL/manifests; episodic/semantic JSONL; working-context snapshot; new run-local reference-only `compaction_lineage.jsonl`; generated readable Work Evidence Markdown.
- Raw traces and raw-trace manifests: `Directly Usable — No Migration`. They are preserved byte-for-byte by the startup reset and remain the original activity/evidence authority.
- Pre-lineage episodic/semantic rows, WorkingContext snapshots, and compacted-memory manifests: `Discard or Rebuild`. One required idempotent startup app-data migration removes `episodic.jsonl`, `semantic.jsonl`, `working_context_snapshot.json`, and `compacted_memory_manifest.json` from every discovered run before agent runtime starts. No content transformation or provenance backfill is attempted.
- New compaction-lineage relations: prospective-only. After reset, an absent/empty lineage file means no current compacted memory. The first successful new compaction creates the first output/record with `previousCompactionId: null`; each later successfully appended record becomes the current head.
- Generated Work Evidence Markdown: `Discard or Rebuild`. It is already a derived projection regenerated from authoritative raw traces, so no migration is required; the next regeneration applies explicit head/tail omission while preserving its file/manifest contract.
- Existing data to preserve: all retained original raw records/IDs, active/archive raw-trace files and manifests, generated Work Evidence source authority, and current active-only Event Monitor semantics. Pre-lineage derived memory and snapshots are explicitly disposable.
- Unacceptable loss/corruption: mutation/deletion of raw evidence during reset; runtime startup after a failed per-run reset; false direct or recursive provenance; M1..M(n-1) projected beside accepted M(n); archived inputs replayed as new context; a lineage record appended before its referenced output exists or after a reachable pre-write failure; snapshot/render divergence.
- Availability/rollout constraint: the reset is required before agent runtime and is retryable/idempotent. No maintenance-window or compaction-publication crash-recovery contract is established. Design must preserve normal current-schema resume and the reachable in-process pending-compaction retry path without inventing filesystem-transaction machinery.
- Related IDs: REQ-003 through REQ-010; AC-003 through AC-014.
