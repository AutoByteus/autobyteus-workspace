The approved behavior basis is [requirements.md](./requirements.md), the cumulative source/runtime trace is [investigation-notes.md](./investigation-notes.md), initial same-version evidence is retained in [runtime-probe-evidence.md](./runtime-probe-evidence.md), the corrective renderer-to-handler witness is [url-identity-probe-evidence.md](./url-identity-probe-evidence.md), and the CR-005 privilege/frame-authorization evidence is [fetch-capability-probe-evidence.md](./fetch-capability-probe-evidence.md).

The BEH-001 selection path correctly reaches the renderer's native video element: File Explorer recognizes the video, constructs an encoded `local-file://` URL for an absolute path in a trusted embedded Electron window, and `FileViewer.vue` renders `VideoPlayer.vue`. `useAuthorizedObjectUrl` intentionally passes that custom URL through rather than buffering it as a Blob. A second reachable renderer path, `contextAttachmentPresentation`, constructs the same scheme for an absolute workspace-image thumbnail in embedded Electron. The routing/capability decisions are healthy, but the duplicated renderer construction and main-process decoding lacked one explicit wire-contract owner.

The task base was broken in `electron/main.ts`: it installed only a late handler and returned ordinary `net.fetch(file:)` responses without preserving ranges. The first reviewed implementation correctly extracted lifecycle, response, stream, and viewer owners; registered `{ standard: true, stream: true }`; added truthful `200/206/405/416` policy; and added the approved viewer failure/Retry state. Later fixed-authority/context rework at reviewed commit `b658f16b5` resolved CR-001 through CR-004 without source deviation.

Realistic API/E2E then exposed a missing cross-boundary invariant in the reviewed design. With `standard: true`, Chromium treats the old empty-authority POSIX URL `local-file:///Users/...` as `local-file://users/...`; the first path segment becomes a lowercased hostname before handler delivery. The strict decoder returns no-byte `404`, correctly refusing to guess a case-sensitive path. Direct Node `new URL` tests did not reproduce this standard-scheme consumption step.

BEH-002 is now structurally healthy in the first implementation: the real VideoPlayer converted the canonicalization-triggered failure into the localized accessible alert and Retry state. That code and its owner remain; the supported source must stop entering the failure state because of URL identity.

The corrective differential isolates the target:

- `{ stream: true }` with the old opaque URL preserves exact case/significant characters and plays/seeks the reported 13 MB video, but a 607 MB later-range seek still fails with `PIPELINE_ERROR_READ` after a correct nonzero `206`.
- `{ standard: true, stream: true }` with `local-file://local/<case-preserving encoded absolute path>` keeps the constant `local` authority stable while the complete path remains in `pathname`. Electron 42.4.1 then passes exact/significant-character video playback, 120-second seek, large 1800-second later-range seek, and the full method/range/security matrix using the existing implemented response/stream owners.

Architecture round 2 then exposed two omitted boundaries:

- Context Files text paste and runtime projection can supply an already-authored `local-file://` locator. `hydrateContextAttachment` deliberately retains it as `external_url`; local messages, send, and projection preserve it; presentation passes it through. Valid legacy empty-authority POSIX and drive-authority Windows locators therefore need transformation before standard-scheme DOM assignment. Multi-character opaque authorities are retained by model tests but the current main decoder already rejects them as filesystem identities.
- Electron 42.4.1 standard normalization erases authored ports and credentials and lowercases the authority before `protocol.handle`; query and fragment survive. A handler parser cannot reject a port/credential it never receives. The product's raw context-locator ingress can reject those before DOM assignment; derived builders never produce them; the handler must state guarantees against the normalized `Request` and continue through the validator when erased inputs become indistinguishable from canonical.

Architecture round 3 accepted both corrections but exposed one downstream current-model consumer. `partitionContextAttachmentsForStreaming` derives `context_file_paths` and `image_urls` from `attachment.type` only. A supported paste such as `local-file://opaque/image.png` becomes `unsupported_local_file(type: Image)`, bypasses presentation containment, and enters `image_urls`. Agent/team server handlers then construct `ContextFile(IMAGE)`, the runtime maps it to LLM image media, memory records it as executable media, and the media client attempts source normalization. The user message can fail even though the current kind says the locator is non-executable.

The existing local submission boundary already provides the smallest correction. Full finalized attachment objects are stored in the optimistic/local `UserMessage` independently from the two executable WebSocket arrays. Team member-input echoes are identity-matched and can merge current non-executable state. Durable run memory, by contrast, stores executable media arrays and has no metadata-only attachment channel. Therefore the target must retain unsupported label/removal/current-message metadata locally, exclude it before both streaming services, preserve it across a matching live team echo, continue reading historical unsupported records, and intentionally avoid a new durable write for newly quarantined invalid input.

Architecture round 4 accepted that structure and raised only the visible history consequence: a newly unsupported non-media locator can currently survive the executable projection path, whereas the target removes it after fresh reload. The user was shown the choice between bounded current-session quarantine and a new metadata-only persistence feature and explicitly chose Option 1 on 2026-07-18. This locks the current-session/fresh-reload outcome without changing the round-4 technical design.

API/E2E round 3 then completed the shared-viewer journey and exposed CR-005. Image, audio, thumbnails, text, the canonical protocol/security matrix, both videos, and the approved UI all pass. Real `PdfViewer`/PDF.js XHR and `ExcelViewer`/Fetch fail before `protocol.handle` under the reviewed `{ standard, stream }` descriptor from both development HTTP and packaged-representative `file://` shell origins. An exact Electron 42.4.1 differential proves `corsEnabled` alone serves PDF XHR but not Fetch, `supportFetchAPI` alone serves neither cross-protocol consumer, and both serve exact PDF/Excel bytes.

Those two additional capabilities cannot be enabled without an authorization correction. The retained ungated probe shows foreign-HTTP and same-origin sandboxed Blob child frames then receive local-file bytes. The `Request` at `protocol.handle` contains no usable origin/referrer/fetch metadata. Default-session `webRequest.onBeforeRequest`, however, retains the request's `webContentsId` and exact `WebFrameMain`. A gate requiring a live registered `WorkspaceShellWindow` plus exact equality to its `webContents.mainFrame` preserves top-frame HTTP/file XHR+Fetch and cancels both child frames before the handler with zero bytes. Browser tool content already uses a separate partition where the handler is absent.

Constraints:

- Scheme privilege registration must occur once and before Electron ready with exactly `standard`, `stream`, `supportFetchAPI`, and `corsEnabled`; request-gate and handler installation occur after ready.
- The default-session local-file request gate must permit only the exact main frame of a live registered workspace shell and fail closed for absent/destroyed/unregistered/subframe identity. `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, enabled `webSecurity`, blocked navigation, and denied new windows remain invariant.
- The renderer capability gates, `local-file` scheme name, and `validateReadableRegularFile` boundary remain authoritative. Old empty/drive-authority URL shapes are obsolete at the protocol but remain recognized only by the isolated context hydration migration.
- The clean-cut URL is `local-file://local/<encoded absolute path>`. `local` is a protocol marker; POSIX `/Users/...` and Windows `/C:/...` live entirely in pathname.
- The handler must support macOS/POSIX paths and Windows drive-letter paths without accepting old URL forms or arbitrary hostname reconstruction.
- Raw supported context locators must become canonical or be classified unsupported before media presentation. Ordinary presentation and protocol parsing must never learn legacy formats.
- Current attachment submission eligibility must be decided once before agent/team WebSocket serialization. Unsupported state remains in the current/local message but cannot enter executable context/media arrays.
- Preserve the existing composer rule that Send requires nonempty trimmed message text. Quarantining an unsupported attachment therefore never creates a newly allowed empty user execution.
- Existing streaming and runtime-memory payloads remain executable-only; no metadata-only transport is added. Existing historical unsupported records remain readable, while newly quarantined invalid input is not durably projected after reload.
- Handler checks apply to the normalized Electron `Request`: wrong authority and query/fragment are observable; raw port/credentials are not.
- Local image, audio, PDF, Excel, and CSV viewers also use `local-file://`; MIME/full-response behavior must remain compatible. Existing PDF.js XHR and Excel Fetch remain unchanged and use the authorized main-frame protocol path; no viewer-specific fallback or binary IPC is added.
- Streaming must avoid whole-file materialization and close the opened handle on completion, cancellation, and error.
- No source media file or existing persisted application record may be rewritten in place. Product-generated File Explorer/workspace-thumbnail URLs are ephemeral; valid raw context input is canonical in current state and any new send naturally carries that current locator.

## Intended Change

Preserve the implemented Electron `local-file-protocol` capability area, correct its renderer-to-handler identity contract with one pure shared codec, and add one isolated context-locator transition before current-model use:

1. Change `registerLocalFileProtocolScheme()` to exactly `{ standard: true, stream: true, supportFetchAPI: true, corsEnabled: true }` before ready. Keep every other scheme privilege false and keep `webSecurity` enabled.
2. Add `shared/localFileUrl.ts` as the sole wire-contract owner. It exports the scheme/authority constants, `buildLocalFileUrl(filePath)`, and `parseLocalFileUrl(requestUrl, platform)`; it has no Electron, filesystem, Vue, store, or response-policy dependency.
3. Make both reachable renderer producers—`fileExplorerContentActions` and `contextAttachmentPresentation`—call the shared builder. It emits `local-file://local/<case-preserving encoded absolute path>` and always adds a pathname-leading slash before a Windows drive path.
4. Add `utils/contextFiles/contextLocalFileLocatorMigration.ts` as the only historical-format owner. It does not open files or enter protocol response policy.
5. Make `contextAttachmentPresentation` assign a local-file media URL only when the attachment contains a canonical current locator. 7. Make both agent/team run stores build the submission plan before finalizing/sending. Update identity-matched team member-input upsert to merge/dedupe existing non-executable attachments with incoming executable attachments, including mixed valid+unsupported sends. Existing historical projections still hydrate unsupported records; newly quarantined unsupported input intentionally has no durable runtime write.
8. Extend `WorkspaceShellWindowRegistry` with one exact main-frame identity query. At `installLocalFileProtocol(...)`, register a default-session `webRequest.onBeforeRequest` filter for `local-file://*/*` before `protocol.handle`. Cancel unless `webContentsId` resolves to a live shell and `details.frame` is that shell's exact `webContents.mainFrame`. Do not authorize by URL string or handler headers.
9. Make `local-file-protocol.ts` use the shared scheme constant and `local-file-response.ts` call the shared parser against the normalized handler URL. Parsing requires scheme `local-file:`, normalized authority `local`, and no handler-visible query/fragment; decodes pathname once; and, on `win32`, requires `/C:/...` and strips its URL-leading slash. Username/password/port checks may remain defensive for direct callers but are not claimed to reject values Electron erased. Filesystem validation remains separate and unchanged after frame authorization.
10. Remove the two inline renderer serializers, response-local decoder, duplicated scheme literal, external local-file pass-through to media, type-only submission partition, and protocol support for old empty/drive-authority forms. The hydration migration is the sole legacy boundary; no protocol translation, fallback, metadata-only transport, PDF/Excel-specific byte path, or second media path.
11. Preserve the implemented PDF/Excel viewer source, method, validation, MIME, full/single-range, status/header, cache, stream, and cleanup owners. Exact CR-005 evidence requires a lifecycle/authorization extension, not viewer or response replacement.
12. Preserve the implemented `VideoPlayer.vue` media-attempt/error/Retry state and localization because live failure containment and focused tests pass.

The visible happy-path layout and native controls remain. The failed state stays centered within the existing black player surface, uses readable high-contrast text, and exposes a keyboard-operable button with visible focus styling. The UI displays a generic localized message rather than native pipeline text or an absolute path.

## Task Design Health Assessment (Mandatory)

- Change posture: `Bug Fix`
- Current design issue found: `Yes`
- Root cause classification: `Boundary Or Ownership Issue` — the renderer/main wire identity had no single owner, and the scheme lifecycle owner omitted the requester-frame authorization invariant needed when established XHR/Fetch consumers require broader session capabilities.
- Refactor needed now: `Yes`
- Evidence: Fixed authority, response/ranges, validation, migration, submission, and viewer UI now pass realistic execution. CR-005 alone remains: the reviewed two privileges block real PDF.js XHR/Excel Fetch before the handler. Exact four-capability evidence serves both, while the ungated/gated differential proves executable child-frame exposure and the sufficiency of exact live-shell-main-frame authorization at `webRequest`.
- Design response: Preserve all passing owners and viewer source. Extend the existing protocol lifecycle owner with the exact four privileges and one default-session scheme-filtered exact-main-frame gate supplied by the live shell registry. Keep URL parsing, validation, response, and stream after that gate; add no IPC/Blob/token/fallback transport.
- Refactor rationale: One protocol-level gate is smaller and safer than duplicate document bytes or per-viewer changes. Handler headers cannot authorize, origin strings admit same-origin Blob frames, and a renderer-minted path token does not reduce the trusted top frame's authority. Exact `WebFrameMain` identity directly distinguishes every tested supported and denied frame.
- Intentional deferrals and residual risk: Per explicit user approval, newly quarantined unsupported input is not retained across a fresh durable reload. AudioPlayer-specific native error UI remains outside approved behavior. Platform codec and Windows live validation remain residual. Future Electron/PDF.js changes that alter requester-frame identity must return to design rather than weakening fail-closed authorization.

## Terminology

- **Local-file protocol owner**: The Electron main-process capability that owns exact `local-file` scheme registration, default-session requester-frame authorization, handler installation, and the response-policy boundary. It consumes live shell identity and does not own filesystem trust policy.
- **Owned workspace-shell main frame**: A request identity whose `webContentsId` resolves to a live registered `WorkspaceShellWindow` and whose `WebFrameMain` object is strictly equal to that shell's current `webContents.mainFrame`.
- **Local-file URL codec**: Pure cross-process wire-contract owner in `shared/localFileUrl.ts`; it owns scheme/authority constants and reversible URL serialization/parsing, but grants no filesystem authority.
- **Context local-file locator migration**: Pure context-ingress boundary that transforms only valid legacy raw absolute locators into the current canonical URL before `ContextAttachment` use; it is not the Electron protocol decoder.
- **Context attachment submission plan**: Pure current-model boundary that preserves the full attachment array for the local user message while deriving executable `contextFilePaths`/`imageUrls`; it excludes `unsupported_local_file` without parsing its locator.
- **Non-executable current attachment**: `unsupported_local_file`; retained for composer/current-message/historical-read fidelity but ineligible for preview/open, executable streaming arrays, server `ContextFile`, and runtime media.
- **Handler-observable identity**: The URL fields present in `protocol.handle` after Electron standard-scheme normalization. In Electron 42.4.1, port/credentials and raw authority case may be erased; query/fragment and wrong authority remain.
- **Fixed local-file authority**: Constant lowercase hostname `local` in `local-file://local/...`. It is a protocol marker, never part of the filesystem path.
- **Local resource URL identity**: One case-preserving encoded platform absolute path stored entirely in pathname after the fixed authority.
- **File byte window**: A tight pair `{ start, length }` identifying the bytes a response body may read. `end` is derived and is not stored redundantly.
- **Media attempt**: One mounted video-element load identified by a monotonically changing renderer-local key. Retrying or changing the source creates a new attempt.
- **Single byte range**: One `Range: bytes=...` selector. Multipart ranges are intentionally unsupported and receive `416` without bytes.

## Design Reading Order

This spec follows the mandatory order: verified current state and approved behavior; design health/removal/data decision; spines and owners; boundaries and interfaces; capability/file allocation; then sequencing, tradeoffs, risks, and implementation guidance.

## Legacy Removal Policy (Mandatory)

- Policy: `No steady-state backward compatibility; remove legacy runtime/protocol paths and isolate the required read/ingress migration.`
- Already removed by the first implementation: inline `installProtocols()` and `net.fetch(file:)` response branch in `electron/main.ts`.
- Newly obsolete in ordinary runtime/protocol code: `local-file:///absolute/POSIX/path` and `local-file://C:/Windows/path` identities, inline serializers, external local-file presentation pass-through, and response-local acceptance of empty/drive-letter authorities.
- Clean cut: one shared codec emits/parses only `local-file://local/<encoded absolute path>`. The isolated context hydration migration is the only file allowed to recognize valid legacy empty/drive forms and immediately returns current canonical state. No legacy protocol parser, viewer fallback, duplicated literal/serializer, second handler, or second transport remains.
- Unsupported opaque/wrong/adorned local-file attachment strings may remain as retained current/historical message metadata but are not an alternate resource identity and cannot reach media assignment or executable submission arrays.
- Preserved current contracts are the scheme name, trusted workspace-shell main-frame capability boundary, exact four-capability lifecycle owner, validation owner, response/stream owner, established PDF/Excel viewers, and video recovery owner.

## Persisted Data / State Transition Decision (Mandatory When Persisted Data May Be Affected)

- Stored subject, location, representative shape, and approximate volume: User-owned local files; normal `workspace_path` locators; and context message/projection locator strings that can retain valid legacy POSIX `local-file:///...`, valid legacy Windows `local-file://C:/...`, canonical fixed form, or unsupported opaque strings. No current non-memory hit was found for this user, but the production schema/readers support the shape product-wide.
- Relevant code-model, serialization, semantic, or physical-store change: Derived URL serialization changes and valid legacy external locator strings become canonical current attachment state at ingress/hydration. Unsupported input becomes non-executable current state and is omitted from new runtime writes. Source files and persisted projection schemas do not change. File Explorer/workspace-thumbnail URLs and media-attempt state remain ephemeral.
- Normal reader/writer behavior and representative evidence: Paste and projection readers converge on `hydrateContextAttachment`. The submission plan stores full current attachment objects in the optimistic/local message but writes only eligible locators to executable WebSocket arrays. Valid legacy input can therefore transition before current use/new send. Historical server projection is read-only and is transformed in memory on hydration; no source-file or central-store writer is introduced. A newly quarantined unsupported item has current-session label fidelity but is absent after a fresh durable reload.
- Required semantics and invariants under direct use: Preserve every source byte, return only the requested valid window, and never modify/transcode/relocate the file.
- Physical-store, privacy/security, disposal/rebuild, and operational constraints: Live registered main-frame authorization and validation before read; no path/native error disclosure in the UI; no browser-session, child-frame, remote-client, enumeration, write, Node, shell, `file://`, or new binary IPC capability.
- Decision: `Migration Required`
- Decision rationale, including concrete benefit versus I/O, downtime, corruption, recovery, and rollout cost: A supported reader/writer path can retain valid legacy locators even though one user's present data does not. Transforming at the established hydration convergence boundary preserves path meaning before Chromium destroys it, avoids a product-wide store rewrite, and keeps protocol/viewer code current-only. Arbitrary opaque hosts are not transformed because the current decoder never authorized them and guessing would create security/case errors.
- Acceptance criteria or design constraints supported by this decision: FR-002, FR-005, FR-006, FR-007 / AC-007, AC-008, AC-010.

### Migration Plan

1. **Owner/boundary:** `utils/contextFiles/contextLocalFileLocatorMigration.ts`, called only by `hydrateContextAttachment` before current attachment construction.
2. **Input classification:** trim raw locator and test the scheme case-insensitively; non-`local-file:` is unchanged; current fixed form is validated/idempotent; legacy empty-authority POSIX and raw one-letter drive-authority Windows forms are decoded once and rebuilt through `buildLocalFileUrl`; raw credentials/port/query/fragment, malformed percent encoding, wrong/multi-character authority, and non-absolute shapes are `unsupported`.
3. **Hydrator ordering/current-model completion:** run the local-file classification before uploaded-route pathname parsing so a local absolute path resembling `/rest/...` cannot change attachment kind. `not_local` continues through the existing uploaded/external/workspace order. `canonical`/`migrated` constructs `external_url` with the canonical locator while deriving a missing display name from the original authored locator. `unsupported` constructs the specialized `ContextAttachment` variant `kind: 'unsupported_local_file'` with original locator/id/display/type; presentation/open logic handles that current kind by returning no resource URL, and projected-message UI renders its label as a non-interactive chip rather than an “Open” control. Ordinary send/presentation code contains no old-format parser.
4. **Submission/write ordering:** transformation occurs on paste and projection hydration before message state/presentation. Immediately before send, `planContextAttachmentSubmission` returns retained current objects plus executable arrays. Both stores finalize local message state from the retained array, then serialize only executable arrays. Valid locators are canonical on new writes; unsupported locators have no server/runtime write.
5. **Live echo/historical read:** an identity-matched team echo merges/dedupes existing non-executable current items with incoming executable items so local metadata survives empty and mixed echoes. Historical projections are transformed independently on every hydration because no single writable store owns all records.
6. **Validation:** unit cases cover current idempotence, legacy POSIX/Windows/significant characters, raw adornments, opaque authorities, malformed encoding, non-local pass-through, unsupported metadata retention, image-extension executable exclusion, valid mixed routing, and live mixed-echo merge. Presentation/integration cases prove only canonical reaches preview/open and only eligible kinds reach streaming arrays.
7. **Interruption/recovery:** transformation/planning are pure and have no partial write. Failure returns `unsupported`; the original stored locator remains intact for display/rollback, and no preview/open/executable request is emitted. Text/valid attachments proceed normally.
8. **Rollback/backup:** no destructive persisted mutation, copy, source-file change, or schema migration occurs. Reverting code restores the unsafe type-only send behavior but original server projections remain unchanged.

## Ownership Boundaries

Authority changes at nine explicit boundaries:

1. **Raw context-locator migration boundary:** accepts locator text from paste or projection hydration before current-model use. It can observe old path identity and raw adornments, returns canonical current or explicit unsupported state, and grants no file authority.
2. **Current submission-eligibility boundary:** accepts only hydrated `ContextAttachment[]`, returns the same current objects for local retention plus executable `contextFilePaths`/`imageUrls`, and categorically excludes `unsupported_local_file` from both arrays. It does not parse historical URL syntax.
3. **Live message-projection boundary:** accepts an identity-matched incoming projection and the existing local message, refreshes executable attachment data, and retains/deduplicates existing non-executable current attachments. It neither invents runtime media nor provides durable persistence.
4. **Renderer routing boundaries:** File Explorer and context-attachment presentation independently decide whether a supported embedded absolute path/current attachment may become a local resource request. They do not parse historical wire shapes.
5. **Local-file URL codec boundary:** accepts a platform absolute-path string for construction or a URL plus explicit platform for current parsing. It owns only fixed-authority wire identity; successful parsing is not filesystem authorization.
6. **Video presentation boundary:** accepts `url: string | null`; owns media attempt/error/retry state and emits no filesystem authority outward.
7. **Electron request-frame authorization boundary:** accepts default-session request identity, resolves a live registered workspace shell, requires exact main-frame object equality, and cancels every other request before the handler. It grants no path/file authority.
8. **Electron local-file handler boundary:** accepts the normalized Electron `Request` only after frame authorization. It encapsulates response mechanisms but cannot infer erased authored fields or requester headers absent at this boundary.
9. **Filesystem validation boundary:** accepts a decoded candidate path and returns either a normalized readable regular-file path or a stable failure. It remains shared and authoritative.

The local-file response may depend on validation, but it may not weaken or replicate it. `main.ts` may depend on the protocol boundary and the validator for the separate text IPC use case; it must not depend on protocol internals.

## Applied Patterns (If Any)

- **Authoritative boundary:** `local-file-protocol.ts` exposes the only lifecycle API; bootstrap never reaches its internals.
- **Boundary codec:** `shared/localFileUrl.ts` owns translation between platform path identity and the single custom-scheme wire identity; routing/validation remain with their respective owners.
- **Isolated migration boundary:** context hydration alone knows valid legacy locator forms and produces current canonical or explicit unsupported state before ordinary runtime use.
- **Current-model projection:** `ContextAttachmentSubmissionPlan` separates current local-message retention from executable transport without inventing a parallel metadata payload.
- **Identity-matched merge:** the existing projection upsert retains only existing non-executable current items for the member-input echo while incoming executable data remains authoritative.
- **Discriminated response plan:** private `full | partial | unsatisfiable` result prevents nullable/contradictory range fields.
- **Resource ownership transfer:** response owner opens the file and either closes it before returning a bodyless response or transfers the handle exactly once to the stream owner.
- **Keyed retry/remount:** a component-local monotonically changing key guarantees a new native media element for Retry and URL changes without a global state machine.

## Key Tradeoffs

- **Dedicated protocol folder vs one large `main.ts` callback:** Three cohesive source files add visible structure but remove a broad bootstrap responsibility and make lifecycle/resource invariants testable. This is proportionate to the cross-boundary defect.
- **Direct `mime-types` dependency vs static map:** A small direct dependency is preferable because current local-file consumers span video, audio, images, PDF, CSV, and multiple Excel extensions. A duplicated map would drift from the File Explorer allowlist and platform MIME expectations.
- **Single range vs multipart ranges:** Chromium media needs single ranges for the approved flow. Rejecting multipart with `416` is simpler, deterministic, and avoids a multipart response encoder with no demonstrated product need.
- **Byte-oriented Web stream vs `net.fetch`/Node stream adapter:** The explicit loop is more code, but it provides positional reads and deterministic cancellation cleanup proven necessary by the large-file probe.
- **Viewer-local error vs global file state:** Local state cannot be shared across viewers, but the failure is native-video-specific and ephemeral. Globalizing it would couple decode state to File Explorer resource state without benefit.
- **Generic message vs raw media error:** Generic localized wording is less diagnostic to an end user but avoids leaking paths/native pipeline detail and remains truthful across missing, unreadable, and unsupported-codec failures.
- **Shared subject-specific codec vs endpoint-local helpers:** One extra shared file and explicit Electron TypeScript inclusion add structure, but the critical scheme/authority/path identity is genuinely consumed in renderer and main. Duplicating it would retain the ownership gap; a generic URL utility would be too broad.
- **Four capabilities ungated vs exact main-frame gate:** The two added flags are the exact runtime minimum for established PDF/Excel consumers but apply across a session. One scheme-filtered `webRequest` listener adds a small ownership surface and fails closed; it is justified by direct child-frame exposure evidence and avoids larger viewer/IPC redesign.
- **Exact frame object vs origin/path tokens:** Object identity is available before the handler, survives HTTP/file shell modes, and directly distinguishes tested child frames. Origin headers disappear at the handler; tokens minted from paths supplied by the same trusted top frame add lifecycle complexity without reducing that frame's authority.
- **Fixed `local` authority vs opaque/encoded payload:** Fixed authority uses ordinary standard-URL structure and keeps the readable path in pathname. A base64/query payload could avoid host rewriting but adds a second representation and parsing surface without evidence; strict fixed authority passed the exact runtime matrix.
- **Hydration migration vs protocol compatibility:** A small context-specific migration file adds a current-model transition and specialized unsupported variant, but preserves valid historical/user input while keeping the security-sensitive protocol current-only. A protocol dual parser would be smaller yet cannot recover post-Chromium case and would weaken the boundary.
- **Read-time transition vs destructive store rewrite:** Hydration repeats a pure transform when historical projections reload, but one boundary serves all disparate readers and original records remain recoverable. A product-wide in-place migration lacks a single owner and adds corruption/rollout risk.
- **Current-session retention vs metadata-only durable transport:** Per the user's explicit Option-1 approval, newly invalid input is visible/removable in the composer and retained in the current local message/live echo, but disappears after a fresh durable reload. Valid attachments remain durable. Adding cross-restart retention would require coordinated web/server/runtime-memory schema work and a new product requirement; reusing media arrays would recreate AR-003.
- **One submission plan vs store-local filters:** A tight plan adds a nested result type, but makes the two existing outcomes—local current state and executable wire arrays—explicit and identical for agent/team paths. Duplicate store filters would be smaller individually but structurally unsafe.
- **Boundary-scoped rejection vs impossible authored rejection:** Accepting Electron's canonicalized port/credential equivalent sounds less strict, but no enforcement data remains and the same validator still governs the exact path. Raw supported context inputs reject before DOM; overstating handler power would be false security.

## Risks

- A file can be truncated/replaced after validation/stat. The open handle and bounded reader must close; Chromium will surface failure through the viewer. Live mutation reconciliation is outside approved scope.
- Incorrect byte-stream controller semantics could reproduce `PIPELINE_ERROR_READ`. Unit cleanup tests are necessary but not sufficient; actual Electron seek/cancel validation is mandatory.
- MIME lookup fallback may not make Chromium decode a format that Electron lacks. The UI must not claim codec support.
- Windows URL parsing cannot be live-executed on macOS. The codec must deterministically build `local-file://local/C:/...` and parse `/C:/...` only for explicit `win32`; normal Windows release validation remains residual risk.
- Direct builder/parser round trips can hide matched mistakes just as the first response tests did. Raw URL rejection tests and the retained Electron renderer/resolved/handler witness are mandatory.
- Context-attachment image previews are a second reachable producer. Leaving their inline interpolation would create an obsolete URL despite fixing File Explorer.
- Historical projections can be rehydrated repeatedly; migration must be idempotent and pure, and unsupported locator metadata must not accidentally regain media eligibility through another presentation helper.
- Any future caller that bypasses `planContextAttachmentSubmission` can reintroduce unsupported state into executable arrays. Both store tests and a search/guard for direct type-only partitioning are required.
- A mixed team echo can erase local unsupported metadata if merge logic preserves only when incoming is empty. The focused identity-matched mixed-echo test is mandatory; unrelated external-user messages must not inherit local state.
- Newly quarantined unsupported metadata is not cross-restart durable by explicit approval. Do not imply otherwise in UI/docs; if product expectations change, reopen requirements and design a metadata-only persistence contract rather than widening executable media.
- Changing the `ContextAttachment` union can expose non-exhaustive assumptions. Focused context model/presentation/send/projection tests and type checking are mandatory.
- Port/credentials are normalized away by current Electron; a future runtime may differ. Defensive parser checks remain, and API/E2E records authored/resolved/handler values rather than assuming.
- Component Retry can be ineffective if it reuses the failed media DOM node. The attempt key/remount is mandatory, not optional styling.
- A second privileged scheme registration or a post-ready call will break the lifecycle contract. Keep one top-level call and one lifecycle owner.
- Electron can report an absent/destroyed requesting frame. Authorization must fail closed; realistic E2E must prove current PDF.js XHR, Excel Fetch, media, and thumbnail requests retain the registered main-frame identity.
- Enabling the required Fetch/CORS capabilities without the pre-handler gate exposes local-file responses to executable child frames. The privilege and gate changes are inseparable and must land/test together.
- `webRequest` uses one listener per event. A later default-session `onBeforeRequest` registration could overwrite the security gate. The protocol owner must remain the sole listener owner and any future policy must be composed there with tests.
- Comparing a request frame's URL/origin instead of exact object identity can admit same-origin Blob/HTML-preview content. Registry lookup plus `details.frame === shell.browserWindow.webContents.mainFrame` is mandatory.
- PDF.js may change its loading execution context across upgrades. Current Electron 42.4.1 realistic evidence must prove the expected main-frame identity; if a future version moves it to an identity the gate cannot distinguish safely, return to design rather than weakening the gate.
- Building/launching validation from this worktree must not terminate, reuse the data profile of, or overwrite the user's currently running package.

## Guidance For Implementation

- Use exactly `{ standard: true, stream: true, supportFetchAPI: true, corsEnabled: true }`; the retained CR-005 differential is the required new evidence. Do not add `secure`, `bypassCSP`, `allowServiceWorkers`, `codeCache`, `allowExtensions`, or disable `webSecurity`.
- Add `WorkspaceShellWindowRegistry.isOwnedMainFrame(webContentsId: number, frame: WebFrameMain)` as a pure live-identity query over the existing registry. It returns true only when the ID resolves to a non-destroyed registered shell and `frame` is strictly equal to that shell's current `browserWindow.webContents.mainFrame`; false for unknown/destroyed/same-ID subframe inputs. It must not compare URLs or know the local-file scheme.
- Make `installLocalFileProtocol` accept the narrow identity predicate. On `session.defaultSession.webRequest.onBeforeRequest({ urls: ['local-file://*/*'] }, ...)`, first require a numeric `details.webContentsId` and non-null/present `details.frame`, then call the predicate; invoke the callback with `{ cancel: true }` unless authorized. Register this listener before the one `protocol.handle`. Do not authorize inside `createLocalFileResponse`, because the handler Request lacks the required requester identity.
- Keep the gate and handler on the default shell session only. Do not install them in `persist:autobyteus-browser`; do not permit any subframe, including `HtmlPreviewer` HTTP or same-origin Blob frames.
- Keep `PdfViewer.vue`, `ExcelViewer.vue`, and `authorizedTransport.ts` unchanged. Do not add a viewer-specific fetch mode, IPC/Blob fallback, capability token, custom header, or duplicate byte path.
- Put `LOCAL_FILE_SCHEME = 'local-file'` and `LOCAL_FILE_AUTHORITY = 'local'` only in `shared/localFileUrl.ts`. Both renderer producers and Electron protocol code import the codec; do not concatenate or parse the wire shape elsewhere.

- `migrateContextLocalFileLocator` must inspect the authored trimmed string before any DOM assignment. Return a tight `not_local | canonical | migrated | unsupported` result. Update `isBrowserOpenableContextAttachment` consistently; neither presentation helper may parse legacy syntax.

The plan returns a shallow copy of every finalized current attachment as `retainedMessageAttachments`, while `executable.contextFilePaths` and `executable.imageUrls` contain only nonblank eligible current locators. `unsupported_local_file` is ineligible regardless of `type`, extension, or locator text. Incoming executable attachments remain authoritative/refreshed; existing `unsupported_local_file` items are retained once in stable local order for empty and mixed echoes. Define/deduplicate by a stable current identity (prefer existing attachment `id` when present, otherwise `kind + locator`), and keep unrelated `handleExternalUserMessage` behavior unchanged. Do not invent unsupported entries when neither existing local nor historical hydrated input contains them.

Existing historical invalid locators remain readable through hydration. Per the approved Option-1 outcome, newly quarantined invalid input is current-session state only after submission/live echo and is absent after a fresh durable reload; any future cross-restart requirement must return to solution design.
- `parseLocalFileUrl` directly requires `local-file:`, parsed hostname `local`, no username/password/port/search/hash, and a pathname that decodes once. For explicit `win32`, it accepts only `/C:/...`-shaped pathnames and strips the first slash; for other platforms it preserves the leading slash. When called from `protocol.handle`, username/password/port are the normalized values Electron delivered; tests may prove direct-call defensive rejection but must not claim detection of authored values Electron erased. It does not reconstruct arbitrary hostnames, accept empty authority, validate the filesystem, or fall back.
- Make `createLocalFileResponse` treat codec parse failure as generic no-byte `404` before method, validation, range, MIME, open, or stream planning. A valid fixed identity with a non-GET/HEAD method reaches the existing `405` policy.
- Recommended response policy:
  - no Range: `200`, full `Content-Length`, `Accept-Ranges: bytes`, MIME, `Cache-Control: no-store`;
  - valid single Range: `206` plus exact `Content-Range` and selected length;
  - malformed/multiple/unsatisfiable Range: `416`, `Content-Range: bytes */<size>`, no body;
  - validation/open failure: generic `404`, no body;
  - non-GET/HEAD: `405`, `Allow: GET, HEAD`, no body;
  - HEAD: same selected/full headers without body and close immediately.
- Accept `start-end`, `start-`, and `-suffix`; clamp an oversized end to file size; reject zero/invalid suffix, start beyond EOF, non-digits, reversed range, and comma-separated multipart ranges. A zero-length file has a valid full `200` with zero body and no valid byte range.
- Open the validated path once per request and use the opened handle's `stat()` for the response size. Close it before returning every bodyless/error response. When a GET body is created, transfer ownership to `file-byte-stream.ts` and make close idempotent.
- Use positional reads bounded by remaining length in a byte-oriented WHATWG `ReadableStream`. Do not materialize the file, create a Blob, or use unverified generic `Readable.toWeb` conversion.
- In `VideoPlayer.vue`, never render raw `resourceError`, `MediaError.message`, protocol URL, or absolute path. Treat either resource or native media error as the same approved generic failure.
- Increment the attempt key for both Retry and URL change. Clear native error on URL change and before refresh. A successful `loadedmetadata` may defensively clear the current-attempt native failure.
- Add explicit strings to non-generated `localization/messages/en/tools.ts` and `zh-CN/tools.ts`; do not hand-edit `tools.generated.ts`.
- Implementation-engineer checks should include the exact four-privilege/no-extra lifecycle assertion; filtered listener-before-handler order; exact registered-main-frame allow; absent/unknown/destroyed/same-ID-subframe cancellation; all prior shared-codec, context migration/model/submission-plan, both run stores, member-input projection, presentation/UserMessage, Electron response/validation, and VideoPlayer tests; `pnpm transpile-electron`; and prior localization/WebSocket/boundary guards.
