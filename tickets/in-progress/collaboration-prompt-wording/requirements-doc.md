## Problem And Desired Outcome

Everything an agent reads about collaboration — its prompt sections, the tool descriptions,
tool results and refusals, the task message, the header of a received message and the `@`
note — was written from the system's point of view ("copy", "run ID", "this run", "spawn",
"nested AgentTeam") and has drifted into contradictions:

- The `teamScoped` switch gives task agents in Team and Org runs the team prompt.
- The team prompt says to message only at handoff points, then tells the agent to message
  copies and teammates.
- The `@` note suggests delegating to a teammate, which `delegate_task` refuses.
- The addressing section describes nested teams, which no longer exist.
- Agents are told their own address and the sender's address, although an address does not
  reach a task agent; a reply sent to such an address reaches a different agent or nothing.
- The same rule is repeated up to five times across prompt and tool texts.

Desired outcome: every agent receives precise, consistent text written for it, in one
vocabulary, each fact said once, with the exact wording of the wording authority.

## Scope Guardrail (Mandatory)

### In-Scope Use Cases

- UC-001: the user starts a standalone agent; it delegates and talks with its task agents.
- UC-002: a task agent receives its task, works, delegates further and reports by ID.
- UC-003: the user starts a team; members hand off by their rules and delegate outside the team.
- UC-004: an organization's direct agent (Project Task Manager) talks with organization units
  and delegates to them; its task agent teams report back by ID.
- UC-005: the user mentions agents with `@` while talking to any of these agents.
- UC-006: an agent calls a collaboration tool wrongly and reads the refusal.

### Out Of Scope

- Tool behavior: who may message or delegate to whom, Task ownership, lifecycle, address
  resolution and refusal conditions stay exactly as they are; only text changes, plus the
  internal fact that selects the prompt, the viewer relation the `@` note needs, and (SR-003)
  returning the existing cross-Task / closed-Task refusal of `send_message_to` as a refusal result
  instead of an internal error (the condition is unchanged).
- Which tools an agent gets (`get_handoff_rules` stays tied to `teamScoped`).
- UI wording for users (Settings, run history "copy" texts), except the optional badge in REQ-010.
- Memory and message storage (Task 8641c0ac).
- The engineer-facing model document's vocabulary (`collaboration_model.md` may keep "copy";
  it gets a short note on the agent-facing words).

### Non-Goals

- No new collaboration capability, tool or parameter; no tool or field renamed.

### Preserved Behavior Boundary

All tool behavior, every refusal condition, address resolution, Task semantics, persisted data
and saved conversations. Saved `[Mentioned collaborators]` notes and saved message headers with
a sender address keep parsing and displaying.

### Review Authority

The Solution Designer owns the wording authority; changes to it during implementation return
here (they change intended behavior).

  standalone agent, task agent, team member, organization direct agent — as wording §3 defines,
  for every root kind and on restore.
- REQ-002 (BEH-002, BEH-010): The rendered sections are word for word wording §4.1, §4.2,
  §5.0, §5.1 (with `{{organization_line}}`), §5.2.
- REQ-003 (BEH-003): §5.3 Handoffs is appended exactly when the agent has handoff rules.
- REQ-004 (BEH-004): No agent-facing text states the agent's own address.
- REQ-005 (BEH-005): The task message and the mode-3 Task message use wording §7.1.
- REQ-006 (BEH-006): Every received-message header built for an agent uses wording §7.2.
- REQ-007 (BEH-007): Tool and parameter descriptions are wording §6, identical on every runtime
  (native tools and the Agent Tools MCP server).
- REQ-008 (BEH-008): Every result and refusal an agent can receive from `delegate_task`,
  `send_message_to`, `update_task`, `list_project_tasks` and `list_available_agents` follows
  wording §7.3 (vocabulary and a next step); the design spec lists them. Each such refusal
  reaches the agent as the tool's refusal result, never as an internal error (SR-003).
- REQ-009 (BEH-009): The `@` note follows wording §8 for the agent the user is talking to;
  saved notes in every earlier form still parse.
- REQ-010 (optional): the UI badge "Delegated copy" reads "Task agent" / "Task agent team".
- REQ-011: Product documentation that describes these texts is updated in the same change.

## Decisions

- DEC-001 (user): wording, vocabulary ("task agent", "talk with", "its ID"), the addressing
  section corrected for flat teams, no lifecycle words, tool descriptions as mechanics.
- DEC-002 (user): no agent is told its own address; replies go by ID (the phone rule).
- DEC-003 (superseded by DEC-011 in SR-005): the sender address left the task message and the
  received-message header.
- DEC-004 (Solution Designer, within the direction): repetitions removed as in views §8.
- DEC-005 (Solution Designer, within the direction): the `@` note decides per viewer (wording
  §8); this corrects the teammate-delegation contradiction.
- DEC-006 (Solution Designer, within the direction): refusal and result texts are agent-facing
  and follow the vocabulary (REQ-008).
- DEC-007 (Solution Designer, within the direction): a task agent with handoff rules gets the
  task agent prompt plus §5.3; tool exposure unchanged.
- DEC-008 (superseded by DEC-011 in SR-005): the task message labelled the ID and said the name
  is not an address or an ID.
- DEC-009 (Solution Designer, within the direction, SR-003): the cross-Task / closed-Task refusal
  of `send_message_to` is returned as a refusal result instead of an internal error, so agents
  read it (REQ-008); the refusal condition is unchanged.
- DEC-010 (user, SR-005): the wording is not changed for LM Studio; small local models struggle
  with any prompt, while Claude and Codex worked before. LM Studio results are information only.
- DEC-014 (user, SR-013): one ID term everywhere, "run ID", matching the tool fields
  (`target_agent_run_id`, `target_team_run_id`, `target_team_coordinator_agent_run_id`): "its run
  ID", "your run ID", "sender run ID", "it returns a run ID to follow up with". The header the
  agent reads has no name: `You received a message from the agent with sender run ID "<id>".`,
  the same phrase as the task message. The user still sees "From <name>" in the chat (the app's
  run-ID lookup); the parser accepts the new and every earlier form. Done in this ticket ("once
  for all"), so Project Task `project_task_9de99841-…` (the run-ID follow-up) is covered by it.
- DEC-013 (user, SR-007; reverted by the user in SR-008 — the agent-facing word stays "task agent"): the agent-facing word was to be "copy" again ("a fresh copy", "a team copy",
  "your copies"), replacing "task agent". Evidence: with the pre-refactor prompts the Project
  Task Manager used "copy" correctly across many sessions (2026-10-16 screenshot: "That starts a
  fresh copy of the team … the earlier copy's team run ID … wakes the same copy with its whole
  conversation … only works if I made that copy's latest assignment"), and the validation rounds
  showed no gain from "task agent" itself. Every other SR-001..SR-006 decision stays (talk with,
  no "this run"/"spawn", no lifecycle words, replies by ID, no own address). Engineer-facing
  documents may keep "task agent" as a synonym; the code's role name `task_agent` is unchanged.
- DEC-012 (user, SR-006): one handle to answer with — the ID. The task message gives the sender
  only as `target_agent_run_id`; the header gives `sender name` and `sender id`; every prompt says
  to answer by `target_agent_run_id`. Deterministic: no choice, no "not both". Tools unchanged:
  `send_message_to` still accepts addresses. Supersedes DEC-011's address-when-it-reaches part.
- DEC-011 (user, SR-005; its address part superseded by DEC-012): no bare name as a way to reach anyone. The task message describes the
  sender only by the values `send_message_to` takes — `recipient_address` (when it reaches the
  sender) and `target_agent_run_id` — so either one the agent picks is correct; the header keeps
  its labelled form with `sender address` only when it reaches the sender; no "not an address or
  an ID" explanation (noise).
