## Problem And Desired Outcome

Everything an agent reads about collaboration — its prompt sections, the tool descriptions,
tool results and refusals, the task message, the header of a received message and the `@`
note — was written from the system's point of view ("copy", "run ID", "this run", "spawn",
"nested AgentTeam") and has drifted into contradictions:

- The `teamScoped` switch gives task agents in Team and Org runs the team prompt.
- The team prompt says to message only at handoff points, then tells the agent to message
  copies and teammates.
- The `@` note suggests delegating to a teammate, which `delegate_task` refuses.
- The addressing section describes nested teams, which no longer exist.
- Agents are told their own address and the sender's address, although an address does not
  reach a task agent; a reply sent to such an address reaches a different agent or nothing.
- The same rule is repeated up to five times across prompt and tool texts.

Desired outcome: every agent receives precise, consistent text written for it, in one
vocabulary, each fact said once, with the exact wording of the wording authority.

## Stakeholders, Actors, And Outcomes

- The user: agents that collaborate correctly and predictably.

## Scope Guardrail (Mandatory)

### In-Scope Use Cases

- UC-001: the user starts a standalone agent; it delegates and talks with its task agents.
- UC-002: a task agent receives its task, works, delegates further and reports by ID.
- UC-003: the user starts a team; members hand off by their rules and delegate outside the team.
- UC-004: an organization's direct agent (Project Task Manager) talks with organization units
  and delegates to them; its task agent teams report back by ID.
- UC-005: the user mentions agents with `@` while talking to any of these agents.
- UC-006: an agent calls a collaboration tool wrongly and reads the refusal.

### Out Of Scope

- Tool behavior: who may message or delegate to whom, Task ownership, lifecycle, address
  resolution and refusal conditions stay exactly as they are; only text changes, plus the
  internal fact that selects the prompt and the viewer relation the `@` note needs.
- Which tools an agent gets (`get_handoff_rules` stays tied to `teamScoped`).
- UI wording for users (Settings, run history "copy" texts), except the optional badge in REQ-010.
- Memory and message storage (Task 8641c0ac).
- The engineer-facing model document's vocabulary (`collaboration_model.md` may keep "copy";
  it gets a short note on the agent-facing words).

### Non-Goals

- No new collaboration capability, tool or parameter; no tool or field renamed.

### Preserved Behavior Boundary

All tool behavior, every refusal condition, address resolution, Task semantics, persisted data
and saved conversations. Saved `[Mentioned collaborators]` notes and saved message headers with
a sender address keep parsing and displaying.

### Review Authority

The Solution Designer owns the wording authority; changes to it during implementation return
here (they change intended behavior).

- DEC-002 (user): no agent is told its own address; replies go by ID (the phone rule).
- DEC-003 (Solution Designer, within the direction): the sender address also leaves the task
  message and the received-message header (same rule).
- DEC-004 (Solution Designer, within the direction): repetitions removed as in views §8.
- DEC-005 (Solution Designer, within the direction): the `@` note decides per viewer (wording
  §8); this corrects the teammate-delegation contradiction.
- DEC-006 (Solution Designer, within the direction): refusal and result texts are agent-facing
  and follow the vocabulary (REQ-008).
- DEC-007 (Solution Designer, within the direction): a task agent with handoff rules gets the
  task agent prompt plus §5.3; tool exposure unchanged.
