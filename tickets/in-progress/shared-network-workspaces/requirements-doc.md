## Problem And Desired Outcome

Independent AutoByteus nodes do not currently share workspace storage across computers merely because each has a folder called “shared.” The user wants ordinary project folders backed by one shared filesystem, reachable over a trusted private network from Mac, Linux and Docker nodes. Existing runtime CLIs, shells and filesystem tools must operate on those folders normally, without copying files, attaching them to messages or switching to an AutoByteus-only file API.

Approved SR-018: the user can host the service natively on Mac, natively on Linux, or in Docker on Linux. Mac Docker agent nodes connect as clients; serving a Mac host folder from inside Docker Desktop is deferred. Native modes do not require Docker. The user selects a supported persistent local folder whose project files are actually served; setup does not silently replace it with a hidden named volume or synchronized copy. This supersedes the historical Linux-only scope and qualifies later all-mode wording through DEC012.

The product is a persistent shared-folder service, not a separate setup utility. Its first invocation owns initial configuration: a non-technical user runs one guided service command per participating computer/supported deployment, supplies connection information and a password/OS approval only when needed, grants necessary disruption approvals, and receives a tested usable shared path. Users must not assemble NFS/client/container configuration themselves. Documentation supports this workflow rather than replacing it.

Observable success: on real Mac and Linux computers, including a Docker node, a runtime writes a file in a shared project; another node reads and modifies that same file; the originating node observes the modification. Participants use the same backing storage and preferably the same absolute mount path; the user explicitly permits different paths if identical paths are impractical. Setup prints the actual usable locations and mapping, rather than treating name equality as proof of sharing. Normal-operation permission/setup safeguards are validated, outage limitations are disclosed, setup is documented, changes are merged, and delivery verifies the increment against DEC017. The full real-machine/runtime journey remains a later qualification target; personal user verification is no longer a pre-finalization gate for this increment.

### Out Of Scope

- Public hosted filesystem service, tenancy, billing, SDK product, custom filesystem driver/storage engine.
- The parked cross-node collaboration Task `project_task_6f01dae7-41fe-4645-94f6-f3ba1ce54069`: discovery, cross-node delegation/messaging, automatic agent wakeups, conversation ingestion or attachment synchronization.
- Sharing private server/runtime data, credentials, databases or internal agent memories.
- Automatic migration or relocation of existing projects, replacing user mounts, changing live network/security settings without approval.
- A new graphical in-app installation/mount-management wizard or live service-management dashboard remains OUT of scope. User-directed informational NFS Guide tab on Nodes is IN scope; it links/copies supported setup commands, not browser-driven mounting or a replacement for one-command setup.
- Hot-attaching arbitrary mounts to already-running containers without recreation; the older May dynamic-mount draft does not authorize this feature.
- Simultaneous same-file merge/coordination engine unless the user explicitly approves that scope expansion and this baseline is revised.
- Windows and arbitrary storage backends beyond the selected, tested reference setup.
- Advanced loss-of-storage hardening: per-action child isolation, guaranteed bounded file/preview/terminal diagnostics, guaranteed unrelated-local responsiveness during a hard-NFS stall, active-stream cancellation/recovery and outage chaos matrices. These are deferred after real use (DEC015); no outage-specific REST expansion for v1.

### Non-Goals

- No offline editing followed by later reconciliation; network outages may stall or fail operations.
- No instantaneous visibility for an already-open reader, universal zero-latency change stream, high-availability/storage-performance SLA or seamless hot-remount guarantee.
- No promise that OS/architecture-specific dependencies, executables and build outputs are portable between Mac and Linux simply because their files are shared.
- No automatic backup-management subsystem; identify operator backup/recovery responsibilities and safe procedures.

### Preserved Behavior Boundary

BEH-001/002/005/006: local-only and node-specific workspace functionality, runtime authorization policies and per-node private state remain supported. Opt-in sharing does not convert existing ordinary workspaces or move their contents. Removing a workspace registration is not permission to delete or unmount shared data.
