## Request Context

The user reported that after launching an independent Agent or Agent Team, all configuration controls remain locked even when the run is already stopped. The user specifically wants to change model options such as Codex Default/Fast mode and reasoning effort, and AutoByteus thinking/reasoning settings. The user clarified that the runtime and model itself do **not** change. On 2026-08-25 the user simplified the workflow further: every active state remains locked; the user explicitly stops the run/team and waits for completion, opens Settings, edits and saves, and only afterward sends the next message that resumes it.

Architecture review round `ARCH-REV-001` found that carrying the pre-launch `Reset to inherited` action into stopped existing-Team editing conflicts with the fixed runtime/model boundary for a reachable customized child. The user confirmed the simplest correction on 2026-08-25: do not add Reset-to-inherited to the stopped-run feature; preserve the existing pre-launch Reset flow unchanged.

Code review round `CRR-003` later identified that SR-003 had turned generic browser concurrency into a product contract without a supported initiating trigger. The user explicitly rejected simultaneous tabs/users and hand-speed timing races as the real browser path and directed the solution to validate normal production behavior rather than imagined or adversarial mechanical possibilities. Accordingly, this revision treats Stop completion, Settings entry, Save completion, and the later browser resume message as sequential; it removes optimistic revisions, draft rebasing, concurrent-writer policies, and unrelated persistence-transition expansion.

The required production-path audit did find independent non-Settings triggers. External-channel ingress is the clearest General Process feature: an inbound message resolves a bound standalone run through `ChannelAgentRunFacade -> AgentRunCommandCoordinator -> resolveCommandReadyAgentRun`, while a bound Team goes through `ChannelTeamRunFacade -> ChannelBindingRunLauncher.restoreTeamRun`. Those paths converge on the same General standalone lifecycle service or Team manager used by Studio Save.

CRR-006 later established that Application Engine does **not** converge there. `createApplicationRunServices` intentionally constructs separate application-scoped Agent/Team managers, lifecycle services, and facades. Application `sendInput` uses those instances, while Studio GraphQL/history uses General Process instances; their live maps and per-ID/root lanes are instance-local. Shared history files therefore do not prove shared lifecycle authority. The advanced base persists Application binding provenance in Agent metadata/Team trees, maintains a global run-ID lookup for nonterminal bindings, removes lookup only after terminal state is persisted, and gates Application input on a nonterminal binding. Normal `reloadAndReenter` clears/rebuilds the lookup after startup, so absence from that directory alone is insufficient during reentry; the persisted binding reference provides the second authoritative route. SR-005 uses the verified binding lifecycle as a lease: owner-aware Studio reads remain locked and direct updates reject while the lease exists; after release, General stopped persistence may proceed. No manager unification, cross-owner lane, browser revision, or multi-client policy is required.

## Findings From Code / Docs / Data / Logs

1. **The visible lock masks a missing end-to-end operation.** The form can already render the desired controls, but existing-run commands do not submit config and no mutation persists it.
2. **Runtime and model can remain fixed exactly as the user clarified.** Both identifiers are already stored separately from `llmConfig`; the update can be a narrow object/null patch.
3. **Requested Codex settings are concrete runtime inputs.** Reasoning effort and Fast mode are normalized from `llmConfig` into thread configuration on create/resume.
4. **Requested AutoByteus settings are concrete runtime inputs.** Its factory passes `llmConfig` into LLM construction on create/restore.
5. **Stopped-only is materially simpler than active-idle editing.** Save does not need to inspect turn queues, close admission, terminate, or interrupt. The existing Stop action establishes the boundary before the form unlocks.
6. **The browser journey is sequential, and external-channel ingress is an independent General trigger.** No normal browser user performs simultaneous Settings Save and message send. External-channel restore reaches the same General activation/root lane: Save-first commits before restore reads; restore-first makes Save return `RUN_ACTIVE`.
7. **Persistence failure is contained.** Because the run was already stopped, a failed write leaves the prior stored config authoritative and no live backend has observed draft state.
8. **Team safety is root-wide.** A member setting can influence future configured or delegated work, and the root owns tasks, messages, member activation, and persistence. Per-member live recycling would bypass that owner.
9. **No data migration is necessary.** Both persisted shapes already store `llmConfig` and normal restore readers consume it.
10. **Historical override intent cannot be reconstructed.** Current stored UI infers customization from value equality. Requirements therefore use a draft-start immediate-parent equality snapshot plus explicit current-draft edit markers only to bound parent propagation, and explicitly omit Reset from stopped-run editing instead of pretending launch-time intent can be cleared.
11. **Catalog failure must be non-destructive.** Current editable components sanitize configs against schemas, while historical mode preserves residual values. Existing-run editing must not turn transient catalog/schema gaps into persisted key deletion.
12. **The three runtime paths did not have equal initial readiness, but the integrated feature now covers all three.** AutoByteus rebuilds its LLM from `llmConfig`; Codex maps reasoning effort/Fast mode into `turn/start`; the integrated Claude bridge now carries supported thinking/effort through bootstrap, session, and SDK query construction.
13. **The installed Claude SDK contract supports the integrated bridge.** Version `0.3.231` exposes typed `thinking` and `effort` query options, and the current adapter uses that existing boundary rather than provider hot mutation.
14. **Claude catalog capability emission is now independently mapped.** Thinking and effort remain separate discovered capabilities; preserve the integrated rule that neither field is exposed merely because the other is supported.
15. **Optimistic concurrency is not justified.** No supported product flow has concurrent config writers. External-channel and Application Engine input change lifecycle/ownership rather than `llmConfig`. The SR-003 `configurationRevision`, stale-write outcomes, and browser revision/rebase state remain invalid; canonical reconciliation for real network or physical-write uncertainty remains valid.
16. **Application Engine is a separate live owner, not another caller of the General lane.** The integrated factories deliberately duplicate instance-scoped managers and lifecycle services; Application input and Studio Save cannot be made safe by asserting convergence that does not exist.
17. **The existing binding lifecycle supplies the proportional correction.** Current history carries binding provenance; the global exact-run lookup accelerates/validates resolution; terminal persistence occurs before lookup release; and `sendInput` rejects terminal bindings. Startup recovery is gated, while post-start reentry can rebuild the directory and therefore requires provenance fallback. An owner reader can fail closed while live and allow General stopped persistence only after verified release.
18. **The visible UI does not need a new ownership concept.** Owner-aware reads can project a live Application lease through existing active/locked editability and `RUN_ACTIVE`; inconsistent/recovery failure stays locked with the existing load/error path.

## Constraints / Dependencies / Compatibility Facts

- Fixed runtime/model selection determines the authoritative schema and the runtime adapter that consumes the config.
- Current server-side generic parameter validation is insufficient for full type/enum/range enforcement; the feature needs a validator matched to the catalog schema.
- Catalog sources can be dynamic or unavailable. A transient catalog failure cannot authorize mutation or stored-value deletion.
- Codex and AutoByteus consume the required settings. Claude advertises thinking/reasoning schema but does not currently consume `llmConfig`; the user approved correcting that adapter in this ticket.
- Standalone and Team send paths already support lazy restoration after an update leaves the run inactive.
- External-channel ingress is an additional normal General restore trigger for bound stopped runs. Its Agent and Team paths converge on the lifecycle owners used by browser resume, so one per-identity General lane is sufficient; it does not justify optimistic writer revisions.
- Application Engine uses intentionally separate live owners. A nonterminal binding must keep Studio config locked even when the General manager reports inactive; terminal binding persistence and lookup release establish the later General eligibility boundary.
- Because the Studio HTTP listener may accept a request while Application recovery runs, ownership resolution must await `ApplicationOrchestrationStartupGate`; failure or inconsistent binding evidence must leave Settings locked and must not write. Because supported post-start reentry clears/rebuilds lookups, canonical Application binding provenance must also be checked before no-lookup can mean released.
- No backward-compatibility wrapper or alternate legacy update path is needed because this is a new API/behavior.
