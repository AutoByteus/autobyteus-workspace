## Findings From Code / Docs / Data / Logs

1. The task-specific half of the carpenter model now exists: configured skills are advertised and read when needed rather than embedded.
2. There is no explicit fundamental model. The closest current subject is `AgentDefinition.instructions`, but it also carries identity, role-specific invariants, tool intent, and sometimes complete workflows.
3. Team execution already has a useful semantic split among team, agent, and generated runtime instructions. Fundamentals would be a fourth subject only if they have an independent author/source and conflict policy.
4. Tool descriptions already own capability and argument mechanics. Fundamentals should express stable working principles, not copy each tool schema.
5. Runtime projection is not uniform: native processes a system prompt, Codex accepts base/developer instructions, and Claude currently wraps composed instructions into turn input. “Put it in the system prompt” must therefore mean a stable instruction semantic, with runtime-specific projection, if all runtimes are in scope.
6. The approved platform-owned Working Environment and Bash sections reuse runtime workspace data, while Agent Identity reuses existing agent-definition fields. No new agent-definition field, authoring surface, or persisted schema is required.
7. The current session receives an explicit working directory, date, timezone, filesystem scope, and permission profile before tool execution. Efficient environment orientation therefore does not mean always running `pwd`; it means trusting authoritative injected context and verifying only the facts that are uncertain or operationally important.
8. Official Codex guidance separates persistent repository instructions (`AGENTS.md`) from reusable task workflows (skills), and describes skills as exposing metadata before loading full instructions when matched. This is structurally consistent with the carpenter-model distinction, but it does not by itself decide AutoByteus ownership or provider projection.
9. The earlier six-part generic fundamentals candidate is rejected. Reasoning, inspection, verification, and reporting advice should not be repeated merely because it sounds desirable; capable models already exhibit much of this behavior.
10. The renewed confusion is not fixed by requiring `pwd` alone. `pwd` reports a command's effective working directory; with no `cwd` override that should equal the configured workspace, while an explicit nested `cwd` legitimately produces another result without changing workspace identity.
11. The necessary environment rule is the separation of path namespaces. The actual workspace value is dynamic runtime data bound into an always-present environment block. Exact skill paths remain dynamic catalog data. Copying every skill path into the foundation would duplicate ownership and undermine the lazy catalog boundary.
12. The earlier system-skill layer proposal is superseded by the approved direct Bash Operating Practice and one ordinary lazy skill model.
13. No cross-kind dependency or skill-call protocol is needed.
14. Current code already has the desired single skill-kind shape; no system/operating/task discriminator should be added.
15. Agent identity should be always present and agent-owned. There is no separate shared generic behavioral-fundamentals layer.
16. `agent.md` is already a natural identity source, but its content contract needs clarification. Rendered frontmatter identity is limited to name and description; the body should emphasize stable responsibilities and ownership boundaries, while detailed workflow belongs in ordinary configured skills. The existing optional role field is not part of the prompt identity contract.
17. There should be no generic Platform Fundamentals block. The minimal agent foundation contains necessary identity, environment/path, approved concise Bash/file practices, and applicable Team Instruction/Team Runtime facts.
18. Workspace-versus-skill separation qualifies for the always-present foundation precisely because it is runtime-specific, cannot be inferred safely from paths, and has failed repeatedly in real runs. The prompt should name the only workspace and define both path namespaces explicitly.
19. Structured Markdown sections make the ownership boundaries directly visible and testable. This reduces accidental mixing without adding behavioral boilerplate; empty sections must be omitted so structure does not create prompt noise.
20. The earlier system-skill classification candidate is rejected. AutoByteus retains one ordinary lazy skill model and one native `## Skills` catalog or provider-native equivalent.
21. The concrete `shell-first-operating-practice` example establishes a separate concise system-prompt owner: Bash-first routing plus a few high-value efficiency examples. The long skill body, generic operating loop, and command manual are not eagerly repeated.
22. Bash availability is an AutoByteus runtime invariant. The prompt must state Bash as primary without conditional availability language and route to another provided tool only when Bash cannot achieve the purpose.
23. The refreshed base invalidates the earlier conditional `## Available Tools` proposal. Text-embedded tool calling and its prompt manifest were deliberately removed; tools are supplied through provider-native schemas and must remain out of the carpenter prompt.
24. The carpenter foundation must apply to all three supported runtime kinds. Their current paths differ substantially: native has a processed system prompt, Codex has base/developer instructions, and Claude currently injects its composed instructions into turn input. The target needs one semantic composition owner plus thin provider projection rather than three independently worded prompt builders.
25. Before the 2026-08-12 refinement, the intended logical order was Agent Identity, Working Environment, Bash Operating Practice, optional Team Instruction, optional Runtime Instruction, and optional Skills/provider equivalent. The new proposal inserts File And Directory Practice immediately after Bash Operating Practice.
26. File and directory work has enough distinct, recurring policy to justify its own concise section. Separating it improves ownership: Bash Operating Practice answers which primary interface to use, while File And Directory Practice answers how to locate, inspect, change, and verify filesystem content efficiently.
27. The former skill's filesystem content is much broader than the prompt needs. The extracted section keeps targeted search, bounded reading, format/change-shape awareness, guarded mutations, and verification; it omits general loops, communication style, command catalogs, Git lifecycle policy, and long recipes.
28. The name `Runtime Instruction` is too broad for implementation. Current production content is not general provider/runtime metadata; it is exclusively team-execution context generated from `MemberTeamContext`.
29. The precise replacement is `Team Runtime`. `Team Instruction` remains authored policy from the selected `team.md` body. `Team Runtime` remains framework-owned and closed to current member alias, fixed messaging contract/roster, and fixed assignment target/protocol content.
30. Every named documentation placeholder now maps to an authoritative source in `prompt-value-binding-spec.md`. Required values fail bootstrap before provider invocation; optional blank values omit only their line/subsection/section; no unresolved template token may reach a provider.
31. Agent description and body are not uniformly required by current file/provider paths. The structured identity contract therefore requires only the agent name, conditionally renders description and responsibilities, and forbids the current description-as-agent-instruction fallback from causing duplicated identity text.
32. `MemberTeamContextBuilder.resolveTeamDefinitionSummary` currently catches definition lookup failure and returns null. That is not safe for an exact-source Team Instruction contract: confirmed blank body means omission, while lookup failure must stop bootstrap.
33. The user clarified that `delegate_task` is a basic automatically provisioned team tool, while `submit_task_result` and `review_task_result` remain task-execution lifecycle concerns. The carpenter Team Runtime therefore renders fixed assignment protocol only; it does not infer or describe the other two tools.
34. The core skill loader rejects missing/blank name and description, but the server loader primarily checks field presence. The target shared validation boundary must require non-blank name/description and a valid absolute manifest path before advertising/materializing an entry.
35. Both concrete Classroom Simulation fixtures resolve with six top-level carpenter sections in the required order, no Skills section, and no Available Tools section. Professor resolves as coordinator with only `student` messageable/delegable; Student resolves as member with only `professor` messageable/delegable. Together they validate identity switching, role derivation, symmetric target restriction, and automatic team protocol against every agent in the real team.
36. Verbatim authored Markdown cannot be inserted without structural normalization: both the professor and team bodies use `##` headings that would otherwise become siblings of carpenter sections. The binding contract now preserves content while shifting authored ATX headings beneath their wrapper and defines an overflow rule beyond level 6.
37. The exact fixtures are 1,814 words for professor and 1,780 words for student after removing the duplicated selector footer and task-specific handoff example. Much of their length is not the platform foundation; it comes from duplication already present across each agent body and the team body. Rewriting bundled source bodies is approved as out of scope and remains a follow-up for the source packages' owning repository.
38. Concrete inspection justified two small Team Runtime contractions: remove the software-engineering-specific `implementation-handoff.md` example from the generic communication contract, and do not repeat selector/allowlist instructions after the membership roster. The roster now owns membership/messageability only; the preceding communication contract owns selector behavior once.

39. After concrete prompt review, the approved logical flow is identity and collaboration first, then operating context/practice, then domain technique: Agent Identity -> applicable Team Instruction -> applicable Team Runtime -> Working Environment -> Bash Operating Practice -> File And Directory Practice -> applicable Skills. No transition sentence is added.
40. `ARCH-REV-001` exposed a consequence of the superseded descriptor-driven design: moving capability-session creation into prompt prerequisites required new cleanup ownership. `ARCH-REV-002` then showed that full cleanup could double-release a shared client. The user-approved correction removes descriptor-to-prompt coupling, so no MCP creation/cleanup change remains in the target.
41. `ARCH-REV-001` confirmed that the native composer output is not the actual final payload because terminal Skills appends dynamic metadata afterward. The complete-payload assertion belongs in `SystemPromptProcessingStep` after the pipeline and before any processed-state or LLM mutation.
42. Architecture rework corrected two stale supplement statements without changing approved requirements: Bash/File practices are always-present prompt content, and authored-body editorial normalization is an explicit external follow-up rather than an open decision.
43. Latest-base verification proves tool definitions are already delivered out of band for all runtimes and there is no Available Tools prompt section. Collaboration tool names in Team Runtime are protocol prose, not tool provisioning.
44. A valid team context now governs two exact automatic provider tools: `send_message_to` and `delegate_task`. A shared exposure resolver unions and deduplicates them with agent-configured names before native/Codex/Claude projection; standalone tool resolution is unchanged.
45. Because the prompt composer consumes only definition, workspace, and team context, MCP remains existing provider transport. The target explicitly forbids moving session creation, adding Codex lease state, or changing ref-counted client cleanup.
46. `CRR-001` proves the server/API/UI removal was not the full native runtime boundary. Core `AgentConfig.systemPromptProcessors`, mutable `DEFAULT_SYSTEM_PROMPT_PROCESSORS`, `SystemPromptPipeline`, `BaseSystemPromptProcessor`, processor definition/registry/default singleton/registration, and package exports collectively retain the exact optional extension that `R-010` and `AC-010` prohibit.
47. No supported production caller needs the generic core registry after the server removal. The singular target is therefore not another restricted registry: `SystemPromptProcessingStep` directly calls one platform-owned configured-Skills catalog appender, validates the resulting complete prompt, then mutates state/configures the LLM. `AgentConfig` carries skill inputs but no prompt-mutator objects.
48. `CR-MP-001` is reachable through normal agent/team authored Markdown. While a fence is active, a closing fence is valid only when it uses the same marker, is at least the opening length, and has only trailing spaces/tabs. A same-marker prefix followed by content must remain content and must not expose following fenced headings to containment.
