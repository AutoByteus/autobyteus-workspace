## Human-transfer analysis / feasibility conclusions (not approved architecture)
A colleague can continue another colleague's assignment without inheriting their brain. What passes is the assignment, decisions with reasons, work products, outstanding obligations, access, and responsibility. Replacement should verify facts rather than blindly trust a summary.
Distinguish logical role/assignment from its current runtime session. Preserve user-facing continuity while recording who executed each portion. Whether one run ID or linked run records realize this is deferred.
A transfer packet should expose objective and approval constraints, completed work with evidence, current state, open work, rejected approaches/reasons, file and artifact references, latest user corrections, and actions with unknown outcome. Preserve original history for retrieval. A summary is a navigation aid, not the only authority.
Two routes: cooperative outgoing summary if possible; uncooperative recovery from durable records/workspace otherwise. Incoming runtime may help synthesize evidence, but outgoing inference must not be required.
Stop old execution before new execution can modify work. Uncertain external operations require reconciliation; no universal exactly-once guarantee is inferred.
Target access, tools, skills, permissions, attachments and context budget must be checked; provider credentials are not transferable content. Smaller target context can use bounded briefing plus source retrieval, but truncating critical constraints silently is unacceptable.
Returning to Codex after Claude work is another handover: the old Codex session is stale. Must incorporate intervening work before resuming substantive execution.
AutoByteus is an execution runtime, not a guarantee of independent/unlimited provider allowance. Target model credentials and usable capacity remain prerequisites. No pricing/reset-time claim made.
