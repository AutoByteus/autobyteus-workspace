## Goal / Problem Statement

Replace AgentTeam's flat, coordinator-projection-based Agent communication model with one truthful hierarchical addressing and handoff model that works consistently for standalone and recursively nested AgentTeams.

Ticket 1 must give a Team-bound Agent:

1. deterministic filesystem-like addresses for Agent and AgentTeam nodes;
2. a reusable natural-language `{from, to, rules}` handoff definition owned by AgentTeam;
3. an intrinsic read-only `get_handoff_rules` tool that converts only the caller's outgoing effective edges into ordered `{when, recipient_address}` choices; and
4. one consistent `send_message_to` Team route across AutoByteus, Codex, and Claude;
5. the same `/...` and `./...` recipient-address model for `delegate_task`, with task execution semantics applied only after the common address resolves to an Agent or AgentTeam recipient; and
6. one canonical absolute logical address per mounted placement, with member paths, parent-Team identity, route selectors, and task-owner facts derived rather than duplicated; and
7. the same canonical identity carried cleanly through the rooted TeamRun execution tree, task execution, structured history, APIs, internal SDKs, external/application integrations, and production frontend state, with kind-specific run IDs; released framework-owned predecessor data uses the blocking migration, while the unused application framework takes a direct target-only cut with no migration or compatibility path.

This ticket covers the AutoByteus project server, structured stored contracts, internal application SDK packages, integrations, and production web client as one atomic identity transition. Native AgentOrg and external repository-owned/pure-text Agent package edits remain separate work.

## Investigation Findings

- The production TeamRun topology is already recursive: `TeamDefinitionTopologyPlanner` creates `memberPath`/`memberRouteKey`, `TeamRunConfig` persists a recursive `memberTree`, and nested Team handles traverse it.
- Model-facing logical communication is nevertheless flat. `MemberCommunicationRosterBuilder` exposes direct Agents, synthetic child coordinators, and a restricted parent boundary; `TeamMessageRecipientResolver` resolves `recipient_name` against that projection.
- The flat projection is duplicated across member bootstrap/context construction and delivery resolution, which risks prompt and runtime disagreement.
- `MemberTeamContext` currently mixes Team instruction, task/token identity, flat recipient projection, and delivery wiring. The new reusable handoff/addressing capability needs a dedicated collaboration contract even if Team-specific context composes it.
- Team definition persistence has multiple read/write paths: shared and team-local definitions use `TeamConfigRecord`; application-owned definitions have a separate config reader/writer; GraphQL maps create/update/read independently. All must agree on the handoff field.
- TeamRun metadata has a strict normalizer/parser and is rewritten on create/restore/refresh. A run-stable handoff contract therefore must be added to the metadata/config snapshot rather than re-read from mutable definitions during restore.
- Integrated SR-006 implements `get_handoff_rules` in the established server-owned AutoByteus and Agent Tools MCP paths. The remaining defect is boundary shape and lifecycle exposure: its current service leaks the generic communication envelope, caller address, source endpoint, and authored edge grouping to the LLM, while provider bootstraps expose it only when package `toolNames` select it.
- `SubTeamMemberTeamDescriptor.representative` was not communication-only before SR-005: task roster/context mapping converted it to `TaskDelegationTeamIdentity.ingress`, and valid AgentTeam targets failed when ingress was absent. Representative removal therefore required the shared typed AgentTeam node to carry real coordinator entry. SR-006 keeps that configured coordinator address and lets the task-owned mapper derive the direct parent and local names before pairing against the caller's canonical local `TeamRunConfig.memberTree`.
- Integrated SR-006 already preserves `send_message_to` operation codes through AutoByteus/MCP adapters. `get_handoff_rules` does not need that delivery-oriented envelope: a successful call needs only actionable handoff choices, while the Team-runtime materialization invariant makes a non-Team invocation unavailable rather than a normal model-visible result.
- Current `stripMemberPathPrefix` rebases descendant `memberPath`/`memberRouteKey` but leaves nested Team `coordinatorMemberRouteKey` root/parent-prefixed. `MixedSubTeamRunFactory` separately strips only the newly created child's own coordinator key. A three-level child can therefore have a localized direct Agent route and a stale coordinator route, breaking exact task-coordinator lookup.
- `delegate_task` has a second public target language today: its schema requires a caller-supplied target kind plus a flat direct-member name, its input resolver matches `memberName`, and its rendered roster advertises those names. Because task delegation and ordinary messaging both select an Agent or AgentTeam recipient before applying different operations, preserving this second name authority would contradict the ticket's canonical-address goal.
- Existing focused tests explicitly assert synthetic representative and parent-boundary behavior. Those assertions become stale and must be replaced rather than retained as compatibility behavior.
- The post-implementation `MemberLogicalAddressContext` factory derives its two display strings but still accepts independently supplied `memberPath` and `immediateTeamPath`. It validates only `memberPath.length === immediateTeamPath.length + 1`; contradictory values such as `['research_team','research_lead']` plus `['another_team']` pass that check and create inconsistent logical identity.
- The post-implementation `ResolvedTeamLogicalPlacement` repeats facts already determined by its canonical address: Agent `memberRouteKey`, owner `teamPath`, one-segment `localMemberPath`, and `localMemberRouteKey`. Message delivery can derive a root selector from the effective Agent address, while task eligibility and current-local mapping can derive the target parent and basename from the same address.
- The previously deferred execution topology is now explicitly in scope. `TeamRunConfig` stores name/path/route/generic-run identity together; Team wrappers duplicate `memberRunId === childTeamRunId`; child execution requires recursive localization; runtime contexts and registries repeat those fields.
- `ConversationTargetAddress` and `TokenUsageExecutionAddress` separately encode equivalent member/task chains, while task Agent/AgentTeam identities repeat logical name/path/route/template/coordinator bundles. These are one concrete execution-address concern.
- Released framework-owned structured persistence that requires conversion includes TeamRun metadata, Team communication projections, task delegation records, token usage, and external-channel bindings. The existing app-data migration framework provides ordered execution, records, backups, atomic writes, and retries; the implemented server-runtime gate now blocks on non-successful canonical identity status and must be preserved. The unused application framework is explicitly not a migration subject.
- Physical Agent memory layout uses concrete TeamRun IDs in `teamRunPath`; that fact is not topology-derived. It should be renamed `ancestorTeamRunIds` and encapsulated, while the directory layout remains directly usable. Context-file locator/draft paths can derive the same relative storage segments from the canonical address without a disk rewrite.
- Production GraphQL/WebSocket and web state use route/path bundles broadly: `AgentTeamContext` has `memberNodesByRouteKey`, `leafAgentContextsByRouteKey`, and `focusedMemberRouteKey`, while task projections synthesize structural/source/relative route variants. A server-only cleanup would preserve the competing identity at the next boundary.
- Application contract versioning already has exact parser/loader gates: `application.json` declares the frontend SDK contract, `backend/bundle.json` declares backend-definition/frontend-SDK contracts, and the worker loader checks the backend definition. Because the application framework has no supported users, the target advances the changed semantic contracts and every project-owned artifact directly to V5. A non-target package fails ordinary exact validation; no application-specific predecessor migration, compatibility adapter, quarantine workflow, or fallback is added.
- Internal application SDK contracts, application launch/run-binding stores, and external-channel bindings also use route/path identity and must change atomically with the server/web contract. Opaque provider raw tool arguments are not a Team routing authority and need not be rewritten.
- A local nested-classroom fixture exists under the imported agents package with root coordinator `Teacher`, child Team `StudentStudyGroup`, and nested coordinator `student_one`. Its current prose uses the superseded task selector and its configs contain no handoffs, so live validation must stage a test-owned copy/overlay rather than edit the source package.
- The repository exposes `importAgentPackage({sourceKind:"LOCAL_PATH",source})`, supports runtime kinds `autobyteus`, `codex_app_server`, and `claude_agent_sdk`, catalogs `gpt-5.6-luna`, and already accepts `llmConfig.reasoning_effort: "medium"` in Codex coverage. The root `pnpm secrets:import` command accepts `$HOME/.autobyteus/server-data/.env` plus an isolated database URL; secret values must never enter evidence.
- CRR-076 / API-F-024 proves the strict Team stream starts too late to own provider segment lifecycle. Native AutoByteus start owns type while content owns only ID/turn/delta; `TeamAgentEventAdapter` is recreated per event; application streaming and Team wire require type; and the browser currently contains a guessed-text path. The existing `AgentRunEventDispatchQueue` plus run-owned lifecycle state is the first common serialized boundary across every provider and every listener, so lifecycle correlation belongs there rather than in provider-specific Team code, WebSocket sessions, application projectors, or the browser.

## Recommendations

1. Use the existing recursive TeamRun topology as the placement authority instead of building another member matrix.
2. Store authored AgentTeam handoffs in `team-config.json` beside members/coordinator because the edge endpoints are topology identities, not prose instructions.
3. Compile/rebase/validate one effective rooted handoff graph at TeamRun launch and persist it with run metadata.
4. Give Agent-facing communication/handoff tools one dedicated collaboration binding; let Team-specific instruction/task/token context compose that binding rather than making tools depend on a flat roster.
5. Extend the shared server-owned Agent communication/tool infrastructure once and project the same contract to AutoByteus, Codex, Claude, and Agent Tools MCP.
6. Replace, do not wrap, synthetic `subteam_representative`, `parent_boundary_agent`, `allowedRecipientNames`, and bare-name recipient behavior.
7. Before deleting representative-bearing member descriptors, make the collaboration-root logical placement resolver common to message delivery and task target selection; map its typed result into the current TeamRun's exact task-owned Agent/AgentTeam execution identity and coordinator entry without using communication representatives.
8. Preserve SR-003's strict localizer only as historical evidence for the integrated baseline; the comprehensive target removes localization entirely by sharing one rooted TeamRun tree and selecting child scope by canonical Team address.
9. Keep `send_message_to`'s code-preserving delivery envelope, but project `get_handoff_rules` directly to `{handoffs:[{when,recipient_address}]}`. Do not expose success flags, codes, generic messages, caller identity, source endpoints, or authored edge grouping when the LLM only needs a condition and destination.
10. Replace the public `delegate_task` `{target:{kind,name}}` selector and the old `send_message_to.recipient_name` field cleanly with `recipient_address` on both tools; do not retain aliases, flat-name, caller-supplied-kind, or task-roster lookup fallbacks. A task roster may advertise canonical addresses but is not an address authority.
11. Keep Ticket 1 static per TeamRun. Dynamic graph refresh, member add/remove, handoff invalidation, and notifications belong to Ticket 2 AgentOrg.
12. Treat TeamRun-tree compilation as the sole constructor of canonical placement addresses. Store only `{rootTeamRunId, memberAddress}` in the shared caller context; derive its parent Team, segments, basename, and storage encoding through `AgentTeamAddress` helpers.
13. Keep `ResolvedTeamRecipient` at Agent `{kind:"agent",address}` or AgentTeam `{kind:"agent_team",address,coordinatorAddress}`. Reuse the Agent collaboration address capability; do not add a second provider-neutral topology subsystem.
14. Replace only the parallel identity and ambiguous run fields inside `TeamRunConfig`; preserve its useful recursive locality as one uniform `rootTeam` tree with genuine Agent launch facts local to Agent nodes and derived lookup indexes kept out of persistence.
15. Give root, persistent child, and restored TeamRuns the same rooted metadata/index plus a selected Team address. Task AgentTeams allocate fresh run IDs while preserving absolute addresses. Delete every logical localization/prefix path.
16. Replace conversation, token, task-scope, event, and frontend scoped-route models with one `TeamExecutionAddress`.
17. Convert all framework-owned structured stores through one ordered blocking migration boundary, then keep current runtime readers strict. Rebuild derived indexes; do not migrate opaque provider arguments or physical run-ID directories.
18. Update GraphQL/REST/WebSocket, internal application SDKs, external/application stores, and production web state atomically. Do not keep route/path aliases or mixed-version adapters.
19. Treat Team collaboration guidance as an intrinsic runtime protocol, not a package-selected optional tool. Auto-materialize `get_handoff_rules` and `send_message_to` for every Team-bound Agent, inject one provider-neutral filesystem-like protocol block, and keep both absent for a standalone non-Team Agent unless separately configured for another supported context.

## Functional Requirements

- **R-001 — Definition field:** `AgentTeamDefinition` shall expose an ordered `handoffs` collection persisted as the optional top-level `handoffs` field in `team-config.json` for shared, team-local, and application-owned Team definitions.
- **R-002 — Edge shape:** Each edge shall use exactly `from: string`, `to: string`, and `rules: string[]`. Each rule is opaque natural language; the framework shall not execute or classify its meaning.
- **R-003 — Path-safe members:** Definition validation shall require non-empty trimmed member names that contain neither slash nor backslash, are not `.`/`..`, and are unique among siblings including case-insensitive collisions.
- **R-004 — Authored endpoint grammar:** Persisted handoff endpoints shall be definition-root absolute (`/` or `/segment...`) and shall reject caller-relative `./`, `../`, malformed separators, and non-canonical segments.
- **R-005 — Endpoint subjects:** `from` shall resolve to an Agent placement. `to` shall resolve to an Agent or AgentTeam node. An AgentTeam target denotes coordinator entry. Self-resolving edges shall be invalid.
- **R-006 — Rule and edge validation:** `rules` shall be a non-empty array of non-empty trimmed strings. Multiple outgoing targets are valid; duplicate effective `(from,to)` pairs are invalid and shall not silently merge or override.
- **R-007 — Runtime address grammar:** Team-bound `send_message_to.recipient_address` shall be the sole logical-recipient field and shall accept only `./`, `./segment...`, `/`, or `/segment...` according to the contract supplement. The external JSON string shall pass through the sole strict parser into opaque `RecipientAddressExpression`; successful caller-relative/root-absolute resolution shall produce one canonical `AgentTeamAddress`. The old `recipient_name` field shall be rejected, not aliased.
- **R-008 — Rooted resolution:** `./` shall start at the caller's immediate Team; `/` shall start at the outermost TeamRun collaboration root. Intermediate segments shall be AgentTeams; a final Agent shall receive exact delivery and a final AgentTeam shall use coordinator entry. Every root/child/task AgentTeamRun shall resolve against the same rooted TeamRun tree by canonical address; no child-local logical namespace shall exist.
- **R-009 — Collaboration reachability:** Any Agent placement in one collaboration root may address any valid Agent or AgentTeam recipient in that same root. Handoff edges shall not act as ACLs.
- **R-010 — Clean-cut replacement:** Bare recipient names, global leaf-name guessing, `../`, synthetic child coordinator recipient projection, coordinator-only parent reachability, and compatibility fallback to the old roster shall be removed from Team logical-address delivery.
- **R-011 — Handoff retrieval projection:** `get_handoff_rules` shall be a read-only no-argument Team capability. The Team collaboration-context builder shall be the sole caller-scope owner and retain compiled edges whose exact `from === caller.memberAddress`. The tool shall consume only that immutable ordered outgoing set, then flatten each edge in edge order and each edge's `rules` in rule order into exactly `{when: ruleText, recipient_address: to}`. Its successful model-visible result shall be exactly `{handoffs: Array<{when:string,recipient_address:AgentTeamAddress}>}`; it shall not expose `accepted`, success `code`, generic `message`, `result`, `member_address`, `from`, `to`, or `rules` wrappers.
- **R-012 — Empty and availability behavior:** A Team-bound Agent with no outgoing handoffs shall receive exactly `{handoffs:[]}`. Team runtime shall intrinsically materialize `get_handoff_rules` and `send_message_to` for every Team-bound Agent independent of package `toolNames`, so the required completion protocol is always executable. A standalone non-Team Agent shall not see the Team-bound `get_handoff_rules` adapter; missing Team context is an internal materialization invariant failure/provider tool error, not a normal successful result shape.
- **R-013 — Agent guidance:** Every Team-bound Agent's runtime system instruction shall use the exact renderer template in `agent-team-collaboration-system-instruction.md`. It shall render two sibling sections after the optional authored Team instruction and before working-environment guidance: `AgentTeam Addressing` first explains the general directory/file/subdirectory analogy, `/` and `./` grammar, invalid forms, the current Agent's mounted address, examples, and coordinator targeting; `AgentTeam Collaboration` then explains `send_message_to`, the direct-child constraint for `delegate_task`, and completion/blocked handoffs through `get_handoff_rules`. The Agent shall evaluate each returned `when`, call `send_message_to` once for each distinct applicable `recipient_address` in first-applicable row order, claim a handoff only after accepted delivery, and finish normally when no condition applies. Multiple applicable rows for one destination are reasons for one combined handoff, not duplicate deliveries. The prompt shall not use a `Team Runtime` wrapper, copy the handoff set, inject a full roster/topology, or require package-authored per-Agent handoff prose.
- **R-014 — One delivery tool:** `send_message_to` shall remain the only ordinary Agent-message delivery capability. Its `recipient_address` schema, description, parser input, instructions, manifests, provider adapters, and resolution shall consistently mean the logical recipient address. “Path” describes the `/...` and `./...` grammar; it shall not become a competing public field or persisted identity.
- **R-015 — Exact-run preservation:** `target_agent_run_id` shall retain its live-only global router, mutual exclusivity with `recipient_address`, direct target-run event behavior, exclusion from Team Communication projection, and existing success/rejection codes without collaboration-code renaming.
- **R-016 — Truthful projection:** Accepted Team-route delivery shall record and display the actual source and receiving Agent placements. AgentTeam-coordinator routing shall not attribute delivery to a synthetic representative.
- **R-017 — Launch compilation:** TeamRun launch shall recursively compile parent and child definition handoffs, rebase child-authored addresses under mount paths, validate the composed graph, and bind one immutable effective snapshot to every member AgentRun.
- **R-018 — Static active run:** Definition/catalog refresh after launch shall not change an active TeamRun's topology, handoffs, or collaboration binding. New launches may use the refreshed definition.
- **R-019 — Definition surfaces:** File readers/writers, cache/provider/service domain models, GraphQL output/create/update inputs, and converters shall round-trip handoffs consistently for every supported Team definition ownership scope.
- **R-020 — Restore snapshot:** Current TeamRun metadata shall persist the effective handoff snapshot and restore it without consulting current definitions for handoff meaning.
- **R-021 — Runtime parity:** AutoByteus, Codex App Server, Claude Agent SDK, and server-hosted Agent Tools MCP shall intrinsically expose canonical `get_handoff_rules` and `send_message_to` for a Team-bound Agent through one shared server-owned Team capability. AutoByteus JSON text and MCP text/`structuredContent` for `get_handoff_rules` shall represent the same minimal guidance object; send adapters shall continue to represent the same code-preserving delivery envelope. Provider-specific prompt timing may differ, but the semantic protocol text and required completion behavior shall not.
- **R-022 — Coordinator-led Team entry:** TeamRun messages with no explicit member target shall continue to select the root Team's configured coordinator; AgentTeam shall continue to require a direct Agent coordinator.
- **R-023 — Shared addressing, separate task execution:** `send_message_to` and `delegate_task` shall share the same strict parser, caller-relative/root-absolute normalization, collaboration-root tree traversal, canonical recipient identity, and syntax/tree failure codes. Task delegation shall separately own eligibility, task Agent/AgentTeam runtime identity, lifecycle, token scoping, and exact task-run messaging; it shall not treat handoffs as ACLs or derive identity from a communication representative. Every eligible AgentTeam target shall use the non-null configured direct-Agent `coordinatorAddress` from the rooted TeamRun tree, without root/local fallback.
- **R-024 — No external package edits:** Ticket 1 shall not edit external repository-owned Agent package Markdown/JSON or treat those package updates as an implementation prerequisite for project compilation/tests.
- **R-025 — Dedicated collaboration contract:** Agent-facing address resolution, outgoing handoff lookup, and AgentTeam-route delivery wiring shall consume one semantically tight collaboration contract. Team instruction/task/token concerns may compose it, but flat recipient projections shall not remain a parallel authority. The shared resolved recipient may expose only its canonical logical address and, for an AgentTeam, exact configured coordinator address; it shall not expose derived owner/path/route projections, full TeamRun nodes/configs, handles, or lifecycle identity.
- **R-026 — Error integrity:** Syntax, topology traversal, missing target, self target, invalid AgentTeam coordinator, and duplicate edge shall produce distinguishable typed failures; rejected attempts shall not deliver recipient input or emit accepted Team Communication. `send_message_to` AutoByteus/MCP results shall preserve existing `accepted`, `code`, `message`, and `result` behavior and exact internal operation codes. `get_handoff_rules` shall return only its minimal success object; a violated Team-context/materialization invariant shall use the provider's tool-error channel with typed internal diagnostics rather than fabricate a handoff list or expose a success envelope.
- **R-027 — Hierarchical task recipient selector:** `delegate_task` shall accept one required `recipient_address` string using exactly the R-007 grammar and shall remove the public `{target:{kind,name}}` selector and any `recipient_name` alias. Resolution shall infer Agent versus AgentTeam from the same canonical recipient returned for `send_message_to`. After shared resolution, existing task eligibility remains separately enforced: the recipient must be a direct physical Agent or direct child AgentTeam of the caller's immediate Team, and the caller Agent remains ineligible. An eligible Agent starts task-Agent execution; an eligible AgentTeam starts task-AgentTeam execution through its configured coordinator. A resolved non-direct recipient fails with `TASK_DELEGATION_TARGET_NOT_ELIGIBLE`, without name fallback, caller-supplied kind, or a separate task roster authority.
- **R-028 — One canonical logical address:** Once the reusable definition graph is mounted for a TeamRun, each Team or Agent placement shall have exactly one canonical absolute AgentTeam node address. Root-absolute and caller-relative recipient strings are request expressions only; `./...` shall be resolved immediately to the canonical absolute address and shall not be stored as a second identity.
- **R-029 — Minimal caller coordinate:** `MemberLogicalAddressContext` shall contain exactly `rootTeamRunId` and the caller's canonical absolute Agent `memberAddress`. It shall not store or accept independent `memberPath`, immediate-Team path/address, route-key, owner, target, handoff, or operation fields. The shared `AgentTeamAddress` capability shall derive segments, basename, parent Team address, ancestors, and storage encoding from `memberAddress`.
- **R-030 — Minimal shared recipient:** The one result shared by `send_message_to` and `delegate_task` shall be exactly Agent `{kind:"agent", address}` or AgentTeam `{kind:"agent_team", address, coordinatorAddress}`. Both addresses are canonical absolute logical addresses. The result shall not carry subject wrappers, owner coordinates, paths, routes, nodes/configs, handles, provider/runtime settings, definition IDs, or run/member/task lifecycle identities.
- **R-031 — Derived operation mapping:** Message delivery shall resolve the effective Agent address inside the root manager. Task delegation shall compare `parentAddress(recipient.address)` with the current TeamRun's canonical Team address, then resolve the exact node by full address. An AgentTeam target shall require its configured coordinator to be a direct Agent child. No consumer may retry root/local shapes, search globally by leaf name, or reconstruct a parallel owner coordinate.

- **R-032 — One native address authority:** The shared Agent collaboration address capability shall own strict canonical `AgentTeamAddress`, derivation helpers, root/caller-relative resolution, and serialization. TeamRun nodes, execution, history, APIs, SDKs, storage selectors, integrations, and frontend projections shall consume that meaning rather than define another parser or logical route type.
- **R-033 — Rooted local TeamRun snapshot:** `team_run_metadata.json` shall persist one schema-v3 `rootTeam` tree. Agent nodes shall keep their canonical address, definition/role/description, typed Agent/platform run IDs, and existing genuine runtime/model/tool/skill/workspace-root/application fields locally. AgentTeam nodes shall keep canonical address, definition ID, one `teamRunId`, one direct `coordinatorAddress`, optional nested placement presentation facts, and `children`. Compiled `handoffs` remain top-level. No separate persisted topology, launch-profile, binding, or derived-index table shall duplicate the node join.
- **R-034 — Rooted TeamRun execution:** Root, persistent child, and restored child TeamRuns shall share the same immutable root metadata tree and derived address index; each selects its AgentTeam node/direct children by canonical address. A task AgentTeam is a genuinely new execution and may materialize fresh typed run IDs from the selected source subtree, but every node keeps the same absolute address and configured coordinator. No persistent-child subtree copy, address localization, route prefix strip/rebase, coordinator rewrite, or root/local fallback shall remain.
- **R-035 — Kind-specific run identity:** Agent execution shall use `agentRunId`; AgentTeam execution shall use `teamRunId`; task execution shall use `taskAgentRunId` or `taskTeamRunId`. The root AgentTeam node shall contain the root `teamRunId`, which must agree with the metadata directory identity. Generic `memberRunId`, duplicate `childTeamRunId`, and wrapper equality invariants shall be removed. The same logical address may have multiple concrete task/persistent instances only when distinguished by these run identities.
- **R-036 — One execution address:** Conversation, task record, event/status, command, WebSocket, token-usage, streaming, and history projection paths shall use exactly `TeamExecutionAddress {rootTeamRunId,taskTeamRunIds,memberAddress,taskAgentRunId}`. The ordered run-ID chain shall resolve through task AgentTeam identities to the correct nested Team scope and the final member address shall validate against that scope. A task AgentTeam's logical address shall not be repeated in the execution locator. Operations may add their own task/invocation IDs but shall not add source/member/team/local route or path identity bundles.
- **R-037 — No synthetic task-instance identity:** `taskId` shall be the sole task-management identity **within its root TeamRun scope**, matching the allocator and root-scoped task-record ledger, and non-null `TaskDelegationRecord.taskRun.address` shall be the sole concrete task execution locator. A cross-root lookup shall therefore accept `{rootTeamRunId, taskId}` explicitly; it shall not pretend that `taskId` is globally unique. Current runtime shall not create or carry `taskAgentInstanceId`, `taskTeamInstanceId`, copied owner/parent TeamRun IDs, copied task run IDs, or copied creation timestamps in parallel task-identity objects. A task-bound runtime/member context may retain only the actual `taskId` required by task-result operations beside its already-owned `TeamExecutionAddress`, whose `rootTeamRunId` supplies the scope. The active ledger may expose one correlated in-memory `ActiveTaskExecutionBinding {kind:"task_agent"|"task_team",taskId,executionAddress}` derived from those two authorities; it is not persisted. Registries, task work packets, status/event/token projection, settlement, notifications, and activation results shall use root-scoped `taskId`, `TeamExecutionAddress`, or the provider-visible minimal `{task_id,status}` result according to their actual subject, without a synthesized instance ID or separate task Agent/Team run-ID result fields.
- **R-038 — Clean project interfaces:** GraphQL, REST, WebSocket, context/memory selectors, external-channel models, application orchestration, and project-owned application SDK contracts shall expose `memberAddress`, `coordinatorAddress`, kind-specific run IDs, or `TeamExecutionAddress` as appropriate. They shall remove `memberPath`, `memberRouteKey`, coordinator route, target route/path pairs, generic member run ID, and task structural/local route fields without aliases. The changed application backend-definition and frontend-SDK semantic contracts shall each use explicit target version `5`; project-owned application/backend manifests, backend definitions, SDK packages, validators, and built artifacts shall declare and enforce that same exact target. The V5 application SDK contracts shall own one exact shared `ApplicationExecutionContext {applicationId,bindingId,producer}` type; the server application domain shall alias that type rather than redeclare it, and metadata/frontend projection boundaries shall validate its complete structure plus canonical producer address instead of casting a generic record. At the Team AgentRun construction boundary, a non-null application execution context shall be validated against the exact concrete execution being created: persistent Agents retain the matching persisted producer address, while task Agent and task-Team-Agent runs preserve the source application/binding/display/runtime assignment but replace the producer address with their exact task execution address before `AgentRunConfig` is created. The runtime shall never pass a persistent producer address unchanged into a task AgentRun.
- **R-039 — Rooted frontend projection:** One `TeamRunFrontendProjectionBuilder` shall atomically project a closed launch/open input—validated canonical TeamRun metadata, exact root lifecycle, initial logical Agent focus, and exactly one discriminated fresh/loaded/historical-unloaded Agent seed per metadata Agent—into two paired frontend views. Agent seeds shall carry only member-address-keyed workspace/dynamic hydration facts and shall not repeat metadata-owned run/config/application identity. Immutable `TeamTopologySnapshot` owns `teamDefinitionName`, the recursive logical/effective-launch-configuration `rootTeam`, and a private derived canonical-address index exposed only through typed queries; it carries no Agent/AgentTeam run binding, `ApplicationExecutionContext`/producer execution address, task execution, timeline, mutable status, sender, argument, or presentation-mutation field. `TeamExecutionState` exclusively owns all persistent/task Agent and AgentTeam run bindings, exact SDK-typed application execution contexts on concrete Agent variants (admitted only after complete structure/canonical-address validation by the projection builder), root lifecycle, canonical `TeamExecutionAddress` index, graph relations, Agent contexts, focus, the one-copy task projection from which active timeline and history derive, and typed navigation/presentation views. `AgentTeamContext` shall contain only `{topology,executions}` and shall not repeat root `teamRunId`, lifecycle, mutable launched `config`, historical hydration, or stream subscription state: root identity/lifecycle derive from the root persistent-Team execution, effective launch configuration derives from topology, application producer identity derives from the concrete Agent execution, hydration enters the execution owner, and connection state stays transport-owned. Pre-launch configuration/focus/pending input shall use a separate deep-readonly `TeamLaunchDraft` with no copied definition topology, run ID, execution address, AgentContext, conversation identity, stream subscription, or history/token subject; the existing definition catalog remains the definition-topology authority for draft rendering/address validation, and no second current Team config may exist beside the draft. Draft and launched-Team selection shall be distinct typed subjects rather than temporary/real meanings hidden in one string ID. Hydration, streaming, commands, history, memory, token usage, desktop/mobile navigation, and same-named leaves shall use those boundaries with no legacy route-key/path fallback, public topology/execution map, provisional execution identity, raw serialized-key access, or persistent-node substitution.

Public/domain selectors shall use canonical addresses. Existing final memory directories and context files/locators shall remain directly usable by deriving the same relative storage segments from the address; logical addresses shall not replace concrete run-ID directory ownership.

## Assumptions

- “Ticket 1” is the AgentTeam-only prerequisite in this document; “Ticket 2” is the later native dynamic AgentOrg effort.
- Filesystem-like paths are logical in-memory/runtime identities, not operating-system filesystem access.
- Handoff rules are LLM-readable guidance and not deterministic boolean expressions.
- An AgentTeam target means coordinator entry; it does not mean broadcast.
- The outermost standalone TeamRun is `/`; the root Team's direct members are `/member`, not `/team_name/member`.
- A reusable nested Team definition authors addresses from its own `/` and receives a mount prefix when composed.
- The final solution design may choose exact class/file names, but it must preserve the behavioral owner/boundary and clean-cut constraints stated here.
- `AgentTeamAddress` identifies both Agent and AgentTeam nodes; rooted-tree lookup determines kind. Canonical form is an invariant of the type. The root address `/` is valid only where an AgentTeam is allowed.
- `TeamExecutionAddress` is a concrete execution locator, not a second logical address; its task run IDs distinguish concurrent instantiations of the same placement.
- Existing context-file locator path segments are a derived storage encoding and may remain byte-compatible even though the domain field becomes `memberAddress`.

## Risks / Open Questions

- The rooted implementation has removed representative-based coordinator routing and contracted the current execution identities. SR-013 must not regress that result while correcting migration-only predecessor interpretation; no consumer may compensate with a localized/root address alternative.
- Shared root addressing can resolve cross-branch and deeper placements that current task lifecycle does not own. Ticket 1 must keep this as an explicit post-resolution eligibility rejection rather than silently expanding task activation across TeamRun managers; cross-Team task ownership expansion is separate product scope.
- Nested TeamRuns currently strip parent prefixes and use a parent-boundary bridge. The target must retain lazy nested execution while forwarding absolute addresses and execution-address events unchanged.
- Current run metadata has a previous explicit legacy upgrade boundary. On fresh flat data that stable prerequisite runs first; when its record is already terminal it is skipped. In both cases the separately identified canonical migration owns final-v3 conversion before strict current readers run, composing the shared migration-only flat decoder if terminal-warning history left a residual safe flat item.
- Provider prompt lifecycles differ: AutoByteus and Codex bootstrap instructions differently from Claude per-turn input composition. The same stable filesystem-like protocol and mandatory completion lifecycle must be present at each provider's established system-instruction seam, while rule content stays tool-retrieved.
- External packages will temporarily retain old prose/tool configuration until their separate change. Ticket 1 intentionally provides no runtime fallback for their bare recipient names.
- The refactor crosses a large identity surface. A missed producer/consumer can reintroduce a second address authority even if central types are clean; an explicit production-source allowlist/inventory is required.
- Migration must distinguish display-only legacy `memberName` from structural route/path. It must derive a TeamRun address only from an agreeing route/path pair and distinguish task-AgentTeam-relative member segments by structural position/enclosing record scope, not by trying root/local alternatives. Invalid data must block without mutating the source.
- The implemented server-runtime gate requires exact success from `20260801_team_canonical_identity` while leaving unrelated established warning statuses non-blocking. SR-015 preserves that single scoped gate by making the token database conversion one named `20260801...` item; the gate must never infer token readiness from the historical `20260703...` record.
- Application bundles/databases are not supported predecessor state because the feature has no users. Project-owned application artifacts and fresh test databases are replaced together; a non-target external artifact fails the current parser/store and receives no compatibility or migration path.
- Frontend persistent and task executions can share one logical address; keying all Agent contexts by `memberAddress` alone would collide. The execution aggregate therefore uses canonical execution-address serialization privately while exposing only typed address/query/view APIs.
- Strict Team stream admission can expose previously hidden producer drift. Rejection is intentionally mutation-free; producer-to-browser contract coverage must use actual mapper output rather than mocks that invent browser-only fields.
- Segment correlation at Team ingress would fix only one surface and fail again for standalone/application/history consumers. The run-owned pipeline must remain the sole stateful owner; provider converters must emit explicit starts, and actual-boundary tests must never fabricate per-content type.
- Browser late subscription needs self-contained canonical content. Removing content type instead of deriving it once at AgentRun would force a second client lifecycle authority or lose correct non-text presentation; retaining required canonical type is a deliberate projection, not a second source authority.
- Task AgentTeam source topology cannot stand in for concrete descendants. A child is absent until a real AgentRun ID exists; showing fewer truthful rows temporarily is preferable to a focusable placeholder execution.
- Target-owned role/description/team-definition display snapshots, definition IDs, run IDs, and physical storage lineage may look redundant in some contexts but represent presentation, concrete execution, or storage ownership. Historical TeamRun `memberName` must be interpreted correctly as display-only migration input, then omitted because v3 intentionally uses the canonical address basename plus retained role/description presentation instead of persisting a duplicate node name.
