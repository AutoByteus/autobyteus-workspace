## Request Context

The user split the earlier native AgentOrg effort into two independent tickets:

1. **Ticket 1 (this package):** make AgentTeam addressing and handoffs truthful, consistent, and reusable.
2. **Ticket 2 (later):** add native AgentOrg definition/run ownership and explicit-refresh dynamic behavior on top of Ticket 1.

The user explicitly decided:

- use filesystem-like `/` and `./` paths consistently for standalone and nested AgentTeams;
- stop faking a child Team coordinator as a parent Team member;
- retain handoff JSON endpoints named `from` and `to` and allow natural-language `rules[]`;
- make handoff retrieval outgoing/sender-centric only;
- provide `get_handoff_rules` rather than repeatedly injecting the whole rule set;
- target an Agent directly or target an AgentTeam through its configured coordinator;
- keep handoffs as Agent/LLM guidance rather than hard-coded predicates;
- keep AgentTeam static per run; dynamic updates belong to AgentOrg;
- use no automatic file-system watching; and
- exclude repository-owned external/pure-text Agent package edits from Ticket 1.

During SR-004 clarification, the user explicitly rejected a separate task target naming system: task delegation selects a recipient just as message delivery does, so `delegate_task` must use the same canonical `/...` and `./...` logical addressing model as `send_message_to`. Different execution semantics may follow resolution, but there must not be a second flat task address authority.

During final user verification after SR-005 implementation and downstream delivery preparation, the user further clarified that mounting the Team definition graph deterministically decides each placement's one canonical address. `memberPath`, immediate-Team path/address, route key, owner Team, and local name are derived views and must not be duplicated as independent shared identity. The user requested another design-principles-led simplification round and initially instructed the solution designer to stop for user review. The user subsequently approved SR-006 and authorized architecture re-review, while deferring broader whole-TeamRun execution-identity normalization until the focused contraction was integrated.

After the SR-006 implementation passed architecture, source, API/E2E, and delivery re-entry and reached integrated checkpoint `66b02ae...`, the user explicitly reopened that deferred decision in this same ticket. The user prefers a larger clean refactor—including structured history, metadata, SDKs, and frontend—over retaining parallel identity merely to avoid migration. The user asked the solution designer to complete the revised requirements and design, but not send the package to a reviewer until the user has reviewed it.

During review of the first comprehensive proposal, the user challenged the normalized `topology + launch profiles + bindings` JSON because it separated facts that are naturally inspected and restored together. Reinspection confirmed that current metadata already keeps genuine runtime/model/tool/skill/workspace/application/platform facts locally on each Agent, reconstructs `workspaceId` from `workspaceRootPath`, and derives `memoryDir` from storage ownership. The user and solution designer therefore converged on SR-008: retain one recursive TeamRun aggregate, remove only parallel logical name/path/route and ambiguous run identities, use native `agent_team` and `coordinatorAddress` terminology, and derive indexes rather than persist joins.

During the subsequent public-tool naming review, the user observed that “send a message to a recipient address” is more natural than `recipient_name` and better expresses the domain intent than `recipient_path`. The distinction is now explicit: `/...` and `./...` are filesystem-like **address grammar**; the public field is `recipient_address`; the raw request value is `RecipientAddressExpression`; and the resolved absolute node identity is `AgentTeamAddress`. This is a current-contract rename, not a persisted TeamRun schema change.

During the handoff-tool and system-instruction review, the user rejected the generic `{accepted,code,message,result}` rule-query response as internal machinery that does not help the acting Agent. The user defined the useful decision as exactly two facts—under what condition to hand off and which canonical recipient address to use—and approved `{handoffs:[{when,recipient_address}]}`. The user also required every Team Agent to call the tool after finishing work, with an explicit filesystem-like logical-address explanation and examples in the system prompt. This implies intrinsic Team runtime exposure of both retrieval and delivery tools; configuration gating cannot remain an independent prerequisite for a mandatory protocol.

After SR-013 was sent for architecture re-review, the user refined only the literal Agent-facing copy. The user rejected “before completing your work, or before stopping because you are blocked” as lifecycle jargon and selected a natural explanation-first block: first explain filesystem-like logical addresses and the Agent's own address, then say, “When you finish your work or are blocked, call `get_handoff_rules` to check your configured handoff rules.” The user requested that exact prose in a dedicated file for direct implementation use and explicitly classified it as pure text with no architecture impact.

After approving that protocol, the user added a mandatory downstream test requirement and authorized architecture review once it was documented: create an example AgentTeam from the imported nested-classroom package; run it under AutoByteus, Codex App Server, and Claude Agent SDK; use `gpt-5.6-luna` for AutoByteus and `gpt-5.6-luna` with medium reasoning for Codex; and allow credentials from `$HOME/.autobyteus/server-data/.env` to be imported with the repository pnpm command. SR-011 treats these as live API/E2E requirements, not as solution-design execution.

ARCH-REV-006 then failed only DR-004 as `Design Impact`. The reviewer confirmed the rooted aggregate, execution/address ownership, migration, handoff protocol, providers, storage, and live contract, but demonstrated that current supported application catalog/open/launch still treats backend-definition/frontend-SDK V4 as current. Because those V4 SDK types carry fields the clean cut removes, SR-012 adds an explicit V5 semantic boundary and atomic artifact/gate sequence. This is the concrete enforcement of the already-approved no-mixed-version requirement; no new user decision is required.

ARCH-REV-007 passed SR-012 and implementation proceeded. During API/E2E migration work, CRR-022 classified CR-F-011 as `Design Impact`: the approved migration rule incorrectly required legacy `memberName` to equal the route/path basename, even though the real maintained historical fixture stores `Program Manager` / `program_manager` and `QA Specialist` / `qa_specialist`. The review also proved a supported upgrade where `20260517_team_run_metadata_member_tree` is already recorded `SUCCEEDED` or `SUCCEEDED_WITH_WARNINGS`; `runPending()` skips that ID, so changing its code cannot normalize its prior output. The user reviewed SR-013, confirmed that the coordinator-required operational AgentTeam invariant remains valid and that a coordinatorless organizational container belongs to the later AgentOrg scope, and explicitly approved architecture re-review without further solution change.

ARCH-REV-008 passed the complete SR-013 package. IR-014 then repaired the token planner's nested task-Team root/chain/member reconstruction. CRR-025 independently confirmed those row semantics but exposed the broader supported-upgrade spine: the pre-ticket `20260703_token_usage_execution_address_backfill` ID can already be terminal after writing old `{segments}` JSON, so `runPending()` skips the revised converter; separately, the migration's per-row database interface cannot uphold the already-approved all-or-nothing transaction contract. These are design ownership/atomicity corrections to BEH-015, not new user behavior. SR-015 therefore reuses the already pending/exact-gated `20260801_team_canonical_identity` record as the single target canonical owner and makes token persistence one store-owned batch transaction.

## Findings From Code / Docs / Data / Logs

### 1. Recursive topology is present but not the Agent logical-address authority

`TeamDefinitionTopologyPlanner.buildSkeleton` recursively assigns each Agent and child Team a `memberPath` and slash-joined `memberRouteKey`. `TeamRunConfig` stores the recursive tree and derives a flat leaf list only as a non-authoritative projection. Nested Team handles already traverse and strip route prefixes at child boundaries.

This makes the desired filesystem analogy an evolutionary correction: use the current truthful topology for Agent logical addressing instead of inventing a separate graph.

### 2. Flat recipient projection is an explicit workaround

`MemberCommunicationRosterBuilder` exposes:

- direct Agents as `local_agent`;
- child coordinators as `subteam_representative`; and
- selected parent Agents as `parent_boundary_agent` only for the child coordinator.

`MemberTeamContextBuilder` stores this list and `allowedRecipientNames` for prompt use. `TeamMessageRecipientResolver` rebuilds the same sender-specific roster at delivery time, then exact-matches `recipient_name` against it. The duplicated build creates two coordination points and prevents a truthful cross-branch namespace.

### 3. Synthetic projection is not required for delivery mechanics

The mixed runtime already has recursive Team/member handles. Parent-to-child delivery enters a `MixedSubTeamMemberHandle`, strips the top segment, and posts to the child run. Child-to-parent delivery prefixes the actual child Agent sender path before it enters the parent delivery coordinator. Communication payloads use concrete participant addresses.

The implementation challenge is therefore root-aware resolution/binding, not inventing a new message transport.

### 4. Definition schema ownership is distributed across explicit source adapters

Shared/team-local definitions and application-owned definitions do not use one identical parser/writer. GraphQL also has independent input/output types and conversion. A handoff field added only to the domain or shared config would be lost on update through another surface.

### 5. Handoff rules need a launch snapshot

Active AgentTeam dynamics are outside Ticket 1. The effective edge graph depends on recursive mounting: a child definition's `/research_lead` may become `/research_team/research_lead` in its parent run. That effective graph must be compiled after topology resolution and stored with the run. If restoration re-reads definitions, an old run could silently receive new rules or broken endpoints.

### 6. A strict public address parser is required

Current internal route-key normalization replaces backslashes, collapses repeated slashes, and strips leading/trailing separators. Those behaviors are useful for some internal canonical identities but would silently reinterpret malformed model input. The Team logical-address contract must have a strict parser that preserves the semantic difference between `/`, `./`, and invalid bare/parent-traversal forms.

### 7. Tool infrastructure can be extended without provider-specific business logic

`send_message_to` is registered as a server-owned AutoByteus tool and a static Agent Tools MCP adapter. Codex and Claude materialize the shared MCP descriptor and normalize provider names back to canonical tool names. `get_handoff_rules` should follow that established path and use a bound collaboration context rather than provider sessions as the rule owner.

### 8. Existing data supports no-migration addition

Observed Team configs use path-safe names and omit handoffs. The normal version-agnostic definition reader can map absence to `[]`. Current recursive TeamRun metadata can accept a new optional snapshot and map absence to `[]`; no existing field needs reinterpretation or transformation. This is `Directly Usable — No Migration`, not a reason to rewrite every file.

### 9. Existing durable coverage has both reusable and stale parts

Reusable coverage areas:

- AgentTeam definition GraphQL create/update/file roundtrip;
- nested mixed Team launch/delivery/restore;
- all-runtime `send_message_to` matrix;
- AutoByteus/Codex/Claude tool gating and prompt projection;
- TeamRun metadata schema/mapper/history;
- exact-run selector tests.

Stale coverage areas after the clean cut:

- `MemberTeamContextBuilder` assertions for visible subteam representatives;
- parent recipients only for the child coordinator;
- flat `allowedRecipientNames` roster manifests;
- nested E2E calls using bare coordinator/parent names.

The later `api_e2e_engineer` must produce its own formal coverage investigation before editing/executing durable coverage.

### 10. Root-canonical delivery can reuse the current parent callback and downward handle mechanics

The child `MemberTeamContext` currently constructs a child-local sender identity, and `mixed-parent-boundary-delivery-intent.ts` prefixes that identity while walking upward. That rewrite exists to support the flat parent-boundary projection. A focused member collaboration binding can instead construct the caller's root-canonical path and root TeamRun ID before dispatch. Non-root managers can forward that intent unchanged through their existing parent callback until the root manager is reached. At the root, `MixedPersistentMemberRegistry.resolveContext` already returns the top-level subteam wrapper for a nested selector, and each `MixedSubTeamMemberHandle` already strips one segment while delivering downward. The target design therefore needs one root resolver, not a new transport.

### 11. The Team resolver's exact-run/task-run branch is not the public exact-run route

`SendMessageToDispatcher` returns immediately to `GlobalAgentRunMessageRouter` when the selected target is `target_agent_run_id`; only `recipient_name` reaches `buildInterAgentMessageDeliveryIntent` and Team delivery. No production builder found in the search constructs a Team intent with an exact-run selector. The exact/task/recovery branches inside `TeamMessageRecipientResolver` are overlapping unreachable policy for the public tool path and should be removed when the Team intent is tightened to a logical address subject. This does not change exact-run behavior.

### 12. Runtime snapshot propagation has several explicit reconstruction seams

`TeamRunConfig` is reconstructed by topology planning, launch identity assignment, metadata restore, `AgentTeamRunManager`, `MixedTeamRunBackendFactory`, and child TeamRun creation. An effective handoff field added only to the initial planner would be silently dropped. The implementation must thread the root snapshot through every root config reconstruction and give lazy child contexts an inherited root collaboration binding containing root ID, Team mount path, and caller-filtered outgoing edges. Persisting a second member topology is unnecessary and would create an overlapping authority.

### 13. Task-Team ingress must be split from communication before representative removal

The synthetic `SubTeamRepresentativeDescriptor` is overloaded. Communication uses it to advertise a child coordinator as a fake parent member, while task delegation maps the same data to the legitimate `TaskDelegationTeamIngressIdentity` required to start a delegated task Team. `DelegationTargetRosterBuilder` also reads it for task guidance, and `TaskDelegationInputResolver.resolveTeamTarget` rejects a Team target without ingress.

The authoritative source already exists independently of communication rosters: the root `TeamRunConfig.memberTree` identifies every placement, while each active owning TeamRun has a canonical local config containing its direct Team coordinator and runtime IDs. The common address resolver can return a typed root placement plus the owning-Team route. Task delegation then maps that result to `TaskDelegationMemberIdentity` or `TaskDelegationTeamIdentity`, requiring a real direct Agent coordinator for a Team target. Task guidance, native AutoByteus context, and MCP task adapters need caller/root addressing identity, not a copied flat target list or communication representative.

### 14. Historical SR-002 finding: stable collaboration codes stopped at provider adapters

`SendMessageToDispatcher` and `GlobalAgentRunMessageRouter` already return `AgentOperationResult` with codes such as `DELIVERED`, argument failures, grant failures, and `TARGET_AGENT_RUN_NOT_ACTIVE`. `AutoByteusSendMessageToTool._execute` reduces the result to a human-readable string. `SendMessageToMcpAdapterProvider` returns an operation result that `AgentToolsMcpResultMapper.toolResultFromOperationResult` reduces to text plus `isError`. Both paths discard `code`.

SR-002 correctly required the send path to preserve dispatcher/global-router codes, and integrated SR-006 now does so. It also applied the same `{accepted,code,message,result}` wrapper to `get_handoff_rules`. SR-010 supersedes only that read-query projection after user review: send delivery still copies exact codes, while successful rule retrieval exposes only `{handoffs:[{when,recipient_address}]}`. Missing Team binding is prevented by intrinsic Team materialization and remains a typed internal/provider tool error rather than normal guidance.

### 15. Historical SR-003 finding: child TeamRun localization was incomplete below one nested boundary

`stripMemberPathPrefix(memberConfigs, prefix)` recursively slices every descendant `memberPath` and derives a new `memberRouteKey`, but the Team branch spreads the original `coordinatorMemberRouteKey` unchanged. `MixedSubTeamRunFactory` separately calls `stripRoutePrefix` only for `input.subTeamConfig.coordinatorMemberRouteKey`, the coordinator of the child being created. It never repairs nested Team entries inside `childTree`.

For a root config containing `/research_team/field_team/field_lead`, localizing `/research_team` produces the Agent route `field_team/field_lead` while the nested `field_team.coordinatorMemberRouteKey` can remain `research_team/field_team/field_lead`. Exact current-local task mapping then correctly refuses the inconsistent tree. A fallback that attempts both shapes would create two route authorities and mask invalid configs.

SR-003 correctly placed the then-proportionate correction in one TeamRun-config localization boundary rather than task delegation. That localizer was required for the SR-006 baseline and remains valid historical evidence that parallel root/local identity is costly. SR-008 supersedes the mechanism itself: root, persistent child, and restored TeamRuns share one rooted metadata/index and select by absolute Team address; task AgentTeams materialize fresh run IDs while preserving the selected subtree's absolute addresses. No localizer or alternate route shape remains.

### 16. `delegate_task` currently duplicates the recipient identity model

The public task schema and parser require `{target:{kind:"member"|"team",name}}`. `TaskDelegationInputResolver` then matches that flat name against `TaskDelegationContext.members`, and `DelegationTargetRosterBuilder` teaches the model those direct-member names. By contrast, the approved message contract resolves `/...` or `./...` against the full collaboration tree. Both operations first answer the same domain question—“which Agent or Team placement is the recipient?”—so retaining the task form would leave a second address authority and force callers to know a target kind the topology already owns.

The clean target is one common recipient resolver returning Agent `{kind:"agent",address}` or AgentTeam `{kind:"agent_team",address,coordinatorAddress}`. `send_message_to` maps that result to ordinary Agent delivery; `delegate_task` first preserves current direct-member/current-TeamRun eligibility, then maps an eligible result to task-owned identity and activation. Task-specific eligibility occurs after shared resolution and does not change address meaning.

Current task activation is scoped to a `TeamRun`: `TaskDelegationService` holds a run-bound ledger and calls `TeamRun.startTaskAgentInstance` / `startTaskTeamInstance`, while mixed task registries search only that run's direct member contexts. The user clarified addressing, not cross-TeamRun task ownership. The proportionate target therefore lets the common resolver identify any root placement, then requires the resolved placement's owning Team path to equal the caller's immediate Team path. Non-direct/deeper/cross-branch placements receive a task-specific eligibility error without name fallback. Historical task records already store structured `ConversationTargetAddress` and receiver kind rather than the live flat selector, so this public input cleanup does not itself require record migration.

### 17. SR-005 finding: the proposed shared placement must not become a config or lifecycle carrier

`ARCH-REV-003` confirmed the common resolver and current-TeamRun task policy, then identified a boundary contradiction in the proposed return type. `ResolvedAgentPlacement.memberConfig` and `ResolvedAgentTeamPlacement.teamConfig` would expose complete root snapshot configs—including provider, workspace, runtime, and recursive child settings—through `TeamRun.resolveLogicalPlacement`, even though that facade exists specifically to prevent task tooling from reading TeamRun config. The proposed `owningTeamRunId` is also not a truthful active-owner identity when a task-scoped TeamRun instantiates the same logical Team placement under a distinct run ID.

Neither operation needs those config or lifecycle values. Root message delivery already owns the config, registry, and handle lookup behind `MixedTeamManager`; after shared resolution it needs only the selected logical Agent address or configured Team ingress address. Task delegation obtains task runtime IDs, role/description, Team definition ID, and coordinator materialization identity from the caller's **current** canonical local config.

SR-005 therefore narrowed the shared value to immutable logical coordinates and omitted all config objects, member/run IDs, provider/runtime settings, handles, and lifecycle identity. That was the correct response to `DR-003`; §18 records the later post-implementation evidence that the remaining route/owner coordinates are themselves derivable and should now be removed by SR-006. The enduring conclusion is one resolver and one identical placement shape without either operation consuming the other's state.

### 18. SR-005 still models one canonical placement more than once

The SR-005 implementation proves that the resolver boundary can remain config-independent, but its shared values are not yet minimal. `MemberLogicalAddressContext` stores a canonical member string, its segment array, the parent-Team string, and the parent-Team segment array. Its factory reduces risk by deriving the two strings, yet still accepts two independent arrays and checks only their relative lengths. It does not require `immediateTeamPath` to be the exact prefix of `memberPath`, so contradictory caller identity remains constructible.

The shared placement repeats the same issue one layer later. For an Agent, `memberRouteKey` is the canonical address without its leading slash. For any non-root subject, `owner.teamPath` is `parentAddress(subject)`, `localMemberPath` is `[basename(subject)]`, and `localMemberRouteKey` is `basename(subject)`. These values do not add domain meaning; they create parallel representations that every constructor and consumer must keep synchronized.

The principles-led SR-006 correction was a contraction, not a new abstraction:

- `MemberLogicalAddressContext = {rootTeamRunId, memberAddress}`;
- `ResolvedTeamLogicalPlacement = {kind:"agent",address} | {kind:"team",address,ingressAddress}`;
- strict address-domain operations own `segments`, `basename`, `parentAddress`, and root selector derivation;
- the resolver derives addresses from its topology traversal cursor rather than copying stored config paths/routes;
- message delivery derives the private selector from the selected effective Agent address; and
- task policy compares `parentAddress(target)` to `parentAddress(caller)`, then performs one exact direct current-local config match by the derived basename and resolved kind. Team ingress must be a direct Agent whose canonical parent equals the Team address.

This does not make an address replace the topology. Syntax derives structural views; topology lookup still determines existence, Agent-versus-Team kind, configured Team ingress, and execution config. `rootTeamRunId` remains necessary because the same canonical logical address can exist in multiple concurrent TeamRun snapshots. Exact AgentRun/task identities remain separately owned.

SR-008 retains that boundary with native target naming: `ResolvedTeamRecipient = {kind:"agent",address} | {kind:"agent_team",address,coordinatorAddress}`. Stable pre-existing machine codes containing `INGRESS` remain byte-compatible, but no target field/type uses that synonym.

The larger `TeamRunConfig`/metadata/event route system predates this shared collaboration boundary and is materially wider. Static inventory shows 78 production files mentioning `memberPath`, 128 mentioning `memberRouteKey`, and 34 mentioning `coordinatorMemberRouteKey`. Those fields participate in history lookup, status/event payloads, conversation segments, task identities, memory/token scopes, and current metadata. Removing them may be a valuable future topology normalization, but it requires separate behavior/persistence investigation. SR-006 makes them non-authoritative for collaboration without pretending to solve that broader system.

### 19. The comprehensive scope remains authorized, but SR-007's persisted normalization is superseded

After SR-006 was integrated, the user explicitly chose to perform the larger refactor now and accepted migration/API/frontend work when it produces a substantially cleaner codebase. The formerly deferred surfaces form one cross-project identity concern. During user review, however, the separated `MountedTeamTopology + TeamAgentLaunchProfile + TeamRunBindingSet` metadata was judged harder to understand than the original recursive execution tree. That feedback is consistent with the design principles: semantic responsibility can be separated in runtime code without spatially normalizing one cohesive JSON aggregate.

The current classification is:

1. **Logical placement:** one absolute `AgentTeamAddress` decided by definition mounting.
2. **Concrete execution:** kind-specific AgentRun/TeamRun/task run IDs; the same address can have multiple executions.
3. **Configured AgentTeam entry:** one direct `coordinatorAddress`; address syntax alone cannot derive which child is configured.
4. **Agent launch facts:** current runtime/model/tool/skill/workspace-root/application/platform fields, local to the Agent node they configure.
5. **Physical containment:** ancestor TeamRun-ID lineage inside memory storage; it is not logical topology.

Display breadcrumbs, basenames, parent Teams, relative recipient expressions, route selectors, URL components, and storage segments are derived values. Definition-local `memberName` remains authoring input before mounting, not mounted identity.

### 20. The original recursive member tree has useful locality but the wrong identity fields

The original `TeamRunConfig.memberTree` naturally answers which Agent or nested AgentTeam exists and keeps each Agent's launch/restoration facts next to that Agent. This is operationally valuable for inspection, mapping, backup, migration, and restore. Its problems are narrower and structural:

- `memberName`, `memberPath`, and `memberRouteKey` encode one placement three times;
- `coordinatorMemberRouteKey` creates a second coordinator route shape;
- generic `memberRunId` changes meaning by node kind and duplicates `childTeamRunId` for Team nodes;
- the root Team uses a wrapper shape different from nested Team nodes;
- persistent child execution copies/localizes the tree; and
- derived leaf/route maps are treated as state rather than rebuilt views.

SR-008 retains the recursive locality and makes the root a normal `agent_team` node at `/`. Agent nodes keep genuine Agent fields and `agentRunId`; AgentTeam nodes keep definition ID, `teamRunId`, `coordinatorAddress`, and `children`. Handoffs remain top-level edges. No separate persisted topology/profile/binding tables or derived index are required.

### 21. Current storage evidence supports local Agent facts, not speculative hoisting

The current metadata types persist `runtimeKind`, `platformAgentRunId`, `agentDefinitionId`, `llmModelIdentifier`, `llmConfig`, `autoExecuteTools`, `skillAccessMode`, `workspaceRootPath`, and `applicationExecutionContext` per Agent. The restore mapper reconstructs `workspaceId` from `workspaceRootPath`; it does not persist `workspaceId`. Storage derives `memoryDir`; it is not metadata.

The primary web launch surface supplies shared Team defaults and per-Agent runtime/model/tool/config overrides. That does not prove that all supported launch surfaces and historical records always have the same `workspaceRootPath`. The evidence-backed target therefore keeps existing genuine fields locally, does not invent a generic `agentProfile`, does not add `workspaceId` or `memoryDir`, and does not hoist workspace until a separate investigation proves a durable equality invariant.

### 22. Concrete execution location still needs one owner distinct from logical address

Conversation, Team communication, token usage, task identity, status/event projection, WebSocket commands, and frontend task keys independently encode a root Team run plus task-Team/member/task-Agent position. Collapsing those values to `memberAddress` would be incorrect because persistent and task instances may occupy the same logical placement concurrently.

One `TeamExecutionAddress` therefore carries:

```ts
type TeamExecutionAddress = Readonly<{
  rootTeamRunId: string;
  taskTeamRunIds: readonly string[];
  memberAddress: AgentTeamAddress;
  taskAgentRunId: string | null;
}>;
```

This is not a second logical address. `memberAddress` selects the logical node; the root/task run IDs select one concrete instantiation. Team execution owns contextual resolution through root metadata and task identities. Invocation IDs, task ledger IDs, event IDs, and provider handles remain with their operation owners.

### 23. Persisted identity cannot be simplified safely by a tolerant normal reader

Representative metadata contains independent path, route, name, coordinator-route, generic run, and kind-specific run facts. A tolerant reader could project them only by selecting one value when they disagree. That would silently rebind history and keep historical schema knowledge in normal runtime.

Framework-owned structured stores are classified separately:

- Team definitions: directly usable; authored local names mount into addresses.
- TeamRun metadata, communication/task records, token usage, external bindings, and application launch/run stores: migration required.
- Derived history indexes/caches: discard and rebuild.
- Physical Agent memory directories and stable context files: directly usable at their current paths.
- Opaque provider raw arguments: directly usable as untyped display/history payloads, never routing input.

The existing app-data migration capability supplies ordering, completion records, backups, atomic file writes, and retries. It must gain an explicit required/blocking outcome checked before service bootstrap/listen. Normal parsers support only schema v3 after successful conversion.

### 24. Public and frontend boundaries must change in the same cut

GraphQL, REST, WebSocket, project-owned application SDKs, external/application binding schemas, and production web state currently carry route/path fields. If only server internals changed, callers would reconstruct the removed authority at the next boundary.

Target transport fields are deliberately small: `memberAddress`, `coordinatorAddress` when an AgentTeam entry relation is exposed, kind-specific run IDs, and `TeamExecutionAddress` for concrete execution. Generated contracts, SDKs, server, and production web land atomically with no mixed-version support. The frontend projects one recursive `rootTeam`, derives `memberNodesByAddress`, and keys persistent/task runtime state by serialized execution address so equal logical addresses do not collide.

### 25. Complete simplification removes parallel meaning, not useful locality or independent facts

The user's intuition that many fields are redundant is correct for logical placement. It does not imply that a canonical address replaces concrete runtime instance identity, the configured AgentTeam coordinator, Agent launch settings, or physical storage ownership. The final schema is simpler because each retained field answers one distinct question:

- `address` answers **where is this node in the mounted AgentTeam**;
- `agentRunId` / `teamRunId` answer **which persistent execution was allocated**;
- `coordinatorAddress` answers **which direct Agent coordinates this AgentTeam**;
- Agent-local launch fields answer **how this Agent is restored or launched**; and
- `ancestorTeamRunIds` answer **which concrete run directories contain memory**.

The four TeamRun questions—what mounted, how configured, which handoffs, and which run IDs—are a schema completeness test, not four persisted normalized sections. Runtime may derive address, run, coordinator, and direct-child indexes, but those are disposable views of the rooted aggregate.

### 26. Public tool naming should express domain meaning, while the type expresses resolution state

The implemented `send_message_to.recipient_name` name came from the flat roster, where the value really was a short name. Under hierarchical collaboration, values such as `./field_team` and `/research_team/field_team` are no longer names. Keeping the field would make the public contract lie about its data.

`recipient_path` describes the filesystem-like notation accurately, but overemphasizes representation and can be confused with physical filesystem paths or the legacy `memberPath` identity being removed. The operation itself sends or delegates to a logical recipient location, so `recipient_address` is the most natural public name.

The clean type progression is:

```text
recipient_address: RecipientAddressExpression
  -> strict /... or ./... parse and caller-relative resolution
  -> AgentTeamAddress
  -> exact rooted-tree lookup
  -> ResolvedTeamRecipient
```

This keeps the API natural without weakening type precision. Both recipient-oriented tools must change together. `recipient_name` and `recipient_path` must be rejected rather than translated, while exact `target_agent_run_id` remains a separate message-only selector. This is a current API/tool-manifest cut and does not require a TeamRun metadata transformation; raw historical provider payloads remain display-only.

### 27. Handoff retrieval is an action projection, not a service-status report

The current caller binding has already done the important authorization/scope work: `MemberTeamContextBuilder` stores only edges whose `from` equals the current canonical Agent address. Returning `member_address` and repeating `from` therefore adds no decision information. Returning `accepted`, a success code, generic count prose, and a `result` wrapper exposes the service/adapter protocol rather than the Agent's next action.

Each authored edge answers a durable graph question and correctly remains `{from,to,rules[]}`. The tool should not mutate that stored model. It projects each rule string to a separate decision row:

```text
{from, to, rules:[r1,r2]}
  -> {when:r1, recipient_address:to}
  -> {when:r2, recipient_address:to}
```

Stable edge order and rule order make the result deterministic. `recipient_address` is directly reusable by `send_message_to`; `when` tells the LLM how to evaluate the natural-language text. `{handoffs:[]}` truthfully means there is no configured outgoing action. No additional wrapper is needed for success.

The lifecycle instruction and tool availability must form one invariant. If every Team Agent must retrieve guidance before final completion or blocked termination, package-selected exposure is structurally invalid: the prompt can require a tool that is absent. Team runtime must therefore compose `get_handoff_rules` and `send_message_to` intrinsically after resolving package tools. Standalone non-Team Agents remain under normal configuration. Provider adapters and prompt timing remain thin variants of this one Team-owned protocol.

### 28. Live validation needs a test-owned environment spine, not production shortcuts

The user-selected fixture is valuable because it exercises a root coordinator, an AgentTeam recipient, a nested coordinator, and a nested peer. Its external source is not current-contract-ready: prose still tells `Teacher` to call the removed `{target:{kind,name}}` selector, and there is no handoff graph. Editing that package would violate scope and make test evidence mutate shared input. A temporary package containing a copied fixture plus a recorded current-contract overlay keeps the public `LOCAL_PATH` import path real while isolating compatibility text and deterministic handoff data.

Credential preparation has the same ownership rule. The local `.env` is input to the repository secret importer, not a file to source into logs or copy into fixtures. Importing it into a disposable database makes runtime credential resolution real without changing the user's normal database. One fresh TeamRun per runtime avoids cross-provider state/history confusion. Since the user requires all three runtimes, unavailable credentials, models, or processes are evidence of Blocked/Fail rather than a passing skip.

The live spine is additive to deterministic coverage. It proves provider tool exposure, prompt timing, model-visible handoff shape, delivery, task lifecycle, and restoration through real runtime seams; it does not replace exhaustive migration/API/frontend negative cases. Exact setup, matrix, assertions, evidence, and cleanup are normative in [nested-classroom-live-validation-contract.md](./nested-classroom-live-validation-contract.md).

### 29. Application SDK compatibility is a semantic admission boundary, not a generated-file detail

The project already distinguishes three independent version domains. Application manifest schema is V4, backend bundle envelope is V1, and iframe transport is V4. Those envelopes did not acquire a different shape in the canonical identity refactor. The breaking contracts are the backend definition and frontend SDK because their public launch/binding/target/event types contain the removed Team route/path identity. Their target version is therefore V5 while the unchanged envelope/transport versions remain stable and refer to the V5 SDK compatibility values.

The target admission spine reuses current ownership rather than inventing negotiation. `parseApplicationManifest` requires `ui.frontendSdkContractVersion === "5"`; `parseApplicationBackendManifest` requires both SDK compatibility values equal `"5"`; and `ApplicationBackendDefinitionLoader` requires `definitionContractVersion === "5"` before exposure validation, lifecycle hooks, or handlers. An old installed bundle is absent from the launchable catalog and appears as a quarantined catalog diagnostic. The message must identify the bundle/manifest path, observed value, required V5 value, and the action to rebuild or reinstall using the current SDKs. No old payload is translated and no incompatible worker is imported.

This admission result must not control durable-state discovery. `ApplicationPlatformStateStore.listExistingPlatformDatabasePaths()` physically enumerates application storage and can recover the application ID without an admitted bundle. The canonical-identity migration uses that store-level inventory first, produces a result for every discovered database (or blocks on an unreadable identity), and only then permits target services/catalog execution. Thus a V4 or missing bundle is rejected as code while its existing platform state is still migrated as data.


### 30. Legacy TeamRun `memberName` was display data; the later migration ID is the executable canonical owner

The previous design made a false equivalence. Historical flat TeamRun metadata wrote `memberName` from the configured display/member label and independently normalized `memberRouteKey`; the store validated their types but never required equality. The stable flat-to-memberTree migration preserved that distinction. `Program Manager` plus `program_manager` is therefore not a contradiction and must not be “repaired” by overwriting the display value.

The structural contract is narrower and deterministic. Flat v1 has one direct structural `memberRouteKey`; it cannot encode nested topology and any nested route/hybrid nested-Team fields remain unsafe. The predecessor recursive tree has structural `memberRouteKey` and `memberPath`; after separator/trim normalization, those two must encode the same ordered segments, each node must be a direct child of its recursive parent, addresses must be unique, the coordinator route must resolve to one direct Agent, and generic/kind-specific Team run IDs must agree. `memberName` may differ arbitrarily as display text and is not compared to the address basename. The v3 target intentionally omits it; canonical display derives from the address basename plus retained role/description and other target-owned presentation.

Migration record lifecycle determines ownership. `runPending()` treats `SUCCEEDED` and `SUCCEEDED_WITH_WARNINGS` as terminal for a migration ID. Therefore `20260517_team_run_metadata_member_tree` remains the stable pending flat-to-predecessor record owner; no corrected design expects it to rerun after a prior success. The separately registered, later `20260801_team_canonical_identity` migration is the sole final-v3 owner. Both migration definitions reuse one pure migration-only flat decoder, so the canonical migration can consume a repaired residual flat item left under a terminal-warning record in memory and write only final v3. It is ticket-owned/unreleased and absent from the inspected operational records, so this covers all supported histories without inventing a third version or requiring a GraphQL retry after startup has been blocked:

```text
fresh flat -> pending 20260517 converts/preserves -> pending 20260801 derives from route/path -> v3
terminal 20260517 + predecessor tree -> 20260517 skipped -> pending 20260801 derives from route/path -> v3
terminal-warning 20260517 + residual safe flat -> 20260517 skipped -> 20260801 shared-decodes in memory -> v3
```

Historical interpretation remains migration-only. Normal v3 repositories never accept flat/memberTree input, and no alias, lazy conversion, or dual reader is introduced.

### 31. Target token conversion needs the pending canonical owner and one transactional store boundary

The old token migration is not an executable target owner. The production predecessor registered `20260703_token_usage_execution_address_backfill` as required on startup and serialized the legacy `{segments}` shape. `AppDataMigrationRunner.runPending()` treats both success statuses as terminal by ID. Current IR-014 source changes the converter under that same ID, so a normal predecessor start followed by upgrade yields zero executions of the corrected converter. A read-only operational snapshot confirms exactly that lifecycle: the old ID is `SUCCEEDED`, the ticket-owned `20260801_team_canonical_identity` record is absent, and roughly 139k Team token rows still carry `{segments}`.

The smallest coherent target is not another migration record. `20260801_team_canonical_identity` is already independently pending, already owns the cross-store canonical identity aggregate, already runs after TeamRun/task conversion, and is already the sole exact-success pre-listen gate. It therefore composes a token semantic migrator as one named item. The old `20260703...` definition is removed from the current registry; its durable record is neither deleted, reset, nor reinterpreted. Pending token legacy-column cleanup depends on exact `20260801...` success. This produces one target owner and one startup decision rather than parallel migration/gate authorities.

The migration-local database boundary must also express the approved invariant directly:

```text
list rows + build strict task-Team index
  -> plan and validate every row without mutation
  -> immutable canonical update batch
  -> TokenUsageCanonicalExecutionAddressMigrationStore.applyBatch(...)
  -> one Prisma/SQLite transaction updates and verifies every targeted row
  -> commit all, or throw and roll back all
```

A planner/index failure never calls the batch method. A transaction failure reports zero migrated rows, returns the enclosing `20260801...` result as `FAILED`, and leaves strict services/listen closed. After repair, the non-terminal canonical ID reruns; already-current file/database items skip, the token transaction commits, and only exact canonical success opens startup. No current token reader accepts `{segments}`, and no runtime fallback is introduced.

## Open Unknowns / Risks

- The identity surface is large. Missing one producer/consumer would recreate a parallel authority even if the central types are clean. Implementation and coverage need a repository-wide legacy-field inventory with a narrow documented allowlist.
- Migration must distinguish semantic roles before validating equality: `memberName` is display-only, while route/path, parent relation, coordinator route, and generic/kind-specific run IDs are structural. It may derive address only from an agreeing structural pair and must never use fallback order.
- Existing metadata may first require the stable flat prerequisite, but terminal records are intentionally not rerun by `runPending()`. The separate pending canonical ID must own final v3 for freshly produced or previously recorded predecessor trees and for repaired residual flat items under terminal-warning history by composing the same migration-only decoder. Recovery cannot depend on the GraphQL manual-retry surface because the exact canonical startup gate may prevent that API from listening.
- IR-010/IR-011 scope exact-success startup blocking to the canonical identity migration. Token conversion must become a named item of that aggregate so the existing gate is truthful; unrelated established warning behavior must remain unchanged.
- Token volume is material: the read-only operational snapshot observed roughly 143.8k rows. Planning and transaction execution must be bounded and observable, update only rows needing conversion, and remain restartable/idempotent; a large batch is not permission for row-at-a-time commits.
- Application platform databases are dynamically discovered. A partially migrated application cannot be silently skipped; each database needs a durable item result and actionable path/identifier.
- Same logical address can identify a persistent and multiple task executions. Frontend/API/runtime maps keyed only by `memberAddress` would collide; `TeamExecutionAddress` serialization must be canonical and consistently used.
- Task-Team nesting produces an ordered task Team run-ID chain. Conversion must use enclosing record/task structure and minimal task identities, not parse synthetic route strings heuristically or repeat logical Team addresses in the locator.
- Rooted tree sharing changes object construction and lifecycle seams. Lazy child creation/restore must select exact direct child nodes and their typed run facts without accidentally materializing siblings or losing private handle ownership.
- Task mapping still needs current-Team direct eligibility. The common resolver must not absorb task lifecycle/policy, and task code must not reconstruct a second address parser.
- AgentTeam coordinator remains configured data. It must not be guessed as the first Agent or inferred from the Team address; TeamRun-tree compilation and migration validate direct-child membership.
- Exact AgentRun routing and send delivery codes already pass coverage. Simplifying the independent rule-query result must not alter those semantics or unrelated MCP tool results.
- AutoByteus, Codex, and Claude materialize tools/instructions at different seams. Coverage must prove that intrinsic Team exposure, canonical-name de-duplication, caller address, filesystem examples, “must” completion/blocked wording, and minimal result semantics remain equivalent.
- The `recipient_address` rename crosses AutoByteus schemas/parsers/manifests, Agent Tools MCP adapters/catalogs, provider instructions, task tooling, tests, and project documentation. A missed surface would expose two public names even if runtime resolution is singular.
- Physical memory storage must not be rewritten merely for cleaner names. Renaming the domain concept without preserving on-disk layout would create unacceptable data risk.
- Transport/SDK/frontend changes are atomic by design. Deployment ordering must prevent an old client from being treated as supported; no permanent alias or dual-shape response is allowed. In particular, leaving backend-definition/frontend SDK identity shapes under V4 would make the existing exact compatibility gates falsely admit old code.
- Generated and vendored copies can drift from source constants if build outputs are not regenerated. Coverage must compare workspace SDK source/dist, both project application source manifests/definitions/scripts, UI vendor copies, and importable packages at V5.
- An old V4 bundle may be absent from the launchable catalog while its durable DB remains present. Migration inventory must prove it does not consume catalog admission and must block rather than silently skip an unreadable database subject.
- Opaque provider payloads may contain text keys resembling legacy fields. The post-change scan must distinguish untyped historical payload from active structured identity instead of destructively rewriting it.
- Implementation exists through IR-014 and API-REV-011 is paused at 61%. CRR-025 proves the terminal token-record and partial-write gaps; SR-015 changes only solution artifacts and claims no corrected implementation, completed migration, or live provider result.
- The local credential assignment and all three runtime dependencies are external live prerequisites. Downstream evidence must distinguish product failure, environment blockage, and provider unavailability without leaking values or manufacturing a Pass.
