## Current Behavior / Current Flow

- Current entrypoint or first observable boundary: Agent definition tool names and runtime bootstrap expose tools differently per runtime. AutoByteus local tools come from `defaultToolRegistry`; Codex receives explicit dynamic tool registrations; Claude receives SDK-created in-process MCP server configs.
- Current execution flow:
  - AutoByteus/native local tools: `registerTools()` -> `defaultToolRegistry` -> `BaseTool.execute(...)` -> tool `_execute(...)` with `AgentContext` / team context.
  - Browser tools: `agent-tools/browser` manifest/service -> AutoByteus wrappers, Codex dynamic tools, Claude SDK in-process MCP tools.
  - External MCP consumption: persisted MCP config -> `McpToolRegistrar` discovers remote tools -> `GenericMcpTool` calls via `McpServerProxy` and managed MCP client instances.
- Ownership or boundary observations: The repo owns MCP client management and first-party runtime projections, but it does not currently host one general first-party MCP endpoint for arbitrary external runtimes. `open_tab` already has canonical server ownership; `send_message_to` and task-plan tools still require more consolidation before safe external MCP exposure.
- Current behavior summary: Multi-runtime tool reuse is already solved for selected tool families by a canonical service plus per-runtime projection pattern. The proposed MCP unification should extend that pattern by adding a first-party MCP exposure adapter, not by moving tool semantics into transport code.
- Downstream implementation state summary: task-delegation settlement exists for server-managed paths and intentionally delays settlement until the worker is idle/offline. The native AutoByteus pure-team backend currently lacks per-member settlement support, so native pure-team task-delegation exposure must be gated or implemented before being considered supported.
- Parallel task-agent refinement summary: current code can create multiple `AgentRun`s in principle, but the team layer cannot yet represent multiple active runs for the same logical member because registries, status, event binding, and task activation are keyed by logical member route. Achieving the user model requires a new dynamic task-agent instance layer, not only changing the settlement coordinator.

## Findings From Code / Docs / Data / Logs

- A general external first-party MCP server does not currently exist in the repo.
- Streamable HTTP is already supported as a consumed MCP transport, and the repo has dependencies on `@modelcontextprotocol/sdk`.
- Browser tools are the strongest candidate for first MCP hosting because canonical contracts/services already exist.
- `send_message_to` requires member/team identity, allowed recipients, approval/lifecycle handling, and Team Communication projection.
- Task-plan tools require authoritative team-run/member routing because their current state is not globally addressable.
- Claude SDK in-process MCP tooling proves the tool definitions can be expressed as MCP-like tools, but it does not solve sharing one address with other runtimes.
- Final-worker settlement is part of the task-delegation semantics, not merely a cleanup optimization. Supported paths must prove worker offline/settled after terminal `update_task_status` when no current work remains.
- Runtime instruction text that says the framework "may settle" is too weak for the approved model and must be changed to mandatory `will`/`must` wording.
- The same-member parallel model cannot be implemented correctly by batching several tasks into one work packet for the logical member. Batching preserves the one-runtime-per-route assumption and prevents independent per-task settlement. The target needs one task-agent instance per runnable task by default, with an explicit concurrency policy if limits are required.
- User schema feedback supersedes the earlier richer-field design: keep `delegate_tasks` model-facing input minimal for reliable LLM tool calls. The target schema is `member_name`, required rich `description`, and optional `reference_files`; do not expose separate `task_name`, `dependencies`, `completion_criteria`, or `expected_deliverables` fields. `delegate_tasks` items are ready-to-run; dependent follow-up work is delegated later after completion notification. `update_task_status` exposes no task selector and uses caller task-agent instance context to identify the task.
- Frontend UX clarification on 2026-05-30: supported task delegation must render concrete task-agent instances as transient active entities keyed by task-agent identity; those entities must disappear from active UI after settlement. A static/offline logical member row may remain only as roster/template context and is not sufficient as task-agent lifecycle presentation.
- Worker-row semantics clarification on 2026-05-31: the internal logical member/template distinction remains valid for team definition and future delegation, but it is not valid to present a task-delegation-only logical assignee as `worker • Offline` or an equivalent active execution row after the final task-agent settles. Logical member templates must be separated into explicitly labeled roster/config/available-member surfaces, and completed task-agent activity must be scoped to completed task/task-agent history rather than to the logical member's normal conversation.
- Current backend stream/status payloads already carry task-agent identity fields, so the identified gap is frontend projection/routing rather than missing backend identity data.

## Constraints / Dependencies / Compatibility Facts

- Existing external MCP config/management is client-side; hosting first-party tools needs new server-side MCP transport code.
- Streamable HTTP should use scoped auth headers or run-scoped URLs; a single global token would be unsafe for team/browser/task tools.
- Browser tools require an active Electron/remote browser bridge binding and must keep honoring remote-browser-sharing pairing controls.
- `send_message_to` must enforce allowed recipients and sender/member identity before delivery.
- Task-plan tools need a stable team-run/member task-plan command/query owner before external MCP calls can mutate state.
- Runtime event normalization must preserve canonical tool lifecycle events for Activity/history/artifacts; external MCP names may need allowlisted normalization similar to the current Claude browser/media handling.
- Frontend team-run projection must preserve task-agent identity from backend stream/status payloads; route-key-only UI state cannot represent parallel or transient task-agent instances.
- Frontend active execution projection and team roster/topology projection must be separate enough that cleanup of a task-agent instance does not fall back to, select, or render the logical worker as an offline execution participant.
- Exact support for any future runtime such as Antigravity must be verified before implementation, especially transport, auth header support, approval/elicitation, cancellation, and result rendering.

## Open Unknowns / Risks

- Whether a target external runtime can accept per-run dynamic headers/tokens in its MCP configuration, or only static user-level config.
- Whether the first implementation should expose only tool calls or also MCP resources/prompts for run metadata and team manifest discovery.
- How long-lived MCP sessions should be cleaned up when an AutoByteus run/team/member terminates.
- Whether approval UI should be mediated entirely by AutoByteus or delegated to external MCP client elicitation when available.
- Whether task-plan state should remain in live runtime memory or be promoted to a server-persisted command model before MCP exposure.
- Native AutoByteus pure-team per-member settlement remains a backend capability risk. It is not a requirement blocker only if pure-team task delegation is not exposed as supported in this ticket; otherwise it is an implementation gap.
- Parallel same-member task agents are an implementation-scope risk: Codex/Claude/Mixed backends need dynamic instance registries and status/event identity changes. If this is too large for the current ticket, the ticket must at least avoid claiming parallel same-member support; however the refined target design should not bake in one-runtime-per-logical-member semantics.
- Frontend task-agent lifecycle presentation is now a requirement risk: if UI keeps route-key-only rows/conversations or falls back to the logical worker after task-agent cleanup, users will still see completed task agents as lingering offline logical workers even when backend settlement succeeds.
