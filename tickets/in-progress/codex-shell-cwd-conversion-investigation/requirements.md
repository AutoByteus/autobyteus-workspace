# Requirements Doc

## Status (`Refined`)

## Goal / Problem Statement

Correct the AutoByteus Codex command-event projection so a per-command working directory exposed by Codex app-server is preserved in the canonical `run_bash` arguments used by live tool lifecycle events, command approval presentation, future application-owned memory traces, and runtime-native history/diagnostic normalization.

The confirmed defect is representational, not executable: Codex app-server already executes the shell command in the requested directory. AutoByteus currently renames the command lifecycle to canonical `run_bash` for downstream presentation and persistence but drops the app-server `cwd` field from canonical arguments.

## Investigation Findings

- Live Codex `0.149.0` emitted a raw model-facing function call named `exec_command` with JSON arguments containing `"cmd":"pwd"` and `"workdir":"<nested-target>"`.
- The corresponding stable app-server `item/started` and `item/completed` notifications contained a `commandExecution` item with `command: "/bin/bash -lc pwd"` and `cwd: "<nested-target>"`; `pwd` returned that directory, proving execution is already correct.
- Version-exact TypeScript and JSON Schema generated by the installed CLI require `cwd` on a `commandExecution` thread item and allow `cwd` on command-approval params.
- The shared AutoByteus parser at `autobyteus-server-ts/src/agent-execution/backends/codex/items/codex-tool-payload-parser.ts` reads structured `arguments`/`args`/`input` plus command fields, but it does not read top-level or nested `cwd` for the `run_bash` case.
- A disposable test through the real Codex thread/event harness produced `normalizedArguments: {"command":"/bin/bash -lc pwd"}` from an input item that also contained `cwd`. The runtime-native history normalizer produced the same omission.
- AutoByteus does not execute this canonical `run_bash` call; the canonical form is used for live tool cards/streaming, approvals, memory recording, and history/diagnostic projection.

See the evidence supplement: [`codex-cwd-probe-evidence.md`](./codex-cwd-probe-evidence.md).

## Design Health Assessment (Mandatory)

- Change posture (`Bug Fix`):
- Initial design issue signal (`No`):
- Root cause classification (`Local Implementation Defect`):
- Refactor posture (`Likely Not Needed`):
- Evidence basis: A single shared Codex argument parser is already the owner used by live conversion, approval projection, and native-history normalization. It fails to promote one authoritative app-server field into canonical arguments.
- Requirement or scope impact: The fix should stay inside the existing parser boundary plus focused regression coverage. No new subsystem, execution path, compatibility layer, or schema is warranted.

## Recommendations

1. Extend the existing Codex `run_bash` argument resolution to preserve app-server `cwd` from both command-item and approval-request shapes.
2. Keep the canonical field name `cwd`, matching AutoByteus `run_bash`; do not leak the model-facing raw field name `workdir` into canonical events.
3. Use stable app-server item/request fields, not opt-in `rawResponseItem` frames, as the production source.
4. Add regression coverage for live start/terminal conversion, command approval conversion, and native-history normalization.
5. Do not backfill old local memory traces; preserve existing files and record corrected arguments for future tool calls.

## Scope Classification (`Small`)

One existing shared parser is the implementation owner. The observable impact spans several consumers, but they already converge on that parser and can be covered with focused tests.

## Scope Guardrail (Mandatory)

### In-Scope Use Cases

- `UC-001`: A live Codex `commandExecution` item with a per-command `cwd` is projected to canonical `run_bash` lifecycle events.
- `UC-002`: A Codex command approval request with `cwd` is presented as a canonical `run_bash` approval request.
- `UC-003`: A Codex native thread-history `commandExecution` item with `cwd` is normalized for diagnostic/history projection, and future live memory traces persist the corrected canonical arguments.
- `UC-004`: Incomplete or older synthetic payloads that omit `cwd` remain parseable without inventing a directory.

### Out of Scope

- Changing Codex's model-facing `exec_command` schema or its raw field name `workdir`.
- Routing Codex shell execution through the AutoByteus `run_bash` executor.
- Changing Codex thread/turn workspace selection, sandbox policy, permission policy, approval decisions, or shell wrapping.
- Backfilling or rewriting existing application-owned memory trace files that were persisted without canonical `cwd`.
- Redesigning unrelated provider adapters, terminal tools, or frontend tool-card layouts.

### Preserved Behavior Boundary

- Preserve BEH-001's Codex-owned execution path and all non-`cwd` outcomes in BEH-002–BEH-004.
- REQ-004 and AC-004–AC-005 prohibit fabricated directory values, command rewrites, execution rerouting, or changes to approval/sandbox behavior.

## Functional Requirements

- `REQ-001`: For live Codex `commandExecution` lifecycle items, canonical `run_bash` arguments must preserve the app-server `command` and `cwd` values when present.
- `REQ-002`: For Codex command approval requests, canonical `run_bash` approval arguments must preserve top-level app-server `command` and `cwd` values when present.
- `REQ-003`: Runtime-native Codex history normalization must preserve `commandExecution.command` and `commandExecution.cwd` as canonical `run_bash` tool arguments.
- `REQ-004`: The change must not execute, re-execute, or reroute a Codex command; alter command text; fabricate a missing `cwd`; or change approval, sandbox, or permission behavior.
- `REQ-005`: The existing application-owned raw-trace schema must remain unchanged. Corrected live arguments must naturally persist for future calls, while pre-change traces remain readable without a migration or backfill.

## Acceptance Criteria

- `AC-001`: Given an app-server `item/started` or terminal `item/completed` `commandExecution` payload with `command` and nested `item.cwd`, the emitted canonical `run_bash` lifecycle payload contains `arguments.command` and `arguments.cwd` with the exact source values.
- `AC-002`: Given an `item/commandExecution/requestApproval` payload with top-level `command` and `cwd`, the emitted canonical approval payload contains both exact values under `arguments`.
- `AC-003`: Given a native-history `commandExecution` item with `command` and `cwd`, `normalizeCodexThreadHistoryItem` returns canonical `toolArgs` containing both exact values.
- `AC-004`: Given a supported parser input with no usable `cwd`, canonical arguments do not contain a fabricated/default directory, and current command mapping remains unchanged.
- `AC-005`: A controlled Codex app-server execution remains Codex-owned and continues to run in the selected per-command directory; the AutoByteus change affects projection only.
- `AC-006`: Existing application-owned raw-trace files remain readable without transformation, and a future live Codex command trace receives `cwd` through the corrected canonical lifecycle arguments.

## Constraints / Dependencies

- Target contract evidence is from installed `codex-cli 0.149.0`; generated app-server protocol is the version-exact authority for this investigation.
- The stable production source is `commandExecution.cwd` / command-approval `cwd`, not opt-in experimental raw Responses API items.
- Canonical AutoByteus `run_bash` already names its working-directory argument `cwd`.
- Tests must use harmless commands and disposable paths; no destructive runtime probe is required for implementation.

## Persisted Data Outcome (When Applicable)

- Stored subject / location: Application-owned per-run raw memory traces whose `tool_call.tool_args` are written from live canonical lifecycle events; Codex-owned native thread history read through the current normalizer.
- Required outcome (`Directly Usable — No Migration`): Existing trace schemas and files remain valid. Future live traces gain an additional `cwd` key inside the existing JSON object. Native Codex histories already carry `cwd` and gain it at read-time normalization after the fix.
- Existing data to preserve, discard/rebuild, transform, or quarantine: Preserve all existing data unchanged. Do not backfill pre-change application-owned traces that lack `cwd`.
- Unacceptable data loss or corruption: Rewriting, dropping, or invalidating existing trace records; changing command/result content.
- Relevant availability, maintenance-window, or rollout constraints: None; no schema or deployment migration.
- Related requirement and acceptance-criteria IDs: REQ-003, REQ-005; AC-003, AC-006.

## Assumptions

- “CWD parameter” refers to per-command working-directory intent, not merely the thread's initial workspace.
- The authoritative translation boundary is the stable app-server command item/request, where model `workdir` has already become `cwd`.
- Existing pre-change local traces are not required to be retrospectively enriched.

## Risks / Open Questions

- Upstream Codex protocol may evolve after `0.149.0`; focused contract-shaped tests should guard the current integration without depending on experimental raw frames.
- Some existing tests use incomplete `commandExecution` fixtures without `cwd` even though current generated V2 items require it. The parser should remain non-fabricating for those fixtures rather than introducing a default.
- No material open requirement question remains if the no-backfill boundary is approved.
