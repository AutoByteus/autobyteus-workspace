# Application-Owned MCP Capability — Design Spec

## Current-State Read

## Intended Change

Add an `application-agent-tools` capability area with one canonical application declaration, route identity, authorization/invocation boundary, and lifecycle. An application declares static `agentTools` in `application.json` and implements the exact `agentToolHandlers` map in its backend definition. The application platform converts selected declarations into immutable application-bound routes.

Claude and Codex receive those routes through latest-base run-session activation. `ApplicationExecutionScope` completes the scoped authority with a tight live base capability `{publishedArtifactPublisher, applicationAgentTools}`; `AgentToolMcpSessionService.activateForRun` resolves selected application routes from the current application execution/sender context, freezes pure-data route snapshots into the active record, and returns the existing headerless deterministic descriptor. Stop/exact resource cleanup calls `deactivateForRun`; restore calls `activateForRun` again and obtains current routes/fingerprints/capability state at the same URL. AutoByteus receives bound `BaseTool` projections over the same route and invocation capability. Each native `ApplicationAgentTool` retains the checked `ParameterSchema` as its advertised definition but specializes `prepareExecution` so raw arguments reach the same common capability/Ajv boundary without generic `BaseTool` coercion or native-only schema validation. The application tool never enters `defaultToolRegistry`, and no new listener, bearer, persisted session state, worker registry, or execution-manager locator is created.

All registered Agent Tools MCP static-adapter names are reserved from application declarations. `AgentToolsMcpHost` exposes one immutable complete static-name snapshot to application readiness, which quarantines any colliding declaration regardless of adapter availability or configured-MCP collision policy. MCP route composition repeats the all-static rejection as defense in depth. Only after proving that no static adapter owns the name may an application route take precedence over a same-name host-configured MCP source. Existing configured-MCP-versus-static `protect_static_adapter` / `prefer_configured_mcp` behavior remains unchanged and internal to that separate policy.

At invocation, one application-tool gateway admits the call, revalidates current declaration, availability, binding/producer ownership, schema, and worker state, invokes the exact worker once, and validates a bounded MCP-safe result. One application catalog transition service remains the only live package/application catalog commit owner: it identifies old package applications before source/registry mutation, closes and drains only their application-tool lanes, stages the next slice, commits bundle/tool state, and recovers or quarantines participants. It does not import or call run-session deactivation. An unchanged active route may resume after reentry; changed/removed routes fail current fingerprint/availability checks. Exact run stop independently removes the whole active session. Application shutdown blocks session activation, drains application calls, stops workers, finalizes runs/sessions, closes the application capability, and leaves process-listener close to `AgentToolsMcpHost` after all scopes.

For the maintained proof, keep `get_brief_context` read-only and the shipped Codex/Luna runtime. Role `toolNames` select only routed business/collaboration/publication capabilities. Each role calls the application tool first, then its `agent.md` states the required business content, canonical workspace-relative artifact, publication, and handoff; it never names `apply_patch`, `edit_file`, `write_file`, `read_file`, `run_bash`, or another foundation/provider operation. Runtime provisioning makes foundation capabilities available and the model reasons over them. The researcher handoff carries the exact marker, canonical path, and complete research body, so the writer has no cross-member file dependency; the writer copies at least one complete non-marker research `Key findings` bullet verbatim into final `Key evidence`. Existing access-controlled trace pairs prove the real application call/result; current Codex `fileChange` and AutoByteus normalized `edit_file` may corroborate the runtime-native edit without becoming prompt/API contract; the Team binding/message, publication, Brief projection, notification, GraphQL, and browser prove exact result use and UI causality. A provider-wide adapter/dynamic-tool change, configured foundation name, prompt-level tool choreography, shell-created/fabricated artifact, runtime/model switch, direct tool mutation, and process-wide result logging are forbidden.

## Terminology

- **Application agent tool**: the canonical business capability declared by an application and executed by its worker. “MCP” describes one projection, not its ownership.
- **Declaration snapshot**: a normalized static tool declaration plus its per-tool SHA-256 fingerprint.
- **Application tool route**: an immutable declaration snapshot paired with exact server-minted application execution identity.
- **Application tool capability**: the application-execution-only port that resolves selected routes and invokes them through the application platform gateway.
- **Raw application tool arguments**: the JSON-object values emitted by the provider/native invocation pipeline before defaults, coercion, schema validation, cloning, or normalization. Both runtime projections pass these values to the common gateway, which alone decides application-schema validity.
- **Application catalog transition**: one serialized package- or application-scoped operation that captures the old live slice, quiesces affected existing applications, stages the next slice without live mutation, commits prepared bundle/tool snapshots, and then recovers, closes, or quarantines participants.
- **Admitted call**: a call that acquired the per-application lifecycle permit before quiesce began.
- **Platform/static adapter name**: any name registered in `AgentToolMcpCatalog` by an Agent Tools MCP static adapter provider. Every such name is reserved from application declarations, regardless of adapter availability or its configured-MCP collision policy.
- **Configured-MCP collision policy**: the existing per-static-adapter choice between `protect_static_adapter` and `prefer_configured_mcp`. It governs only a host-configured MCP source colliding with that static adapter; it never determines whether an application may declare the name.
- **Brief context marker**: the exact first text line returned by the maintained handler and copied verbatim into each successful role artifact: `Brief context: {"briefId":"…","title":"…","observedStatus":"…"}`. The object uses that fixed key order and compact JSON with ordinary string escaping, so arbitrary title text cannot break the one-line witness. It proves result use; it is not a routing input or stored schema field.
- **Business-focused Agent instruction**: a role-local contract that names the business call, required content, canonical artifact path, publication, and handoff/failure outcomes, but no runtime foundation or provider operation. The model selects from capabilities automatically supplied by its runtime.
- **Runtime-native file-change evidence**: current-provider activity such as Codex `item/fileChange` / `file_change` and AutoByteus normalized `edit_file`. It can corroborate how the fixed runtime created an artifact; it is not role prompt vocabulary, application configuration, or a cross-runtime application API.
- **Deterministic Agent Tools run session**: latest-base active-only MCP record keyed by a non-secret ID derived from normalized AutoByteus run ID. Its URL is stable for the run history, but all authorization/execution state is live and rematerialized on activation.
- **Application call lane**: per-application admission/in-flight state owned by `ApplicationAgentToolCallLifecycle`. It governs worker/catalog transition and is not the run session or a substitute for exact-run deactivation.
- **Complete research handoff**: one existing Team message containing the exact Brief context marker, canonical workspace-relative research path, and full bounded research checkpoint body. It is the writer's authoritative research input for this maintained workflow; it does not replace the separately published research artifact.
- **Agent-to-UI proof join**: the evidence relationship `member run/toolCallId -> Team binding applicationId/bindingId/memberAddress -> tool-result briefId -> published revision bindingId/producer -> Brief projection briefId -> browser-selected briefId/latestBindingId`. No single generic audit record duplicates all payloads.

## Legacy Removal Policy (Mandatory)

- Policy: `No backward compatibility; remove legacy code paths.`
- Manifest version `4` and backend-definition version `6` cease to be accepted by the current readers. Maintained generated/importable packages are rebuilt as manifest `5` / backend definition `7`.
- Do not add `mcpTools`, `tools`, handler aliases, manifest fallback fields, dual version branches, a global registration fallback, or an AutoByteus-only application handler path.
- Do not retain an application-tool route after its declaration fingerprint stops matching the current catalog.
- There is no existing application-tool implementation to preserve. Existing platform/configured tool paths are not legacy and remain unchanged except for deterministic session/native composition around an application-local name.

## Persisted Data / State Transition Decision (Mandatory When Persisted Data May Be Affected)

- Stored subject, location, representative shape, and approximate volume: generated/importable package `application.json` and backend bundles for maintained/imported applications; application `app.sqlite`; platform `platform.sqlite` bindings, journal records, and launch overrides; file-owned Agent/Team definitions; process global MCP configuration. Two maintained source applications were inspected; both currently use manifest `4` / definition `6`.
- Relevant code-model, serialization, semantic, or physical-store change: the package manifest gains static `agentTools`; the backend definition gains `agentToolHandlers`; maintained Agent config selects the sample tool; maintained role prompts/launch input/result text gain a deterministic first-call/result-use business contract. Latest-base deterministic run-session ID is derived from already-persisted run ID; live application context/routes/capabilities remain in memory. No database or platform-state field changes.
- Normal reader/writer behavior and representative evidence: package/definition readers are strict-version readers; devkit regenerates package artifacts from source. Application and platform databases are read independently of package tool fields. Agent/Team definitions remain plain current files with the same `toolNames` field.
- Required semantics and invariants under direct use: all existing application business rows, binding identity/status, journals, overrides, Agent/Team identity, and configured MCP credentials/names must retain their current meaning and bytes/semantics.
- Physical-store, privacy/security, disposal/rebuild, and operational constraints: package artifacts are reproducible and contain no required durable state; application databases and global MCP credentials are not disposable and must not be rewritten.
- Decision: two explicit outcomes apply:
  - `Discard or Rebuild` for generated/importable package artifacts on manifest `4` / backend definition `6`.
  - `Directly Usable — No Migration` for application/platform databases, Agent/Team definition storage, and global MCP configuration.
- Decision rationale: rebuilding derived packages from maintained source gives the current strict contract without I/O, downtime, corruption, rollback, or mixed-schema complexity in durable stores. A database migration provides no benefit because no durable column or semantic changes.
- Acceptance criteria or design constraints supported: REQ-016–REQ-023; AC-028–AC-044.

No migration plan is applicable.

## Ownership Map

- **SDK contract package** owns the public static declaration, supported result/caller/handler shapes, name/schema subset constants/normalization, and contract version constants. It does not own runtime authorization.
- **Application bundle subsystem** owns import-safe parsing and placement of normalized declarations on the internal bundle snapshot. It never imports the backend entry module.
- **AgentToolMcpCatalog** owns the complete registered static-adapter-name set and route composition. Its per-adapter configured-MCP policy remains a separate internal concern: it never defines which static names an application may declare. For an application route, any registered static adapter is an unconditional collision; only a non-static name may proceed to application-over-configured precedence.
- **AgentToolsMcpHost** remains the latest-base process owner for the dedicated `127.0.0.1:0` listener, local admission, dispatcher, active-session registry, catalog, and scoped authority factory. It additionally owns the narrow outward `staticAdapterToolNames` snapshot used by application readiness. The snapshot is captured after default adapter registration, is read-only, includes inactive and `prefer_configured_mcp` adapters, and exposes no adapter implementations, configured-MCP policy, raw route dependencies, or listener base URL.
- **ApplicationAgentToolCatalog** owns current in-memory per-application declaration snapshots and per-tool fingerprints. It is not a process-global registry and never holds handlers.
- **ApplicationDefinitionRuntimeReadiness** owns whether an application and its Agent/Team definitions are runnable. It rejects every application declaration colliding with the complete host static-adapter-name snapshot, then validates selected names against process tools and the exact application catalog. It does not inspect adapter availability or configured-MCP policy.
- **ApplicationAgentToolCapabilityAssembly** owns construction-time sealing: it exposes a stable port to the execution scope and is completed once with the gateway. It is not a service locator and accepts no arbitrary registrations.
- **ScopedAgentToolMcpSessionAuthority** remains the latest-base per-execution-scope activation/deactivation owner. Its ledger accepts deterministic `activateForRun`, compensates an activation it cannot record, exposes exact `deactivateForRun`, blocks new activation before close, and removes owned live records on scope close. It receives one tight base-capability value at assembly completion and does not persist live capability references.
- **AgentToolMcpSessionService** owns fresh run-session materialization. For every create/restore activation it derives current sender/owner/execution capabilities, asks the catalog for current exposure, freezes the resulting routes and fingerprints, inserts one active record, and returns the existing headerless descriptor on the host-owned listener. A zero-route run remains `not_exposed`. It never starts an application worker or reuses a stopped session object.
- **MCP session catalog** owns current MCP route-table composition. Its application branch receives the current application execution context plus the tight nullable application capability, rejects every static-adapter collision, then permits application-over-configured precedence. Its existing configured-MCP branch independently applies `protect_static_adapter` / `prefer_configured_mcp`. It emits pure immutable application routes; the capability reference exists once in session execution capabilities rather than inside each route.
- **AgentProviderFactoryBuilder** owns the combined execution-factory seam. It receives `agentToolMcpRunSessions` for Codex/Claude and `applicationAgentTools` for the local AutoByteus composer. It does not recreate the superseded issuer, read the session registry, or make AutoByteus call the local HTTP endpoint.
- **AgentRunManager / AgentRunResourceManager** remain the exact published-run stop owners. The resource manager reaches only `deactivateForRun(runId)` after exact-current removal and releases the other run attachments once; Team and provider adapters never deactivate a session directly.
- **ApplicationAgentToolNativeSchemaProjector** owns the AutoByteus compatibility check. It accepts only the normalized portable subset, maps through the current `McpSchemaMapper`, canonicalizes `ParameterSchema.toJsonSchema()`, and rejects any validation-semantic mismatch. It never extends or weakens `ParameterSchema`/`BaseTool` and never silently drops a property.
- **ApplicationAgentTool** owns the AutoByteus application-call preparation seam. Its checked `ParameterSchema` is the native advertised definition only. Its `prepareExecution` override preserves the original argument object while reproducing generic agent-ID setup, pre-start cancellation, and result-mode resolution/normalization; `_execute` passes those raw arguments to `ApplicationAgentToolCapability`. It does not call generic coercion or schema validation, and it does not change any other `BaseTool` subclass.
- **AutoByteus backend factory/composer** owns native materialization. Existing automatic exposure resolvers remain authoritative; the new composer only replaces an explicitly selected application-local name with its checked bound projection.
- **ApplicationAgentToolGateway** is the authoritative invocation boundary. It owns the order of admission, current-state checks, validation, authorization, worker call, and result validation.
- **ApplicationRunOwnershipService** remains the authoritative application binding/producer status reader. It owns the Team-root/configured-member/descendant identity rules; the gateway must not read stores itself.
- **ApplicationAgentToolCallLifecycle** owns per-application admission and drain state, not package or worker sequencing.
- **ApplicationAgentToolWorkerInvoker** owns the narrow worker-state policy: use/join `ready`/clean startup, reject unexpected `failed`/`stopping`, never retry the invocation.
- **ApplicationCatalogTransitionService** replaces `ApplicationCatalogRefreshCoordinator` and the catalog-mutation portion of `ApplicationReentryService.reloadAndReenter`. It owns the catalog-transition mutex, exact package/application participant calculation, sequencing across source mutation, staged bundle/tool commit, targeted reconciliation, rollback, and final outcome. It accepts command-owned mutation/rollback functions but no arbitrary catalog snapshot or participant IDs.
- **ApplicationReentryService** remains the per-application lifecycle owner behind the transition service. Its revised public methods prepare server-derived participants by marking availability, quiescing/draining tool calls, and stopping exact workers, then recover/reopen or quarantine those participants after a prepared catalog commit. It no longer reads or mutates bundle/catalog state and is not called by REST or package commands directly.
- **ApplicationBundleService** owns live bundle state plus package/application staging and prepared non-throwing slice commits. Package commands and REST reentry may not call destructive `refresh()`/`reloadApplication()` methods after the clean replacement.
- **ApplicationBackendDefinitionLoader/Host** own exact handler-map validation, handler execution with application context, and worker-side result validation.
- **ApplicationPlatformLifecycle and application-host composition** jointly preserve the established nested shutdown ownership: block new application execution/run activation, drain application-tool lanes, stop application workers and managed runs/resources (thereby exactly deactivating their sessions), close scoped application/general authorities, then close `AgentToolsMcpHost` and its listener after no provider client can retain a live process-local URL.
- **Brief Studio researcher/writer `agent-config.json` files** own the maintained Codex/Luna runtime/model and routed business-capability selection. They select `get_brief_context`, `publish_artifacts`, and required collaboration routes; they do not list runtime foundation operations.
- **Brief Studio researcher/writer `agent.md` files** own the role-local business work contract closest to each model: invoke `get_brief_context` exactly once as that role's first business tool action, require a successful matching result, create the required canonical artifact with its required content, publish the workspace-relative path, and complete or truthfully fail the handoff. They name no runtime/provider foundation operation. The researcher additionally sends the exact marker/path and complete checkpoint body; the writer drafts from that body without a cross-member file dependency. `team.md` and `BriefRunLaunchService` reinforce this contract but cannot replace it.
- **Runtime/provider foundation provisioning** owns the ordinary capabilities available to the configured Agent. The model chooses how to create its artifact; the application prompt neither configures nor names that mechanism. No Brief-specific adapter, dynamic registration, MCP route, provider-composition change, or provider-name alias is introduced.
- **CodexItemEventPayloadParser / CodexItemEventConverter** retain their existing normalization of provider file-change activity to AutoByteus `edit_file` segment/tool lifecycle evidence. This is optional runtime-specific corroboration only; it is not part of the application prompt, application API, or cross-runtime acceptance contract.
- **PublishedArtifactPublicationService and its path contract** remain the authority for resolving workspace-relative paths against the exact run/session workspace before artifact persistence. Prompts do not reconstruct an absolute path or bypass this boundary.
- **Brief Studio `getBriefContext` handler** owns the binding-derived, read-only business lookup and the canonical compact-JSON `Brief context:` marker. It neither accepts routing identity from the model nor changes brief/application state.
- **Agent run memory/trace owners** retain their existing access-controlled paired `tool_call`/`tool_result` records under a member `agentRunId`; the Team binding remains the authority that joins that run to `applicationId`, `bindingId`, and `memberAddress`. Neither owner gains duplicate application payload/audit fields.
- **BriefArtifactReconciliationService** remains the authoritative application projection owner for published artifacts. It maps the existing producer and binding identities to the brief and moves the final-writer publication to `in_review`; the application tool never calls this owner.
- **Brief Studio GraphQL/detail UI** retains its existing launch, notification-refresh, query, and rendering responsibilities. It exposes the resulting brief status, binding diagnostics, final artifact path/body, and artifact count without a new API or tool-specific screen.

`ApplicationExecutionScope`, `AgentToolsMcpHost`, and REST/host-management surfaces remain thin composition/public boundaries around these governing owners; they do not gain application business rules.

## Return Or Event Spine(s) (If Applicable)

`DS-005`: `Application handler -> worker result validator/size guard -> worker JSON-RPC response -> engine client -> application tool gateway host validator -> MCP adapter or native ApplicationAgentTool/BaseTool return -> provider effective result`.

An application-controlled `isError: true` result remains a successful JSON-RPC response whose MCP tool result is marked failed. A thrown handler, invalid result, stale route, authorization failure, or transport failure is not converted to application content; the provider receives a sanitized execution failure and no retry occurs.

`DS-014`: `model-issued get_brief_context -> RuntimeToolTraceSequencer paired tool_call/tool_result -> business artifact creation by a runtime-supplied foundation capability -> optional provider-native file-change/normalized edit evidence -> member agentRunId -> application Team binding (applicationId, bindingId, memberAddress) -> researcher Team message (marker + relative path + complete body) -> relative publish path resolved against that member workspace -> published artifact event/revision (producer, bindingId, briefId) -> BriefArtifactReconciliationService projection -> GraphQL brief detail -> browser DOM`. Source evidence asserts that role/team/launch prompts contain no foundation/provider operation names and configs contain only routed business/collaboration/publication capabilities. Execution evidence proves a real workspace artifact and publication; for current Codex it may additionally reject shell-created/fabricated output through existing native file-change observability.

This proof spine reads and joins existing authoritative records. It does not add a generic gateway log containing arguments/results, a second audit aggregate, or a tool-call-driven UI mutation. Operational application-tool logs keep their existing redacted correlation/outcome policy; ordinary access-controlled Agent run history retains the call/result content under its existing security and retention policy.

## Bounded Local / Internal Spines (If Applicable)

- Parent owner: `ApplicationAgentToolCallLifecycle` (`DS-009`).

- Parent owner: `ApplicationBackendHost` (`DS-010`).
  - `receive invokeApplicationAgentTool -> require loaded definition -> select exact handler -> create caller context -> invoke once -> validate/measure result -> respond`.
  - This matters because handler-map ownership and “fail before leaving worker” are worker-local invariants.

  - `normalize requested names -> resolve registered/active/protected static views -> resolve exact application routes -> if application route and any registered static adapter then fail -> else application route wins over configured MCP -> otherwise apply existing configured-MCP protected/prefer branch -> freeze table`.
  - This matters because application/static validity and configured-MCP/static precedence are different policies. The complete static check must occur before application precedence, while the existing per-adapter configured policy remains intact.
- Parent owner: `ScopedAgentToolMcpSessionAuthority` and `AgentToolMcpSessionService` (`DS-015`).

  - `deactivateForRun -> remove the exact ledger entry -> delete the exact active record`; scope close blocks new activation and iterates only its owned exact session IDs.
  - This matters because restoration rematerializes current application identity/routes/capability at the stable run URL and because the session owner, not package reentry, governs run liveness.
- Parent owner: `ApplicationCatalogTransitionService` (`DS-011`).
  - `acquire transition lock -> capture old target slice -> quiesce/stop existing participants -> apply command mutation -> stage target slice -> prepare non-throwing commit -> commit bundle/tool slices -> reconcile/recover or rollback/quarantine -> finally release`.
  - This matters because every supported live catalog mutation must cross one boundary before package state changes and because unrelated application call lanes must remain open.
- Parent owner: native `ApplicationAgentTool` (`DS-012`).
  - `receive raw provider argument object -> bind agent identity if absent -> reject already-aborted preparation -> resolve/normalize result mode -> return the same object -> inherited execute rechecks abort -> _execute invokes common capability`.
  - This matters because the ordinary generic `BaseTool` preparation is intentionally coercive, while application tool validation meaning must remain identical to the MCP path. The specialization is confined to this adapter.
- Parent owner: Brief Studio maintained role contract (`DS-013`).
  - Researcher: `receive launch -> call get_brief_context exactly once as first business tool action -> require success -> retain returned marker -> create brief-studio/research.md with the exact marker and required 200–500-word business body -> publish_artifacts with that relative path -> handoff exact marker + path + complete body`.
  - Writer: `receive complete researcher handoff -> call get_brief_context exactly once as first business tool action -> require success -> require returned briefId to match researcher marker -> consume the handoff body without a cross-member file dependency -> copy at least one complete non-marker Key findings bullet verbatim into final Key evidence -> create brief-studio/final-brief.md -> publish_artifacts with that relative path -> complete the required Team handoff`.
  - A missing/error result, brief mismatch, artifact creation/publication, or handoff failure terminates normal publication and reports the blocker; retained evidence separately rejects fabricated or shell-created normal output. Neither role guesses identity, repeats the call, or names a runtime/provider foundation operation.
  - This matters because tool availability and a shared Team instruction do not govern the model-local action order. Each role prompt is the authoritative local sequence while Team/launch text provides consistent reinforcement.

## Ownership Boundaries

1. **Package -> platform:** only normalized static declarations cross. Backend code is not imported during scan.
2. **Application execution scope -> scoped run-session authority/provider factory:** the scope completes the authority with `{publishedArtifactPublisher, applicationAgentTools}` and creates provider factories with `{agentDefinitionService, agentToolMcpRunSessions, applicationAgentTools}`. Codex/Claude receive only the activator; AutoByteus receives only the application capability. The registry, local base URL, gateway, and worker handles do not cross.
3. **MCP catalog/host -> application readiness:** only the immutable complete registered static-adapter-name set crosses. Adapter objects, availability, and configured-MCP collision policy remain in the MCP catalog. Readiness uses this set solely to reject application declarations.
4. **MCP/native projection -> application tool capability:** callers pass a route and the original JSON-object arguments. MCP forwards the session call object; native `ApplicationAgentTool` returns that same object from its specialized preparation and `_execute` forwards it without coercion, defaults, normalization, cloning, or `ParameterSchema` validation. They cannot pass an application ID, binding ID, worker ID, or handler function separately.
5. **Gateway -> ownership service:** the full compound route identity is checked by the existing ownership owner. The gateway does not read lookup/binding stores.
6. **Gateway -> worker invoker:** only an already authorized invocation command crosses. The invoker owns engine-state/start policy but not authorization.
7. **Host -> worker:** only tool name, validated arguments, and immutable public caller context cross. The raw MCP session, run-session ID/path, native Agent context, process registry, and run managers remain host-side.
8. **Worker handler -> application capabilities:** the handler receives the same application-owned storage/notification/agent/resource/artifact capabilities as other handlers plus immutable caller identity. It cannot address another application.
9. **Catalog transition -> package mutation:** `ApplicationPackageCommandService` supplies exact package identity and command-owned apply/rollback operations. It cannot mutate the live bundle/tool catalogs or choose participant application IDs.
10. **Catalog transition -> call lifecycle/worker owners:** the transition invokes quiesce/drain/open/close and exact worker stop/recovery through their public methods. It does not manipulate counters, waiter promises, worker handles, or handler maps directly.
11. **Catalog transition -> live catalog commit:** only a fully parsed package/application candidate and prepared non-throwing application-tool delta cross. The live bundle and tool slices commit synchronously with no `await` between them; unrelated package slices retain their existing objects/routes.
12. **Brief role prompt -> application tool:** the model supplies only the declared empty argument object; application/binding/brief identity comes from the scoped route and handler context. The successful result carries the canonical marker used by the artifact, not a prompt-supplied substitute.
13. **Brief role prompt -> runtime foundation selection:** after context validation, the role names only the required business artifact, content, canonical workspace-relative path, publication, and handoff outcome. The runtime supplies its ordinary foundation capabilities and the model selects how to satisfy the request. Provider-specific file-change events and AutoByteus normalization remain optional verifier inputs and do not cross backward into the prompt, `toolNames`, application tool gateway, or application API.
14. **Researcher -> writer Team handoff:** the exact marker, canonical relative path, and complete bounded research body cross through the existing addressed Team message boundary. The writer does not open the research file or infer content from a summary.
15. **Role -> published artifact:** `publish_artifacts` receives the canonical relative path only after the role has produced the required workspace artifact; its existing service resolves that path against the exact member workspace. Verification joins the actual workspace/revision evidence and may additionally join provider-native file-change evidence. The role does not supply or guess a worker/application path.
18. **Run activation -> active MCP session:** the scoped activator receives owner/sender/exposure/current execution context and reads the tight base capability. The session service freezes current execution capabilities and route data into one active-only registry record and returns a headerless descriptor. The deterministic ID/path is lookup identity, not authorization, and no live record or capability is persisted.
19. **Package transition -> active run session:** no session API crosses. The package owner closes/drains only the affected application's call lane and mutates its worker/catalog state; existing session lookup and non-application routes remain active. Subsequent application calls pass through current availability/fingerprint/ownership checks. Only exact managed run finalization deactivates the whole session.
20. **Process host -> execution scopes:** only `sessionAuthorities`, listener readiness through `listen()`, host finalization through `close()`, and the frozen static-adapter name snapshot cross. Main-server composition never receives route dependencies or the listener base URL.
16. **Published artifact -> Brief application projection:** only the existing artifact event/revision with producer and binding identity crosses. The tool handler and Agent trace do not mutate or project brief state.
17. **Proof reader -> existing authorities:** verification may join access-controlled Agent run history/events, Team communication/binding, workspace/publication evidence, application projection/repository state, and browser output by their existing IDs. It does not write proof state, broaden record access, or bypass an owning API/store boundary in production code.

## Dependency Rules

Allowed directions:

- SDK contracts -> no server/runtime package.
- Backend SDK -> SDK contracts.
- Bundle parser/devkit -> SDK declaration parser/contract.
- Application tool catalog -> bundle snapshot and SDK declaration types; never backend handler code.
- Agent Tools MCP catalog -> complete registered static-adapter-name list; Agent Tools MCP host -> frozen `staticAdapterToolNames` snapshot; application runtime composition -> readiness dependency. No adapter object, availability function, or configured-MCP collision policy crosses into application subsystems.
- Studio/standalone startup -> `AgentToolsMcpHost.listen()` before recovery/activation; execution scopes -> `sessionAuthorities.begin/complete`; final process shutdown -> host `close()` only after managed runs/resources and scoped authorities close. No dependency points back to main-server route registration or general internal-base discovery.
- Application execution scope -> tight session base capabilities `{publishedArtifactPublisher, applicationAgentTools}` and provider-factory execution input `{agentDefinitionService, agentToolMcpRunSessions, applicationAgentTools}`. General execution uses the same shapes with `applicationAgentTools: null`.
- Codex/Claude construction -> `AgentToolMcpRunSessionActivator`; AutoByteus construction -> optional `ApplicationAgentToolCapability`. Provider adapters do not depend on session service/registry/host or package lifecycle.
- AgentRun exact-current finalization -> `AgentRunResourceManager` -> `AgentToolMcpRunSessionDeactivator.deactivateForRun`. Team members, provider adapters, package transition, and application call lifecycle do not depend on deactivation.
- MCP catalog/adapter and AutoByteus projection -> application tool capability; neither may depend on gateway internals.
- AutoByteus application-tool projection -> `ApplicationAgentToolNativeSchemaProjector` -> current `McpSchemaMapper`/`ParameterSchema` public APIs for advertisement, then bound `ApplicationAgentTool` -> `ApplicationAgentToolCapability` for raw invocation. The SDK contract and server catalog never depend on `autobyteus-ts` native schema types.
- Native `ApplicationAgentTool.prepareExecution` may reuse protected/public `BaseTool` lifecycle APIs and types (`getName`, `getToolResultExecutionMode`, `setAgentId`, `ToolExecutionOptions`, `ToolExecutionPreparation`) but must not call `super.prepareExecution` or treat its checked `ParameterSchema` as an invocation validator. Because the base result-mode normalizer is private, the adapter owns an exact local guard for `in_process | external_result`; no global base-class edit or new shared helper is introduced.
- Application tool gateway -> narrow availability reader, catalog reader, ownership reader, payload validator, call lifecycle, and worker invoker.
- Worker invoker -> engine launcher/controller only.
- Worker loader/host -> SDK handler/result types and worker payload validator.
- Studio Settings/GraphQL -> `ApplicationPackageCommandService` -> `ApplicationCatalogTransitionService`; package commands retain registry/install mutation and rollback, but receive no bundle/tool catalog commit or application lifecycle dependencies.
- REST application availability -> `ApplicationCatalogTransitionService.reloadAndReenter`; it does not call bundle reload directly.
- Catalog transition service -> bundle staging/prepared package/application commit, application tool catalog prepared delta, revised `ApplicationReentryService` participant lifecycle, and readiness/reconciliation owners through public methods. It does not receive call counters or engine handles directly.
- Platform lifecycle -> application tool lifecycle/worker/execution-scope owners through their public methods; application-host lifecycle -> host listener close only after scopes/provider clients are gone.
- Brief Studio role configs -> maintained `codex_app_server` / `gpt-5.6-luna` plus routed application/collaboration/publication names only. Runtime foundation operations are not configured names.
- Brief Studio `agent.md` role sequence -> declared business tool/result contract, required canonical artifact/content, existing `publish_artifacts` relative-path contract, and existing Team messaging. `team.md` and `BriefRunLaunchService` may repeat the business invariant for context, but they depend on—not replace—the role-local sequence.
- Runtime/provider composition -> automatically supplied foundation capabilities -> model reasoning. Existing Codex parser/converter -> optional normalized file-change evidence. Application prompts and configs depend on neither provider vocabulary nor event normalization; evidence readers may depend on the latter without reversing the direction.
- Researcher handoff -> writer model input through the existing Team message boundary. The bounded complete research body is the writer's source; no production service reads Agent files on the writer's behalf.
- Brief Studio `getBriefContext` -> existing binding-aware repository/database reads through the application handler context. It returns the canonical text marker and matching structured fields, and has no dependency on launch, artifact reconciliation, GraphQL, or UI code.
- Existing Agent trace writer -> provider tool events; existing Team binding -> application/member/run identity; existing artifact reconciliation -> artifact event and Brief repositories; evidence code may join their public/authorized read surfaces without introducing a production aggregate.
- Brief Studio UI -> existing GraphQL detail/notification refresh surfaces. It never reads application tool worker state or Agent-memory internals directly.

Forbidden shortcuts:

- No application tool in `defaultToolRegistry`, configured MCP registry, or a module-global application map.
- No `applicationId -> AgentRunManager/TeamRunManager/ApplicationExecutionManager` locator.
- No provider-specific application authorization, handler selection, retry, schema, or lifecycle policy.
- No application declaration/readiness rule derived from `configuredMcpCollisionPolicy`, `listProtectedStaticToolNames`, adapter availability, configured MCP registration, or currently requested/selected names. Every registered static-adapter name is reserved.
- No application route selected before checking the catalog's complete registered static-adapter index. Application-over-configured precedence applies only after the absence of a static adapter is established. Existing configured-MCP-versus-static protected/prefer behavior must not change.
- No accepted application schema keyword that the checked current native projection cannot round-trip; no nullable/length/closed-object fallback and no modification of `McpSchemaMapper`, `ParameterSchema`, or `BaseTool`.
- No generic `BaseTool` argument coercion or `ParameterSchema` invocation validation on the native application-tool path. Do not disable coercion globally; specialize only `ApplicationAgentTool` and pass the raw object to the common capability/gateway.
- No application code import during bundle scan and no handler function crossing the process boundary.
- No route chosen from tool arguments, deterministic run-session ID/path, display name, or name alone. The route path is non-secret lookup identity, not application authorization.
- No caller above the gateway depending on the gateway plus ownership/catalog/controller internals.
- No fixed application-tool timeout, detached continuation, or automatic invocation retry.
- No worker lazy restart from `failed`. `stopped`/in-progress clean startup may be started/joined by the worker invoker; an unexpected `failed` state requires reentry or another owning backend recovery path.
- No `ApplicationPackageCommandService -> ApplicationBundleService.refresh/reloadApplication`, package command -> application tool catalog, or REST reentry -> direct bundle mutation dependency. No live catalog commit outside `ApplicationCatalogTransitionService`.
- No whole-catalog replacement for a package/application transition. Stage and commit only the target package/application slice; unrelated application declarations, routes, admissions, and workers stay untouched.
- No maintained role config or prompt dependency on a runtime foundation operation and no representation of one as an application/MCP/configured registry route. Source coverage rejects operation names in the business prompts rather than enforcing one provider vocabulary.
- No provider event or normalized observability label presented as an application capability. A current-runtime file-change event may corroborate execution but cannot become prompt text, routing authority, or a cross-runtime pass requirement.
- No fabricated or shell-created normal artifact accepted as proof. An artifact-creation, publication, or handoff failure blocks the normal path; an unevidenced purported success fails verification.
- No researcher artifact/publication, or writer artifact/publication, before that role's one successful `get_brief_context` call. No cross-member file dependency, retry loop, guessed/fabricated marker, or summary-only research substitution.
- No random bearer issuer/revoker, main-listener Agent Tools route, global/default session service, partial-owner deactivation, persisted live session/capability state, per-application listener, or independent listener rebind. The latest-base host/scoped authority/active registry/exact-run lifecycle is the only session owner.
- No package transition call to `activateForRun` or `deactivateForRun`, and no session activation call to worker start/reentry. These lifecycles meet only at application route currentness/availability checks inside the gateway.
- No absolute-path guessing or dependency on a write-tool-returned path. Both maintained publications use the exact canonical workspace-relative path and the existing publication resolver.
- No routing identity (`applicationId`, `bindingId`, or arbitrary `briefId`) supplied in the maintained tool arguments or copied from launch prompt text as an authority; the scoped route/handler caller remains authoritative.
- No direct call from `get_brief_context` to `BriefArtifactReconciliationService`, brief write repositories, GraphQL, or UI projection. The tool is read-only; only the existing published-artifact path changes the visible brief.
- No new process-global log of application-tool arguments/results, no duplicate proof table, and no trace payload copied into operational diagnostics. Existing access-controlled Agent run history may retain its ordinary tool events under existing policy.
- No direct MCP invocation, fake provider, mocked Agent, or database mutation may satisfy the new real-Agent/UI acceptance criteria. Such checks remain lower-level coverage only.
- No provider/runtime/model switch as a substitute for making the shipped maintained Codex/Luna workflow coherent; the actual configured demonstration must pass.

## Applied Patterns (If Any)

- **Immutable capability route:** same local pattern as scoped Agent Tools MCP routes, extended with application identity and declaration snapshot.
- **Complete namespace snapshot:** the MCP catalog retains adapter/policy mechanics and the host exports only the deterministic all-static name set needed by readiness. This is a narrow read boundary, not duplicated collision logic.
- **Sealed two-phase assembly:** same construction pattern as scoped MCP session authority. It solves the real construction cycle (`ApplicationExecutionScope` is needed before `ApplicationEngineLauncher`, while runtime backends need a stable application tool port). Completion is one-time and typed; it is not arbitrary late registration.
- **Bound adapter over common owner:** same product pattern as `send_message_to`/`delegate_task`; native and MCP adapters invoke one governing capability.
- **Checked adapter:** the native schema projector uses the existing mapper but accepts its result only after normalized JSON-schema round-trip equality; it does not teach the canonical contract about native types.
- **Specialized raw adapter preparation:** `ApplicationAgentTool` uses the existing public polymorphic preparation seam but replaces generic coercion/validation only for this subject. The specialization retains the tight base execution lifecycle and keeps application schema policy in the common gateway.
- **Nested lifecycle owners:** `ApplicationAgentToolCallLifecycle` owns only admission/drain, revised `ApplicationReentryService` owns per-application prepare/recover/quarantine, and `ApplicationCatalogTransitionService` owns the package/application catalog transaction that invokes those boundaries.
- **Staged package-slice commit:** package/application candidates and tool deltas are prepared without live mutation, then committed synchronously under one transition lock; unrelated package slices never enter the plan.
- **Fresh active-state materialization:** the stable deterministic run route contains no persisted authority. Every create/restore activation builds current execution capabilities and route snapshots from the current scope/catalog; stop deletes the live record.
- **Orthogonal nested lifecycles:** the scoped run-session authority owns run liveness and exact deactivation, while application call lifecycle/catalog transition owns per-application admission, worker, and catalog change. Neither invokes the other's lifecycle API.
- **Process capability host:** `AgentToolsMcpHost` owns one dedicated local server and the session mechanisms behind it. Composition coordinates start/stop but cannot register routes on the main listener or expose the private base.
- **Strict current-contract replacement:** follows current manifest/backend version gates and rebuildable package workflow.
- **Business-focused role invariant with shared reinforcement:** each Brief role prompt owns the exact ordered application call, required artifact/content/path, relative publication, and handoff behavior without foundation-operation vocabulary; role configs own honest routed business selection; Team and launch text repeat the invariant for context but do not become a second authority.
- **Read result carried into the write outcome:** one handler-owned marker makes result use visible in ordinary artifacts while keeping the tool itself read-only and the existing publication/projection path authoritative.
- **Runtime-selected operation plus routed publication:** the role prompt names only the business artifact; the runtime/model owns foundation-operation selection; provider/platform events may corroborate the actual file change; the artifact subsystem separately owns workspace-relative resolution/publication. Keeping these boundaries distinct avoids fake configured exposure and provider vocabulary in business contracts.
- **Complete handoff instead of a cross-workspace read:** the researcher sends the bounded body through the existing Team message owner; the writer consumes that input without requiring a provider-facing file reader.
- **Joined evidence, not a proof aggregate:** real application call/Codex fileChange/normalized edit traces, Team message/binding, workspace-relative publication, artifact projection, and browser detail are correlated by existing identities instead of copying payloads into a new log/table.

### Collision policy separation

Application declaration validity and configured-MCP precedence are deliberately independent:

### Latest-base run-session composition

The application capability extends the latest-base tight execution capabilities; it does not replace run activation:

```ts
type AgentToolMcpSessionBaseExecutionCapabilities = Readonly<{
  publishedArtifactPublisher: PublishedArtifactPublisher;
  applicationAgentTools: ApplicationAgentToolCapability | null;

interface AgentProviderFactoryBuilder {
  createForExecution(input: Readonly<{
    agentDefinitionService: AgentDefinitionService;
    agentToolMcpRunSessions: AgentToolMcpRunSessionActivator;
    applicationAgentTools: ApplicationAgentToolCapability | null;

```

`ApplicationExecutionScopeKernelBuilder` completes its scoped authority with the real application capability and passes the same capability separately to the provider builder. `GeneralProcessRunSupervisor` completes the same shapes with `null`. Codex and Claude receive `agentToolMcpRunSessions`; AutoByteus receives `applicationAgentTools`. No provider receives the session registry, local base reader, package transition, or worker handle.

Activation is fresh and synchronous:

```text
create/restore -> activateForRun(current owner/sender/exposure/context)
  -> build current agent/team execution capabilities, including applicationAgentTools
  -> catalog resolves current static/configured/application exposure
  -> freeze pure route table and current declaration fingerprints
  -> insert deterministic active-only record
  -> return headerless http://127.0.0.1:<process-port>/mcp/agent-tools/<derived-run-id>
```

The following lifecycle matrix is normative:

| Event | Run-session record | Application call lane/worker/catalog | Required application-route effect |
| --- | --- | --- | --- |
| Initial create | Fresh deterministic active record | Current application state is read; no worker is started solely by activation | Current selected route/fingerprint is frozen when exposed |
| Exact run stop | Deleted by managed resource finalization via `deactivateForRun` | No package/catalog mutation | Entire route returns redacted missing-session behavior |
| Supported restore | Fresh record at the same deterministic path | Current application state is read; no hidden worker restart | New current routes/capability are materialized; no stopped object is reused |
| Package reload with unchanged declaration | Existing run session remains active | Only affected app lane drains; worker/catalog transition then reopen | Old immutable route passes current fingerprint/ownership checks again |
| Package reload with changed declaration | Existing run session remains active | Only affected app lane drains; new declaration commits | Old route fails stale; a later run activation receives the new route |
| Package removal/quarantine | Existing run session remains active for other routes | Affected app lane stays closed and worker/catalog is removed/quarantined | Old application route fails unavailable/stale; platform/static routes remain usable |
| Process shutdown | Scopes block activation; runs/resources deactivate; authorities close; host closes last | App lanes drain and workers stop before host close | No provider survives with a live scope and dead listener URL |

The deterministic path is not an application selector or authorization credential. Every application call still uses its frozen compound route identity and must pass current catalog fingerprint, application availability, binding/producer ownership, and worker readiness at the common gateway.

### Schema subset

Tool names use the one provider-safe current rule `^[A-Za-z][A-Za-z0-9_.-]{0,127}$` and remain case-sensitive. Descriptions are trimmed and must remain non-empty.

The v5 contract deliberately accepts only the validation semantics that the current native `McpSchemaMapper -> ParameterSchema -> toJsonSchema()` path can reproduce. The normalized root is exactly `{type: "object", properties, required}`. Each named property has one non-null `type` from `string | integer | number | boolean | object | array`; property descriptions are trimmed or deterministically synthesized during normalization. Nested objects recursively use only `type`, `description`, `properties`, and `required`. Arrays require one recursively supported `items` schema. The only additional validation keywords are:

- `enum` containing unique strings on a string schema, mutually exclusive with `pattern`;
- `pattern` on a non-enum string schema;
- `minimum` and/or `maximum` on integer/number schemas, with `minimum <= maximum`.

Defaults, `null`/nullable forms, `minLength`, `maxLength`, `minItems`, `maxItems`, `additionalProperties`, `const`, `format`, `$ref`, `$id`, recursion, composition/unions/conditionals, boolean schemas, tuple items, executable/custom keywords, and every unlisted keyword are rejected at SDK/devkit/server package validation. Omitting `additionalProperties` intentionally retains ordinary JSON Schema open-object semantics; this ticket does not claim closed objects. A later richer contract must first extend the shared native schema model and its validation/serialization semantics rather than adding a package-only exception.

`ApplicationAgentToolNativeSchemaProjector` maps the normalized schema with the existing `McpSchemaMapper`, converts the result back through `ParameterSchema.toJsonSchema()`, canonicalizes both sides, and requires validation-semantic equality including every nested property and array item. A missing/dropped/changed keyword or property is an application-local readiness diagnostic. The MCP projection advertises the same normalized schema directly. Native `ApplicationAgentTool.getArgumentSchema()` returns the checked `ParameterSchema` for the provider-facing definition, but its application-only `prepareExecution` override does not invoke generic schema validation or coercion. Consequently both MCP and native calls reach the gateway's cached Ajv 8 strict/all-errors validator with raw JSON, and that gateway is the sole runtime-neutral application-schema authority before any worker call.

Accepted example:

```json
{
  "type": "object",
  "properties": {
    "query": { "type": "string", "description": "Search text.", "pattern": "^.{1,200}$" },
    "limit": { "type": "integer", "description": "Maximum records.", "minimum": 1, "maximum": 50 },
    "tags": { "type": "array", "description": "Optional tags.", "items": { "type": "string" } }
  },
  "required": ["query"]
}
```

Rejected examples include `{ "type": ["string", "null"] }`, `{ "type": "string", "minLength": 1 }`, and any object containing `"additionalProperties": false`; the native model cannot faithfully advertise those semantics today.

### Native raw preparation and parity

`ApplicationAgentTool` specializes the public polymorphic preparation method; it does not change `BaseTool`:

```ts
override async prepareExecution(
  context: AgentContext,
  args: Record<string, unknown> = {},
  options: ToolExecutionOptions = {},
): Promise<ToolExecutionPreparation<Record<string, unknown>>> {
  const toolName = this.getName();
  if (this.agentId === null && typeof context?.agentId === "string") {
    this.setAgentId(context.agentId);
  }
  if (options.signal?.aborted) {
    throw new Error(`Tool '${toolName}' execution aborted before start.`);
  }

  const resultExecutionMode = normalizeApplicationAgentToolResultMode(
    await this.getToolResultExecutionMode(context, args, options),
    toolName,
  );
  return { toolName, args, resultExecutionMode };
}
```

The adapter-local normalizer accepts exactly `in_process | external_result` and throws the same invalid-mode class of error otherwise because the base normalizer is private. The application adapter uses the inherited default `in_process` mode. It never calls `super.prepareExecution`, `getArgumentSchema().validateConfig`, or any conversion/defaulting function; it returns the same object reference. The native tool phase calls this override before its started event, and inherited `BaseTool.execute` calls it again then performs its existing post-preparation abort check before `_execute`. `_execute` forwards the prepared raw object to `ApplicationAgentToolCapability.invoke`. No worker cancellation protocol, timeout, or retry is added.

### Catalog transition operation matrix

`runPackageTransition` receives one exact operation contract rather than a raw refresh callback:

```ts
type ApplicationPackageCatalogMutation<T> = Readonly<{
  kind: "import" | "reload" | "remove";
  packageId: string;
  applyBeforeStage: () => Promise<T>;
  finalizeAfterCommit?: (value: T) => Promise<void>;
  rollbackSource: (value: T | undefined, cause: unknown) => Promise<void>;
}>;
```

The functions own package registry/root/install actions only. They cannot receive bundle/tool catalogs, lifecycle services, worker handles, or application IDs. The transition service derives participants and owns every live-state action.

| Operation | Old participant handling before command mutation | Candidate/commit | Failure and rollback |
| --- | --- | --- | --- |
| Import | The target package is absent, so the old participant set is empty and no existing application lane is quiesced | Apply registry/root addition, stage the new package slice, commit new bundle/tool entries, refresh readiness; no worker is eagerly started solely for import | Remove the added root/record/managed install, stage the now-absent slice, and remove any committed new entries; existing package/application lanes were never participants |
| Reload package | Capture every live application whose `bundle.packageId` equals the target, mark reentering, drain, and stop those exact workers before built-in materialization or source rescan | Stage only the target package, commit its bundle/tool slice, then recover only previously active current applications; new inactive apps remain normally startable and removed apps stay closed | If the command can restore source state, restore then re-stage/recover it; an external or built-in source that cannot be restored leaves the affected apps quarantined while the pre-commit live slice is not presented as runnable against changed files |
| Remove package | Capture/drain/stop all old package applications before removing root/registry records | Stage an empty target slice, synchronously remove its live bundle/tool entries, reconcile removal, then finalize managed-install deletion while lanes remain closed | Restore root/record first, stage the actual restored package, recommit and recover prior active apps only if readable/valid; partial/unreadable restoration remains quarantined |
| Exact-application reentry | Resolve the current package and capture/drain/stop only the exact application before staging its current source | Commit only that application slice, validate handler readiness during recovery, activate/reopen on success | No package registry mutation exists to roll back; invalid/missing current source commits the diagnostic/removal outcome for that application and leaves it closed/quarantined |

The transition lock covers apply, stage, commit, finalize, and any rollback commit. It serializes catalog transitions, not ordinary tool calls. `ApplicationBundleService` builds candidates without clearing its live maps, and the prepared bundle/tool assignments contain no validation or I/O, so the paired live commit cannot yield or partially fail. Agent/Team definition cache refresh, availability reconciliation, worker load, and event recovery occur afterward while affected application admission remains closed.

### Fingerprint example

`fingerprint = sha256(canonicalJson({name, trimmedDescription, normalizedInputSchema}))`.

Canonicalization sorts object keys and set-like `required`/string-enum values but retains ordering where the supported schema treats an array as ordered. It is per tool. Adding another tool does not invalidate an unchanged route; changing this tool's name, description, or schema does.

## Key Tradeoffs

- **One canonical capability, two projections:** this is less superficially uniform than forcing native through HTTP, but it preserves current native fundamentals, avoids local network/auth overhead, and follows an established universal-tool pattern.
- **Static declarations plus worker handlers:** metadata and handler code live in two artifacts, so exact matching is required at worker load. The benefit is import-safe package discovery and lazy/isolated business code.
- **Per-tool fingerprint:** slightly more normalization work than an app-wide generation. It correctly lets unchanged routes survive unrelated tool additions and code-only updates while rejecting changed declarations.
- **One-time assembly:** introduces a narrow construction pattern, but it avoids a dependency cycle and mutable global state. It is completed once before lifecycle readiness and fails closed before completion/after close.
- **Stable route, fresh live authority:** deterministic tokenless run identity keeps restored provider configuration stable, while deleting and rematerializing active state avoids persisting application capabilities or stale routes. This requires current route composition on every activation rather than treating the deterministic URL as durable authorization.
- **One session can outlive one application route's availability:** package reload/removal may leave an application route in an already-active immutable route table until the run ends, but the common gateway's current availability/fingerprint/ownership checks reject stale or unavailable calls while platform/static routes continue working. This is preferable to coupling package lifecycle to provider-session churn.
- **Portable JSON-schema subset:** excludes nullable values, length keywords, defaults, and closed objects even though Ajv/MCP could express them. This is intentionally narrower than the initial draft so the unchanged native mapper/model advertises the same validation semantics. A future richer contract must extend the shared native model first.
- **Checked advertisement, raw native invocation:** the native adapter intentionally does not use its checked `ParameterSchema` as a pre-gateway invocation validator. This small specialization duplicates only the base class's two-value result-mode guard because the base helper is private, but it avoids a global base-class change and guarantees that common Ajv sees the same raw JSON as MCP. The generic coercive behavior remains intact for every other tool.
- **All static names reserved, configured precedence preserved:** an application cannot reuse an inactive or configured-preferred static name, which is stricter than current IR-001 routing but exactly matches the approved ownership rule and prevents availability-dependent ownership. The complete set crosses the host as names only; adapter implementations and the existing browser/configured-MCP precedence remain internal to the MCP catalog.
- **One staged catalog transition owner:** removing the small refresh coordinator and narrowing reentry to participant lifecycle is more refactor work than inserting drain calls at two sites, but it prevents either supported path from bypassing lifecycle and gives package rollback one real before/after commit basis. The global transition mutex serializes catalog commits only; unrelated application tool calls remain open.
- **1 MiB application-tool payload limit:** rich content larger than 1 MiB is rejected, but this matches established application communication scale and leaves ample envelope headroom under the 4 MiB worker frame. Large data should be represented by application resources/artifacts, not embedded in a tool frame.
- **Fail closed after unexpected worker failure:** later calls remain unavailable until an owning recovery/reentry path restores the worker. This avoids turning tool invocation into a hidden restart/retry owner and is the approved resilience posture.
- **Read-only tool plus existing business write:** this produces a longer proof path than making the tool mutate status, but it preserves the handler's read concern, the artifact reconciliation owner's write authority, and the intended role of business tools as inputs to Agent work.
- **Business artifact instruction rather than provider-wide tool expansion or provider vocabulary:** the maintained workflow stays on Codex/Luna but `agent.md` describes business outcomes. Runtime provisioning/model reasoning select the foundation operation. Optional provider events can corroborate current execution without becoming the role contract or motivating a generic Codex dynamic/MCP file exposure change.
- **Complete handoff rather than writer file read:** sending roughly 200–500 words duplicates the research body in the ordinary Team message and published artifact, but their purposes differ: the message is the writer's immediate input and the artifact is durable application output. This bounded duplication removes an unavailable cross-member file-read dependency without new storage/API authority.
- **Workspace-relative publication:** the prompt no longer has a write-tool-returned absolute path, but the two artifact paths are canonical and the existing publisher resolves them against exact run context. Verification must join that resolution rather than infer workspace identity from path text alone.
- **Prompt reliability without a platform or provider policy:** duplicating the exact first-call/business-artifact/relative-publication/handoff invariant in both maintained role prompts and reinforcing it in Team/launch text is intentional because each model needs a local ordered business contract. The marker, actual workspace artifact, Team message, publication, and trace provide evidence; the platform does not gain a generic workflow abstraction or foundation-operation prompt policy for one demo.
- **Joined evidence instead of a consolidated audit record:** correlation requires reading several existing owners, but avoids duplicate persisted truth and broad payload logging. The proof is test/evidence composition, not a production routing dependency.

## Risks

1. **Task-created Team authorization:** persisted bindings do not enumerate every later descendant. The ownership extension must require the server-minted Team execution identity, verify its `rootTeamRunId` is the exact bound Team run, require its `agentRunId` to equal the application producer/sender, and enforce exact configured-member mapping when that address is in the persisted member list. Do not accept a free-form member/root tuple from tool arguments.
2. **Catalog transition rollback:** package source/registry rollback can itself fail or restore an unreadable package. `ApplicationCatalogTransitionService` must never reopen from the captured old in-memory snapshot alone; it restores command state, stages and validates the actual restored slice, then recovers. Failed restoration leaves only the affected participants closed/quarantined, reports aggregate errors, and releases the transition lock.
3. **Worker construction cycle:** directly injecting `ApplicationEngineLauncher` into `ApplicationExecutionScope` creates a cycle. Use the one-time capability assembly exactly; no module-global setter.
4. **Schema parity:** current mapper behavior includes permissive fallbacks and property drops for inputs outside its supported shape. The SDK parser must reject those shapes first, and the native projector must compare the mapped round trip and fail readiness rather than trusting the mapper. Contract tests must exercise every supported keyword recursively and every explicitly rejected family.
5. **Native pre-gateway parity:** accidentally calling `super.prepareExecution`, validating through the checked `ParameterSchema`, or cloning/normalizing arguments would reintroduce a native-only interpretation. Tests must cover direct `prepareExecution`, the real ToolPhase/inherited `execute` path, and common-gateway worker non-invocation for coercible strings, empty-string arrays, and nested values. Architecture coverage must prove the specialization exists only on `ApplicationAgentTool` and `BaseTool` is unchanged.
6. **Collision-policy regression:** the complete static set and configured-MCP protected subset are both derived from the same adapter index but have different meanings. A vague `protected` name or shared filtered set can reintroduce application shadowing; conversely treating all static names as configured-protected would break the existing browser `prefer_configured_mcp` contract. Tests and API names must keep the two policies separate.
7. **Native result semantics:** the bound tool must return the same canonical MCP-result envelope used by existing generic MCP tools; do not stringify structured/rich results in an application-only branch.
8. **Error leakage:** raw worker exception strings may contain paths or business data. MCP/native outward failures and operational application-tool logs must use typed safe messages and must not record arguments, results, deterministic run-session paths, or live capability references. Existing access-controlled Agent run memory may retain ordinary provider `tool_call`/`tool_result` content under its current security/retention policy; do not copy those payloads into process-wide diagnostics.
9. **Generated artifacts:** strict version bumps will make stale built packages unusable. Maintained outputs must be regenerated in the same change and package validation must fail clearly for retired versions.
10. **Test environment:** the design stage's earlier worktree lacked Vitest, but IR-001 later established dependencies and CRR-001 executed a focused temporary Vitest collision probe successfully. The probe was removed. Corrected implementation and API/E2E stages must record durable or retained execution evidence under their own ownership.
11. **Model prompt compliance:** selected routes and shared Team text do not guarantee the role will follow the first-call/business-artifact/complete-handoff flow. Exact imperative role-local ordering and fail-closed checks reduce ambiguity; the actual application call/result, workspace artifact/publication, Team message, and UI outcome remain the evidence. Provider-native file-change evidence may corroborate current execution but cannot substitute for those business outcomes.
12. **Provider availability and nondeterminism:** the expanded journey depends on the configured Codex/Luna provider and may be slower/flakier than direct MCP coverage. Use the maintained real configuration, bounded orchestration, terminal-state waits, and normal failure evidence. If provider access or required artifact/publication behavior is unavailable, report `Blocked`; do not replace it with a mock, runtime/model switch, fabricated output, or lower-level call.
13. **Correlation/trace timing:** run events, Team messages, workspace artifacts/publication, artifact projection, notifications, and UI refresh are asynchronous. Evidence collection must wait for terminal member/Team state and projection convergence, pair application calls/results by `toolCallId`, resolve each canonical relative path under the exact member workspace, optionally join current-provider file-change events to that `agentRunId`, and then join exact persisted IDs. Do not use event order, path text, provider label, or title alone as identity.
14. **Abstraction drift back into prompts:** failure diagnostics may tempt implementation/tests to prescribe one foundation operation. Source coverage must instead reject foundation/provider operation names in maintained role/team/launch prompts and assert the business artifact/content/path/publication/handoff contract. Runtime-specific event expectations stay in verifier-side coverage only.
15. **Handoff size/content drift:** a summary-only handoff would silently reintroduce a read dependency, while an unbounded body could harm message reliability. Keep research at the existing 200–500-word target and require the exact published body in the one handoff; durable coverage compares the handoff and artifact content.
16. **Relative-path/workspace mismatch:** researcher and writer are separate runs and may have distinct workspace roots. Each role creates and publishes its own canonical relative path through its own session context; the writer never tries to open the researcher's relative path. Evidence must resolve each path under the correct member run.
17. **Fabricated or shell-only artifact risk:** because the prompt intentionally avoids implementation vocabulary, proof cannot infer correctness from prompt text. API/E2E must join the real workspace artifact, publication revision, handoff content, and UI state; current-provider native file-change evidence can strengthen the rejection of a shell-only/fabricated normal outcome without being mandated in the application prompt.
18. **Latest-base session regression:** resolving conflicts could accidentally restore the bearer/main-listener/issuer seam or drop application route authority. Architecture and executable coverage must prove dedicated listener topology, tokenless deterministic path, tight nullable application capability, fresh restore materialization, exact-run deactivation, and absence of legacy entrypoints.
19. **Package/run interleaving:** an admitted application call may settle while exact run stop or package quiesce begins. Preserve existing completion-coupled call permits and exact managed-run finalization; do not invent timeouts/cancellation. New application admissions fail after quiesce, and new HTTP lookup fails after exact session deletion.
