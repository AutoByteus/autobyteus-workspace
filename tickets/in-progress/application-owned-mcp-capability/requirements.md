# Application-Owned MCP Capability — Requirements

## Status (`Draft`/`Design-ready`/`Refined`)

`Design-ready — approved by the user on 2026-08-27, amended by explicit post-API direction, refined on 2026-08-28 so application prompts remain business-focused, and reconciled with the latest-base deterministic Agent Tools MCP run-session contract after DR-004`

## Goal / Problem Statement

Enable an application package to declare and implement its own business-specific agent tools, and expose those tools through the existing Agent Tools capability only to Agent/Team executions that belong to that application, regardless of the supported runtime selected in the Agent configuration. Claude and Codex consume the process-owned, tokenless, loopback-only Agent Tools MCP run route; AutoByteus consumes a bound local projection. Platform-owned tools and host-configured MCP tools remain process-owned shared capabilities. The maintained Brief Studio demonstration must additionally prove the capability through an actual model-backed Agent call whose result is used in the existing publish/projection workflow and becomes observable in the existing Brief Studio UI. This ticket establishes the application capability and its production boundary first; it does not publish or redesign the broader external developer-facing SDK journey.

## Investigation Findings

- Latest `origin/personal` makes `AgentToolsMcpHost` the correct physical MCP transport owner: one dedicated `127.0.0.1` listener on an OS-assigned port, local request admission, process/static catalog, configured-MCP resolution, active run-session registry, dispatcher, and scoped activation authority. Provider descriptors are tokenless and their deterministic run route is not authentication.
- Each run-session activation already carries authoritative `ApplicationExecutionContext` (`applicationId`, `bindingId`, producer `agentRunId`) when the run was launched from an application binding. General-process activations do not carry that context. Stop deletes all live session state; restore derives the same run-session ID and rematerializes current live state rather than reading a persisted route/capability.
- The application backend worker is the current owner of application business handlers and storage, and the host/worker JSON-RPC boundary is the established application invocation path.
- Application package scanning and runtime-definition readiness happen without starting application workers. A static package declaration is therefore required; discovering tools by importing application code would violate current package-import safety and lazy worker startup.
- One `ApplicationExecutionScope` serves the current `ApplicationPlatformRuntime` lifetime and may serve multiple Studio applications. Application-tool isolation must therefore use the session's exact `applicationId`, not create one execution scope per application or add an application-to-manager router.
- The current engine request path has no fixed 30-second completion deadline. Application-tool calls can use the same completion-coupled request path and must not reintroduce timeout-driven ambiguous completion.
- The shared Agent Tools MCP descriptor is currently issued only to the Claude Agent SDK and Codex App Server backends. AutoByteus native resolves its fundamental platform tools locally from the process registry. The clarified target intentionally preserves those basic native tools while adding application-owned business tools through the application-scoped MCP capability for AutoByteus-native application runs as well.
- The current MCP dispatcher verifies that `tools/call` arguments are an object, but it does not validate them against the advertised tool `inputSchema`. Application-owned tool arguments therefore need an explicit schema-enforcement requirement before the worker boundary; otherwise the declaration is advisory rather than a contract.
- Post-API inspection confirmed that external-provider Agent runs already retain access-controlled paired tool-call/result traces (`toolName`, `toolCallId`, arguments, effective result/error), while the application Team binding independently maps `applicationId` and `bindingId` to the exact member address and `agentRunId`. Brief Studio's existing artifact event, `brief_bindings`, projected artifact, notification, GraphQL detail, and UI diagnostics provide the remaining identity spine. This evidence can prove the real Agent journey without adding generic operational logging of application arguments/results.
- API-REV-002 and CRR-005 established a production-reachable provider-composition mismatch: Codex receives the Agent Tools MCP descriptor but not configured ordinary registry `read_file`/`write_file`; those names therefore cannot be treated as Codex application configuration. `publish_artifacts` already resolves workspace-relative paths, and the bounded research body can cross in the Team handoff.
- API-REV-003/CRR-007 and API-REV-004 established diagnostic facts about the current fixed provider: Luna can choose its provider-owned patch primitive, Codex emits `item/fileChange` / `file_change`, and AutoByteus normalizes it as `edit_file`. The user subsequently clarified that these runtime mechanics must not be copied into `agent.md`: the role describes the business artifact and sequence, while runtime provisioning and model reasoning choose the operation. Exact provider events remain useful execution evidence, not the application prompt/API contract.
- DR-004 established a latest-base Design Impact after `origin/personal` advanced to `ebef77eb32bbeaefd4fccdb6998240264c82a3c1`: the completed `agent-tools-mcp-session-resume` ticket replaced random bearer issuance on the shared listener with deterministic tokenless run-session activation on a dedicated loopback listener and exact-run stop/restore cleanup. Twelve merge conflicts overlap the session/host/provider/kernel owners used by this ticket; the combined design must adopt, not bypass, that new authority.

## Design Health Assessment (Mandatory)

- Change posture: `Feature` / `Larger Requirement`
- Initial design issue signal: `Yes`
- Root cause classification: `Boundary Or Ownership Issue`
- Refactor posture: `Likely Needed`
- Evidence basis: application business tools belong to the application package and worker lifecycle, while the only current dynamic MCP discovery/registration authority is process-global. Directly registering application tools into that registry would mix owners, allow cross-application leakage, and make package reload mutate unrelated process state. Latest-base run-session activation is healthy and reusable, but the ticket implementation was built on its superseded bearer/issuance owner. The two lifecycles need one explicit composition: run activation owns live session materialization/deactivation; application transition owns per-application call drain and catalog/worker change.
- Requirement or scope impact: the solution must add application-local declaration, validation, route composition, authorization, worker dispatch, and lifecycle coordination while preserving the dedicated loopback listener, deterministic tokenless run identity, fresh restore activation, exact-run deactivation, and separate general/application execution families.

## Recommendations

1. Implement **application-owned agent tools exposed through the existing Agent Tools MCP host**, not one network MCP server per application.
2. Keep static tool metadata package-owned and handlers worker-owned. Do not execute application code during package scan merely to discover tool schemas.
3. Compose tool routes during each live run-session activation from server-minted current execution context. Never copy application tools into the process-global tool registry or persist live capabilities/routes.
4. Use application-local precedence over host-configured MCP only inside the owning application's session, reject collisions with platform/static tools, and allow the same local tool name in different applications because application identity is part of the route.
5. Dispatch through an application-platform-owned gateway that validates current binding ownership and package declaration before invoking the worker. Do not give MCP transport code raw engine managers or application execution managers.
6. Make this a clean current-contract change with regenerated maintained application packages; do not add aliases, dual handler shapes, or old/new runtime branches.
7. Keep the existing automatic and configured exposure rules intact: the native foundation baseline and automatic Team collaboration tools continue to be provisioned exactly as today, configured platform/global tools remain additive, and selected application-owned business tools add one separate exact application-scoped MCP capability. Do not add application business tools to either automatic baseline or process-global state.
8. Validate invocation arguments against the package-declared JSON input schema before dispatching to the application worker.
9. Make the maintained Brief Studio proof an actual Codex/Luna Agent journey: reinforce the first-call/result-use and required-artifact outcomes in each individual role prompt, but keep those prompts business-focused and free of foundation tool names. Let the model choose from the runtime's automatically supplied capabilities; retain current Codex file-change/AutoByteus normalization only as execution evidence. Pass the complete research checkpoint in the researcher handoff so the writer does not require a cross-workspace read, publish workspace-relative paths, and assert the existing final-artifact/status UI rather than making the read-only tool mutate application state.
10. Rebase the feature design onto latest-base `activateForRun`/`deactivateForRun`: application scopes supply a live nullable application capability to session composition and AutoByteus construction; restore recomputes routes from current context/catalog; package reload/removal drains only the application lane and never tears down the containing run session.

## Scope Guardrail (Mandatory)

### In-Scope Use Cases

- `UC-001`: an application package declares business-specific agent tools and implements their handlers.
- `UC-002`: an application-owned Agent, configured Team member, or task-created Team member explicitly receives selected platform/global and same-application tools.
- `UC-003`: a live application Agent Tools MCP run session lists and invokes a selected application tool against the owning worker through the dedicated loopback route.
- `UC-004`: two applications may declare the same local tool name without seeing or invoking each other's handler.
- `UC-005`: Studio and standalone enforce identical application-tool selection, authorization, dispatch, result, and cleanup behavior.
- `UC-006`: package reload, application removal, worker failure, run termination, and platform shutdown coordinate application-tool admission and stale-route behavior.
- `UC-007`: a maintained application demonstrates one real read-only application-owned tool through the production path.
- `UC-008`: an actual configured Brief Studio Agent follows its maintained role prompt, calls the read-only application tool first, uses the result in its published work, and the same binding/brief is observable in the existing browser UI.
- `UC-009`: stopping an application Agent deactivates its live Agent Tools run session; restoring the same run reuses the deterministic route identity while rematerializing current application identity, routes, fingerprints, and live capabilities. Package reentry/removal remains an independent per-application call-drain lifecycle.

### Out of Scope

- Publishing, versioning, or documenting the packages as a generally consumable external developer SDK.
- Redesigning the complete application authoring experience, framework integrations, scaffolding, or public documentation journey.
- Allowing an application package to install, spawn, or supply an arbitrary third-party `stdio`, SSE, or remote MCP server/configuration.
- Application-managed remote MCP credentials, marketplace/consent UI, billing, or per-user permission policy.
- Replacing the shared Agent Tools MCP endpoint, provider adapters, `ApplicationExecutionScope`, or `GeneralProcessRunSupervisor`.
- Automatically exposing every application or global tool to every Agent.
- A generic applicationId/runId execution-manager registry, service locator, or per-mounted-application execution scope.
- Background or detached application-tool jobs; this ticket covers completion-coupled tool calls only.
- A write-capable replacement for `get_brief_context`, a direct “tool called” business-state projection, or a new GraphQL/UI workflow solely to demonstrate tool execution. Brief Studio uses its existing artifact publication, notification, query, and rendering surfaces.
- A platform-wide Codex adapter/dynamic-tool exposure for ordinary registry `read_file`/`write_file`, changing the maintained proof to a different runtime/model/credential source, or configuring a provider-native file operation through application `toolNames`. Runtime foundation provisioning remains runtime-owned; the application prompt describes the required artifact rather than the operation used to create it.
- Reintroducing bearer authentication, random session identity, Agent Tools routes on the main listener, persisted live session/application capability state, or a second listener per application. Those are superseded by the latest-base run-session contract.

The minimum contract types needed to declare and implement application tools are in scope. Broader SDK publication and developer-experience work remains explicitly deferred.

### Preserved Behavior Boundary

BEH-001–BEH-009 preserve existing platform/static tools, configured global MCP tools, the AutoByteus-native foundation baseline, automatic Team collaboration tools, the Memory Compactor exclusion, provider-neutral descriptors, the dedicated loopback Agent Tools listener, deterministic tokenless run-session identity, fresh restore activation, exact-run deactivation, GeneralProcessRunSupervisor/ApplicationExecutionScope separation, RootTeamRun-local task capability routing, application binding authorization, package import safety, Studio/standalone parity, application storage ownership, and the read-only meaning of `get_brief_context`. Application-tool routing and the maintained proof must not weaken or bypass those owners.

### Review Authority

- Every blocking `Design Impact` or implementation-correction finding must cite an approved requirement, acceptance criterion, or preserved-behavior ID that it protects.
- A finding that would introduce new product behavior, policy, threat model, migration obligation, or operational contract is a `Requirement Gap`; it must return for explicit user approval before becoming authoritative.
- An adjacent concern outside the approved boundary may be recorded as a non-blocking risk, recommendation, or separate-ticket candidate. It must not be treated as a required design correction.
- A downstream reviewer comment does not amend this requirements basis. The solution designer must update the canonical requirements and obtain renewed user approval before a scope-changing proposal can govern design or implementation.

## Functional Requirements

- `REQ-001` — Each application may declare zero or more application-owned agent tools using one static package-owned definition per tool: provider-safe local name, non-empty description, and object-valued JSON input schema.
- `REQ-002` — The matching handler implementation executes only inside that application's backend worker and receives the ordinary application handler capabilities plus immutable caller identity derived by the host; application code must not register handlers in process-global state.
- `REQ-003` — Agent/Team `toolNames` remain the explicit selection mechanism for application-owned business tools and existing configured tools. Declaring an application tool does not grant it to any Agent that did not select its name. For the same application-owned Agent definition and binding, changing among supported runtime kinds must not remove or change the meaning of a selected application tool. Existing automatic native-foundation and Team-collaboration provisioning remains additive and is not converted into explicit configuration by this ticket.
- `REQ-004` — Application runtime readiness must validate every selected tool name against the union of allowed process tools and the exact owning application's catalog. Missing tools, invalid declarations, duplicate local names, missing handlers at worker load, and forbidden collisions must fail closed with application-specific diagnostics.
- `REQ-005` — One physical `AgentToolsMcpHost` and its dedicated process-wide `127.0.0.1` listener must remain the transport for provider runtimes that consume Agent Tools MCP descriptors; the feature must not create a listener/process per application or put Agent Tools routes back on the main listener. Provider descriptors remain headerless/tokenless and use the deterministic route derived from the AutoByteus run ID. Application-tool availability must nevertheless remain invariant across supported AutoByteus, Claude, and Codex execution through their established runtime projection boundaries; native fundamental tools do not move onto HTTP MCP.
- `REQ-006` — A live run-session activation may receive an application-tool route only when its authoritative execution context identifies an application, binding, and producer run that belong together. A general-process activation or another application's activation must not list or invoke the route. The deterministic route ID is routing, not authorization; local admission plus live server-minted session state and current binding checks govern access.
- `REQ-007` — Application-tool dispatch must follow the exact immutable route identity captured at live run-session activation and revalidate the current application, attached binding/producer, declaration fingerprint, availability, and worker before handler invocation. No caller-provided application ID, deterministic route ID, or global run lookup may choose the target.
- `REQ-008` — The platform MCP host owns the dedicated local transport, admission, active run-session composition, and MCP result mapping; the application package owns declarations; the application worker owns handler code and business state; the application platform owns binding authorization, worker routing, and per-application tool-call lifecycle. The deterministic run-session ID is never treated as a credential.
- `REQ-009` — Tool-name policy must be deterministic: application declarations that collide with platform/static Agent Tools MCP names are invalid; same-name declarations in different applications are allowed; within an owning application session an application tool is authoritative over a host-configured MCP tool with the same name; outside that application the configured MCP tool retains its existing behavior.
- `REQ-010` — An application tool receives JSON-object arguments validated against its package-declared input schema and may return bounded MCP-safe text/rich content and optional structured content with explicit tool-error status. Schema-invalid, unserializable, or over-limit input/result values fail before crossing or leaving the worker boundary.
- `REQ-011` — The handler caller context must include the exact application ID, binding ID, producer agent-run ID, and resolved Team member address when applicable. The handler must not infer caller ownership from an arbitrary ID supplied in tool arguments.
- `REQ-012` — Application tool composition must preserve non-identical general and application execution scopes, managers, and cleanup while reusing the same process run-session authority. The provider-factory/kernel composition may supply a non-null live application capability only for the application execution family: AutoByteus uses it for bound local application tools; Claude/Codex use the scope's `activateForRun` boundary, whose session composition receives the same capability. General execution supplies `null`. This must not change the automatic non-compactor native foundation baseline, the automatic Team collaboration trio, configured-tool additivity/deduplication, the native local/in-process execution path for those tools, or the Memory Compactor's empty tool exposure.
- `REQ-013` — Normal package reload must block new application-tool admission for that application, await already admitted tool calls, stop/reload the worker and catalog, then reopen admission only after the current package is valid. No fixed completion timeout or automatic retry is introduced.
- `REQ-014` — An active run-session route is immutable. A tool added after activation is unavailable to that active record; a removed or schema/description/name-changed declaration fails closed for that route; a code-only handler update with an unchanged declaration may execute in the current worker after successful reentry. A later stop/restore creates a fresh active record at the same deterministic URL and resolves the current catalog rather than reviving the old route object.
- `REQ-015` — Worker crash/removal, exact-run termination, application removal, and platform shutdown must reject new calls, settle or fail in-flight calls explicitly, and release owned state idempotently. Exact-run termination deactivates the whole run session; application package transitions do not. The platform must never report a tool call as failed solely because of a local completion timeout while knowingly allowing it to continue.
- `REQ-016` — The package/backend contracts must make one clean current representation authoritative. The application manifest owns static tool declarations; the backend definition owns the exact matching handler map. No alias, dual representation, runtime fallback, or global-registration compatibility path is allowed.
- `REQ-017` — Current durable application databases, platform binding/journal state, Agent/Team definitions, and global MCP configuration remain directly usable without transformation. Generated/importable application package artifacts using the prior contract are rebuildable artifacts and must be regenerated on the current contract rather than migrated in place.
- `REQ-018` — For a fresh Brief Studio draft run, each relevant maintained role prompt must itself require exactly one successful `get_brief_context` call as that role's first business tool action: the researcher before creating or publishing the research artifact, and the writer after receiving the researcher handoff but before creating or publishing the final artifact. Each role must reuse the returned `briefId`, title, and observed status rather than calling again or guessing identity. A missing/error result or a researcher/writer brief-identity mismatch must stop the normal publication sequence rather than publish against an assumed brief.
- `REQ-019` — The maintained proof must run an actual configured model-backed Brief Studio Agent/Team rather than a direct MCP client or mocked model decision. Evidence must correlate one `get_brief_context` call/result pair per participating member with the authoritative application ID, binding ID, member address, member agent-run ID, and returned brief ID by joining the existing access-controlled Agent run trace with the application Team binding. Generic application-tool arguments/results must not be copied into new process-wide operational logs; if no real configured provider is usable, the live proof is blocked rather than replaced with a mock.
- `REQ-020` — `get_brief_context` remains read-only. Each successful researcher/writer artifact must contain the exact machine-observable line `Brief context: {"briefId":"…","title":"…","observedStatus":"…"}` derived from that member's result, using compact JSON with that fixed key order and ordinary JSON string escaping so arbitrary title text cannot break the one-line marker. The ensuing state change must use the existing `required business artifact -> publish_artifacts(workspace-relative path) -> application artifact relay/reconciliation` path. For the maintained Codex run, provider-native `fileChange` and AutoByteus normalized `edit_file` may corroborate how the runtime fulfilled the artifact request, but the application prompt and business contract do not name or select that implementation. For the same launched binding and brief, final publication must produce the existing `in_review` status, final writer artifact, ready-for-review notification/refresh, and Brief Studio UI rendering; no new application mutation tool, storage field, GraphQL operation, or UI workflow is required.
- `REQ-021` — The maintained demonstration remains explicitly `codex_app_server` / `gpt-5.6-luna`. Its `toolNames` may select only routed application/Agent-Tools-MCP business, collaboration, and publication capabilities needed by the workflow; they must not list runtime foundation operations. Each `agent.md` must describe the business sequence and required canonical artifact, not direct the model to call `apply_patch`, `edit_file`, `write_file`, `run_bash`, or any provider-specific equivalent. The researcher creates and publishes `brief-studio/research.md` and hands the writer the exact marker plus the complete research checkpoint body. The writer consumes that handoff body without a cross-member file dependency, copies at least one complete non-marker `Key findings` bullet verbatim into the final brief's `Key evidence`, creates and publishes `brief-studio/final-brief.md`, and completes the handoff. The runtime automatically supplies its normal foundation capabilities and the model chooses the appropriate operation. Publication/handoff failure produces a truthful blocker; fabricated publication is forbidden. Runtime evidence may assert the actual operation was a native file change and not shell fallback without feeding those mechanics back into the role prompt.
- `REQ-022` — Every Claude/Codex run activation must derive its deterministic tokenless Agent Tools route from normalized run ID and materialize fresh live session state from the current sender, owner, runtime exposure, application execution context, application capability, declaration snapshots, configured sources, and observer. Stop/exact-run cleanup deletes that active record; restore activates the same route URL with newly resolved current state. None of those live values is persisted or reconstructed from the deterministic ID alone.
- `REQ-023` — Run-session lifetime and application package lifetime are orthogonal and must compose explicitly. Package reload/removal closes and drains only the affected application's application-tool lane, commits/re-enters through `ApplicationCatalogTransitionService`, and leaves active run sessions and non-application routes intact. During quiesce application calls fail unavailable; after recovery an unchanged fingerprint may resume, while changed/removed routes fail stale/unavailable. Exact-run termination or execution-scope close deactivates the run session. Platform shutdown orders execution quiesce, application call drain, worker stop, run/session finalization, capability close, and process listener close through their existing owners.

## Acceptance Criteria

- `AC-001` — A valid package with no application tools remains valid and preserves current tool provisioning exactly: every non-compactor AutoByteus-native Agent receives `run_bash`, `read_file`, `edit_file`, and `write_file`; an eligible Team member receives `get_handoff_rules`, `send_message_to`, and `delegate_task`; configured tools remain additive and deduplicated; the Memory Compactor receives no tools.
- `AC-002` — A valid package can declare one application tool and load a backend definition with exactly one matching handler.
- `AC-003` — Duplicate declarations, invalid names/descriptions/schemas, missing handlers, and undeclared extra handlers are rejected with an application-local diagnostic.
- `AC-004` — Package scanning and validation discover tool metadata without importing or executing the application backend entry module.
- `AC-005` — The same application-owned Agent definition selecting one application tool and one configured platform/global tool receives both when launched with AutoByteus, Claude, or Codex; runtime override does not remove or rebind the application tool, and AutoByteus additionally retains its automatic foundation baseline.
- `AC-006` — An application-owned Agent that does not select a declared application tool cannot list or invoke it.
- `AC-007` — A selected application tool missing from that application's catalog quarantines/fails readiness for that application rather than being silently omitted.
- `AC-008` — Configured and task-created nested Team members preserve the same application context and tool visibility as directly configured members, including automatic provisioning of `get_handoff_rules`, `send_message_to`, and `delegate_task` independently of configured application-tool selection.
- `AC-009` — A shared Agent definition used inside an application resolves application-local names in that application's catalog, while the same definition outside application execution receives no application-local route.
- `AC-010` — Studio and standalone, across AutoByteus, Claude, and Codex application runs, use the same application catalog, selection, authorization, and invocation contract. Claude/Codex use the shared Agent Tools MCP route; AutoByteus may use its established bound-tool projection without changing observable application-tool identity, availability, isolation, or result semantics.
- `AC-011` — A general-process Agent Tools MCP session cannot list or invoke an application tool, even when it requests the same name.
- `AC-012` — App A and App B may declare the same local name; an App A session invokes only App A's handler and an App B session invokes only App B's handler.
- `AC-013` — An application declaration colliding with a platform/static tool fails readiness; no platform/static adapter is shadowed.
- `AC-014` — In an application session, an application declaration wins deterministically over a configured global MCP tool of the same name; the configured tool remains unchanged in general/other-application sessions.
- `AC-015` — Tool invocation authorizes the session's application ID, binding ID, and producer run against the current attached binding before calling the worker.
- `AC-016` — The worker receives only the selected tool name, validated arguments, immutable caller context, and its normal application handler capabilities; it does not receive a process manager, registry, or raw MCP session.

## Constraints / Dependencies

- One shared process `AgentToolsMcpHost` remains the physical transport and active run-session registry owner; it owns exactly one dedicated loopback listener and exposes the complete immutable static-adapter-name snapshot needed by application readiness.
- `ApplicationExecutionScope` remains one per `ApplicationPlatformRuntime`, not one per application.
- `GeneralProcessRunSupervisor` and application execution managers/session authorities remain separate.
- Application identity must come from the existing binding-created `ApplicationExecutionContext`; do not introduce a run/application manager locator.
- Package discovery remains static and import-safe; handler execution remains worker-isolated.
- The existing completion-coupled engine request path and JSON-line frame writer are reused; one bounded application-tool frame limit may be added instead of a family of overlapping limits.
- Minimal contract and devkit changes needed for this capability are in scope; npm publication and polished external SDK experience are not.
- Existing access-controlled Agent memory/run-trace retention is the call/result evidence owner. Application binding, artifact projection, GraphQL, and browser surfaces remain the identity/business/UI evidence owners; the application-tool gateway does not become a generic payload audit log.

## Persisted Data Outcome (When Applicable)

- Stored subject / location: generated/importable package manifests and backend bundles; durable `platform.sqlite` application bindings/journals/overrides; per-application `app.sqlite`; file-owned Agent/Team definitions; global MCP configuration.
- Required outcome: `Discard or Rebuild` for generated/importable package artifacts on the prior contract; `Directly Usable — No Migration` for durable application/platform data and global MCP configuration.
- Existing data to preserve, discard/rebuild, transform, or quarantine: rebuild maintained package outputs from source on the current contract; preserve all durable runtime/application data unchanged; quarantine an imported package built for the retired contract until it is rebuilt/reinstalled.
- Unacceptable data loss or corruption: loss or rewrite of application business databases, bindings, journals, launch overrides, Agent/Team definitions, or user-configured global MCP servers/credentials.
- Relevant availability, maintenance-window, or rollout constraints: package/tool catalog replacement occurs through existing application reload/reentry; live run-session/application capability values remain in memory only; no database maintenance window is required.
- Related requirement and acceptance-criteria IDs: REQ-013–REQ-023; AC-021–AC-044.

## Risks / Open Questions

- **Resolved runtime boundary and non-regression:** the current automatic native foundation and Team collaboration tools remain automatically provisioned under their existing eligibility rules; configured tools remain additive. An application itself declares and implements its business tools; selected application tools are a separate application-scoped MCP capability whose availability and application-local meaning are invariant across AutoByteus, Claude, and Codex runtime selection, without global registration.
- Input validation must be made explicit: valid object arguments must also satisfy the declared JSON input schema before handler execution. The supported self-contained JSON Schema subset and validator placement are design details after this requirement is approved.
- **Resolved worker-failure posture:** an application-tool call never retries a failed/in-flight invocation. After an unexpected worker crash, later tool calls fail closed until normal application reentry or another owning backend path restores the worker; the application-tool invocation boundary itself does not turn a failed worker into an implicit retry/restart policy.
- The exact manifest and backend-definition contract version numbers are design details, but a clean current-contract bump and package rebuild are required by REQ-016/REQ-017.
- The exact MCP content union and one serialized frame-size value are design details; the behavior must satisfy REQ-010 and AC-018–AC-020.
- **Resolved maintained-proof direction:** Brief Studio uses Option A from `api-e2e-agent-ui-proof-gap.md`. Individual role prompts—not only `agent-config.json` or `team.md`—make `get_brief_context` the first business call and make result use visible in ordinary published artifacts. API-REV-004 proved the current Codex/Luna runtime can fulfill that workflow. The user's 2026-08-28 clarification now keeps runtime mechanics out of `agent.md`: roles specify the business artifact/publication/handoff; runtime provisioning and model reasoning choose the foundation operation. Current Codex `fileChange` and normalized `edit_file` remain verifier-side evidence only. The existing application projection and UI, not the read-only call itself, own the state transition.
- **Resolved latest-base composition:** DR-004 adopts the finalized `agent-tools-mcp-session-resume` contract as upstream authority. Application identity/routes/capability are rematerialized inside `activateForRun`; package drain never deactivates that run session; exact-run/resource finalization owns `deactivateForRun`; the process host owns the listener.
- The live Agent/browser proof depends on one usable configured provider. Absence of credentials/runtime availability is an explicit blocked proof state, not permission to substitute direct MCP or a mocked Agent decision; the already-passed direct MCP path remains valid lower-level evidence only.
- If the user instead intends application packages to bundle arbitrary external MCP server processes/configuration, that is a material scope expansion and requires renewed requirements approval.
