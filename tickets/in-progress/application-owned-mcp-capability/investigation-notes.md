# Application-Owned MCP Capability — Investigation Notes

## Investigation Status

- Bootstrap Status: Complete
- Current Status: Architecture review round 4 passed `SR-004`, implementation baseline `IR-001` was produced, and code review `CRR-001` returned `Fail — Design Impact`. `CR-DI-001` found that the design/source incorrectly reused the configured-MCP-versus-static collision-policy subset for application declarations. `SR-005` corrects the canonical all-platform/static-name boundary without changing the approved behavior basis; implementation and API/E2E remain paused pending architecture re-review and source correction
- Investigation Goal: Establish the current production spines and exact ownership boundaries needed to add application-owned MCP tools without global registry mutation or cross-application leakage.
- Scope Classification: `Large`
- Scope Classification Rationale: The feature crosses package contracts, application worker protocol, ApplicationPlatformRuntime/ApplicationExecutionScope boundaries, Agent Tools MCP session composition/dispatch, reload/shutdown lifecycle, and durable coverage.
- Scope Summary: Application-owned business tools exposed to same-application Agent/Team executions through the existing shared authenticated Agent Tools MCP host. External SDK distribution and arbitrary package-provided MCP server processes are excluded.
- Primary Questions To Resolve:
  - Where should the application-local tool catalog live relative to package and worker lifecycle?
  - How should an MCP session compose selected platform, configured-global, and application-local routes?
  - How should application tool calls cross into the correct worker with exact ownership and lifecycle guarantees?
  - What static package metadata is required for import-time validation without executing application code?
  - What reload, close, collision, error, and persisted-data behavior is required?

## Design Health Assessment Evidence

- Change posture: `Feature` / `Larger Requirement`
- Root cause classification: `Boundary Or Ownership Issue`
- Refactor posture evidence summary: The shared transport/session infrastructure is reusable, but the current process-global catalog cannot become the owner of application-local business tools. The design therefore requires one application-owned catalog/dispatch/lifecycle boundary and thin native/MCP projections now.

## Findings From Code / Docs / Data / Logs

- Platform/common tools and user-configured MCP tools currently share a process-wide lookup/collision domain.
- Application execution sessions already carry authoritative application execution context.
- Application worker is the existing owner of application business code and lifecycle.
- Application package import remains prebuilt-only and must not execute arbitrary app code merely to discover tools.
- Application definitions currently refer to plain tool names. Requirements choose exact-application routing, reject platform/static collisions, allow cross-application reuse, and give the owning application precedence over configured-global MCP inside its session.
- Application session route tables are already immutable snapshots. A declaration fingerprint can preserve that invariant while failing closed after removal/schema change.
- `ApplicationEngineClient.request()` currently has no local fixed completion timeout. Application tools should reuse completion-coupled semantics and never auto-retry a possibly mutating handler.
- The current platform shutdown stops workers before closing the execution scope. The target must block application-tool admission and drain admitted calls before worker stop while retaining the larger owner order.
- The shared Agent Tools MCP path currently projects only to Claude/Codex. The target must additionally project application-owned business tools to AutoByteus-native application runs while leaving native fundamental tools on their existing local path.
- `send_message_to` confirms the current universal-tool pattern: automatic/common exposure policy is shared, but AutoByteus receives a bound local tool that calls `SendMessageToDispatcher`, while Claude/Codex receive a scoped MCP descriptor whose adapter calls the same dispatcher. The Agent Tools endpoint does not currently provision the native tool.
- Host-configured MCP tools follow a similar product/runtime split: native uses its MCP tool wrapper/client path, while external providers receive configured tools re-projected through the Agent Tools MCP catalog.
- `tools/call` currently checks only object shape, so the declared input schema requires a new enforcement boundary before application code receives arguments.
- `ApplicationRunOwnershipService` already centralizes application/binding/run membership and status checks; a new gateway should consume that reader instead of reconstructing authorization from stores.
- The final design keeps worker start/restart policy behind a narrow worker invoker assembled after orchestration exists: a clean stopped/starting worker may be started or joined, while an unexpected failed/stopping worker is rejected until an owning recovery/reentry path restores it. No failed invocation is retried.
- The execution-scope-before-launcher construction order requires a one-time sealed application capability assembly. Passing a launcher into MCP/native adapters or using a module-global setter would invert ownership.
- Persisted Team binding members cover configured members, while task-created descendants carry a server-minted root Team execution identity. Application-tool authorization must validate that root against the exact binding and producer against the sender rather than persisting every descendant as a new binding member.
- Brief Studio's existing binding-to-brief correlation and brief repositories provide a real application-owned read-only proof without a database or UI change.
- Automatic native tool provisioning is owned explicitly by `resolveAutoByteusRuntimeAgentToolExposure`: `run_bash`, `read_file`, `edit_file`, and `write_file` precede configured names for every non-compactor native Agent.
- Automatic Team collaboration provisioning is runtime-neutral: member Team context adds `get_handoff_rules`, `send_message_to`, and `delegate_task` independently of persisted `toolNames`.
- The final AutoByteus `AgentConfig` receives the already composed tool instances; neither `AgentConfig` nor `AgentFactory` adds another hidden tool set. Application MCP integration must therefore be additive at the server-owned composition boundary and must not modify the two automatic resolvers' current meaning.
- Generic `BaseTool.prepareExecution` intentionally coerces string integers/numbers/booleans, converts an empty string to an empty array, and recursively coerces supported nested values before `_execute`. The MCP application route reaches the common gateway with raw JSON instead. Application runtime parity therefore requires `ApplicationAgentTool` to override only its own preparation, preserve the raw argument object, and let the common gateway's strict Ajv validator decide schema validity.
- The specialization does not require a global base-class hook: the public method is polymorphic, the generic coercion/validation helpers are private, and the native tool phase plus inherited `execute` both call the override. The adapter must reproduce only the ordinary `agentId`, pre-start abort, and result-mode preparation contract; its checked `ParameterSchema` remains an advertised definition rather than an application-call validator.
- Static adapter registration and configured-MCP precedence are distinct from application declaration validity. `configuredMcpCollisionPolicy: "prefer_configured_mcp"` means a host-configured MCP source may replace that static route; it does not make the platform/static name available for an application package to own. Every name in the MCP catalog's static adapter index is reserved from application declarations even when the adapter is currently unavailable.
- Application readiness is the primary fail-closed boundary for that complete reserved set. MCP session composition repeats the all-static check as defense in depth before selecting an application route. Application precedence then applies only when there is no registered static adapter and a same-name configured MCP source exists. Native construction relies on successful application readiness and must not import MCP catalog internals or reimplement the name policy.

## Open Unknowns / Risks

- Resolved product decision: application-owned business tools are explicitly selected, application-provided MCP capabilities whose identity and availability remain invariant across supported runtime selection; exact application session/execution identity prevents cross-application visibility. The automatic native foundation and automatic Team collaboration rules remain unchanged and additive.
- Approved lifecycle basis: calls arriving after a worker crash fail closed until the normal owning lifecycle restores the worker; the tool boundary does not lazily restart or retry the call.
- Design decision: manifest version `5`, backend definition version `7`, canonical `agentTools` declarations and exact `agentToolHandlers` map; no compatibility reader.
- Revised design decision (`ARCH-DI-001`, `SR-004`): a portable self-contained object JSON-schema subset remains limited to exact current native mapper round-trip semantics. A checked native projector supplies the advertised `ParameterSchema`, while `ApplicationAgentTool.prepareExecution` bypasses generic coercion/`ParameterSchema` invocation validation and forwards the same raw JSON object to the common capability/gateway. It preserves ordinary agent-ID setup, pre-start cancellation, and result-mode resolution/normalization locally. `McpSchemaMapper`, `ParameterSchema`, `BaseTool`, fundamental tools, and configured tools remain unchanged.
- Revised design decision (`CR-DI-001`, `SR-005`): the complete set of names registered by `AgentToolMcpCatalog` static adapters is the platform/static namespace forbidden to application declarations. The per-adapter `configuredMcpCollisionPolicy` remains solely the configured-MCP-versus-static rule. `AgentToolsMcpHost` exposes a frozen `staticAdapterToolNames` snapshot to application readiness; MCP application route composition rejects any registered static adapter regardless of policy or current availability, then allows application-over-configured precedence only when no static adapter exists.
- Design decision: one canonical MCP-safe result union and one 1 MiB serialized application-tool payload limit, enforced before host-to-worker request and before worker-to-host result.
- Design decision: Brief Studio demonstrates `get_brief_context`, deriving durable business state from immutable caller `bindingId`.
- Revised design decision (`ARCH-DI-002`): `ApplicationCatalogTransitionService` replaces the separate refresh/reentry live mutation paths, while revised `ApplicationReentryService` retains only participant preparation/recovery/quarantine. Settings/GraphQL package commands enter the transition before registry/root/source mutation; it derives old participants from the live package slice, invokes reentry lifecycle, stages only the target slice, commits prepared bundle/tool state synchronously, then reconciles/recovers or restores and re-stages rollback state. Unrelated application lanes and catalog slices stay untouched.
- Residual implementation risk: rollback source restoration can itself be unreadable or incomplete. Only the affected participants may remain closed/quarantined; the transition lock must always release and the old in-memory snapshot must never be reopened without staging the actual restored source.
- Residual validation risk: dependencies now exist from IR-001, but downstream must still correct source, pass renewed source review, then execute the full Studio/standalone AutoByteus/Claude/Codex matrix under API/E2E ownership.
