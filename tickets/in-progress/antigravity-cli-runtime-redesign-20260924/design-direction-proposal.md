# Proposed AGY design direction — not an approved design spec

This is Solution Designer's recommendation in response to the user's request for an opinion. It does not supersede Draft requirements or authorize implementation. See `agy-cli-experiment-report.md` for evidence and limits.

## Recommendation

Build **one shared AGY run core** and choose one explicit interaction contract. After the user's SR-006 preference for the existing chat frontend and durable raw traces, the better-aligned **conditional recommendation is `stream-json` over ordinary process pipes, without node-pty**. This yields actual response/tool/turn events for the existing projection stack. The user's SR-010 decision explicitly sets new AGY runs to `autoExecuteTools=true` by default and accepts the absence of per-action approval buttons in headless mode. A bounded AGY control showed that its broad `--dangerously-skip-permissions` mode allows a harmless shell command while retaining structured events. The user has clarified that AGY should reuse the normal AutoByteus normalized raw-trace pipeline, not add a separate provider-NDJSON archive. The complete solution baseline still needs identity-continuity and team-scope confirmation. The earlier terminal-first recommendation is now historical rather than a live choice for the default AGY experience.

## Shared invariant core (applies whichever transport is selected)

1. **Identity:** Snapshot the full current AutoByteus agent/member identity (name, description, authored instructions, enclosing team and collaboration instructions) at run creation; generate a unique run-local `.agents/agents/<name>/agent.md` with `mainAgent: true` and body as the real AGY system-level agent instructions. Reuse the source `agent.md` authored body, but do not blindly copy the whole source file: one exact-copy probe worked only when AGY folder/flag matched its frontmatter display name, and team context is composed outside that file. No first-user-message identity bootstrap. Validate files and supported CLI/project contract before launch; flags or `init.agent` alone do not prove loading.
2. **Project/workspace:** Persist a run-owned primary capsule and launch new runs with `--new-project --agent <generated-name>`, using `--add-dir` for the actual user workspace. Do not write generated identity, hooks, MCP secrets or permissions into the user's own `.agents` or global AGY settings. Keep the capsule while the conversation must be restorable; exact resume should use AGY's associated project, not create another new project.
3. **Conversation ownership:** Keep AutoByteus `runId` distinct from AGY's generated conversation ID. A run is provisional until AGY's ID is observed and durably bound. Resume only by `--conversation <stored-ID>`; compare requested and observed IDs *before accepting new input*. If AGY silently makes a fresh ID, fail closed and show non-restorable rather than rebinding. Never use `--continue` to restore a specific AutoByteus run.
4. **Identity continuity:** An existing conversation should provisionally retain its original identity snapshot; edits to the agent definition affect new runs. This matches one AGY resume probe but is an intended-behavior decision for the user, not an approved rule.
5. **Per-run isolation and lifecycle:** One process/session owner per run, explicit startup, cancellation/close semantics, version/model checks, separate concurrent capsules, and observable startup/restore/permission errors. Keep the transport-specific event/terminal handling outside the shared identity and binding core.

## Transport boundaries and release gates

- **Native TUI:** Browser terminal is the single direct-human input and approval surface. Treat screen bytes as opaque. A run-local log can show a `Created conversation` line after the first real prompt; a hook can corroborate ID on tool invocations, but neither proved a dependable idle/pre-prompt ID channel. Before shipping TUI restore, repeatedly validate an unambiguous non-screen ID capture and exact-resume mismatch detection across supported CLI versions. Until the ID is captured, show the run as provisional/not yet restorable. Do not mark a PTY turn complete merely because input was pasted.
- **Structured stream:** A Node `child_process.spawn` with piped stdin/stdout/stderr (not `node-pty`) can send AGY NDJSON user messages and consume `init`, `step_update`, and per-turn `result`. Map the exposed deltas/tool states into canonical `AgentRunEvent`s so current WebSocket/chat/Event Monitor and `AgentRunMemoryRecorder` → `RuntimeMemoryEventAccumulator` → `ExternalRuntimeMemoryWriter` can display and persist the normal AutoByteus normalized `raw_traces_active.jsonl`. The provider NDJSON is input to this adapter, not a separately required durable archive. Register AGY as a recordable external-provider runtime so the existing recorder actually attaches. `init` is the strongest observed early ID source. **Fidelity limit:** AGY may expose only a summary for a tool result (tested `view_file` gave `2 lines, 17 bytes` instead of file bytes), and does not expose hidden reasoning simply because token usage reports thinking. The normalized trace records what the runtime supplies plus known app input, not unseen internals. For the user-approved new AGY default of `autoExecuteTools=true`, AGY's `--dangerously-skip-permissions` puts the process in `always-proceed` mode, as the harmless shell control showed. It is broader than a scoped allowlist and must not be applied silently to explicitly `false` runs or by changing global AGY settings. With `false`, headless `request-review` can soft-deny tools while returning exit 0 / top-level SUCCESS; surface the denial as a failed tool event without a manual-approval workflow. No claim of interactive approval parity or transparent fallback to TUI without a separately validated contract.

  **SR-015 raw-capture refinement:** Verbatim CLI stdout/stderr for read, allowed/denied/nonzero command, file write, and two tool-using turns is stored in `agy-tool-event-capture/` and analyzed in `agy-tool-event-capture-analysis.md`. This is investigation evidence, **not** a production provider archive. `tool` ACTIVE and terminal updates shared a step index; a two-turn stream kept one conversation ID and advanced indexes. The `user_input` update omitted input text, so record the app's submitted message; `result.response` repeated assembled assistant deltas, so avoid a duplicate assistant message. A denied tool emitted ERROR plus `result.denied_actions` even with overall SUCCESS. A command that exited 7 emitted tool DONE without a structured exit code, while file write and file read omitted full content. The converter must represent AGY-emitted state without inferring underlying command success or fabricating unseen bytes. Correlation by conversation ID/step index is a candidate requiring production lifecycle validation, not a guaranteed provider call-ID contract.

  **Codex App Server analogy:** Existing AutoByteus Codex maps per-run `autoExecuteTools=true` to `approvalPolicy=never` and `sandbox=danger-full-access` on both start and resume, and auto-accepts residual approval server requests. AGY can map the same run-level choice to its all-tools flag on both new and exact-resume process launch; the proven target is no-prompt execution plus observable tool events, not byte-for-byte API equivalence. Codex's `false` path uses app-server request/response approvals; AGY headless stream has no equivalent supported approval response. This is the narrow remaining permission asymmetry.

  **AGY selection default (user-approved behavior, technical shape still proposed):** The default belongs to **new editable launch configuration transitions**, not merely a switch painted on the frontend and not a backend override of a stored false value. Current `buildAgentRunTemplate`/`buildTeamRunTemplate` set false; desktop standalone `AgentRunConfigForm.updateRuntimeKind` mutates the draft directly, mobile uses `agentRunConfigStore.updateAgentConfig`, team root/member edits use `applyTeamLaunchConfigEdit` and `TeamScopeConfigEditor`, and org launch config has its own store. A shared runtime-aware draft transition should make AGY selection atomically choose `autoExecuteTools=true` for the selected standalone/root/member scope and initialize AGY-seeded drafts likewise. Existing saved-run configs and non-AGY default behavior must not be rewritten. Team inheritance and explicit member overrides must be checked so an AGY member under a non-AGY root still defaults true. The effective persisted boolean, not the UI display alone, drives AGY flag selection on create and exact resume. If someone explicitly turns it off, do not force the flag: show any AGY denial as a failed tool event, without an actionable approval button. This is a candidate production-path design requiring the normal post-approval architecture pass.
- **Team capability:** A PTY-only backend is not sufficient evidence for reliable orchestrated team turn completion. If team members are a day-one requirement, either validate the structured transport/permission contract and ship it deliberately, or treat team support as not ready. Do not replicate the old enqueue-equals-complete behavior.

## Decisions requested from user before authoritative architecture

1. **Resolved by user clarification:** AGY NDJSON is converted into canonical AutoByteus events, which feed normal chat/Event Monitor and normalized durable raw traces. No separate verbatim provider-NDJSON archive is required. The current tested CLI stream does not expose every internal tool payload or hidden reasoning; record only what is supplied.
2. **Resolved:** Selecting AGY in a new editable standalone/team/member launch defaults `autoExecuteTools=true` and the backend uses AGY's broad all-tools `--dangerously-skip-permissions` mode; no per-tool Approve/Deny UI is required in headless mode. Explicit off is not a separate manual-approval feature; AGY's ordinary policy applies and denials must be visible. The user did not direct a default change for other runtimes or removal of the toggle.
3. Should conversations created by the new integration retain their original identity when agent definitions change? Is day-one team/member AGY support required as proposed? There is no legacy AutoByteus AGY run history to migrate.

The final architecture may differ after these behavior decisions and additional selected-transport validation. No design spec has been authored.
