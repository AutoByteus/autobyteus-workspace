## Historical Old-Design Assessment (Evidence Versus Proposal)

**Reusable concepts:** run-owned process lifetime; per-run generated primary workspace to isolate generated `.agents` content and MCP secrets; real user workspace via `--add-dir`; exact provider conversation binding; native TUI output treated as opaque if a terminal UX is retained. These address real ownership and concurrency problems recorded in the June package.

**Do not carry forward uncritically:** first-app-message identity injection, `agentDefinition.instructions`-only identity, log-regex-only conversation capture at shutdown, synthetic “turn complete” on PTY input enqueue, and large frontend terminal routing copied into now-reworked stores. The old branch also lacks newer CLI custom-agent and structured stream capabilities.

**Candidate design directions, not authoritative yet:**
1. PTY/terminal UX retained: generate a run-local custom main-agent definition from the *current shared identity composer* in the per-run capsule; launch a new AGY project with `--agent <run-local-name>` and real workspace through `--add-dir`; capture CLI-created conversation ID through a **verified post-creation** channel and compare on exact resume. A hook alone is not enough before tool invocation. This preserves native approvals but does not create structured assistant output.
2. Normal chat UX using `stream-json`: same custom-agent identity, structured `init`/`result` conversation binding and turns. This matches current backend/event/history architecture better. The AGY all-tools flag passed a harmless headless shell control, so the existing per-run AutoByteus auto-approve preference can plausibly map to it; the disabled path still cannot offer native interactive approval through the documented stream. Confirm the product policy before design.

The above alternatives must not be collapsed into one implementation until the user approves the intended interaction and permission behavior.

## SR-019 — Minimal task-root, capsule MCP and configured-skill resolution

The user explicitly chose a **short** main-agent workspace statement, not capsule/configuration explanations or prescriptive `cd` commands. The exact proposed body addition is:

```markdown
## Working Environment
- Agent workspace: `<selected real workspace>`
- Resolve task and project locations from the agent workspace unless an explicit target says otherwise.
```

The capsule remains an internal durable configuration/project root. AGY's `init.cwd` can be the capsule; the native carpenter `pwd` assertion must not be copied. The user accepts model-directed task targeting, not a static path sandbox. A disposable AGY 1.2.10 control using this **exact minimal stanza**, capsule primary cwd, real `--add-dir`, and explicit allowed coding tools created `minimal-file.txt` through `write_to_file` and `minimal-shell.txt` through `run_command` in the selected real workspace, neither in capsule. The shell tool parameters contained a relative redirect, but a subsequent AGY `pwd` tool output reported the selected workspace; this observation does not prove all commands or versions use that cwd. Raw JSONL/stderr and inspected targets: `agy-minimal-workspace-agent-probe.py`, `agy-minimal-workspace-agent-probe/summary.json`. The reviewer’s unguided relative-write negative control remains valid for the old design.

The same-day capsule MCP control used a disposable local stdio MCP server under capsule `.agents/mcp_config.json`; AGY sent `server/discover`, `initialize`, `tools/list`, `tools/call`, streamed `call_mcp_tool` ACTIVE/DONE and returned its exact marker. A same-name config in capsule and added real workspace selected the capsule server in one additional 1.2.10 control; only its server logged `tools/call`. Scripts/raw events and summaries: `agy-capsule-mcp-probe.py`, `agy-capsule-mcp-probe/`, `agy-mcp-config-precedence-probe.py`, `agy-mcp-config-precedence-probe/`. This is **not** a live call to AutoByteus's scoped tool server, nor universal precedence/exclusive MCP proof. AGY may also discover user/global or added-workspace MCP entries; the run-owned AutoByteus entry must be generated only in the capsule and production-scoped calls verified downstream.

The custom main-agent frontmatter needs an explicit coding-tool list in the observed CLI; initial probes without one did not use file/shell tools. A `tools: ["*"]` control failed executor construction, as did naming dynamic/auxiliary `call_mcp_tool`, `command_status`, `send_command_input`, or `sed_file` as frontmatter tools, despite some appearing in `init.tools`. An eight-name coding list `[view_file, write_to_file, replace_file_content, multi_replace_file_content, grep_search, list_dir, find_by_name, run_command]` passed constructor/turn control in AGY 1.2.10; raw/summary under `agy-main-agent-toolset-probe/`. Dynamic MCP tools still appeared and worked without frontmatter `call_mcp_tool`. Recheck the list against every supported provider version; do not infer frontmatter validity from `init.tools`.

Skill policy resolution follows existing AutoByteus external-backend code rather than inventing an AGY-only strict ban: `autobyteus-ts/src/agent/context/skill-access-mode.ts` has `PRELOADED_ONLY` and `NONE`; Claude `claude-session-bootstrapper.ts`, Codex `codex-thread-bootstrapper.ts`, and shared `workspace-skill-materializer.ts` skip **AutoByteus-configured** materialization for `NONE` but do not remove user-owned/provider-global workspace skill files. AGY CLI [skill documentation](https://www.antigravity.google/docs/skills/) lists workspace/global/plugin discovery. SR-018 probes showed both capsule and added-workspace skills discovered, even with `skills: []` and disabled slash expansion. Therefore the revised AGY design materializes resolved configured skills into capsule `.agents/skills` only under `PRELOADED_ONLY`, none under `NONE`, and does not claim it can prevent AGY from using unrelated user/global skills. That is parity with the current configured-skill contract, not a new universal restriction or a changed approved requirement. Detect same-name configured-versus-user workspace collisions rather than overwrite or silently mask them.

AGY-native subagent spawning/management is **not** in this ticket. Team/org members use separate AutoByteus-managed AGY main runs. The only reason an AGY page covering subagents was consulted was to confirm the shared `agent.md` frontmatter schema; no subagent design was adopted. No product integration, AutoByteus MCP call, normalized trace E2E or review pass is claimed by these provider controls.
