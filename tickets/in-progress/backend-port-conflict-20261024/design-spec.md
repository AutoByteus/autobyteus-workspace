### Retained Group Anchor — resolution of IMP-DI-001
D2's snapshot-overlap premise is replaced, not patched with faster polling. Create an internal group/session leader **before** user code; keep it alive for the entire native command-group lifetime, including after the user shell returns and after its agent ends. Its verified live identity pins the group number, so adoption observes members of a still-owned group rather than reclaiming an old numeric PGID. Never transfer authority from a dead command shell to an unanchored group.

`AnchoredCommandHandle` has one execution target (host or exact WSL distro), one fixed anchor identity/group, command-root PID when available, output streams, command-result promise, anchor-exit notification and release control. It is in-memory and scope-owned, not a user-visible process or stored run config. POSIX retains the actual ChildProcess and exit state plus observed birth identity; WSL retains its exact bridge child/control channel and Linux anchor PID/PGID/SID/birth identity. Later frames may not change anchor identity. User command/output records reference this same handle, not copies of its authority.

**POSIX launch:** spawn a small self-contained Node anchor with the current runtime executable, `detached:true`, stdio ignore/pipe/pipe/ipc. Keep its script in a static TypeScript string module (no runtime .ts execution, generated source file or asset-copy dependency). When the host runtime is Electron, explicitly set its Node-mode launch flag for the anchor only; do not leak that extra flag into user-command environment. The launcher obtains resolver command executable/args/cwd/env, and sends those as data on IPC only after readiness, scope registration and OS verification. Anchor uses spawn with `detached:false`, user stdin ignored, stdout/stderr inherited; the resolved shell therefore joins the anchor's exclusive session/group. No user source is interpolated into anchor code. IPC emits READY(anchor PID), STARTED(actual command PID), RESULT(actual code and signal); Node child exit, not pipe-close, produces RESULT. A successful result does not exit the anchor. Anchor catches TERM with a handler (not inherited ignore disposition), remains alive during graceful drain, and exits only on explicit RELEASE or terminal failure. IPC message listener keeps it alive without busy-loop polling. Existing Node detached contract establishes a new POSIX session; verify PGID==anchor PID before START. On macOS do not use nonexistent ps sid field; the actual detached ChildProcess plus live PGID/birth check is the authority.

**WSL launch:** do not require Node or Python inside the distro. Use its existing bash capability with Linux util-linux `setsid --wait` to run a small static bash anchor script: `wsl -d <selected distro> --cd <resolved cwd> --exec setsid --wait bash --noprofile --norc -c <anchor script> <argv0> <nonce> <resolved shell> <shell args...>`. Argument vectors carry user command as data; no command-source concatenation into the anchor. `setsid --wait` handles the possible intermediate fork and keeps the bridge associated until anchor exit. The anchor PID is the Linux leader reported by the script, NEVER the Windows wsl.exe PID or an assumed setsid PID. Before START, independently observe the reported PID within that exact distro and require PID==PGID==SID, non-zombie status, and birth identity (Linux /proc start ticks or equivalently precise platform birth token), plus the exact ready exchange from the captured bridge. This establishes a new, exclusively launched session/group; a mere old PID/PGID marker is insufficient. If setsid or identity inspection is missing/unsupported, fail command launch clearly before user code. No unsafe fallback to the current unisolated group and no automatic install. This is an operational dependency/error case to test, not live WSL certification.

The WSL anchor uses stdin solely as control and stderr for a bounded nonce-framed control stream; user shell stdin is /dev/null and cannot consume START/RELEASE. Use a128-bit fresh nonce and anchored exact READY/STARTED/RESULT grammar, bounded buffering and split-frame tests; strip only valid frames, preserve every other stderr byte. READY is emitted before user code, and parent verifies its identity before START. START is accepted once; script launches the resolved shell as an asynchronous child with job control off, reports its actual PID and waits for that command, NOT all descendants. The wrapper does not exec the command or exit when it returns. TERM uses a caught trap, not ignored disposition; wait retries after a trapped interruption while the child still lives, never fabricates a successful result. Once command ends, report its shell exit status and remain in a control-read loop; a caught TERM must not break that loop. Normal command args/cwd/env/stdio remain as resolved today. WSL command exit status follows existing shell/bridge semantics; POSIX keeps exact Node code/signal. Native tools' timeout/abort result formatting remains their current contract. User code deliberately killing the internal anchor or leaving the session/group is outside the ordinary retained-survivor guarantee; it is reported as uncertainty, not reclaimed by guessing.

Anchor readiness gate has bounded1500ms wait (consistent with current background WSL identity wait), clipped by tool/host deadline. Initial proof failures or scope close before START close the captured control channel; a gated anchor exits without executing user code. Confirm its exit; force only the captured host child when necessary, never signal an unverified Linux group. Once START is committed, scope owns the handle even if STARTED/result delivery fails. Closing an admission race cannot unregister the anchor or authorize a late START. Late callbacks only complete/clean their own lease, not start more work. Unexpected control loss/anchor exit is an incomplete ownership result; preserve known identities for diagnostics and do not reauthorize by PGID. Normal parent disconnection causes anchor exit nonzero; crash recovery is not promised.

### Command Result, Adoption And Retirement
`run_bash` normally completes from RESULT of the actual resolved shell (exceptional settlement is specified below), including fast/empty/nonzero commands; it does not wait for anchor exit or descendant-held output pipe close. Its existing short adoption delay can remain, but every group observation now has the same live anchor on both sides. Enumerate remaining command members, excluding anchor, and adopt their real PIDs while retaining the lease. `start_background_process` returns the real command PID from STARTED, not anchor PID; when that command ends, its status follows RESULT, while the lease continues to own any descendants. Output buffering/list/stop tools never display anchor/control frames. Stop by a recorded process resolves to its retained group lease, matching existing group-stop semantics.

Only release an anchor after the user command has completed AND a successful current group observation finds no other live members. Confirm anchor/bridge exit after RELEASE; release is not a stop command and must never be used with live command members. Immediate empty foreground completion retires promptly. For retained groups, a single scope maintenance timer (1s, unref, batched bounded observation per target) retires naturally emptied groups; no per-command polling loops or per-agent host owners. This timer is garbage collection, NOT ownership continuity: ownership remains anchored even when observation is delayed or fails. Unknown inspection retains the lease; it does not mean empty. Suspend/drain maintenance with the scope close promise to avoid release/signal races. New commands cannot be launched through a used lease. One small anchor per live group is the deliberate resource cost of proof, not one permanent process per historical command.

### Command-Promise Settlement And Tool Result Mapping (SR-005 clarification)
D3's RESULT wording covered the normal path but left exceptional settlement underspecified. Killing the group can kill the emitter before RESULT (P-008); RESULT is not the only terminal input. **AnchoredCommandLauncher owns one exactly-once completion latch per handle**, installed before READY/START, plus the one-shot STARTED waiter. It exposes an internal discriminated completion outcome: `result {code,signal}`, `interrupted {reason}`, or `failed {reason,message}`. This promise always resolves a terminal outcome once a handle exists; it does not reject unobserved in the background. Invalid setup before a handle can be registered rejects launch normally; the executor catches process-launch failures as described below. No background record or command promise may be fabricated with an undefined PID.

Scope still owns cleanup, not command formatting. Before TERM or a no-START cancellation it synchronously calls the handle's `noteStopRequested(reason)` with `tool-timeout`, `tool-abort`, `host-shutdown` or `explicit-stop`; this records intent but does not prematurely settle a running command. Scope never waits for command completion to perform or finish group stop. Conversely, once its bounded stop attempt completes (confirmed absence OR unconfirmed deadline/failure), scope calls `finishStop(outcome)`; launcher settles any still-pending completion without requiring another child event. Thus expected force or a missing exit event cannot leave a command hanging. Unconfirmed cleanup settles as `failed`, not as a claimed successful interruption. The scope retains an unconfirmed lease for safety/reporting independently of whether the tool caller has received a result.

Normal RESULT, explicit command-spawn failure, anchor exit/control loss, and finishStop are all inputs to the same latch. A validated RESULT received first preserves its actual code/signal permanently, including when remaining background work is later stopped. On terminal anchor/control loss without a RESULT, allow at most50ms (clipped to the current shutdown/stop deadline) to process already queued control frames; do NOT await stdout/stderr close. If a valid RESULT arrives in that window, use it; otherwise an expected stop intent produces `interrupted` once exit/stop is confirmed, and unexpected loss or unconfirmed stop produces `failed`. If expected stop is still verifying, finishStop/deadline supplies the fallback; this wait is bounded by the existing3s collective stop budget. Late/duplicate RESULT, exit, disconnect, timer and release events cannot settle again or overwrite earlier command success. A new generation/lease cannot receive the old completion.

A process spawn error after START must be an explicit terminal input: POSIX anchor catches the command ChildProcess error, emits a bounded SPAWN_FAILED code/message and does not wait for a nonexistent exit. WSL shell exec-not-found/permission failures report their real126/127 RESULT and stderr, preserving shell semantics. Anchor/bootstrap spawn failure or handshake failure rejects the STARTED waiter and resolves any created handle completion as failed; scope releases only after verifying that no command was launched/group is empty. start_background_process rejects its start promise on these failures rather than returning a running record. If STARTED was already delivered, subsequent failure updates that record using the same completion outcome; do not leave status running merely because no RESULT arrived. A failed/unconfirmed cleanup must not mark a record stopped without absence evidence.

**ShellCommandExecutor is the sole mapping owner to the unchanged TerminalResult shape:**
| Completion / trigger | exitCode | timedOut | Output / adoption |
|---|---|---|---|
| Normal RESULT | Actual command code (null for signalled POSIX exit) | Whether this executor's timeout or AbortSignal actually fired before settlement | Captured user stdout/stderr; adopt survivors only if no stop intent and the scope remains open |
| Confirmed stop without RESULT, tool timeout/abort | null | true (preserves current executor's AbortSignal convention) | Captured output plus concise interruption reason; no adoption |
| Confirmed stop without RESULT, host shutdown/explicit stop | null | false unless this executor's own timeout/abort also fired | Captured output plus application/explicit-stop reason; no adoption; do not mislabel as user timeout |
| Spawn/transport/anchor failure or unconfirmed stop | null | Only if own timeout/abort fired | Captured output plus bounded failure/cleanup-unconfirmed reason; no successful adoption or invented exit0 |
No new public result field or blanket rejected run_bash promise is needed for asynchronous process failures. Keep pre-existing argument/cwd validation exceptions unchanged. The existing executor maps child error to TerminalResult(null, error text); adapt that behavior to launch/control failures. Clear executor timers/AbortSignal listeners exactly once when completion is claimed, flush the control decoder's buffered non-protocol bytes, and snapshot user output already received through the bounded settlement window. Do not discard partial output on failure, or await descendant-held pipes for completion. Keep background-output consumers attached through the lease when normal adoption occurs; detach only executor-owned listeners. Output/transport cleanup cannot itself block result settlement or erase the scope's unconfirmed-cleanup report.

Required focused tests: forced timeout and host-stop with no RESULT (P-008 shape) settle within stop budget with the above distinct timedOut mapping; unexpected control loss; command spawn error before STARTED; missing handshake; complete/exit/disconnect order permutations, duplicate and late RESULT, previously completed shell with later background stop, preserved partial stdout/stderr and no-EOF descendants. Assert both command completion and independent scope cleanup result; neither substitutes for the other. These are design obligations, not newly executed production tests.

### Verified Stop Sequence
Close admissions and include pending leases; use one total3s default drain budget, not3s per command. Existing agent/idle stop never closes this scope. Scope takes a fresh snapshot with live matching anchor identity before each group signal. Signal verified group TERM (anchor's caught handler preserves authority), wait up to500ms, re-observe all non-anchor live members even if command shell exited. If none, RELEASE anchor and confirm exit; outcome is stopped/already-exited only when the whole lease is confirmed absent. If members resist, reverify anchor and send one group KILL including anchor; poll within the shared remaining budget to confirm group absence and known member exits. Because KILL intentionally removes the anchor, no subsequent numeric-group signal is authorized after that step. If observation fails, group remains, or identity is uncertain, outcome is unconfirmed. Do not treat signal delivery, anchor loss or a failed query as success.

Batch observations by target and drain groups concurrently. Bound new OS inspections to≤500ms within the remaining collective budget and limit their output; preserve denial/malformed/timeout details. The same scope stop operation serves explicit stop_background_process, tool timeout/abort and host close; remove old observer.stopProcess policy and raw PID/group callers after both entry forms switch. Only the observer may translate a verified handle to an OS signal; no port-based or name-based authority. Platform birth checks and retained handles mitigate reuse, not all adversarial OS races; an unexpectedly dead anchor fails closed. Normal completed shell/adopted-survivor path must succeed—IMP-02 is no longer acceptable as an unconfirmed normal outcome.

P-007 demonstrates both candidate anchors preserve a live leader across fast command exit/adoption and graceful TERM; P-008 demonstrates TERM-resistant foreground work does not falsely complete and force removes the owned anchor+child. These are feasibility fixtures on macOS, not production integration. The bash candidate was locally detached by Node; Linux setsid and WSL bridge are source/primary-contract-based until their downstream tests.

## Desktop Shutdown Contract
Extract a small cached shutdown coordinator under electron/application. In will-quit, preventDefault until stop settles; subsequent quit attempts reuse it. Broadcast app-quitting once; after success mark complete and resume app.quit once without recursion. Cache a Promise, not only a boolean that lets later callers return before shutdown finishes. Ordinary closing the last macOS window is still not app quit.

BaseServerManager.stopServer keeps managed-child-only authority. Use20s graceful backend budget then owned-child force termination and2s confirmation budget; no unbounded close wait. Child exit and pipe close are distinct; inherited pipe handles must not masquerade as a live backend. Nonzero cleanup exit, forced fallback or unconfirmed exit is an explicit shutdown failure, not clean restart success; StatusManager must not launch a replacement within that failed restart attempt. A later explicit retry can proceed with fresh port diagnosis. Windows uses the concrete managed-child IPC entry below BEFORE any tree-force fallback; taskkill without /f is removed as the purported graceful entry. No advisory port owner is signalled.

Application stop attempts backend AND browser-runtime teardown even when one fails, aggregates failures and flushes logs.30s total desktop quit ceiling leaves bounded completion headroom; on failure/ceiling record incomplete shutdown and use nonzero exit rather than claim clean success. No recursive timer calling app.quit. Under the normal verified path, quit only follows cleanup. Forced OS kill is outside R1.
