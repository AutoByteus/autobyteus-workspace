E-001..021 and P-001..008 plus IMP-01..03 in the canonical investigation establish three independent problems: missing application-lifetime ownership of native command groups, false-success leader-only termination, and generic desktop conflict handling. Desktop quit also fails to await cleanup. Existing native background managers belong to transient agent contexts; ending an agent is intentionally not the requested cleanup boundary. ## Terminology
Owned command group: process execution target + process group established by a native command this host launched, with current identity evidence. Port owner: advisory OS observation only; never cleanup authority. Command scope: runtime-only host lifetime, distinct from agent lifetime and background-output records. Group anchor: internal persistent session/group leader, NOT the user command shell or a displayed background process. Command result: completion of the user command shell, not exit of the anchor.

## Spine Narratives / Ownership Map
DS-001 retains current generation cancellation and readiness logic. Availability checks both required IPv4 client127.0.0.1 and bind0.0.0.0 addresses (sequential temporary binds with guaranteed close). Only EADDRINUSE enters conflict polling; other errno fails honestly. At expiry do one bounded owner lookup, not a repeated OS-command loop. Recheck after a failed launch only after its owned child has exited; a live own backend is not diagnosed as external. Guards do not claim to reserve the endpoint.

DS-002 establishes and retains group ownership BEFORE the user command is allowed to start, not only when a tool finishes. NativeCommandProcessScope is created once per host, passed through process provider factory → native factory → explicit AgentConfig.nativeCommandProcessScope → context → manager/executor. AgentConfig.copy retains that reference. It is not serializable initialCustomData. Core standalone consumers may own their own explicitly constructed scope; no process-global registry. An unhosted manager's local scope is its own lifecycle, not a server fallback. Hosted factories require the supplied host scope. Both start_background_process and run_bash use the same AnchoredCommandLauncher; in-flight commands are registered before START authorizes user code, and retain the same anchor through their result/adoption. Ending an agent or losing its context does not release a live group.

DS-003 freezes new native command admissions, drains owned groups early in Fastify preClose, then executes ALL existing lifecycle/provider/resource cleanup. Native drain returns a report instead of throwing in preClose; final onClose aggregates/throws incomplete cleanup after other cleanup attempts. Startup-failure cleanup also closes the scope even if app/hooks were not fully created. Studio and standalone use the same small host-shutdown integration helper, not two versions of the policy. Direct backend SIGTERM and the Windows child IPC request enter the same ServerProcessShutdown owner; it exits nonzero on incomplete cleanup. The old local signal-only closure is removed, not left as a second owner. Desktop observes termination, not a successful kill call.

DS-004 serializes only plain diagnostic data. All snapshots (including getStatus) carry the same current value. Restart/starting/running clears previous details. Stale async diagnosis cannot overwrite a newer generation. UI does not parse error prose to choose recovery.

## Bounded Local Spines / Concrete Ownership And Termination Contract (D3)
Parent owner: NativeCommandProcessScope; states open → closing → closed, one shared close promise. Scope owns admission, group lifetime and the TERM/verify/KILL/release sequence. ProcessGroupObserver is the bounded OS observation/signalling mechanism, not another lifetime coordinator. Manager owns per-agent output/tool records. Launcher creates one anchored group and reports events; it does not decide host shutdown policy.

### Retained Group Anchor — resolution of IMP-DI-001
D2's snapshot-overlap premise is replaced, not patched with faster polling. Create an internal group/session leader **before** user code; keep it alive for the entire native command-group lifetime, including after the user shell returns and after its agent ends. Its verified live identity pins the group number, so adoption observes members of a still-owned group rather than reclaiming an old numeric PGID. Never transfer authority from a dead command shell to an unanchored group.

`AnchoredCommandHandle` has one execution target (host or exact WSL distro), one fixed anchor identity/group, command-root PID when available, output streams, command-result promise, anchor-exit notification and release control. It is in-memory and scope-owned, not a user-visible process or stored run config. POSIX retains the actual ChildProcess and exit state plus observed birth identity; WSL retains its exact bridge child/control channel and Linux anchor PID/PGID/SID/birth identity. Later frames may not change anchor identity. User command/output records reference this same handle, not copies of its authority.

**POSIX launch:** spawn a small self-contained Node anchor with the current runtime executable, `detached:true`, stdio ignore/pipe/pipe/ipc. Keep its script in a static TypeScript string module (no runtime .ts execution, generated source file or asset-copy dependency). When the host runtime is Electron, explicitly set its Node-mode launch flag for the anchor only; do not leak that extra flag into user-command environment. The launcher obtains resolver command executable/args/cwd/env, and sends those as data on IPC only after readiness, scope registration and OS verification. Anchor uses spawn with `detached:false`, user stdin ignored, stdout/stderr inherited; the resolved shell therefore joins the anchor's exclusive session/group. No user source is interpolated into anchor code. IPC emits READY(anchor PID), STARTED(actual command PID), RESULT(actual code and signal); Node child exit, not pipe-close, produces RESULT. A successful result does not exit the anchor. Anchor catches TERM with a handler (not inherited ignore disposition), remains alive during graceful drain, and exits only on explicit RELEASE or terminal failure. IPC message listener keeps it alive without busy-loop polling. Existing Node detached contract establishes a new POSIX session; verify PGID==anchor PID before START. On macOS do not use nonexistent ps sid field; the actual detached ChildProcess plus live PGID/birth check is the authority.

**WSL launch:** do not require Node or Python inside the distro. Use its existing bash capability with Linux util-linux `setsid --wait` to run a small static bash anchor script: `wsl -d <selected distro> --cd <resolved cwd> --exec setsid --wait bash --noprofile --norc -c <anchor script> <argv0> <nonce> <resolved shell> <shell args...>`. Argument vectors carry user command as data; no command-source concatenation into the anchor. `setsid --wait` handles the possible intermediate fork and keeps the bridge associated until anchor exit. The anchor PID is the Linux leader reported by the script, NEVER the Windows wsl.exe PID or an assumed setsid PID. Before START, independently observe the reported PID within that exact distro and require PID==PGID==SID, non-zombie status, and birth identity (Linux /proc start ticks or equivalently precise platform birth token), plus the exact ready exchange from the captured bridge. This establishes a new, exclusively launched session/group; a mere old PID/PGID marker is insufficient. If setsid or identity inspection is missing/unsupported, fail command launch clearly before user code. No unsafe fallback to the current unisolated group and no automatic install. This is an operational dependency/error case to test, not live WSL certification.

The WSL anchor uses stdin solely as control and stderr for a bounded nonce-framed control stream; user shell stdin is /dev/null and cannot consume START/RELEASE. Use a128-bit fresh nonce and anchored exact READY/STARTED/RESULT grammar, bounded buffering and split-frame tests; strip only valid frames, preserve every other stderr byte. READY is emitted before user code, and parent verifies its identity before START. START is accepted once; script launches the resolved shell as an asynchronous child with job control off, reports its actual PID and waits for that command, NOT all descendants. The wrapper does not exec the command or exit when it returns. TERM uses a caught trap, not ignored disposition; wait retries after a trapped interruption while the child still lives, never fabricates a successful result. Once command ends, report its shell exit status and remain in a control-read loop; a caught TERM must not break that loop. Normal command args/cwd/env/stdio remain as resolved today. WSL command exit status follows existing shell/bridge semantics; POSIX keeps exact Node code/signal. Native tools' timeout/abort result formatting remains their current contract. User code deliberately killing the internal anchor or leaving the session/group is outside the ordinary retained-survivor guarantee; it is reported as uncertainty, not reclaimed by guessing.

Anchor readiness gate has bounded1500ms wait (consistent with current background WSL identity wait), clipped by tool/host deadline. Initial proof failures or scope close before START close the captured control channel; a gated anchor exits without executing user code. Confirm its exit; force only the captured host child when necessary, never signal an unverified Linux group. Once START is committed, scope owns the handle even if STARTED/result delivery fails. Closing an admission race cannot unregister the anchor or authorize a late START. Late callbacks only complete/clean their own lease, not start more work. Unexpected control loss/anchor exit is an incomplete ownership result; preserve known identities for diagnostics and do not reauthorize by PGID. Normal parent disconnection causes anchor exit nonzero; crash recovery is not promised.

### Command Result, Adoption And Retirement
`run_bash` completes from RESULT of the actual resolved shell, including fast/empty/nonzero commands; it does not wait for anchor exit or descendant-held output pipe close. Its existing short adoption delay can remain, but every group observation now has the same live anchor on both sides. Enumerate remaining command members, excluding anchor, and adopt their real PIDs while retaining the lease. `start_background_process` returns the real command PID from STARTED, not anchor PID; when that command ends, its status follows RESULT, while the lease continues to own any descendants. Output buffering/list/stop tools never display anchor/control frames. Stop by a recorded process resolves to its retained group lease, matching existing group-stop semantics.

Only release an anchor after the user command has completed AND a successful current group observation finds no other live members. Confirm anchor/bridge exit after RELEASE; release is not a stop command and must never be used with live command members. Immediate empty foreground completion retires promptly. For retained groups, a single scope maintenance timer (1s, unref, batched bounded observation per target) retires naturally emptied groups; no per-command polling loops or per-agent host owners. This timer is garbage collection, NOT ownership continuity: ownership remains anchored even when observation is delayed or fails. Unknown inspection retains the lease; it does not mean empty. Suspend/drain maintenance with the scope close promise to avoid release/signal races. New commands cannot be launched through a used lease. One small anchor per live group is the deliberate resource cost of proof, not one permanent process per historical command.

### Verified Stop Sequence
Close admissions and include pending leases; use one total3s default drain budget, not3s per command. Existing agent/idle stop never closes this scope. Scope takes a fresh snapshot with live matching anchor identity before each group signal. Signal verified group TERM (anchor's caught handler preserves authority), wait up to500ms, re-observe all non-anchor live members even if command shell exited. If none, RELEASE anchor and confirm exit; outcome is stopped/already-exited only when the whole lease is confirmed absent. If members resist, reverify anchor and send one group KILL including anchor; poll within the shared remaining budget to confirm group absence and known member exits. Because KILL intentionally removes the anchor, no subsequent numeric-group signal is authorized after that step. If observation fails, group remains, or identity is uncertain, outcome is unconfirmed. Do not treat signal delivery, anchor loss or a failed query as success.

Batch observations by target and drain groups concurrently. Bound new OS inspections to≤500ms within the remaining collective budget and limit their output; preserve denial/malformed/timeout details. The same scope stop operation serves explicit stop_background_process, tool timeout/abort and host close; remove old observer.stopProcess policy and raw PID/group callers after both entry forms switch. Only the observer may translate a verified handle to an OS signal; no port-based or name-based authority. Platform birth checks and retained handles mitigate reuse, not all adversarial OS races; an unexpectedly dead anchor fails closed. Normal completed shell/adopted-survivor path must succeed—IMP-02 is no longer acceptable as an unconfirmed normal outcome.

P-007 demonstrates both candidate anchors preserve a live leader across fast command exit/adoption and graceful TERM; P-008 demonstrates TERM-resistant foreground work does not falsely complete and force removes the owned anchor+child. These are feasibility fixtures on macOS, not production integration. The bash candidate was locally detached by Node; Linux setsid and WSL bridge are source/primary-contract-based until their downstream tests.

## Desktop Shutdown Contract
Extract a small cached shutdown coordinator under electron/application. In will-quit, preventDefault until stop settles; subsequent quit attempts reuse it. Broadcast app-quitting once; after success mark complete and resume app.quit once without recursion. Cache a Promise, not only a boolean that lets later callers return before shutdown finishes. Ordinary closing the last macOS window is still not app quit.

BaseServerManager.stopServer keeps managed-child-only authority. Use20s graceful backend budget then owned-child force termination and2s confirmation budget; no unbounded close wait. Child exit and pipe close are distinct; inherited pipe handles must not masquerade as a live backend. Nonzero cleanup exit, forced fallback or unconfirmed exit is an explicit shutdown failure, not clean restart success; StatusManager must not launch a replacement within that failed restart attempt. A later explicit retry can proceed with fresh port diagnosis. Windows uses the concrete managed-child IPC entry below BEFORE any tree-force fallback; taskkill without /f is removed as the purported graceful entry. No advisory port owner is signalled.

Application stop attempts backend AND browser-runtime teardown even when one fails, aggregates failures and flushes logs.30s total desktop quit ceiling leaves bounded completion headroom; on failure/ceiling record incomplete shutdown and use nonzero exit rather than claim clean success. No recursive timer calling app.quit. Under the normal verified path, quit only follows cleanup. Forced OS kill is outside R1.

Explicit AppUpdater install continuation must await the same application stop before invoking existing quitAndInstall, because the installed updater may start installation before emitting quit. Add a prepare-for-install callback at its composition boundary; failed preparation becomes existing install error, no installation. This is lifecycle preservation only: tests use a mocked updater, no download/install. Normal auto-install-on-quit stays behind final quit; do not call app.exit(0) to bypass it. Preserve existing isolated updater-disabled behavior.

## Windows Managed-Child Shutdown Entry / Startup Cancellation (AR-001)
**Transport and association.** Keep the existing Node-mode child spawn, not HTTP, public port, process-name lookup or a new supervisor. WindowsServerManager changes stdio to ['ignore','pipe','pipe','ipc']; its existing env sets ELECTRON_RUN_AS_NODE=1. Immediately attach ManagedBackendShutdownClient to that captured ChildProcess, before async readiness waits. Its lifetime is that child, not whichever PID later occupies the port. Parent listens to that child's message/error/disconnect/exit events; no response from a different launch/generation is accepted. macOS/Linux keep SIGTERM as their external trigger; both triggers use the same backend shutdown owner. No forced SIGTERM emulation on Windows.

**Small wire contract.** JSON-serializable strings only: `autobyteus.embedded-server.shutdown.v1:ready`, `:request`, `:complete`, `:failed` (the latter three use the same full prefix). No PID, command, handle transfer, arbitrary object dispatch or serialized error. Adapters match exact literals and ignore other messages. One stop promise per captured child, one request, no retry queue or correlation field: the dedicated channel and single child lifetime are the identity. Keep protocol literals in the two transport endpoint modules and pair them with a cross-boundary contract test, following the existing separately packaged platform-fatal transport convention; do not introduce a general contracts package for four strings or duplicate domain state models.

**Backend owner and initialization.** Add `ServerProcessShutdown` in server shutdown code. Construct/register it at the FIRST synchronous step of startConfiguredServer, before asynchronous process prerequisites or Studio creation; it installs process message and POSIX signal adapters, then advertises :ready only when the request latch is active. This is control readiness, NOT HTTP readiness. Before that point the parent waits on the same20s stop deadline; an import/config failure exits nonzero and is not mislabeled as graceful cleanup. No guarantee is made for a hung pre-runtime import.

The owner has a single shutdown request latch and single completion promise. During startup it marks cancellation immediately but does not close resources concurrently with initialization. The startup path checks cancellation before each subsequent asynchronous initialization/listen/recovery/background-task stage and after the active stage settles. A control-cancellation sentinel is handled separately from startup fatal errors (never wrapped into an HTTP initialization failure). A startup-settled barrier resolves in finally, including errors; it does not wait on the shutdown promise (no circular wait). The shutdown promise waits that barrier, then invokes the latest registered cleanup authority once. Before Studio ownership transfer this is the existing prerequisite unwind; after successful buildStudioServer transfer it is app.close, including native scope preClose and the remaining host resources. Transfer cleanup authority before the next cancellation checkpoint; do not clear prerequisite ownership flags without registering the replacement. Partial Studio construction continues to unwind through its existing failure cleanup plus the scope closure already required by D1. Cancellation during prepare/listen/recover waits that active stage, closes the fully constructed app, and never advances to the next stage. If an initializer hangs past the parent deadline, outcome is unconfirmed/force fallback, not success.

After normal startup settles the same request directly invokes app.close. Repeated SIGINT/SIGTERM/request events reuse the single completion. Standalone host close still uses its public host owner/native-scope integration; no desktop IPC is added to unrelated standalone launch modes. Direct non-IPC CLI startup has only signal adapters and no ready message.

**Completion and budgets.** After all cleanup attempts, backend emits :complete only for confirmed successful cleanup, or :failed for aggregate failure, then exits0 or1 respectively. Bound the process.send flush callback to250ms; failed/unconfirmed flush exits1 rather than falsely acknowledging success. Native3s drain remains inside the20s graceful child-stop window. The parent send callback means transport enqueue only, never cleanup. Successful Windows stop requires both :complete AND actual child exit0 within the20s window; account for result/exit event ordering and ignore inherited stdout/stderr close delays. :failed, nonzero exit, disconnect/missing result, invalid protocol or a timeout is incomplete, never clean success.

At the20s graceful deadline, if the captured backend is still alive, invoke taskkill /pid <owned child pid> /f /t with bounded subprocess lifetime and allow at most2s additional exit confirmation. Check captured child state immediately before force action and preserve existing ownership protections; never chase a reused numeric PID or diagnostic listener. A child already exited is never signalled again. Force/error remains a failed stop even if the Windows tree exits; it does NOT prove WSL command groups drained. No new backend is launched in that failed restart attempt. Future user retry rechecks fresh port state. On app quit, existing D2 aggregate/nonzero outcome and30s ceiling apply. No-PID/spawn-error and already-exited cases report what was established; do not erase an unconfirmed live child reference to manufacture stopped state.

**Desktop startup cancellation.** stopServer first cancels the pending startup generation, independently of the child's capability readiness; no-child/pre-spawn cancellation returns without a request or later launch. If a child already exists, stop retains its control client even though HTTP readiness is cancelled. If :ready was already received send immediately; otherwise latch stop intent and send once on :ready within the ORIGINAL20s deadline. A ready/response from a cancelled generation may finish that child's stop but cannot emit RUNNING or alter a newer startup snapshot. Cache stop through concurrent quit/restart calls. Missing IPC capability is not a legacy compatibility fallback: fail honestly, then bounded owned-child force fallback if necessary.

**Tests and evidence boundary.** P-006 proves ready/request/completion/exit signalling with real Node spawn+IPC and both success/failure on macOS, NOT cleanup implementation or Windows certification. Tests must exercise the real server entry/close and Windows manager transport contract (platform force action mocked on macOS), requests before readiness/during prereqs/build/listen/recover, duplicate request/signal, failed ready/send/flush/disconnect, complete-without-exit and exit-without-complete, stale child messages, nonzero cleanup and force ordering. Changed-build Electron Node-mode IPC compatibility is a downstream packaging test; task-local Electron binary was absent during design and the installed app was not used. No live Windows certification is demanded or claimed.

## Diagnostic Interface / UI

## Key Tradeoffs / Risks
A persistent small anchor per live group adds launch/resource overhead but gives continuous authority without probabilistic snapshot overlap or stopping previews when an agent ends. POSIX uses the already available Node runtime; WSL uses existing bash plus explicit setsid, with a truthful pre-launch unsupported-capability error instead of unsafe grouping. The implementation must measure fast-command latency and natural-exit retirement, preserve byte output/result semantics, and test packaged Electron Node-mode anchors without touching the installed app. WSL live execution remains unavailable evidence, not a guaranteed tested result.
Explicit runtime scope adds limited plumbing but prevents orphaned per-agent state and preserves user-approved agent lifetimes. Verified cleanup can report failure where old code said success; that honesty is necessary.20s graceful desktop stop accommodates existing server teardown (historical clean exit took~7.7s), while native drain has its own early3s bound. Process inspection has OS race/permission limits; no certainty claim for arbitrary escaped daemons. A bind test can race launch; endpoint recheck is diagnosis, not reservation. macOS runtime evidence is not Windows certification. Installing this change is outside task, so installed app behavior will not change until a later authorized build/install.
