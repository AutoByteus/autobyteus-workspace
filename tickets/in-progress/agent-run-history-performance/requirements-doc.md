# Agent Event Monitor Recent-Activity Performance Requirements

## Status (`Draft`/`Design-ready`/`Refined`)

`Refined for architecture round 12` — source commit `aa9705a28057b369fd63ed7199c1f1f5c655df0e` remains the technical behavior baseline but is pre-supersession evidence for placement/styling and does not authorize API/E2E. The user approved one centered ChatGPT-like return control: quiet white circle, subtle neutral border/shadow, simple dark downward arrow, no visible wording, and no feed-height reservation. Cursor expiry uses this exact same treatment; it introduces no amber/warning variant.

## Goal / Problem Statement

Opening an agent or team-member row currently reconstructs and transports the run's complete raw-trace corpus, including every completed archive segment, and the frontend then deduplicates, retains, and mounts the resulting unbounded history. Long-running agents therefore make row selection slow and produce an unusably long Event Monitor scrollbar.

The normal Event Monitor must instead open as a fast rolling window over only the active raw-trace file. It must initially show and retain at most 100 recent visual events, continue rolling as live events arrive, preserve still-mutable event identities when completed events are available for eviction, and never consult archived raw-trace segments for this surface. When the user deliberately scrolls to the top, the surface may page backward through the current active trace in internal additions of at most 50 earlier canonical events until reaching that active trace's beginning. The internal batch size must not appear in user-facing copy, and ready/loading/beginning/recovery chrome must not reserve vertical feed space. Archived files remain stored and unbrowseable from this surface. The unused conversation copy control must be removed.

## Investigation Findings

1. `LocalMemoryRunViewProjectionProvider` currently calls `getRunMemoryView` with `includeArchive: true` and no limit. The storage layer reads all complete archived segments plus `raw_traces_active.jsonl`, deduplicates and sorts them, and the projection layer reconstructs the whole corpus.
2. The GraphQL projection queries have no window argument; they return all `conversation[]` and `activities[]` entries. Tool arguments/results are duplicated between the two arrays.
3. A real archived `x_marketer` run returned 1,725 conversation entries plus 794 Activity entries in a 47,537,621-byte response. The current frontend conversation dedupe took about 27.9 seconds for those 1,725 entries in an exact local benchmark.
4. The conversation feed mounts every message and assistant segment; the Activity feed separately mounts every Activity record. Neither retained state nor DOM work has a duration-independent bound.
5. Source inspection confirms that successful compaction rotates the settled prefix into an archive and rewrites the active file from the compaction boundary forward. The active file is therefore the correct normal recent-activity source. It is not a formal hard size bound when compaction has not happened: the largest observed active-only file was about 5.08 MB / 988 records and projected to a 9.09 MB GraphQL response with 609 conversation entries and 379 activities. Its current frontend conversation dedupe still took about 906 ms.
6. Active team restore currently requests projections for all members, and active standalone discovery can hydrate unselected runs. Making every normal projection active-only and server-bounded prevents those background paths from reintroducing archive-scale work even before a row is focused.
7. The workspace header contains a separate `CopyButton` and eagerly constructs a full joined conversation string. The user stated that this control is unused and explicitly requested its removal.
8. Architecture review finding `AR-001` identified that a simple oldest-edge trim contradicts the requirement to evict completed events before still-mutable ones. The refined contract below defines completion by visual kind, completed-candidate eviction, and a deterministic hard-cap fallback for the reachable case of more than 100 concurrently mutable events.
9. Architecture review finding `AR-002` identified that `conversation.updatedAt` changes for non-visible protocol traffic and therefore cannot drive the unseen-activity button. The refined contract requires an explicit visible-presentation revision emitted only after an actual bounded center-feed change.
10. Implementation source review finding `CR-001` proved that a transient append can report a handler change and then be synchronously evicted by completed-first enforcement, leaving the final bounded presentation identical while the reviewed effect-OR-eviction contract still increments the revision. Revision decisions must therefore compare the net bounded presentation before the mutation with the final bounded presentation after enforcement.
11. Implementation source review finding `CR-002` found an existing team reopen path that replaces a reused member conversation without resetting the presentation baseline. Every conversation/context replacement path must reset the revision baseline unless subscribed live runtime state is intentionally preserved.
12. Architecture review finding `AR-003` proved the first witness field proposal was broader than the actual central card: tool results/logs are Activity-only, and raw argument-object replacement can leave the derived command/path/text summary unchanged. The refined witness contract is semantic and central-render-specific; these non-visible changes must remain no-ops while real card/static/media/error/inter-agent/usage/compaction changes remain detectable.
13. Delivery live validation connected the integrated frontend to an older remote backend on port 8000. That backend still has `includeArchive: true` and lacks the recent projection policy, while the integrated backend with `includeArchive: false` was running separately on port 29695 against another data root. The multi-minute observation therefore did not exercise the server half of this solution and cannot by itself establish an `AC-009` failure. A corrected run must use one integrated frontend/backend candidate and a safely isolated, consistent snapshot of the representative data.
14. Architecture finding `AR-004` identified that static provider evidence, response exclusion, and instantaneous FD inspection cannot independently prove the absence of transient archive opens, and that live-source equality becomes non-attributable after the legitimate live owner restarts. Corrected validation uses path-only runtime auditing when available and separates copy identity, validation-process access, snapshot raw-trace immutability, old-owner activity, and mode-specific live-source equality.
15. Architecture finding `AR-005` identified that representative execution outcomes must follow the team's API/E2E workflow rather than route directly from a design decision table. API/E2E executes after architecture approval; every Fail first returns to code review for origin classification, Pass receives proportional test-code review before delivery, and Blocked reports the exact dependency to the user.
16. After testing the integrated latest-100 behavior successfully, the user refined the UX: initial selection must remain latest-100 and fast, but an explicit top-of-feed action should add at most 50 earlier events per request, stop at the beginning of `raw_traces_active.jsonl`, and never cross into an archived segment. This supersedes the earlier “no Load earlier affordance” decision while preserving the archive exclusion boundary.
17. Architecture finding `AR-006` found that the first paging design declared `eventId` only at the transport boundary: current message/reasoning replay drops raw IDs, current historical conversion semantically merges equal entries, and current message/segment DOM keys are ordinal. The page path must preserve distinct source identities and deterministic per-visual keys through actual rendering and scroll anchoring.
18. Architecture finding `AR-007` found that reusing the normal conversation projection entry would transport raw `toolResult` and invoke recursive semantic serialization even though the central tool card does not render result/log detail. Earlier pages require a dedicated typed central-presentation DTO and linear identity conversion instead.
19. Hands-on Electron verification on 2026-07-21 showed that the implemented sticky `Load 50 earlier` pill remains visible throughout the feed, exposes a server-owned batch size that has no user meaning, and reserves a large top band. When unseen activity exists, the simultaneous wide `New activity · Jump to latest` pill obscures additional content and makes the center surface visually noisy. The feed already owns scroll position and request coalescing, so earlier paging can be triggered by a deliberate user scroll reaching the top and represented by a zero-layout progress overlay; browse exit still needs an explicit control because it discards the frozen browse snapshot rather than merely scrolling a DOM list.
20. The round-10 lower-right arrow implementation did not account for `SkillImprovementComposerCta`, which conditionally renders the existing **improve skills** action at the lower-right immediately above the composer. The user supplied the live coexistence screenshot and a centered reference, then explicitly approved bottom-center placement for the arrow. This is a bounded cross-feature placement correction: the skill action remains unchanged at lower-right, while the conditional return arrow is centered within the Event Monitor feed above the composer and never joins or stacks with that action.
21. Architecture round 11 accepted that centered placement and ownership, but found that stale design guidance and round-10 source still gave cursor expiry an amber warning variant. That branch contradicts the user's approved single quiet neutral arrow. Expiry changes recovery semantics only; ordinary unseen, frozen browse, released-page, and expired states must have the exact same target, geometry, white surface, neutral border/shadow, dark glyph, focus treatment, and accessible name.

Detailed evidence is recorded in `investigation-notes.md`. Observable behavior is specified in `history-window-ui-ux-spec.md`.

## Recommendations

1. Change the normal local replay provider to read `raw_traces_active.jsonl` only (`includeArchive: false`). Read and normalize the active file as a complete lifecycle source, build replay events, then select the newest 100 canonical replay events before building the existing projection bundle. This preserves in-file tool-call/result correlation while bounding transport and frontend hydration.
2. Keep the normal GraphQL projection intrinsically active-only/latest-100, and add explicit standalone-run and team-member active-trace page boundaries for on-demand earlier browsing. The page size is server-fixed at 50 earlier canonical replay events, the cursor is opaque and active-trace-generation-bound, and neither operation accepts an archive selector or arbitrary page size. Each page event preserves one stable source/lifecycle identity and contains only typed central visual variants with deterministic subvisual IDs; it never reuses the result-bearing normal conversation projection entry.
3. Introduce one frontend Event Monitor window policy that defines completion/mutability and enforces the 100-visual-event cap for both historical hydration and live event dispatch. Evict oldest completed candidates first; only when fewer completed candidates exist than the overflow may the hard-cap fallback evict oldest mutable candidates. Defensively apply the same candidate policy to the final mounted center feed.
4. Bound per-run Activity state to 100 recent records. No Activity-panel redesign is required.
5. Preserve existing bottom-follow behavior. Drive it from a cheap explicit visible-presentation revision based on a net pre-mutation/post-enforcement bounded-presentation witness, not `conversation.updatedAt` or a transient handler effect. When the user has scrolled upward inside the recent window, a net visible append/update/eviction must not force the viewport downward and must expose only one compact bottom-center downward-arrow control until the user returns to the bottom. Use a quiet white circular surface, subtle neutral border/shadow, simple dark arrow, no visible text, explanatory tooltip, count, or layout footprint, and only a non-visual accessible name. Keep the existing conditional **improve skills** action at lower-right; the two controls must not overlap, stack, or trade positions at wide or narrow widths. Non-visible protocol traffic and an inserted event that is synchronously evicted while leaving the final presentation identical must not expose the action.
6. Remove the workspace header conversation `CopyButton` and the eager full-conversation string computation that only served it.
7. Keep paged history outside canonical live conversation and Activity state. Reaching the top through a user-originated scroll establishes a server-consistent active-trace snapshot, preserves the viewport when older events are inserted, keeps live updates running separately, and exits back to the current latest-100 state through the same compact downward-arrow control.
8. Bound the resident browse window to 300 central visual events. Further top reaches advance the window by one server-fixed page and release the farthest newer page; the full browsable range remains the current active trace, not the resident DOM/state size.
9. Remove the persistent sticky earlier-history control and all visible page-size wording. Idle and beginning states render no top chrome. While an earlier request is in flight, show a small absolutely positioned three-dot progress indicator that does not affect the first event's offset or feed scroll height. Do not initiate a page on mount or chain pages merely because a prepend/short feed remains near the top; one request requires one deliberate transition to the top, with hysteresis before another request. Rare retry/expired recovery uses compact overlay controls and the existing minimal return arrow rather than a banner or pill.

## Scope Classification (`Small`/`Medium`/`Large`)

`Large`

Rationale: The completed performance change already crosses the local run-history projection policy, standalone/team projection consumers, frontend historical/live state, Event Monitor scrolling, Activity retention, localization, and copy cleanup. The approved refinement adds explicit GraphQL pagination boundaries, opaque cursor/generation policy, source-to-DOM event/subvisual identity, a closed central-only page projection, isolated linear frontend browse conversion/state, bounded page turnover, compaction-expiry recovery, and additional localized interaction states. It still avoids archive access, storage migration, and a full-history schema.

## In-Scope Use Cases

- Select or reopen a long-running standalone agent and quickly see its latest active-file activity.
- Select a team member without reconstructing that member's archived trace segments.
- Restore/discover active runs without background archive-scale projection work.
- Follow live activity at the bottom while the Event Monitor rolls past 100 visual events.
- Scroll upward within the recent window without being pulled down, then return through a compact downward-arrow affordance when needed.
- Reach the top to load one internal page of earlier canonical events from the same current active trace, continue until its beginning, and return to latest without seeing an internal page count or loading an archive.
- Continue viewing existing collapsed Thinking and tool cards with no disclosure redesign.
- Use the Activity panel with recent bounded data and no new visible workflow.
- Use the workspace after the conversation copy control has been removed.

## Out of Scope

- Loading, paging, searching, exporting, or otherwise exposing archived raw-trace segments in the Event Monitor.
- A separate archive/history screen, any paging into archived raw-trace segments, or an unrestricted full-history control.
- Deleting, truncating, migrating, compressing, or changing retention of authoritative raw traces.
- Changing compaction or raw-trace rotation behavior.
- Redesigning Thinking, tool-card, Activity-panel, composer, Team Communication, Task Delegation, or Memory Inspector presentation.
- Changing Skill Improvement eligibility, action behavior, copy, or lower-right composer-context placement; it is included only as a required coexistence state for the centered Event Monitor arrow.
- Eliminating the existing conversation/activity transport duplication in normal projection or creating a canonical archive timeline; active-trace page responses may use a dedicated central-feed projection shape.
- Providing a replacement full-conversation copy/export action.

## Functional Requirements

- `REQ-001` Every normal standalone and team-member run projection used by the workspace Event Monitor must read only the subject's active raw-trace file and must not open or reconstruct completed archived raw-trace segments.
- `REQ-002` The backend projection must select at most the latest 100 canonical display/replay events from the normalized active-file events before constructing the returned conversation and Activity projection arrays.
- `REQ-003` In normal latest mode, the central Event Monitor must render and retain at most 100 recent visual events per run. A user message counts as one event; each assistant text, Thinking, tool, media, task/inter-agent, or error segment counts as one event; each center-timeline compaction row counts as one event. Streaming deltas and lifecycle updates to an existing segment/card do not count as separate visual events. When mutable events are protected under `REQ-004`, the window is the protected mutable set plus the newest completed events that fit, rather than a blind chronological tail. Explicit active-trace browse mode is governed separately by `REQ-010`–`REQ-012`.
- `REQ-004` Live events must append or update exactly once. To enforce the hard 100-event cap, eviction must remove oldest completed candidates before any still-mutable candidate. Completion means: user/static notification/inter-agent/media/error events are complete after atomic insertion; streamed text/Thinking is complete after its `SEGMENT_END` marker or containing AI message completion; tool/file/terminal cards are complete only in terminal `success`, `error`, `denied`, or `interrupted` status; center compaction rows are complete only in `completed` or `failed` phase. If overflow remains after all completed candidates are exhausted—a reachable case such as more than 100 concurrently mutable segments—the deterministic hard-cap fallback must evict the oldest mutable candidates, preserve the maximum at 100, and allow a later update carrying that stable identity to create at most one source-limited newest-edge representation. No archive lookup or duplicate retained representation is allowed. The backend historical snapshot remains the newest 100 canonical replay events under `REQ-002`; after hydration, its projected nonterminal tool/compaction states participate in the same client completion and eviction policy as live continuation.
- `REQ-005` When the Event Monitor is at the bottom in normal latest mode, a net bounded-presentation change must continue to follow the bottom. When the user scrolls upward, a net retained visible append, content/lifecycle change, center-compaction change, or eviction-only presentation change must not force-scroll the viewport and must expose a compact icon-only downward-arrow affordance until latest is reached. The control is an absolute overlay centered horizontally within the Event Monitor feed, with its hit target's lower edge inset 8 px above the feed boundary and therefore above the separate composer sibling; it reserves no layout height and does not migrate to the lower-right at narrow widths. Its visible surface is a quiet white circle with a subtle neutral border/shadow and simple dark arrow. It shows no visible wording, explanatory tooltip, count, badge, or pulse and retains only a localized non-visual accessible name meaning “Jump to latest activity.” The lower-right remains available to the independently conditional **improve skills** composer action, and the two controls must not overlap at supported wide or narrow widths. In latest mode, manually returning to the near-bottom threshold clears unseen state. In frozen browse mode, manually reaching the bottom of the resident browse snapshot does not exit browse, reveal live state, discard pages/cursors, or clear the arrow; only explicit arrow activation performs that transition. “Net change” means the ordered bounded center presentation after mutation and enforcement differs from the ordered bounded center presentation captured immediately before mutation. Protocol messages that do not alter that final presentation, and transient events synchronously removed by enforcement such that the pre/post presentations are equal, must not increment the revision or expose the action. This behavior must not use the generic conversation timestamp, deep/full-payload serialization, or a transient mutation-effect OR condition.
- `REQ-006` Thinking and tool cards must preserve their current collapsed-by-default behavior and current explicit expansion interaction.
- `REQ-007` Per-run Activity store data must be bounded to at most 100 recent activity records, without adding a new Activity navigation or archive UI.
- `REQ-008` The separate conversation copy control in the agent workspace header and its dedicated eager full-conversation text derivation must be removed, with no replacement action.
- `REQ-009` Existing active and archived raw-trace files must remain unchanged and directly usable. The optimization is a read/display policy change only and must not migrate or delete stored data.
- `REQ-010` When the current active trace contains events earlier than the normal latest window, a deliberate user scroll that transitions into the top threshold must request one immediately preceding server-owned page of at most 50 canonical replay events in chronological order. Arming and firing require one current, unconsumed upward user-intent session created directly by a trusted wheel, touch, supported keyboard-scroll, or native-scrollbar interaction with the feed; scroll-position events alone can never create that authority. The session is consumed before the request and invalidated by run/subject change, request start, programmatic scroll/anchor work, interaction end/idle expiry, blur, or cancellation. After a request, queued API scroll events, scroll anchoring, media/layout reflow, continued wheel/touch momentum, and continued near-top position remain ineligible; another request requires the prior interaction to end, an input-quiet boundary, and a fresh user interaction that moves outside the re-arm distance and intentionally reaches the top again. No page is requested on mount or selection. The fixed batch size is an internal transport detail and must not appear in visible or accessibility copy. Ready and beginning states render no persistent top control or reserved space; loading uses a small three-dot absolute overlay that produces no layout shift, and rare retry feedback uses a compact icon-only zero-layout overlay. Repeated top reaches may traverse only `raw_traces_active.jsonl`; they must never open, reconstruct, or page into an archived raw-trace segment. Page transport must contain only the bounded semantic fields used by the central Event Monitor render/retained interaction; raw tool results, logs, Activity detail/context, and generic payload objects are forbidden.
- `REQ-011` Active-trace browsing must be an ephemeral view state separate from canonical live conversation and Activity stores. The first user-originated top reach must establish a server-consistent browse window consisting of the current latest 100 active replay events plus up to 50 immediately preceding events; later top reaches add at most 50 earlier events using an opaque cursor. Every canonical page event must carry a stable identity from its raw trace or tool lifecycle (with deterministic legacy fallback), and every rendered subvisual must use a deterministic identity derived from that event identity plus visual kind and ordinal. Distinct event identities must never be content-deduplicated even when content and timestamp are equal. Live state continues updating independently and must not force-scroll or mutate the frozen browse window. The compact downward-arrow affordance exits browse mode, discards its pages/cursors, and restores the current live latest-100 presentation. A compaction or active-file rewrite that invalidates the cursor must not fall back to archives; recovery keeps the same icon-only return arrow with the exact ordinary quiet-white/neutral-border/simple-dark treatment, without an amber/warning variant, explanatory status text, or persistent inline banner.
- `REQ-012` Active-trace browse mode must retain and mount at most 300 central visual events. When another internal earlier page would exceed that bound, the farthest newer browse page is released without moving the current top reading anchor. No persistent banner is added; the compact return-to-latest arrow remains the recovery path. The anchor and component disclosure identity must use the stable rendered subvisual IDs rather than array indices. This resident bound does not shorten the browsable source range: the user may continue through deliberate top reaches until the beginning of the current active trace.

## Acceptance Criteria

- `AC-001` Given a run directory containing both `raw_traces_active.jsonl` and one or more complete archived segments, opening its standalone or team-member projection performs no read/open of an archived segment and the result contains no archive-only event.
- `AC-002` Given more than 100 canonical display events in the active file, the projection is built from exactly the newest 100 events in deterministic chronological order; given 100 or fewer, all active-file events are eligible.
- `AC-003` In normal latest mode, a browser/component scenario with more than 100 mixed user messages, assistant text segments, Thinking segments, tool cards, and compaction rows observes no more than 100 mounted central Event Monitor visual events. With only completed events it confirms the newest 100 by stable identity/content; with a mix of completed and mutable events it confirms oldest completed candidates are evicted before an older mutable event.
- `AC-004` After at least 1,000 additional live append/update messages, the central Event Monitor remains at or below 100 visual events and the per-run Activity store remains at or below 100 activity records, with no duplicate live card/message. A deterministic 101-all-mutable scenario proves the hard-cap fallback evicts the oldest mutable event; a later update for that identity yields no more than one source-limited newest-edge representation and the bound remains 100.
- `AC-005` While pinned to the bottom in latest mode, a net visible append/update leaves the latest change visible. While scrolled upward or in active-trace browse mode, a net retained segment/card update, center-compaction change, membership/order change, or eviction-only presentation change does not force the viewport to the bottom, increments the explicit visible-presentation revision once, displays one localized icon-only downward-arrow overlay, and activating it exits browse mode if applicable, moves to current latest, and clears the control. Manually returning to the near-bottom threshold clears unseen only in latest mode. Manually reaching the bottom of a frozen browse snapshot leaves the browse presentation, pages/cursor, unseen state, and arrow intact until explicit arrow activation. The first top-triggered browse request returns at most the server-consistent latest 100 plus 50 earlier events; every later request returns at most 50 earlier events. Each top transition reaches a stable usable page within 2.0 seconds, records TTFB/total/payload/linear-conversion/hydration/anchor evidence, and does not block composer use or live-state ingestion. A tool fixture whose raw result contains a unique multi-megabyte sentinel produces byte-identical serialized central `events` to the result-null equivalent when all central fields/IDs are held constant (cursor/generation/timing metadata excluded), the sentinel/result/log fields are absent, explicit semantic tool status/summary/error still render correctly, and conversion performs no recursive walk of the result.

## Constraints / Dependencies

- Local application-owned raw traces remain the normal display authority across AutoByteus, Codex, and Claude runtimes.
- The active file may still grow when compaction has not occurred. The server must therefore bound returned canonical events even though reading the complete active file is accepted for this scope.
- Build tool interactions from the complete normalized active-file record set before selecting the latest replay events; raw-record tail slicing may split a call/result pair and is not the approved design.
- A tool call may have been archived while its result remains active. The Event Monitor must not read the archive to repair that card; source-limited active-file evidence is acceptable and must degrade safely.
- The normal projection's conversation/Activity semantics remain unchanged but gain active-trace page availability metadata. Dedicated standalone and team-member earlier-page queries use their existing explicit identity shapes and a server-owned opaque cursor; there is no generic ambiguous run/member selector, archive selector, client-chosen limit, or full-history response.
- Historical and live visual-event counting must share one frontend policy rather than independently guessing from message count.
- Completion/mutability classification and completed-first eviction must be shared by conversation retention, Activity retention, and final center presentation. Historical items without an active live lifecycle are treated as complete unless their projected tool/compaction status is explicitly nonterminal.
- The visible-presentation revision is ephemeral per `AgentRunState`. It starts/resets at `0` on initial historical hydration or any run/context conversation replacement, including the non-live replacement branch in `teamRunOpenCoordinator.mergeHydratedMembers`; subscribed live contexts that intentionally preserve their conversation also preserve their revision. It increments once only when a bounded lightweight pre/post presentation witness differs after enforcement, including a real eviction-only result, and does not increment for net no-op/non-visible messages. Run selection or revision reset establishes a new feed baseline and clears unseen state rather than showing the jump action.
- The witness is duration-independent and bounded by the 100-event presentation. It compares ordered visual identity plus the shallow semantic primitives actually rendered by, or used for retained interaction in, the central Event Monitor: text/Thinking content; user attachment identity/label/preview/open inputs; derived message and total token/cost text; the exact derived tool-card name, summary/path/command, status presentation, error, and approval/highlight interaction identity; static notification/inter-agent/media/error values; and the exact compaction-row primitives. It does **not** include Activity-only tool logs/results, raw argument-object identity, non-rendered source fields, generic timestamps, or payload references merely because they changed. Tool results/arguments are never recursively serialized and archived/full history is never scanned. Existing narrow render-presentation helpers must be reused so semantic replacement with equal visible/interactive values remains witness-equal.
- Page cursors are opaque, contain no filesystem path or archive selector, are bound to the authorized standalone/team-member subject, the active trace's rewrite generation, and an existing canonical event anchor, and remain valid across ordinary appends. A foreign-subject cursor is rejected; a missing anchor or changed generation returns a typed cursor-expired result. The page owner reconstructs lifecycle-correct events from the active file before selecting the page; raw-record slicing is forbidden because it can split tool call/result evidence.
- Page identity is a typed carrier, not transport-only metadata. Message/reasoning/compaction events use normalized raw-trace identity when present; tool call/result records share one tool-lifecycle identity; ID-less legacy records use a deterministic bounded-field fingerprint plus occurrence ordinal. The identity survives replay, page selection/DTO, page-only conversion, browse blocks, central presentation, `data-*` anchor lookup, and Vue keys. Each multi-visual event derives collision-safe subvisual IDs from `(eventId, visual kind, kind ordinal)`.
- The dedicated page DTO is a closed discriminated union of central user/text/Thinking/tool/media/compaction visuals. Tool cards contain only invocation identity, effective name, an allowlisted shallow string summary-input map, explicit derived central status, error, and any bounded action primitives; raw tool result/log/Activity context/generic payload fields are not part of the schema. The page converter is O(events + visuals), indexes/merges only by stable IDs, and must not call the normal semantic `dedupeProjectionEntries`/`stableJson` path.
- Browse pages are component/view state, not additions to `AgentRunState.conversation` or the Activity store. The existing recent-window enforcer must never immediately evict a newly fetched older page, and older tool activities must never repopulate or expand the secondary Activity panel.
- Realistic validation against existing live data must use a consistent disposable snapshot and an isolated integrated backend process. The existing live server and validation server must never concurrently own `/home/autobyteus/data`. Bootstrap/catalog readiness, row projection TTFB/total, payload/cardinality, response-to-hydration, click-to-usable, mounted visual count, and integrity must be measured separately as specified by `integrated-live-validation-plan.md`. Archive no-open is independently re-proved only with a request-bounded path-only runtime open audit; otherwise the representative run must say that clause was not re-executed and rely on the prior durable instrumented evidence. Integrity evidence distinguishes quiesced source-to-snapshot equality, validation-process non-access to the live root, snapshot raw-trace immutability, and live-source equality. Live-source equality is required only while the old owner stays stopped; it is `N/A`, not a failure gate, if the legitimate old owner restarts. Runtime tracing is required for that restarted-owner mode; if unavailable, the validation must keep the old owner stopped or report the restarted-owner topology as blocked.
- Exact initial/latest maximum `100` and server-owned earlier request maximum `50` remain the bounded transport policy. The user explicitly rejected exposing that page size in the interface. The `300` browse-resident bound is the design safety bound that preserves access to the whole active trace through page turnover.

## Risks / Open Questions

- A single rendered reasoning/text/media value can still be large; count bounding does not impose a byte-size cap. Raw tool results/logs are specifically excluded from earlier-page transport, so they are not part of this residual page-payload risk.
- More than 100 concurrently mutable visual events is reachable but abnormal. The approved hard cap takes precedence only after completed candidates are exhausted; the specified stable-identity/source-limited fallback avoids crashes and duplicate retained cards but may omit content evicted before a later update.
- The lightweight witness relies on a complete inventory of central render/retained-interaction semantics. Missing a newly rendered value could suppress a revision, while including Activity-only/detail state could create a false jump action. Focused tests must cover every current center-rendering event kind; future render-model extensions must update the shared presentation helper/table and witness tests together.
- The existing projection duplicates tool data into conversation and Activity arrays. The duplication becomes bounded but is not eliminated here.
- Active-team restore still projects multiple member windows. Each is bounded and archive-free, but a very large team may merit separate focus-lazy work later if measured performance remains poor.
- A current frontend can still connect to an older remote node whose backend is archive-inclusive. The frontend cap protects final retained/rendered state but cannot prevent that old server's archive I/O, response construction, transport, or pre-cap hydration work. Remote nodes must be upgraded before this performance guarantee applies; capability/version-warning UX is outside this approved change.
- The Event Monitor's existing token/cost total will describe the retained recent window once older items are evicted; it is not a full-run accounting surface.
- The active file can itself be large. The approved page contract bounds response/hydration/DOM work, but the first implementation may still reconstruct the complete active trace per explicit page request to preserve tool lifecycle correctness. If `AC-015` fails because server scan/reconstruction dominates, a derived active-trace replay index becomes a measured design follow-up rather than speculative storage complexity.
