# DS-001 — managed Ubuntu desktop identity and icon
Approved SR-001 / autobyteus-12. Authorities read: architecture-design, design-principles, DESIGN.md, TESTING.md, root + web AGENTS, RELEASE, project data-migration conventions. No conflict, new project policy or new art. Medium / High: bounded user-mode change, but materially changes the on-disk representation consumed by Ubuntu and old released launchers, and the window→desktop identity contract. Review independently. No privileged or executable trust changes.

### Production paths
**UC-001/003.** Keep the current login user's *desktop ID* autobyteus-managed.desktop, independently of original download name or temporary mount. Native AppRun owns the generated desktop resources. Change its ordering: after proper managed-path validation, redirect a noncanonical download directly to the canonical outer image with the original arguments; redirect after installation as well. Only the running canonical managed GUI's AppRun ensures branded resources before supervising Electron. Do not publish a new icon/entry from a newer download on top of an older installed version. Keep operational Node bypass and explicit uninstall handling separate. No work in the root provisioner, privileged writer, portable launch or renderer.
- Source is the **already packaged** resources/icons/512x512.png next to the native AppRun (derive from real running executable, not child args or mutable APPDIR). Place a stable, user-local, app-specific PNG outside the mount and outside /opt, e.g. ~/.local/share/autobyteus-managed/desktop-icon.png. Desktop Icon field is its absolute, desktop-key-escaped path, not a transient filename, theme-wide replacement or bare generic icon. Keep Name, Exec target with %U, categories, UID ownership marker and Terminal behavior. Add StartupWMClass=autobyteus-managed, matching UC-002. Only canonical image's artwork is authoritative. No new image generation, root permission, shell commands, programmatic shell reload, favorites writes or installation-time network.
- A simple in-place edit of ~/.local/share/applications/autobyteus-managed.desktop is unsafe here: old download's Menu rejects the changed bytes before exec. Publish the new file at applications/autobyteus/managed.desktop under the user's existing applications root (same default ~/.local/share); this has the **same freedesktop desktop ID**. The old flat path is absent at rest. An unchanged old download can recreate its exact legacy shortcut and redirect: the fixed installed launcher reconciles it. Keep these two representations only for a bounded transition, never permanently, never rely on desktop lookup precedence when both exist. Both owned forms have the same Exec target. No duplicate visible item once reconciled and no loss of normal pinned-launcher target. No promise to change how obsolete binaries uninstall from Downloads; the supported removal command uses the installed image.
- Track known prior bytes from exact shipped template for this canonical store+UID (legacy recognition isolated at menu migration boundary). Inspect flat/nested/icon before mutation; no replacing or deleting symlinks, nonregular or foreign content, or following redirected app-owned subdirectories. Respect existing edited-file refusal/diagnostic. Publish complete icon first, then new desktop entry atomically (non-clobber absent destination, compare exact app-owned contents on repeat); only then remove exact old generated flat entry. Empty or missing owned state is repairable; a partial own installation or both versions after interruption converge on next canonical launch. Idempotent current launch must not continuously rewrite files/invalidate the shell index. Conflicting foreign item wins preservation, never create a second silently or displace a custom shortcut. Do not use UID marker alone as authority. No mandatory global cache rebuild. An icon-only I/O failure is not an authorization/sandbox failure: preserve any usable previous shortcut and avoid destructive changes/reenrollment; diagnostic without unnecessary loss of otherwise healthy startup. No application data migration, central version marker or database.
- Uninstall via documented installed image: after successful owned-system uninstall remove only exact known legacy/current generated entries and matching branded asset, removing only empty owned directories. Identify against installed version's packaged branding (current mount remains in use by AppRun); never delete unrelated files or arbitrary user paths referenced by desktop contents. Failure/cancel before uninstall doesn't remove user's menu. Update documentation for discovered path/ID and first corrected launch.

**UC-002.** Use the existing ElectronApplication composition point where the packaged protected Linux install is already confirmed by detectLinuxManagedInstall; on that branch call app.setDesktopName('autobyteus-managed.desktop') before creation of **any** window. Electron v42's native window creation derives both Wayland app_id and X11 WM class from this setting. Do not change app.name/productName, profile, signing ID, global package desktopName, BrowserWindow icon or userData. Keep packaged window icon path as existing fallback, not proof of dock association. The same default and secondary managed windows should belong to the same entry; other modes unchanged.

### Proof and change scope

Electron wiring test: selected only in verified managed mode before window creation. Preserve existing protected-startup and Node tests. Current TESTING.md desktop isolation applies.
- Actual isolated Ubuntu GNOME with Ubuntu Dock or representative GNOME Shell plus Ubuntu Dock extension: record OS, Shell/extension, Electron build, backend. First capture baseline with real packaged predecessor, Applications entry artwork and **Shell.WindowTracker** associated desktop ID (or equivalent observation for the actual running window) for menu and terminal launch. Then observe corrected **actual Applications and dock visuals** AND reported desktop ID; show no separate generic running tile/duplicate, stable icon after quit, and old unmodified shortcut automatically repaired on first corrected canonical start. Exercise launcher-bearing old download redirect and documented uninstall. Isolated fixture should include existing favorite to check same-ID retention; never edit user's favorites. Native Wayland primary; exercise X11 or XWayland on Ubuntu as applicable. A GNOME-less Xvfb/Openbox session or grep/Gio lookup alone is insufficient for visible dock acceptance. No unsafe/debug mode on user's desktop. Use disposable GNOME session/VM, test-signed official-shaped personal AppImage and synthetic user data; capture only test screenshots. For existing state, run a previous released-source launcher + equivalent legacy managed setup/update via disposable trust, not just a hand-written new-entry launch. If real shell association or live registry update contradicts the mechanism, return evidence for correction; do not mark as verified.
- Scope: native launcher menu and caller/ownership tests, scoped Electron application identity and tests, operator documentation. No expanded desktop environment matrix, updater/provisioning changes, production credentials, release, user-host writes or package format change.
