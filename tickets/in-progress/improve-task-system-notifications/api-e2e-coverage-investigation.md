## Current Requirement And Design Basis

The approved behavior requires a clean split between task-delegation runtime/model input and visible `SYSTEM_TASK_NOTIFICATION.content`. Task-delegation must own display copy server-side, stamp in-scope activation/result/revision system messages with display content metadata, and preserve mixed-member de-duplication so each stamped message produces one `SYSTEM_TASK_NOTIFICATION` and no duplicate `MEMBER_INPUT_MESSAGE`.

Visible notification content must be natural, task-centered, and concise for member activation, team activation, result-submitted, and revision-requested flows. It must include task id, task/summary/result/review comment, and reference files where applicable, but omit sender/delegator/reviewer framing, execution/run/submission/review ids, lifecycle mechanics, JSON/tool-call snippets, and `send_message_to` warnings. Runtime/model content must remain actionable while avoiding non-actionable internal identifiers. Backend task-delegation events, warnings, lifecycle status, and routing/correlation metadata must remain available.

The model-facing review free-text argument is now `review_task_result.comment`; `message` must not be accepted as a legacy alias. Acceptance review text is `acceptanceComment` in status/domain payloads. Tool schema, manifest, runtime instructions, parser, serialization, and live model/tool behavior should use task-centered `comment` terminology.

The implementation handoff legacy check is clean: no backward-compatibility mechanisms were introduced, no legacy old behavior was retained, strict parser accepts `comment` only, and durable unit/integration/E2E expectations were updated before code review. Code review passed with no findings, but explicitly left live mixed-runtime E2E execution to this stage.
