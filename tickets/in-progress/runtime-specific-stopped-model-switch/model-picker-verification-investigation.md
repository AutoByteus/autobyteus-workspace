# Model picker verification investigation — 2026-09-25

## Result and boundary
- **Outcome:** Evidence-only clarification of the delivered model-switching package, with a separate presentation concern for user decision. No requirement, design, implementation, saved run, or delivery status was changed by this probe.
- **Approved basis:** `requirements-doc.md` SR-002 and `design-spec.md` SR-003 remain authoritative. Delivery is awaiting explicit user verification; this investigation is not acceptance or a `Delivery Completed` receipt.
- **Environment:** Ticket-packaged Electron app running its bundled backend on loopback port 29695. A Nuxt development frontend was also started against that backend on port 42881 and stopped after the probe. Its browser session showed an availability/loading mismatch, so the packaged Electron UI and direct backend queries are the decisive evidence for the user's screenshot.

## Direct observations
1. Read-only GraphQL `providerModelCatalogSnapshots(runtimeKind:"claude_agent_sdk")` returned **11 exact runtime IDs** at probe time: `default`, `opus`, `claude-fable-5`, `claude-fable-5-1[1m]`, `haiku`, `claude-opus-4-6`, `claude-opus-4-7`, `claude-opus-4-8`, `claude-opus-5`, `claude-sonnet-4-6`, `sonnet`.
2. The saved model in the observed stopped Team is `claude-fable-5-1` (without `[1m]`), which was **not** among those 11 currently returned IDs. The offered `claude-fable-5-1[1m]` is a distinct exact ID. The SDK-reported canonical name for it is `claude-fable-5-1`.
3. The backend option query returned the runtime-offered alternatives without a capacity/unavailable reason. In the packaged Electron dropdown, the accessibility tree showed **12 entries**: the 11 offered IDs plus the saved historical ID. Scrolling the dropdown exposed lower Opus and Sonnet entries that were below the screenshot's visible portion. No backend omission among the 11 currently reported IDs was found.
4. The visible “Saved / runtime-offered model” header combines two fallback reasons. `RuntimeModelConfigFields.vue` places exact IDs missing from the separately formatted frontend groups into this fallback. The saved unsuffixed ID is missing from the current runtime catalog, while `default` is an SDK-offered alias that the general launch-picker display builder folds under `opus`. Thus `default` appears as a raw fallback ID, even though it is runtime-offered, and the group does not explain which row is which.
5. Claude model rows use canonical names for display. Consequently the saved unsuffixed `claude-fable-5-1` and offered `claude-fable-5-1[1m]` both appear as `claude-fable-5-1`, despite different selection IDs. This is a real ambiguity in the picker, not two copies of the same option.
6. The Claude backend catalog is populated from the SDK's `supportedModels()` report. “All runtime-offered” in this package means all IDs that call currently returns for this environment, not all conceivable Claude models or arbitrary model IDs. Catalog contents can change across sessions/environments.

## Assessment and proposed product decision
- The core approved behavior — offering every currently returned Claude runtime model without our context-size gate — is evidenced for this stopped Team picker. The screenshot's apparently short list is a scroll/viewport effect, not evidence that the lower options are missing.
- The current presentation is confusing: a mixed fallback label, bare `default` alias, and indistinguishable exact IDs undermine user confidence. The design required preserving a saved-model fallback, but did **not** prescribe the combined label or duplicate visible labels. This is not a reason to reinstate a capacity filter.
- Recommended refinement, **not yet approved**: distinguish “Current saved model (no longer in runtime catalog)” from runtime-offered choices; explain `default` as the runtime's default alias; and show exact-ID distinctions such as `[1m]` where two rows would otherwise have the same label. Preserve the same 11 runtime choices, saved-run visibility, fixed runtime, Save validation and history. Ask the user whether to include this UX correction in the current delivery before treating the package as verified.
- No model was selected or saved, no run was resumed, and actual provider continuation was not re-tested by this read-only investigation. Downstream validation reports remain the authority for executable coverage.

## Subsequent user correction (supersedes the proposed presentation remedy)
The user clarified that `default` should be filtered by the **Claude backend provider model catalog**, not hidden by a frontend-only rule: the frontend should just display the backend's offered models. When `default` resolves to a concrete model already listed (currently `opus`), the backend selection-facing catalog should omit that redundant alias consistently for provider snapshots and stopped-run options. The earlier recommendation to *label* `default` in the UI is withdrawn. Existing runs saved with exact `default` must remain readable/continuable and must not be silently rewritten; fresh Save validation currently uses the same catalog and therefore needs an explicit compatibility design for unchanged saved values. This correction is a requirement/design revision, not part of the SR-004 evidence-only result.
