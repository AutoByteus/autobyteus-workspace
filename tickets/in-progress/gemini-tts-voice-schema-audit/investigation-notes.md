## Practical schema mapping clarified for user (SR-002)
- `generate_image` does not synthesize voice. `generate_speech` adds the selected audio model's `generation_config` JSON Schema to its tool parameters. The app's `voice_name` is an ENUM of 30; even a hand-supplied extended ID fails `GeminiAudioClient.generateSpeech` validation. Unknown config keys are not forwarded to Google by this adapter.
- Google's provider schema uses a **voice identifier string** in the single-speaker `speechConfig.voiceConfig.voice` field, rather than an immutable 30-name-only app enum. Catalog discovery is a separate `voices.list` operation on the Developer API; the provider then validates whether an ID is supported/entitled for the chosen route/model. Avoid claiming “all voices” are universally available to any key/route.
- Multi-speaker is distinct: Google's documented one-call config allows only up to two **prebuilt** voices under `prebuiltVoiceConfig.voiceName`. Do not generalize arbitrary extended/custom IDs into that field without route-specific evidence; custom multi-character use needs per-turn synthesis/assembly per Google.
- This clarification does not approve changing the schema, request shape or tool interface. It only sharpens the answer to the user's investigation question.

## Voice identity versus speech delivery (SR-003)
- Current `generate_speech` already covers: transcript text; 30 featured voices; single-speaker; mapped dialogue up to two prebuilt speakers; one global style instruction applied to every turn; WAV file result. The 2026-10-01 live Vertex Express success validates one basic single-speaker TTS path, not every voice or dialogue option.
- **Style** is how a selected voice delivers a particular turn (e.g., quietly or excitedly). It does not create a new reusable voice identity. Google's turn-level style is richer than the app's one-global-style mapping.
- **Voice design** creates a *new synthetic persona* from a description, then returns a stored reusable ID and sample audio. The existing speech tool could theoretically synthesize from that ID if its fixed enum/validation changed, but the app currently neither creates/manages it nor accepts its ID.
- **Voice replication** derives an identity resembling a real consenting adult speaker from reference and consent recordings. It is not ordinary style control; it needs source/consent upload, storage/expiry/delete decisions, privacy safeguards and provider access. The app currently neither creates/manages such a voice nor accepts its ID.
- For both voice-design and replication IDs, Google's one-request multi-speaker feature is limited to prebuilt voices; custom voice dialogue would require separate calls per turn and assembly if offered. Do not infer that custom ID support automatically extends the existing one-call two-speaker dialogue.
- Practical priority recommendation, not approved scope: first make `generate_speech` capable of using provider-available catalog IDs and an existing custom single-speaker ID with truthful route errors; consider per-turn style next. Treat in-app voice creation/replication as optional separate workflows, not a hidden `generation_config` flag. Vertex Express Voices API remains undocumented, so do not promise creation/discovery through that key.
