## Current state / health / intended change
Missing Linux install/privilege boundary, not a renderer bug. The actual failure precedes app main. Linux packaging selects AppImage and has no restricted-host setup owner (build/scripts/build.ts:311–313,398–406); shipped desktop Exec bypasses Chromium. Electron updater can replace a user-owned AppImage but cannot safely install into a protected location (SR-010). Current update policy already decides opt-in and drives the same install as a click (electron/updater/appUpdater.ts:112–139,296–320). Preserve that policy; replace only its managed-install mechanism. Refactor needed now: separate the Linux protected install transaction from generic quitAndInstall. No blanket refactor. Capability reuse, distinct launch modes and privilege boundary are the fired structural triggers; no new renderer, preference store, general privileged command interface or OS-wide update engine.
## Spines, owners and behavior map
1. L1 (UC-001/002, BEH-001/002): file exec or desktop entry → AppRun-level pre-Electron launcher → select existing protected file for this login UID (never redirect to self) or attempt ordinary sandboxed startup → Chromium → existing UI/server as original user. Use a real bounded pre-main sandbox-capability child on the same artifact, or intercept the actual early, identified Chromium sandbox fatal; choose the latter to avoid probing on healthy launches. Observe only pre-main failure; unrelated crashes/long-lived app exits do not trigger installation. Propagate argv, streams, signals and exit status; measure zombie/child cleanup. A responsive packaged GUI, not a launcher stub, validates it. Desktop Exec must route through same launcher with no implicit bypass; inspect final generated file, not just builder options.
2. L2 (UC-005 / SCN-005): confirmed restricted-host startup failure → explain destination and privilege in terminal/desktop → explicit install → system authentication → one-shot install program creates protected artifacts → original user starts protected image → same data identity. On refusal/failed preflight leave no partial active install and report actionable diagnostic. On a managed file, never prompt in a retry loop: failed attachment is repair, not fresh setup. Older binaries not carrying this launcher cannot be intercepted. No auth on capable launch. A noninteractive caller cannot authorize setup implicitly.
3. L3 (UC-003 / BEH-003): server or tooling invocation → direct real Electron ELF in its supported mode → existing Node/server lifecycle, preserving arguments and signals. Do not prompt or reinterpret Node mode/explicit automation requests as interactive first launch.
4. U1 (UC-004 / BEH-004): release job → build actual per-arch AppImage → compute digest of final bytes → sign release record → validate complete artifacts → updater metadata last. App's existing check/download/channel/opt-in → protected install client stages request → OS-managed writer verifies immutable staged bytes → readiness → coordinator defers automatic activation to the next independently requested ordinary quit → atomic activation → fixed-path unprivileged relaunch on explicit restart, or next ordinary launch after normal quit; report running version, not just download success. Manual updates share verification. Current app/embedded server version pairing stays intact. Do not automatically terminate ongoing work to hit an update timer.
5. U2 return/local: staging refusal propagates to existing update failure notification before stop; opt-out cancels pending automatic activation, not normal operation. Installation lock serializes activation for the installation. On commit failure keep old file runnable and follow current recovery. Existing appUpdateInstallAttempt and automatic failure logic keep one authority; do not leave electron-updater's independent autoInstallOnAppQuit active for managed installs. No success notification until verified transition.
## Privilege and interface boundaries
- AR-001 selected crossing, no alternative implicit: user intentionally starts the official downloaded release (initial trust assumption). The normal-user launcher reads only its bundled standalone native provisioner, verifies the expected build-pinned digest, snapshots the checked bytes in a kernel-sealed read-only executable file, checks all write/grow/shrink/sealing locks and retains the same open descriptor until the one-shot authorized child has exited. No writable mapping, path supplied by caller, on-disk mutable extraction, FD reuse, or privileged shell/interpreter. Root code consists only of the bootstrap program and its statically embedded fixed service/profile/menu templates, writer binary and public key. No commands or resources from the unverified AppImage run as root. Use autobyteus-web/linux-install/cmd/{launcher,provision,writer}/main.go and internal/release/record.go. Build writer first, embed in provision, then pin completed provision digest in launcher before packing AppImage; no circular signature on the final AppImage.
- Ubuntu authorization: launcher explains the operation and exact helper path that the OS will display, then invokes system pkexec for the retained **parent's** read-only descriptor path, not a child-inherited descriptor. PKEXEC_UID is set by pkexec from the invoking real UID; provision requires effective UID zero and a valid nonzero local PKEXEC_UID, resolves account via OS, derives all destinations from that UID and fixed constants. No UID/path/env overrides. No generic auth exemption, retained grants, or custom password handling. In graphical sessions use Ubuntu's registered agent; on a real terminal without one use Ubuntu's ordinary separately registered pkttyagent tied to this launcher process, wait for readiness, then pkexec with internal agent disabled. A headless noninteractive process cannot enroll. The system dialog identifies the program by path and requested account, **not by verified publisher**. Authentication proves permission, not publisher identity. The launcher retains custody during the prompt without delegating mutable code or assuming a custom policy is already installed. Failed seal, unsupported execution, auth refusal/cancel or absence of suitable agent stops: no retries with weaker policy. SR-013 VM witnessed stock 24.04 polkit and normal one-shot password verification; 26.04 and graphical acceptance remain required.
- Provisioning resource custody/order: parent supplies only bounded signed record, signature and final AppImage bytes through stdin (OS auth agent uses independent session/tty); bootstrap stages in root-private storage, verifies pinned desktop key, record, length/digest, arch and requested release before committing anything. No input path dereference, archive extraction, user-controlled service files or network trust injection. Set installer directories, service identity and protected immutable service assets; initialize writer store with first verified inode+attrs; install inactive socket/service and exact AppArmor profile; load profile then enable socket; return committed only when all ready. Parent then writes its own user-menu entry (never write into HOME as root) and launches canonical executable as that UID. Subsequent launch completes missing menu entry idempotently if parent was interrupted. On setup failure reverse only objects created by this attempt; leave existing managed installations intact, disable created socket and unload created policy before removing its files. Refusal before authorization writes no host state. Uninstall uses root-owned installed provisioner and same Ubuntu prompt; disable socket, stop owned writer, unload owned profile, remove only verified owned files/identity if unused; caller removes owned menu entry. No profile/data deletion. No host changing operation was part of the design VM witness.
- Per-user managed installation under protected /opt/autobyteus-desktop/<numeric-uid>/app/AutoByteus.AppImage. Root-owned ancestor, fixed numeric UID binding, no writable ancestor for desktop users. A locked non-login service identity owns only the managed app staging/activation area; bootstrap, verifier, trust anchor, service definitions, desktop integration and AppArmor configuration stay admin-owned. One active installation per login UID avoids one user's beta/opt-out decision replacing another user's executable. Service instance constrained to its own store. Desktop entry for that user executes canonical copy with user arguments. No privilege for Downloads, mount wildcard, interpreter, browser or generic basename. AppArmor attachment equals exact protected AppImage, persisted for reboot; give scoped userns under Ubuntu semantics tested in SR-009. Other apps retain Ubuntu defaults. The label permits app process tree to construct sandboxes; it is not full containment of the app or protection against all code running as the desktop user.
- Routine writer is a systemd socket-activated local service, **not root**, with no network, sudo, package-script execution, arbitrary exec or filesystem destinations. Peer credential check against install UID; fixed service-owned paths, bounded stream of manifest/signature/payload, reject symlink traversal and race-by-handle, ordinary file only. Stage in private same-filesystem temp, hash actual staged bytes, verify exact signed manifest and type/product/platform/arch/version/channel/size/digest; enforce strictly newer semver (including beta), bind staged transaction to approved channel and expected current version. Signed bytes never become shell/installer code for the writer. Fsync file and parent and atomically rename without unlink-first. On failure discard stage only. Maintain root-provisioned publisher trust; separate test keys never accepted by production. Authenticate release record, not sha from mutable feed alone. Protect against replay, huge input/disk exhaustion, concurrent writers, test feed in production. Budget one bounded pending image per install. Root-owned service updated only by authenticated maintenance, not arbitrary payload updates; ordinary compatible image releases need no elevation. Future incompatible installer/trust-root maintenance must explicitly fail closed.
- Protocol: stage(expected release, signed record, signature, actual bytes) → opaque stage ID or refused; activate(stage ID, expected current version) → installed identity or refusal; discard(stage ID). Client does not supply target path, executable command, key, or script. Stage IDs local, expiring, tied to owner UID and manifest; recovery inspects committed image identity to reconcile interrupted activation, never executes staged files as privileged user. Normal app state/channel preference remain user's. On opt-out stop automatic requests; manual path remains. User's chosen beta channel permits authenticated beta only under existing channel policy, a beta client may accept newer stable per product rules. Prevent other local UIDs requesting activation. No plaintext passwords.

## DS-002: managed activation lifecycle (AR-002; replaces U1/U2 generic stop/ready wording)
Conservative rule for managed automatic installs: **verified stage while running, activate only as part of an independently requested normal quit**. Never infer idle from a timer, closed renderer, empty window list, or server process being stoppable. No update-generated app.quit() on automatic download. No new end-user clicks or active-work tracking: a session may remain open indefinitely, next ordinary start uses newer bytes. UI says “Ready for your next quit,” not “installed.” An explicit Install and Restart click is independent consent to stop/relaunch now. No automatic reopening after an intentional normal quit. Portable, Mac and Windows policy unchanged.

ElectronApplication constructor (electron/application/electronApplication.ts:73–91) composes one managed session coordinator, application/managedUpdateSession.ts, only for verified protected context: takes writer client, ApplicationShutdown, concrete server exit check, canonical installed executable and preference/state reader. AppUpdater owns download, toggle/channel and reporting, not stop/activation; route managed events/commands into coordinator and observe its results. Narrow the interaction to stageDownloaded(file,release), settingsChanged, requestRestart, and owner of willQuit(event); existing AppUpdateAutomaticPolicy drives automatic downloads but its immediate downloaded→install and ready-on-download are NOT used for managed mode. appUpdater.ts:442ff must not mark updateStaged before a verified stage receipt. Constructor disable native autoInstallOnAppQuit on managed path. ElectronApplication.installLifecycleHandlers: one will-quit handler dispatches to managed coordinator or normal shutdown, not both.

1. Stage: request writer with bound release, channel and current identity; advance attempt generation. While awaiting, pending is not ready. A late reply after cancellation/new generation is discarded. If verified, store {stageID, expected digest, channel, generation}. A manual download may remain staged with automation off; no automatic activation absent opt-in.
2. Automatic normal quit: will-quit receives independent quit, including last-window normal Linux close. Synchronously preventDefault once; latch quit intent; own shutdown.stop() exactly once; no second handler resumes quit before transaction ends. If not verified at quit boundary, don't wait for a download, quit normally; next check rediscovers it. Retain existing broadcast and bounded stop semantics. Stop rejection or server not confirmed gone: no activate; preserve existing shutdown failure handling. Release successful quit through re-entry pass latch, without a second activation. No relaunch for normal quit, on failure log next-start notification and keep old file.
3. Manual: if verified and generation matches, obtain explicit restart intent from existing IPC, then coordinator starts prepareForInstall semantics (allow incomplete stop only when existing code confirms server gone). Reject duplicate manual/normal entrants while in-flight; latch manual-restart intent once. On success use Electron app.relaunch({execPath: canonicalOuterImage,args: []}) as desktop UID then exit, never relaunch inner FUSE path. Explicit E2E arguments/isolated env handled by existing test profile. On refused activation after confirmed stop, old image remains authoritative; restart old canonical path as original UID only when server is confirmed gone; if unknown, do not launch a second server. On lost reply use status before choosing outcome, not blind retry. For both paths record pending outcome against expected release, reconcile with running app.getVersion() next start; writer receipt does not assert GUI readiness.
4. Both activation paths re-read stage identity, channel and (automatic only) opt-in immediately before dispatch. Coordinator serializes settings/generation and dispatch in one main-process event turn. Turning off or changing channel before dispatch invalidates pending automatic activation (discard, no stop initiated by toggle); turning off during independently requested quit allows ordinary quit with old version. After dispatch writer atomic transaction has started: opt-out governs subsequent updates, not undo. Never have ApplicationShutdown.quit auto-resume alongside coordinator. Update appUpdateController/appUpdateIpc manual readiness to refuse unverified attempts rather than treating native downloaded as ready. Notification and recovery errors are observable, no fallback to native quitAndInstall.

## DS-002: authenticated identity and atomic commit (AR-003)
Single contract in linux-install/contract/desktop-release.md with shared positive/negative byte fixtures, Go reader internal/release/record.go; JS signer scripts/desktop-package/sign-release.mjs and CI validator consume same fixtures. Signed content example (digest illustrative):
{"format":1,"product":"autobyteus-personal-desktop","artifact":"AppImage","os":"linux","arch":"x64","version":"1.5.14-beta.1","channel":"beta","size":339972678,"sha256":"0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef","minWriter":1}
Signer emits compact UTF-8 JSON in shown order plus one LF. Detached .sig is standard base64 of 64-byte Ed25519 signature over exact manifest bytes, no newline. Bounded <=4 KiB manifest, reject duplicate/missing/unknown fields, nonintegers, invalid encoding, unsupported format/minWriter, mismatched target, wrong key, bytes/size/hash mismatch. Only accepted arch x64/arm64 = installed CPU, version exactly three nonnegative canonical SemVer integers optionally -beta.N; channel must agree with suffix; stable allows stable only, beta allows newer stable or beta per appUpdater.ts:378–380. Strict numerical SemVer ordering (stable greater than beta of same core), never equality/downgrade incl channel switch. Fixed ceiling 2 GiB per AppImage; check space, enforce bytes limit while receiving. No install path/command/origin/key in manifest. Use production desktop public key embedded in bootstrap and installed verifier; test key is separate build-only trust domain. CI signs after final packaging, verifies metadata version/size/hash/arch against actual final bytes and validates positive and rejection vectors before publishing feed last. Unprivileged client uses version/sidecar to request; only writer enforces trust, never trusts request's claim of installed version.

Writer-authoritative committed state is the fixed regular **inode with two user xattrs on that same inode**: user.autobyteus.release = exact signed bytes, user.autobyteus.signature = raw signature. First provisioning verifies and writes file+xattrs, fsync then same-filesystem rename and parent fsync; require installed FS supports user xattrs/rename/fsync, check BEFORE publishing menu/profile. Incoming signed image staged privately under writer UID; verify, set attrs, read back, fsync before reporting receipt. Opaque stage ID bound to peer UID, current live digest, signed candidate and generation. At activate lock store, re-open live without following symlinks; verify its xattrs, use signed current record as sole version authority; compare expected digest, admissibility and channel again. After interruption or on new writer start, hash actual live bytes against signed metadata before trusting baseline. No second version file, unlink-first or symlink selector. rename incoming over live, fsync containing directory before ACK. Crash before rename leaves old image+old record; after rename one complete pair is visible; crash before fsync or lost ACK → status re-reads and verifies actual fixed inode, reports old/new identity; do not guess or report success prematurely. Incomplete/unverifiable committed pair → fail closed, explicit repair, not version zero. Pending files disposable on restart, conservative discard; never discard live. Write access only to service account; root code/keys/config outside writable store. Real filesystems must be tested, local inode feasibility probe is not power-loss validation.
Example: bootstrap installs signed 1.5.13; on beta channel 1.5.14-beta.1 accepted from that digest, then 1.5.14 stable from beta digest; stale stage referencing 1.5.13, same-version alternate bytes, beta in stable mode or unauthenticated 1.5.15 all refused. Queries return writer's current signed identity, not client running version. Add client stage/activate/discard/status and contract golden vectors; no app-data migration. FS xattrs not preserved by arbitrary cp; supported installer writes them itself, external copies never count as authoritative managed installs.

## DS-003 — First-install release record acquisition (L2, prior to authentication)
A single downloaded file is sufficient as user input. Only on the restricted-host, not-already-managed first-install branch, after the user chooses Install, the **unprivileged launcher** obtains the two detached assets for the exact release it is running. No read of adjacent Downloads files, no "latest" lookup, no second AppImage download, no requirement to preserve the downloaded basename. No network on healthy portable launch, original-download redirection, existing managed launch or cancellation. Explain that initial setup requires reaching the official release service before requesting any password. No offline managed onboarding promised; normal installed launch remains offline-capable.

**Build/release contract:** produce one typed build identity from the personal target, validated package version and target arch (not host GOARCH for cross-build). Embed product, version, arch, official repository and canonical release asset basename into launcher; provisioner independently pins expected personal product/version/arch and public key. CI with production trust must assert official repo AutoByteus/autobyteus-workspace, release tag exactly v<version>, and final canonical artifact basename from build.ts's Linux name owner, independent of the local path. Do not source release identity from runtime env, argv, mutable updater metadata, local filename, HTML or redirects. No extra hash of the final file embedded inside itself. After final packaging publish <canonical-AppImage-basename>.release.json and that name plus .sig next to the artifact before advertising it. Reuse these same assets/record contract for updates. Example for the 1.5.13 x64 naming convention (illustrative, not an existing signed release): AutoByteus_personal_linux-x64-1.5.13.AppImage.release.json. Renaming the downloaded image to MyApp.AppImage changes neither request.

**Access and refusal:** two anonymous HTTPS GETs from https://github.com/AutoByteus/autobyteus-workspace/releases/download/v<version>/<canonical-sidecar-name>. Use normal system TLS verification; cap redirects at 3, HTTPS port 443 only, no credentials, allow exact github.com and release-assets.githubusercontent.com; reject others, no downgrade. Do not log redirect query strings. 20-second total acquisition deadline, no automatic retry loop, only final HTTP 200, max 4096 bytes manifest and exactly 88 ASCII standard-base64 bytes signature for 64 decoded bytes (no LF). Enforce bounds on actual response, not only Content-Length. Unprivileged launcher verifies signature and release tuple and hashes the opened local outer file against size/digest before polkit. Keep that regular-file handle through streaming; if bytes change afterwards the privileged verifier must independently reject. Root does not fetch, resolve a URL or trust client precheck. Offline, TLS failure, missing assets, mismatched key/tuple/digest or redirect refusal: stop before authorization, leave machine unchanged and sandbox intact, explain reconnect/retry versus invalid official download. No path search, unsigned alternate, permissions downgrade, or enrollment in another version. Build-only fixtures may compile an isolated test origin and separate trust key; production binary has no user-selectable origin/key.
Verification additions: real renamed package with exact tagged test assets, no calls on capable/installed paths, same-version wrong bytes, 404/offline and redirect/size refusal before auth; staged service still rejects wrong bytes. Real publishing is outside this ticket. Existing releases without the new launcher are not retrofitted.
