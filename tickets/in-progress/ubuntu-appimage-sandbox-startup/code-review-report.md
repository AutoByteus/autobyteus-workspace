### F-API-03 — Missing installed image: correctly refused, no repair guidance

**Supported explicit edge; in scope.** A user reopens a valid downloaded AppImage on an enrolled desktop with an incomplete protected installation. L2 requires a repair diagnosis rather than another enrollment attempt. The fixture isolates the missing image; it does not establish or require support for arbitrary manual modifications. The expected outcome is safe refusal and a concrete next step, **not** automatic repair or removal.

- **Observed:** API-04e repeated normal graphical launch and the uninstall action from the same renamed download on Noble. The error is solely the raw `lstat … AutoByteus.AppImage: no such file or directory`; both exit 1, no new grant, no server. See `evidence/API-04e-repair-repeat.log`, `API-04e-repair-launch.png` and `API-04e-repair-uninstall.png`. Restoring the original test inode permitted healthy launch/normal authorized removal, with the same synthetic data hash (`API-04e-removal.log`). This control is not a proposed user instruction.
- **Origin:** `autobyteus-web/linux-install/internal/launch/managed_linux.go:15–43` distinguishes absent enrollment root, then validates its protected directories/writer. At lines 32–37 the missing *live file* returns the bare OS error. `cmd/launcher/main.go:47–55,116–121` returns that error **before** uninstall or ordinary launch dispatch. `internal/launch/consent_linux.go:40–46` shows exactly the supplied text. Neither later sandbox-failure wording nor documentation is on that error path.
- **Required outcome:** identify an incomplete protected install in the dialog; give a safe administrator-inspection/repair step without suggesting a blocked uninstall, another password attempt, manually replacing the image, or weaker protections. Keep ordinary absence distinct from damaged enrollment; do not relax admission or removal.

### F-API-04 — Authorized installation: low-space cause lost before graphical explanation

**Supported explicit edge; in scope.** A user approves a genuine initial install onto a volume with inadequate space. L2 requires a failed preflight to leave no partial active setup **and** report an actionable diagnostic. Available storage is an installation precondition independent of the test instrument.

- **Observed:** API-06d used the genuine graphical consent/Ubuntu authorization flow and a 32 MiB empty private install volume. Helper stderr identifies insufficient installation space, but the dialog only says “Ubuntu authorization or installation refused: exit status 1.” `evidence/API-06d-rollback.log` records both messages, the absence of owned components after rollback and the unchanged work hash; `API-06d-rollback.png` shows which message the user actually saw. The helper exit is distinct from the outer launcher's recorded exit 133. This is **not** failed authentication or failed rollback.
- **Origin:** `internal/install/provision_linux.go:105–110` recognizes low available space. `cmd/provision/main.go:39–49` writes that reason to stderr and uses generic exit 1. `internal/launch/authorize_linux.go:64–70` forwards the streams to the parent's streams and returns the generic pkexec execution error. `cmd/launcher/main.go:101–103,116–121` feeds only the wrapper error to the graphical explanation. No desktop user can infer storage rather than credentials from that message.
- **Required outcome:** carry enough bounded, trustworthy failure information to let the nonroot launcher tell the user the install volume lacks space and to make space (or ask an administrator), then retry. Distinguish this known preflight failure from canceled/denied authorization; unknown causes must not be labeled low space. Do not display arbitrary helper output as trusted UI, add credentials/privileges or alter rollback. The output contract, not a new privileged recovery service, is what needs correction.
