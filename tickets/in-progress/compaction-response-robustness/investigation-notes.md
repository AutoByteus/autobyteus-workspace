## Request Context

The user reports that compaction is production-critical and asks why the Daily Assistant run failed. They suspect brittle JSON (“adjacent”) requirements, ask whether commentary breaks parsing, question whether highly structured output is necessary, and consider file writing as an alternative. They then identify the crucial behavioral clue: earlier compaction looked correct, while later compactor output was strange and appeared to misunderstand the conversation history instead of returning compacted memory. On clarification, the user rejected adding a hierarchy of XML tags: keep one history block and its rendered content, make only a few wording refinements in the otherwise preserved `agent.md` so it explicitly describes summarizing a target agent's conversation history, and add only a concise user-message identification plus a visible plain-text start/end boundary. After reviewing the exact generated prompt, the user found its overall section order acceptable and characterized the original `agent.md` as approximately 98–99% correct; no prohibitive instruction about continuing/performing actions, removal/reordering of common sections, or post-history task restatement is wanted. After comparing a proposed `items` contract with the original response section, the user explicitly chose the original six-array response instructions unchanged because their detailed field explanations and exact example are already clear and repeatedly tested. The user then approved renaming the sole generic outer tag to `<target_agent_conversation_history>` for an explicit target-agent boundary, without adding a second/nested wrapper.

User verification of the built Electron package later established two additional supported behaviors. First, changing the live ratio from 80% to 20% caused three successful operations in one parent turn before the prompt fell below the new threshold. Second, after the prompt legitimately grew back to the 20% threshold, two visible failures occurred: each parent execution launched an initial and correction child even though all four child LLM requests failed before usable assistant output.

After distinguishing a typed runner failure from invalid model output, the user chose a strict availability policy: compaction is important enough that a final compaction failure must stop the current target-agent turn even when the prompt is below the hard input limit. The user will send a later `continue` message after the provider recovers. That new message is an explicit retry signal, not permission for same-turn or background retries.

Architecture review round 3 then established that this policy needed an origin boundary, not only a pending-presence check. The user approved the simplest resolution: authoritative USER origin alone may retry; agent/system messages remain in the existing queue without starting a turn, invoking the provider, or being dropped. On successful user retry the user turn proceeds first and retained non-user work resumes afterward; failure leaves it queued. The agent runtime remains alive throughout, so this is a turn gate rather than agent shutdown.

On 2026-08-15 the user again changed a live 371,352-token parent prompt from 80% to 20%. Compaction correctly triggered, but the child request was rejected with HTTP 400 `unexpected end of hex escape`. Exact trace correlation proved a local deterministic defect rather than context overflow or provider downtime: middle omission split the shield emoji in a parent tool result, creating a lone surrogate only in the derived compactor prompt. The user approved a reasonable safety correction and agreed that provider-facing conversation history should be made safe while raw source traces remain unchanged. Valid multilingual text and valid emoji are retained; the design does not reduce content to ASCII.

In the discussion immediately before this reproduction, the user articulated a broader product direction: conversation-history compaction may ultimately be a standalone unstructured continuation-summary capability, while episodic/semantic memory is distilled separately from raw/work traces. That separation is architecturally credible, but the user did not explicitly authorize replacing the currently implemented six-array contract in this Unicode-fix round. SR-005 therefore records the narrow proven input-safety defect and preserves the current approved implementation basis. A clean-cut compaction-versus-memory redesign should be handled as a separate requirement/design revision if the user explicitly activates it.

## Constraints / Dependencies / Compatibility Facts

- The model may ignore or misunderstand instructions; syntax and minimum semantic shape require host enforcement.
- The compactor system prompt is persisted in a built-in agent definition but the final processed prompt also includes platform-generated context; both layers matter.
- The renderer's omission of private reasoning/system content and canonical tool-protocol formatting are valuable and should remain.
- One response-contract repair attempt must remain below the pending-operation lifecycle so a recovered usable-but-invalid response does not produce a stale visible failure card; runner failure must bypass this loop.

- The generic `WorkingContextCompactionStrategy` does not mandate JSON; response rules remain within the production strategy/summarizer boundary.

- Unicode repair/sanitization applies only to derived compaction/provider text. Raw trace/tool values and canonical stores remain unchanged, and safe truncation must preserve configured bounds and omission semantics.

## Open Unknowns / Risks

- Exact model behavior cannot be guaranteed; a syntactically valid envelope can still contain an incomplete or inaccurate summary. This remains a compactor-quality risk beyond deterministic contract validation.
- Architecture design must refine the compactor-authored identity/instructions without reordering the generated common sections, and must preserve the current history renderer output unchanged inside the minimal boundary.
- Design resolution: the correction uses a new child run because the runner owns one create/post/collect/terminate lifecycle per call; this avoids inheriting the misdirected child conversation and yields distinct run IDs.
- One repair increases worst-case latency/token usage; final design should keep the budget fixed at two attempts and preserve interruption/timeout cleanup.
- A future file-backed transport may be useful for a demonstrated truncation/transport problem, but must be independently designed with isolated staging and least authority.
- The exact provider/response-ingestion error for the four newest child runs is unavailable because current retained events/traces preserve only generic request recovery. Quota/rate limiting is plausible but unproven.
- The intended REQ-014/REQ-015 outcome is strict and user-controlled. Every final compaction failure stops the current target-agent turn and leaves the pending request in `awaiting_user_retry`; no timer, provider retry, or automatic re-arm scheduler is needed. A distinct USER-origin turn executes the pending operation once before dispatch. AGENT/SYSTEM entries stay in the existing queue and resume after successful recovery. Proactive-versus-hard-cap pressure remains diagnostic, not a reason to bypass compaction.
- Compactor-model input-capacity preflight/chunking remains a separate future topic; the four newest attempts were only about 191k characters and no evidence establishes context overflow.
- The earlier four generic request-recovery failures remain causally unobservable, but the separate 2026-08-15 HTTP 400 is fully explained by the captured lone surrogate. Do not generalize the proven Unicode cause backward to those older children.
