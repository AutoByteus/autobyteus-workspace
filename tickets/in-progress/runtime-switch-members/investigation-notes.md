## Findings

| ID | Finding | Established by |
| --- | --- | --- |
| F-01 | **Why the first delivery was a single agent.** A standalone run keeps its provider binding in its own `run_metadata.json` (`runtimeKind`, model, `platformAgentRunId`), edited by `StandaloneStoppedRunSelectionUpdater` and activated by `StandaloneAgentRunLifecycleService`. A member's binding is part of the saved structure of its root (`ConfiguredAgentExecutionNode` in the Team/Org execution tree; a copy's in the coordinating run's tree plus its own run file), edited by the Team/Org mutators and activated through each root's handle. The team recommended the single run as the smaller slice; the user accepted it (2026-10-30). | Read: `agent-run-metadata-types.ts`, `run-execution-tree-shared-records.ts`, `docs/modules/agent_team_execution.md` |
| F-02 | **One activation path for every member kind.** `ConfiguredAgentExecutionHandle` is "the root-neutral owner of one configured or task AgentRun's provider/local mechanics" (`agent-collaboration/execution/backends/configured-agent-execution-handle.ts`). Team members, Org members and delegated copies are all built by `RootAgentExecutionRegistry.createHandle(sourceNode: TeamRunAgentNode, mode, …)` from a flat `TeamRunAgentNode` (`root-agent-execution-registry.ts:300-345`), and activate through `initializeReady`: plan and prepare a candidate, `callbacks.commitPlatformBindingChange(change)` (the root persists under its lock), then `commitPublication` (`handle:354-390`). The plan comes from `ConfiguredAgentActivationPlanner` (`configured-agent-activation-planner.ts`): `new`, `restore_native`, `restore_external`, or `replace_external_without_conversation`, decided by the member's conversation activity. | Read |
| F-03 | The three roots implement the same seam: `commitAgentPlatformBindingChange(change)` in `RootTeamRun` (via `TeamAgentPlatformBindingCommitter`), `AgentOrgRun` (`agent-org-run.ts:292`) and `StandaloneAgentRunRoot` (`standalone-agent-run-root.ts:378`; its delegated copies), each applying an `adopt…`/`replace…` tree mutator under its persistence lock before the cache update and publication. The change type has two kinds today, `adopt_or_retain` and `replace_without_conversation` (`collaboration-agent-platform-binding.ts`). A native member stages no binding. | Read |
| F-04 | **Team edit.** Patches target the root Team `/` (its default launch, which followers follow through the browser's planner) or one exact configured Agent address; `TeamRunModelConfigMutator` replaces only `llmModelIdentifier` and `llmConfig` ("cannot change runtime kind, workspace, … provider bindings"). Org: `AgentOrgRunConfigMutator` resolves Org, mounted-Team and Agent scopes and patches the same two fields. Both run in the root's transition lane and refuse a managed (running), fail-stopped, archived or application-bound root. | Read: `team-run-model-config-mutator.ts`, `agent-org-run-config-mutator.ts`, `docs/modules/agent_team_execution.md`, `agent_orgs.md` |
| F-05 | **Delegated copies.** The user's choice per copy is `userLaunchSelection {llmModelIdentifier, llmConfig, selectedAt}` on the agent-level record and `userTeamLaunchSelection` on a Team-level record, beside the started launch which is never changed (DEC-005, AR-005). `effectiveCopyAgentLaunch` is the one rule (own choice, else the Team's for a follower, else started); `withCopyLaunch` applies it to a `TeamRunAgentNode` (model and settings only today). The copy's own `run_metadata.json` carries a `taskAgent` section with the same selection. 14 code sites touch `userLaunchSelection` (records, schemas, own-file records, restoration, the selection domain, projectors). A copy may be edited while the root runs, if the copy itself is stopped (`delegated-launch-selection-service.ts`, `docs/modules/agent_communication.md`). | Read |
| F-06 | **Memory and views are per run folder and not runtime specific.** Member memory sits at `agent_teams/<team>/<agentRunId>/…`; task agents at `agents/<taskAgentRunId>/`; recording, the raw-trace archive, the journal, the chat projection (when given the member's memory folder) and the hand-over notice (a preface source on every run of the shared `AgentRunManager`) are the standalone run's. Memory discovery takes a member's runtime for the journal target from `configuredPlacement.launchConfiguration.runtimeKind` / the task member's launch (`memory-run-discovery.ts:100-150`), so the open-file rule of 316 (`openRawTraceRuntimeKind`) must reach those three lists. | Read |
| F-07 | The web already carries the runtime in a selection (`ExistingRunModelSelection.runtimeKind`, added by 316), the hierarchical planner has a per-scope `runtimeKind` and links followers by equality of runtime, model and settings, and the patch it plans spreads the draft selection; the member rows and the delegated rows pass `runtime-locked`. | Read: `existingHierarchicalModelConfigDraft.ts`, `ExistingRunSettings.vue:70,85` |
| F-08 | `ConfiguredAgentExecutionHandle.replaceModelChoice` swaps a stopped copy's model on the live handle while its root runs; a runtime switch needs the same for the runtime and the pending switch. | Read: `configured-agent-execution-handle.ts`, `configured-agent-execution.ts` |
| F-09 | **Unclear:** (a) whether a copy's own `run_metadata.json` is projected from its tree record at every commit (so that new optional fields need only be added to the projection) or written by a second path; (b) the exact reader list of `userLaunchSelection` for the web DTO projections (`collaboration-execution-tree-dto-projection.ts`, `team-execution-view-projector.ts`); (c) settled by reading: `AgentConversationActivityInspector.inspect` reports `present` when a `user` or `assistant` trace exists in the active file or any complete archived segment, `none` otherwise, `indeterminate` for damaged data (`agent-conversation-activity-inspector.ts`); a marker-only file is `none`, a switched member's archive keeps it `present`. | (a), (b) to read in the architecture review and the implementation |
