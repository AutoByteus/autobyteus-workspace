# Requirements Doc — Secure Centralized Secret Provisioning (Clean-State Revision)

## Status (`Draft`/`Design-ready`/`Refined`)

`Design-ready — user-approved for architecture review. The clean-state basis remains approved, and the packaged existing-user custom-provider-v1 transition now uses automatic one-time migration with a simple delete-and-reconfigure failure path. Implementation, API/E2E, and delivery remain unauthorized until a passing architecture gate.`

This document supersedes the earlier incremental requirements package. Earlier review, implementation, test, and delivery reports remain preserved as evidence, but they are not authority for the target architecture unless this document explicitly retains the behavior.

## Goal / Problem Statement

AutoByteus must keep provider, model, media, search, agent-runtime, custom-provider, desktop, Docker, and testing functionality working while moving credential values out of plaintext application configuration and provider metadata.

The target must be substantially simpler than the superseded design:

1. each running environment selects one SQLite application database through `DATABASE_URL`;
2. encrypted secrets are ordinary application-owned records in that same database;
3. one automatically generated external root-key sidecar protects those records;
4. provider implementations obtain a narrow `ProviderApiKeyResolver` and resolve their own credential at the point where they construct the provider SDK/client;
5. model catalogs and model definitions remain independent of credential availability;
6. test Store selection is simply test application-database selection, not a separate backend manifest or second Store database;
7. every importer invocation receives its target explicitly as `--database-url`; it never infers a target from `.env`, `.env.test`, the assignment source, or parent process state.
8. the API-key Settings screen receives each provider exactly once through one `ProviderSettingsGroup`: the existing `LlmProviderObject` plus four existing `ModelDetail` lists grouped by LLM/audio/image/video capability. The read reorganizes existing working contracts instead of inventing reduced duplicate DTOs; existing catalog APIs remain available to their other consumers and model catalogs remain credential-independent;
9. the fixed application-owned custom-provider-v1 file receives one bounded startup migration into current secret-free metadata plus encrypted vault entries; if preservation cannot complete safely, the legacy file is deleted and the application stays usable so the user can reconfigure from the frontend.

Security is an implementation quality of existing functionality, not permission to remove, hide, or silently change supported product behavior.

7. Google’s current Gemini Developer API documents `models.list`; the current Express REST reference documents `countTokens`, `generateContent`, and `streamGenerateContent`, not a model-list route.

## Design Health Assessment (Mandatory)

- **Change posture:** large security refactor, data-model simplification, cleanup, and behavior preservation.
- **Root-cause classification:** boundary/ownership issue, duplicated policy/coordination, shared-structure looseness, and legacy/compatibility pressure.
- **Refactor needed now:** yes.
- **Why:** the superseded package made credential custody a separate deployment/runtime subsystem and allowed authentication/configuration concepts to influence catalogs and model construction. It also represented the same provider/configured fact repeatedly inside capability-specific catalog rows and then proposed a separate reduced Settings DTO family despite established working provider/model types. Both directions duplicate authority.
- **Clean response:** make `DATABASE_URL` the sole application-database selector; keep one secret lifecycle owner, one Prisma repository, one external root-key owner, one narrow provider resolver port, provider-owned point-of-use resolution, and credential-independent catalogs. Give the API-key screen one provider-centric grouped read that reuses established provider/model types, keep existing catalog-query consumers intact, and delete duplicate credential-status/merge machinery without adding a replacement DTO family.

## Recommendations

1. Submit the fully aligned custom-provider migration/delete-and-reconfigure behavior for architecture review; the user has authorized this handoff.
2. Preserve the current branch and downstream evidence, but treat current source as a refactor input rather than target authority.
3. Use normal Prisma migrations for the two secret tables in the selected application database.
4. Use a deterministic database-adjacent root-key path and make backup/restore treat database plus key as one pair.
5. Keep the resolver API narrow and storage-neutral; do not expose `SecretManagementService`, Prisma, secret IDs, or backend details to `autobyteus-ts` provider clients.
6. Delete superseded structures in the same implementation rather than maintain adapters or dual paths.

## Functional Requirements

- `REQ-001` One GraphQL field, `providerSettings(runtimeKind: String)`, must serve the API-key Settings screen and return each displayed provider exactly once as `ProviderSettingsGroup { provider, llmModels, audioModels, imageModels, videoModels }`. `provider` must reuse the existing `LlmProviderObject`; the existing `apiKeyConfigured` Boolean is computed once by the exact provider owner and is never taken from a capability/model occurrence or another provider. For ordinary key-backed providers, it is `true` only for the exact confirmed vault slot and otherwise `false`. For Gemini, it preserves the established aggregate meaning: `true` when AI Studio or Vertex Express is confirmed configured, or when Vertex Project has complete project/location configuration; active-mode selection remains exclusively in `GeminiSetupState`. The four non-null lists must reuse the current `ModelDetail` type unchanged, including current metadata fields, and use `[]` when that provider has no models for a capability. The group is a page-level organization of existing contracts, not a new reduced provider DTO, model-summary DTO, capability availability wrapper, status-message protocol, or model definition. The backend composition owner must join provider and model data by exact provider ID. The web must consume this one grouped collection directly, without merging four repeated provider arrays or maintaining a second credential-state map. Catalog membership must not depend on credential presence, validity, or vault readiness. Existing catalog queries remain supported for their current non-Settings consumers; this requirement does not contract or replace their `ModelDetail` contract.
- `REQ-002` One canonical SQLite database URL must be the only physical database selector for both ordinary application data and encrypted secret data. A running application obtains it from `DATABASE_URL`; the standalone importer obtains it only from its required `--database-url`. The shared `ApplicationDatabaseLocation` owner must normalize the running application’s relative file URL exactly once against `AppConfig.getAppRootDir()`—never a downstream caller’s working directory—and must require the importer URL to identify an absolute SQLite file before Prisma, migration, vault, inspection, importer execution, and diagnostics use the canonical location.
- `REQ-003` Normal Prisma migrations must create `secret_entries` and `secret_encryption_metadata` in the selected application database before vault initialization.
- `REQ-004` The root key must be exactly 32 random bytes, generated with the platform cryptographic RNG, stored only in the derived owner-only sidecar, never auto-regenerated over an established metadata domain, and verified value-free on every startup.
- `REQ-005` Secret encryption must use AES-256-GCM with a fresh 12-byte nonce and 16-byte tag per entry, HKDF-SHA-256 per-entry key derivation bound to `encryption_domain_id` and `secret_id`, and version/domain/ID-bound AAD. Wrong key, tampering, missing paired state, or unsupported format must fail closed.
- `REQ-006` `SecretManagementService` must own write-only save/replace, idempotent remove, value-free configured checks, health, and authorization. GraphQL/UI/provider services must expose only provider-specific operations; no generic raw-secret read API exists. Ordinary provider Save/Remove returns only Boolean command completion; the caller already knows the exact provider ID and refetches `providerSettings` for authoritative state. Custom Probe/Create input must be exactly name, base URL, and transient key; the server owns the sole custom type/runtime. Probe returns only discovered `{id,name}` models, Create only the assigned provider ID, and Delete only Boolean completion. Failures use the typed GraphQL error path rather than `statusMessage` or `instructionCode`. The web must not maintain a second credential map or search another provider's configured state.
- `REQ-007` `ProviderApiKeyResolver` must remain storage-neutral, injected through the existing factory/client construction path, and called lazily by the concrete provider at SDK/client initialization. `autobyteus-ts` must not import server secret-management, Prisma, filesystem, environment aliases, or a service locator.
- `REQ-008` Model definitions, model metadata, runtime models, LLM/media configuration, GraphQL model-catalog DTOs, and catalogs must contain no authentication requirement, secret ID, credential-provider ID, resolved secret, Store/backend field, or provider credential state. The API-key screen reuses the current `ModelDetail` objects inside its grouped read; this transport reuse does not give models credential authority and does not change the credential-free model-catalog contract used by selectors/runtimes.
- `REQ-009` Secret identities must use stable provider-owned `SecretId` values. Google IDs must be `provider.google.ai-studio.api-key` and `provider.google.vertex-express.api-key`; the old `provider.gemini.ai-studio-api-key` name has no compatibility alias. OpenAI LLM/audio/image share `provider.openai.api-key`.
- `REQ-010` Gemini option save/remove must be independent. One explicit non-secret `GEMINI_SETUP_MODE` (`AI_STUDIO`, `VERTEX_EXPRESS`, or `VERTEX_PROJECT`) is the sole runtime authority. The concise UI must distinguish configured from active, expose `Use this mode`, never prefill secrets, and keep at most one editor expanded. The specialized query and every Gemini mutation return the same exact `GeminiSetupState`: nullable `activeMode`, nullable AI Studio/Vertex Express configured booleans, and nullable complete Vertex Project `{project,location}`. Save is three option-specific commands—key only, key only, or project+location—with one required `activateAfterSave` Boolean; generic nullable field bags are forbidden. `useGeminiMode` and `removeGeminiConfiguration` accept only the exact mode union. Mutation responses must not add operation, outcome, stage-outcome, or instruction-code fields. The actual returned state lets the UI detect a partial compound action without a parallel protocol. Absent/invalid/incomplete selection is closed and visible; only the selected slot/configuration is used, with no priority, alternate-key retry, save-order inference, or fallback.

## Persisted Data Outcome (When Applicable)

- **Existing ordinary application SQLite data:** `Directly Usable — No Migration`. Normal Prisma migrations add the two new tables.
- **Unreleased superseded separate Local Store DB/key/test state:** `Discard or Rebuild`. It is not a target runtime authority and receives no compatibility reader or data mover.
- **Legacy plaintext application `.env` credential aliases:** `Discard or Rebuild` as runtime authority. Files remain operator-owned/untouched; users explicitly reconfigure/import.
- **Fixed application-owned custom-provider-v1 file:** `Migration Required`. Complete valid data is transformed once into secret-free v2 metadata plus encrypted entries. If preservation cannot complete safely, the legacy file is deleted and the canonical current state becomes empty so the user can reconfigure without losing application availability.
- **Tracked test scenario manifest:** `Discard or Rebuild`; scenarios move to test code/internal fixtures, while non-secret database and Gemini-mode selection move to the small test environment config.
- **New `GEMINI_SETUP_MODE` setting:** `Directly Usable — No Migration`; absence means `Not selected`. The user or a test explicitly selects a mode through the normal Settings/API command, which persists it in that environment's ordinary writable runtime configuration. The committed `.env.test` never owns or rewrites this mutable selection. No implicit priority initializes it.
- **New database/root-key pair:** must be preserved together after first use; loss of either established component is a closed recovery/restore condition, not automatic regeneration.

## Assumptions

1. Supported production databases are SQLite file URLs.
2. The application configuration owner can canonicalize relative SQLite URLs against one documented application root before consumers use them.
3. Tests can use a disposable application database and therefore do not require a secret-specific read-only mode.
4. A same-user local attacker is outside strong-isolation claims; owner-only files and least exposure still materially improve credential custody.
5. Existing provider/model behavior is the compatibility baseline except where this document explicitly approves a change (provider-centric API-key Settings grouping, independent Gemini option persistence/removal, secure custody, and simplified test configuration).
