# Secure Centralized Secret Provisioning — Requirements

## Status (`Draft`/`Design-ready`/`Refined`)

`Refined — CR-001 Requirement-Gap Revision; User Approved; Architecture Re-review Required` (2026-07-21). Architecture review round 4 authorized the previously approved package and implementation reached source review. Source review then found that the solution basis omitted supported AutoByteus remote LLM/audio/image discovery and construction authenticated by `AUTOBYTEUS_API_KEY`; the implementation consequently disconnected that production path. This revision formalizes the preserved behavior as BEH-013/REQ-019/AC-019 and UC-018. The user explicitly required all existing functionality to remain while only key provisioning moves through the new secret storage. CR-002–CR-005 remain bounded implementation/packaging corrections. No rework is authorized until architecture review passes this revision. All prior in-process/separate-Store/Docker/Claude decisions remain unchanged, including `EXT-ANTHROPIC-AGENT-SDK-AUTH`.

## Goal / Problem Statement

AutoByteus currently places many provider credentials in ignored `.env` or `.env.test` files and loads them into broad `process.env` state. Agent file, terminal, PTY, external-runtime, and worktree flows can consequently encounter or inherit credentials, and every new worktree may require a human to locate or copy an ignored test file before real-provider coverage can run.

The product needs a server-owned secret-management boundary that:

- keeps raw AI, search, media, custom-provider, and live-test credentials out of repositories, worktrees, ordinary configuration, agent-visible files, and inherited environments;
- supports Electron, direct local server, Docker, Kubernetes, and company-managed infrastructure without making Electron mandatory;
- treats each local Docker container or single Kubernetes server Pod as an independent node with its own persistent Local Store, while requiring a future separately installed enterprise adapter for multi-node/replica centralized custody;
- lets the server choose a replaceable `SecretStorageBackend` at startup or through non-secret Settings configuration;
- provides an in-process AutoByteus `LocalSecretStorageBackend` for local use without a daemon, local network server, IPC protocol, or Electron-owned custody;
- derives the normal Local Store from each server's configured data directory, so the existing Docker server-data volume persists its own Store without new Compose mounts or environment variables;
- keeps normal local credentials and real-E2E credentials in physically separate encrypted SQLite databases with independent encryption keys;
- lets a developer provision the real-E2E Store once, after which every tracked worktree can run real-provider tests without copying `.env.test` or requesting the key again;
- preserves a typed extension contract for companies to add Kubernetes, Vault, AWS, or company-specific backends, while explicitly deferring those concrete adapters from the first delivery;
- resolves a credential before LLM/client construction without storing it in serializable `LLMConfig` or coupling individual clients to secret storage.
- lets the Claude Agent SDK explicitly opt into the same managed Anthropic definition without duplicating the stored value, while delivering the resolved value only to the exact Claude Code child environment just before spawn.
- preserves AutoByteus remote LLM/audio/image discovery and invocation through one managed `provider.autobyteus.api-key` definition, while keeping `AUTOBYTEUS_LLM_SERVER_HOSTS` as non-secret endpoint configuration and never restoring an ambient key read.

The first delivery claims `LOCAL_HARDENED`, not strong isolation. It removes plaintext repository/worktree/config custody, broad child-environment inheritance, ordinary value readback, and built-in file-tool Store access. In Claude `managed-secret` mode, the exact Claude Code child is an intentionally authorized credential consumer and necessarily receives the Anthropic key in its own process environment; supported process-spawning/environment-inspection tools and settings paths must not propagate or expose it. The tier does **not** claim protection from that authorized Claude process or its SDK/executable, an unrestricted same-user shell/process, the current all-in-one container identity, a privileged host/debugger, a compromised trusted server/provider process, code explicitly granted a raw real credential, or the upstream provider. `STRONG_AGENT_ISOLATION` and its separate identity/container/network enforcement are a future delivery.

## Investigation Findings

1. `AppConfig` loads `${dataDir}/.env` through dotenv into `process.env`, writes provider/search credentials back to it, and mixes secret/non-secret ownership.
2. `OpenAILLM` delegates to `OpenAIResponsesLLM`, which reads `process.env[apiKeyEnvVar]`; `LLMFactory.createLLM()` is already async and currently accepts `(modelIdentifier, configInput?)` before invoking `(model, LLMConfig)`.
3. `LLMConfig` serializes/clones and can flow into retained run configuration or provider request parameters; it is not a safe credential carrier.
4. Search, media, metadata discovery, and custom OpenAI-compatible providers have parallel ambient credential paths, so an LLM-only change would be incomplete.
5. Test setup explicitly loads superrepo/package `.env.test`; real LLM/agent/media/search tests gate on environment keys. Fakes cannot replace scenarios intended to detect real provider/model/SDK behavior.
6. All `.env.*` files are currently broadly ignored in package `.gitignore` files. Non-secret test configuration can be tracked after explicit ignore exceptions, but typed `test-config/live-e2e.json` is clearer than global dotenv as the canonical scenario/store contract.
7. Electron, direct Node server, Docker, Kubernetes, and remote-node operation are all supported deployment shapes. The custody boundary must therefore be server-selected and not Electron-owned.
8. The current server database is SQLite through `DATABASE_URL`. Electron resolves it to `~/.autobyteus/server-data/db/production.db`, while test/direct servers can select `test.db` or a worktree/data-directory-specific database. Storing real-E2E secrets as rows in the ordinary application database would therefore recreate worktree coupling or force tests to mount/use normal application state.
9. The current Docker Compose configuration already persists `AUTOBYTEUS_DATA_DIR=/home/autobyteus/data` through the `autobyteus-server-data` named volume. The normal Local Store can live below that directory and persist automatically. This ticket leaves the Docker topology, volumes, and launcher unchanged and does not attempt to share the host real-E2E Store with Docker.
10. Kubernetes supplies Secret values to Pods via explicit volume mounts or environment variables, while workload identities can let the trusted server fetch from external managers. Any mount/environment/service-account identity visible to an agent shell in the same container remains reachable.
11. The product currently has no AutoByteus user, role, owner-principal, or administrator-identity subsystem. Backend workload identity authenticates the server to custody and is distinct from application-user identity. This ticket preserves existing Settings access behavior.
12. A separate Local Store process under the same OS user would add lifecycle/IPC/versioning complexity without creating a meaningful security boundary. SQLite already supports multiple local server processes through transactions/locking, and the server already owns secret resolution. The Local backend therefore runs in Agent Server.
13. Separate default and real-E2E databases satisfy the approved host/local two-context requirement with less policy than arbitrary named profiles. They allow independent keys and independent reset/backup without imposing a Store-sharing model on Docker deployments.
14. The second-principles audit found no supported caller for organization/deployment/environment scope fields, caller-selected storage addresses, Settings CAS/version inputs, a Local Store connection alias, arbitrary profiles, or a general backend cross-store copy port. Those elements are removed rather than standardized.
15. Architecture review round 1 confirmed that format metadata alone cannot authenticate an empty database/key pair. The current Store format therefore requires a random `store_id` plus an authenticated pair verifier created with the root key and validated before any Store becomes ready.
16. The first-delivery security boundary must be explicit: Local custody plus clean environments/file-tool roots is `LOCAL_HARDENED`; strong same-user/container isolation requires a later separate-identity enforcement delivery.
17. The existing `SecretManagementService.resolveForUse(consumer)` API is already the correct generic resolution boundary. Claude support requires a precise `agentRuntime/claude_agent_sdk/apiKey` consumer identity and catalog authorization, not a Claude-specific secret API or a second stored Anthropic key.
18. The pinned Claude Agent SDK accepts an explicit child `env`; the current AutoByteus wrapper instead begins with the broad parent environment. Managed mode can therefore resolve just in time and build an empty-base child environment, but the authorized Claude executable necessarily observes its own credential and JavaScript cannot guarantee zeroization.
19. Managed mode must remove supported descendant leak paths: no caller-provided `env`; SDK `tools: []` disables all Claude built-ins rather than relying on `allowedTools`; no user/project/local settings, hooks, plugins, or external MCP configuration can inject/spawn with the credential. Explicit AutoByteus-owned MCP tools execute outside the Claude child through sanitized server launch policy.
20. Anthropic's current official authentication guidance is inconsistent. The Agent SDK overview/legal page says third-party products should use API keys and may not offer Claude.ai login without approval, while the newer-dated June 15–16, 2026 Help Center update says Agent SDK, `claude -p`, and third-party app usage still draw from subscription limits during the paused billing change and explicitly identifies third-party apps authenticated through the Agent SDK. This establishes that the round-3 premise is not unambiguous. Current AutoByteus also successfully exercises the local CLI path; that proves technical reachability, not permission by itself. The user retains both modes and requires release-time monitoring of the authoritative policy conflict.
21. Source review proved a supported path absent from the earlier solution basis: base `LLMFactory` initialization/provider reload and audio/image factory discovery called AutoByteus remote providers, whose `AutobyteusClient` read `AUTOBYTEUS_API_KEY`. The implemented explicit-auth conversion correctly made that client require a supplied key but removed all production discovery callers, so configured remote models disappeared.
22. One definition is sufficient because the same AutoByteus gateway key authenticates discovery and runtime requests across LLM, audio, and image. Least privilege still requires distinct semantic consumers: `modelDiscovery/{llm|audio|image}/AUTOBYTEUS/apiKey`, `llm/AUTOBYTEUS/apiKey`, and `media/{audio|image}/AUTOBYTEUS/apiKey`.
23. A remote model's creator/provider identity is not necessarily its credential owner. Model registration materializes a required non-secret `credentialProviderId`: native definitions assign their known credential owner once, while AutoByteus-runtime models explicitly assign `AUTOBYTEUS`. The construction target omits displayed/creator provider and exposes only credential owner plus its tagged authentication requirement. This avoids duplicated factory/runtime branches and prevents an AutoByteus-hosted OpenAI model from resolving `provider.openai.api-key`.
24. `AUTOBYTEUS_LLM_SERVER_HOSTS` remains non-secret endpoint configuration. It is preserved by migration and remains visible/editable through the existing server endpoint settings. `AUTOBYTEUS_API_KEY` is a migration-only alias that is scrubbed, recorded as reprovision-required for `provider.autobyteus.api-key`, and unavailable to normal runtime.

Exact source paths and refreshed evidence are recorded in [investigation-notes.md](./investigation-notes.md). The target diagrams are in [secret-storage-architecture.md](./secret-storage-architecture.md).

## Design Health Assessment (Mandatory)

- Change posture: `Larger Requirement` — security-boundary feature plus cross-cutting refactor.
- Initial design issue signal: `Yes`.
- Root cause classification: `Boundary Or Ownership Issue` reinforced by `Duplicated Policy Or Coordination` and `Legacy Or Compatibility Pressure`.
- Refactor posture: `Needed` in this change.
- Evidence basis: generic configuration owns secrets; consumers read ambient process state; worktrees duplicate ignored credential bootstrap; agent processes inherit trusted state; custom metadata embeds keys; deployment packaging has no single backend contract.
- Requirement or scope impact: introduce one lifecycle owner above backend adapters, explicit client-construction authentication, in-process local custody with physically separate default/real-E2E Stores, tracked non-secret test configuration, backend capability reporting, legacy cutover, and agent execution isolation. Do not introduce an unrelated user/admin subsystem, daemon, IPC protocol, or arbitrary profile framework.

## Recommendations

1. Adopt dependency direction `ConsumerProvisioningService -> SecretManagementService -> SecretStorageBackend`.
2. Implement `LocalSecretStorageBackend` as an in-process Agent Server component. Do not create a daemon, TCP/HTTP service, socket/named-pipe protocol, launcher, or Electron-owned store.
3. Use a separate encrypted SQLite file and independent key for normal local custody and real-E2E custody. Bind one backend instance to one bootstrap-configured Store path; requests cannot select another Store.
4. Require dedicated real-test credentials to be provisioned directly into the real-E2E Store. Do not ship default-to-E2E copy in the first delivery; setup has no default-Store read path and no automatic inheritance/fallback.
5. Track all non-secret test configuration. Canonicalize live scenario/Store mapping in typed JSON; retain/commit `.env.test` only for verified non-secret settings if existing tooling still needs it.
6. Keep the existing Docker Compose topology, persistent volumes, and launcher unchanged. A normal Docker node derives its Local Store below `AUTOBYTEUS_DATA_DIR` and users configure credentials on that node through the normal product flow. Do not prescribe a Docker real-E2E mount; operators remain free to customize their deployment outside this ticket.
7. Make each backend expose one tagged lifecycle capability: `WRITABLE` or `EXTERNALLY_MANAGED`. Settings writes are available only for writable backends; externally managed deployments show status/instructions.
8. Keep `LLMFactory` responsible for model lookup/default merging. Pass resolved authentication separately and construct `LLMConstructionContext` internally.
9. Ship only InMemory (test) and Local adapters initially. Preserve a typed registration/capability/conformance extension contract for future Vault/AWS/Kubernetes/company adapters; do not imply that centralized multi-node custody ships in this ticket.
10. Remove environment/custom-record fallback and migrate/reprovision cleanly.
11. Enforce first-delivery realpath-aware file-tool roots, empty-base process-environment allowlists, descriptor hygiene, redaction, and honest `LOCAL_HARDENED` reporting. Defer `STRONG_AGENT_ISOLATION` until separate identity/container/network enforcement is delivered and verified.
12. Replace Claude's ambient auth selection with explicit `cli | managed-secret`. Keep `cli` as the default external-account path. In managed mode, reuse the existing generic `resolveForUse` service with the exact Claude runtime consumer, deliver only to the exact SDK child, block supported settings/tool/diagnostic leak paths, and never copy parent environment or fall back between modes.
13. Preserve AutoByteus remote LLM/audio/image behavior through one managed gateway definition, distinct discovery/construction consumers, and a server-owned discovery service. Keep downstream model provider identity separate from `credentialProviderId`; synchronize remote registrations by runtime/source, not by downstream provider.

## In-Scope Use Cases

- `UC-001` **Built-in provider credential lifecycle:** configure, replace, inspect value-free status, or remove a built-in provider key from direct web or Electron Settings through the server's writable selected backend.
- `UC-002` **Custom provider lifecycle:** probe and create an OpenAI-compatible provider from transient credential input, persist metadata without the value, construct/discover using the derived definition, and delete provider plus credential without readback.
- `UC-003` **Backend configuration:** configure backend kind and non-secret adapter options through deployment/startup configuration and supported Settings surfaces.
- `UC-004` **Local backend bootstrap:** Electron embedded, direct local, normal Docker, and single Kubernetes server-Pod deployments construct the Local backend in process. Normal use derives the default Store below that independent node's configured data directory/persistent-volume domain; tracked host live-test configuration explicitly selects the separate real-E2E Store.
- `UC-005` **Physical Local Store lifecycle:** initialize and inspect one configured encrypted Store database/key pair, authenticate the pair even when no secret records exist, reject mismatched/corrupt/unsupported Stores, and keep each Store independent. No arbitrary named-profile lifecycle exists.
- `UC-006` **Real-E2E Store provisioning:** directly provision one selected definition into the separate real-E2E Store through trusted hidden input, without value readback and without any default-Store access or copy path.
- `UC-007` **LLM construction and invocation:** create an LLM using resolved authentication and a secret-free `LLMConfig`, then complete a provider request/stream.
- `UC-008` **Non-LLM client construction:** provision search, media, and live-metadata clients through equivalent explicit subject boundaries and complete their provider operation.
- `UC-009` **Deterministic testing:** run default unit/integration/UI coverage with synthetic values and temporary stores where storage behavior matters, without real backend/provider credentials.
- `UC-010` **Real-provider worktree testing:** run substantive real-provider API/E2E from any fresh host worktree using tracked non-secret configuration and the once-provisioned host real-E2E Store. Docker E2E Store sharing is not prescribed.
- `UC-011` **Local backend concurrency/reset lifecycle:** multiple local worktree servers may read the same real-E2E Store; writes are transactional/locked. Ordinary server runtime-data reset preserves Local Stores; a confirmed Store reset targets exactly one physical Store.
- `UC-012` **Container deployment and extension boundary:** deploy one independent Local Store per unchanged Docker node or single Kubernetes server Pod/PVC. Multi-node centralized custody requires a separately installed future Vault/AWS/Kubernetes/company adapter; first delivery rejects unregistered kinds value-free.
- `UC-013` **Capability-aware Settings:** represent writable versus externally managed backend behavior so lifecycle actions are enabled only when supported.
- `UC-014` **First-delivery agent hardening:** prevent built-in file-tool Store access and provider/backend state inheritance through purpose-built environments while preserving authorized workspace behavior; report `LOCAL_HARDENED` and explicitly withhold strong same-user/process isolation.
- `UC-015` **Legacy cutover:** preserve non-secret metadata/configuration, remove legacy plaintext credential paths, record affected definition IDs, and start only the current secret-free runtime.
- `UC-016` **Backend conformance:** validate every enabled backend implementation against its base resolve/status/health contract and declared lifecycle capability using synthetic values and isolated temporary stores.
- `UC-017` **Claude runtime authentication cutover:** select exactly default `cli` or explicit `managed-secret`; launch CLI mode without secret resolution, or resolve the exact Claude runtime consumer just in time and deliver `ANTHROPIC_API_KEY` only to the Claude Code child. Both paths use empty-base purpose-built environments, no fallback, value-free failures, early diagnostic redaction, and no caller-supplied environment. Native Anthropic consumers remain separately authorized to the same definition.
- `UC-018` **AutoByteus remote model gateway lifecycle:** save/status the AutoByteus gateway credential through the existing provider Settings flow; discover and reload remote LLM/audio/image catalogs using explicit Store-backed authentication; retain downstream provider metadata while tagging `credentialProviderId=AUTOBYTEUS`; construct/invoke a selected remote model with the same definition; and run the corresponding real-E2E capabilities without `AUTOBYTEUS_API_KEY` in runner/server environment or tracked files.

## Out of Scope

- A new AutoByteus user, login, role, administrator principal, or route-authorization system.
- Protection from a privileged host operator/debugger or compromised trusted provider/control process.
- Making a raw credential unknowable to reviewed code or an SDK process that must receive it directly.
- Any concrete Vault, AWS, Kubernetes Secret, or other centralized enterprise adapter in the first delivery; only the extension contract is in scope.
- General migration of unrelated messaging, release, signing, callback, or build-system credentials.
- Changes to existing Docker Compose topology, named volumes, or launcher behavior, including a prescribed Docker real-E2E Store mount.
- Arbitrary named local profiles, profile inheritance, or per-request Store selection.
- Automatic cross-Store inheritance or fallback.
- Default-to-real-E2E secret copy; first delivery supports direct dedicated E2E provisioning only.
- Automatic import of existing plaintext values into the new Store.
- A Local Store daemon, network service, IPC protocol, process launcher, or OS-specific keychain integration.
- `STRONG_AGENT_ISOLATION`, separate OS/container identity enforcement, or a claim that same-user/all-in-one agent processes cannot read the Local database/key pair.
- Automatic Claude authentication selection, ambient raw-key inheritance, and legacy `auto`/`api-key` modes. Explicit managed-secret authentication is in scope.
- Inventing proprietary cryptographic algorithms; the local backend must use vetted authenticated-encryption primitives.

## Functional Requirements

- `REQ-001` **Typed secret catalog:** every in-scope credential has a stable product-owned definition ID and semantic consumer bindings. Current runtime maps only validated definition IDs to the active backend; adapter-specific physical prefixes/paths remain trusted bootstrap configuration, and migration-only aliases remain outside the current catalog. Runtime/user requests cannot supply backend paths.
- `REQ-002` **No supported plaintext custody:** values are not persisted in repository/worktree `.env`, `.env.test`, application `.env`, JSON metadata, ordinary application database columns, command lines, public frontend config, logs, traces, or artifacts. Local Store values occupy authenticated ciphertext in their dedicated databases.
- `REQ-003` **First-delivery file boundary:** in-process file tools enforce realpath-aware authorized roots and deny Local Store database/key paths, including symlink/traversal aliases. First delivery does not claim that arbitrary same-user processes are filesystem-isolated from those files.
- `REQ-004` **Purpose-built process environments:** terminal, background, PTY, MCP, Codex, Claude, browser/application workers, and future agent-controlled children start from an empty base plus per-runtime allowlists. They receive no unrelated provider-key aliases, Store key/path variables, backend bootstrap identity, secret-bearing inherited file descriptors, or broad `process.env`. The only first-delivery exception is `ANTHROPIC_API_KEY` delivered to the exact Claude Code child after an explicit `managed-secret` resolve under REQ-018; the parent, siblings, AutoByteus-owned tool children, and other runtime children do not receive it. This is environment non-inheritance, not separate-process-identity isolation.
- `REQ-005` **Least-privilege runtime resolution:** only server-owned consumer provisioning services call internal `resolveForUse`; each request names one semantic consumer identity, and `SecretManagementService` maps it through the catalog to one definition. No GraphQL/agent raw-value, list-values, arbitrary-name, backend-path, or secret-dump API exists.
- `REQ-006` **Service above backends and degraded control plane:** `SecretManagementService` owns catalog-bound lifecycle/resolution policy, per-definition status, value-free operation events, and error mapping. `SecretStorageConfigurationService` owns active-backend health. Health is exactly `READY`, `LOCKED`, `UNAVAILABLE`, `CORRUPT`, or `INCOMPATIBLE`; per-definition state is returned only when health is `READY` and is exactly `MISSING` or `CONFIGURED`. Non-ready startup keeps Settings/health reachable in degraded secret mode, disables provider consumers and writes, and returns a value-free instruction code. Subject-specific services still own provider credential validation.
- `REQ-007` **Preserve current Settings access and configure storage separately:** existing subject-specific Settings/GraphQL access behavior remains; no user/admin subsystem is added. Secret inputs are never prefilled or persisted in browser storage, clear after successful submission/when the editor closes, and expose loading/error/status without echo. `SecretStorageConfigurationService` owns typed non-secret backend selection/options separately from provider secret lifecycle. Electron's default Local Store selection requires no ordinary UI control.
- `REQ-008` **Output hygiene:** secret inputs/headers/URL parameters and credential-bearing structures are structurally redacted at GraphQL, error, log, trace, stdout/stderr, telemetry, support, and artifact boundaries. `SecretValue` string/JSON/inspect output is redacted.
- `REQ-009` **Complementary deterministic and real tests:** synthetic/fake coverage remains default where valid. Real-provider suites remain required for scenarios whose purpose includes real authentication, SDK/model/protocol, streaming/tool/media, quota, or provider-specific behavior.
- `REQ-010` **Typed backend selection and capabilities:** server bootstrap selects one backend configuration before provider/model initialization. Every backend supplies the base resolve/status/health contract and one tagged lifecycle capability. A backend instance is bound to one configured custody location; unavailable configuration never falls back to another Store or environment values.
- `REQ-011` **Credential-consuming code refactor:** LLM, metadata, custom discovery, search, and media clients stop reading credential environment variables or retaining keys in model/config records. `LLMFactory.createLLM(id, {configInput, authentication})` composes `LLMConstructionContext` internally.
- `REQ-012` **In-process AutoByteus Local Secret Storage Backend:** Agent Server directly constructs an encrypted SQLite-backed `LocalSecretStorageBackend`; Electron does not own it. No separate process, server, daemon, socket, named pipe, or protocol is introduced. The default Store is derived below the configured server data directory; Electron therefore resolves under `~/.autobyteus/server-data`, while ordinary Docker resolves inside its existing persistent server-data volume without Compose changes. A Docker container or single Kubernetes server Pod may operate as one independent Local Store node using its own persistent volume. The configured Store has one database and independent 256-bit key, owner-only permissions, authenticated encryption, transactional/locked writes, bounded busy handling, and a reusable backend adapter. Current-format metadata includes a random `store_id` and an AES-GCM authenticated pair verifier under a domain-separated key derived from the root key; open validates it before `READY`, including for an empty Store. One missing file, verifier failure, or database/key mismatch is `CORRUPT`; an unsupported schema/encryption/verifier format is `INCOMPATIBLE`; neither is regenerated or rewritten. Staged pair creation is crash-fail-closed rather than falsely claimed as cross-file atomic. Ordinary server reset preserves Store files; deletion requires an explicit exact-Store reset or include confirmation.
- `REQ-013` **Container deployment and future enterprise extension:** first delivery ships Local custody for direct/Electron/unchanged Docker/single-Pod Kubernetes use. Multiple server containers/Pods/replicas never share one Local SQLite Store. The typed adapter registration/configuration/capability contract permits future Vault/AWS/Kubernetes/company adapters, but no concrete centralized adapter or strong worker-separation deployment is delivered here; selecting an unregistered kind fails value-free without fallback.
- `REQ-014` **Clean migration and legacy retirement:** migration preserves non-secret provider/test metadata, removes recognized credential aliases and custom-provider values, records reprovision identities, and deletes legacy readers/writers without plaintext backup/import/fallback.
- `REQ-015` **Backend substitutability and first-delivery conformance:** all registered adapters satisfy the common resolve/status/health/error contract; writable adapters additionally satisfy atomic save (create-or-replace) and idempotent remove semantics. First delivery runs the reusable synthetic suite against InMemory and Local read-write/read-only variants, plus a test-only externally-managed capability fixture for projection behavior. No production enterprise adapter is an acceptance dependency. Local conformance uses isolated temporary Stores, not the shared real-E2E Store.
- `REQ-016` **Tracked, secret-free test configuration:** the repository tracks canonical live scenario and real-E2E Store selection/configuration and may track `.env.test` only after it contains verified non-secret settings. Every worktree receives the configuration automatically; tests never search/copy another checkout.
- `REQ-017` **Physical Store isolation and one-time host E2E setup:** the host real-E2E Store is provisioned once per machine with dedicated test credentials through trusted hidden input and selected by tracked bootstrap configuration. It uses a database and key distinct from the default Store. Setup and runtime have no default-Store read/copy/fallback path. Host runtime real-provider tests open only the real-E2E Store, preferably read-only. Subsequent worktrees require no routine human secret handling. Docker Store sharing/mounting is outside this requirement.
- `REQ-018` **Claude Agent SDK authentication cutover:** server configuration accepts exactly `cli` and `managed-secret`; default is `cli`, and legacy/invalid `auto` or `api-key` fails `CLAUDE_RUNTIME_AUTH_MODE_INVALID` before lookup or spawn. `cli` performs no `SecretManagementService` call and uses only explicitly allowed external Claude CLI/account state. `managed-secret` calls `resolveForUse({kind:"agentRuntime",runtimeKind:"claude_agent_sdk",credentialSlot:"apiKey"})` immediately before each model-discovery or run spawn; the catalog authorizes that consumer to reuse `provider.anthropic.api-key`. `ClaudeSdkClient` builds an empty-base child environment and adds exactly `ANTHROPIC_API_KEY` from the returned `SecretValue`; it never mutates parent `process.env`, accepts caller `env`, uses a command-line argument/file/config/session payload, serializes/persists/logs the value, or falls back to CLI/ambient aliases. Managed mode passes `tools: []`, loads no user/project/local settings, hooks, plugins, API-key helpers, or external MCP configuration, and uses strict explicitly materialized AutoByteus in-process MCP tools; AutoByteus-owned tool execution runs outside the child under sanitized launch policy. AutoByteus drops temporary references after SDK child construction/completion without claiming deterministic JavaScript or SDK-memory zeroization. Missing/locked/unavailable/corrupt/incompatible custody, invalid binding, spawn failure, and provider auth failure are distinct value-free outcomes. Native Anthropic LLM/metadata remain separate authorized consumers of the same definition.
- `REQ-019` **AutoByteus remote gateway preservation:** `provider.autobyteus.api-key` is the single definition for AutoByteus remote LLM/audio/image discovery and runtime requests. The catalog authorizes exactly `modelDiscovery/{llm|audio|image}/AUTOBYTEUS/apiKey`, `llm/AUTOBYTEUS/apiKey`, and `media/{audio|image}/AUTOBYTEUS/apiKey`. The existing provider Settings row exposes write-only save/replace/remove and value-free status for this definition and triggers the established reload flow; an explicit successful removal authoritatively clears all AutoByteus-runtime catalog subsets without lookup. `AUTOBYTEUS_LLM_SERVER_HOSTS` remains non-secret endpoint configuration. With no configured host, discovery performs zero secret lookup and authoritatively clears the matching model-kind AutoByteus runtime subset. With hosts, the server-owned remote discovery service resolves just in time and passes ephemeral authentication to storage-neutral core discovery. A model keeps its downstream provider identity but declares non-secret `credentialProviderId=AUTOBYTEUS`; generic LLM/media provisioning uses that construction descriptor. Successful discovery atomically replaces only `runtime=AUTOBYTEUS` registrations for the corresponding model kind, preserving native models with the same downstream provider; a transient pre-authoritative refresh failure preserves the last-known-good remote set and returns a value-free outcome. Missing/non-ready custody fails closed and never reads `AUTOBYTEUS_API_KEY`; explicit successful removal and absent hosts are authoritative lifecycle/configuration results, not transient failures. Migration scrubs that alias, records this definition for reprovision, and preserves hosts. Real tests resolve the same definition from the read-only real-E2E Store.

## Constraints / Dependencies

- Actual existing secret values must never be inspected or included in solution artifacts or conversations.
- Provider SDKs require plaintext in trusted memory unless a gateway is used; JavaScript cannot promise deterministic zeroization.
- One-time first-machine provisioning and later rotation/revocation cannot be eliminated because AutoByteus cannot create external provider credentials.
- A committed Store selection/path is configuration, not proof of authority. Local database/key files remain outside the checkout and agent environment.
- Direct real-key execution trusts the reviewed server/provider code receiving that key; use test-scoped credentials and protected execution.
- Automatic local unlock through an owner-only key file is lower assurance unless process/filesystem isolation protects that machine-local key. Physical database/key separation improves defense in depth but does not defeat arbitrary same-user code execution.
- Host read-only E2E use requires the provisioning writer to finish/checkpoint/close before test execution; tests must not provision concurrently with real-provider execution.
- A Local SQLite Store belongs to one independent server node/persistent-volume domain. It is not a shared multi-replica database; multi-node deployment requires a separately delivered/installed centralized backend.
- Kubernetes Secret objects are not encrypted merely by base64 encoding; operators own etcd encryption/RBAC where native Secrets are used.
- The externally-managed lifecycle variant remains an extension/test contract in first delivery; no concrete enterprise adapter is implied.
- Claude CLI/account authentication is external runtime-owned state and is not imported into AutoByteus custody. Managed-secret mode intentionally trusts the exact Claude SDK child with one Anthropic credential; the child/SDK can observe it, JavaScript cannot guarantee zeroization, and a compromised Claude executable remains outside the non-disclosure guarantee.
- `EXT-ANTHROPIC-AGENT-SDK-AUTH` is a maintained external release dependency: release review must re-check Anthropic's official Agent SDK overview, legal/authentication guidance, and dated subscription-usage Help Center notice. The current official sources conflict; technical operability and user/operator consent are not treated as independent proof of contractual permission.
- `AUTOBYTEUS_LLM_SERVER_HOSTS` is non-secret configuration and may be tracked or managed through existing Settings; the corresponding API key must exist only in the selected Store. Remote endpoint availability and account capabilities determine which real LLM/audio/image scenarios can execute.

## Persisted Data Outcome (When Applicable)

- Stored subject / location: application `.env`, ignored `.env.test`, custom-provider schema-v1 JSON, public Nuxt credential fields, future dedicated encrypted default/real-E2E Store databases and keys, backend configuration, and migration ledger.
- Required outcome: `Migration Required` for application/custom/test configuration representation; legacy values are `Discard or Rebuild` through reprovisioning rather than automatic import. The new Local Store databases start on the current schema and have no prior profile schema to migrate because that design was never implemented.
- Existing data to preserve, discard/rebuild, transform, or quarantine: preserve provider IDs/names/types/base URLs and verified non-secret test settings; transform custom schema to metadata-only current form; remove credential aliases/values; create reprovision markers; never create plaintext quarantine/backup.
- Unacceptable data loss or corruption: loss of non-secret custom-provider identity/endpoint metadata, unrelated non-secret application/test configuration, or migration atomicity; silent fallback to legacy values is also unacceptable.
- Relevant availability, maintenance-window, or rollout constraints: secret consumers remain unavailable until required values are provisioned into their configured backend/Store; one physical Local Store must not be concurrently upgraded by old/new versions during schema change.
- Related requirement and acceptance-criteria IDs: REQ-002, REQ-012, REQ-014, REQ-016–REQ-019 / AC-007, AC-009, AC-012, AC-015, AC-016, AC-018, AC-019.

## Assumptions

- The AutoByteus server remains the trusted control/provider-client boundary.
- Electron starts its embedded Agent Server; that server constructs the Local backend in process against the default Store.
- Direct local and real-E2E servers can construct the same Local backend implementation against different bootstrap-selected physical Stores.
- Companies can implement/register additional adapters in the open-source server, but none is shipped by this first delivery.
- Worktree creation starts from tracked Git content, so committed non-secret configuration is present without copying.
- A root live-test launcher can derive the canonical host real-E2E Store paths without user-provided secrets.
- The team workflow performs source review before real API/E2E direct-secret execution.
