- Primary Questions Resolved:
  1. Does Electron own custody? No. Electron starts its embedded Agent Server; the server constructs `LocalSecretStorageBackend` in process. The same server-owned contract supports direct/server/container modes.
  2. Is a separate local service required? No. A same-user daemon/IPC boundary would add lifecycle and compatibility machinery without meaningful isolation. SQLite transactions/locking are sufficient for the approved local workflow.
  3. How do tests avoid per-worktree setup? Git tracks non-secret scenario/Store configuration. The real-E2E Store is provisioned once through hidden input or the explicit operator command with `--target e2e`; every worktree then selects it automatically without copying or loading the source.
  4. Can `.env.test` be committed? A credential-bearing legacy source remains ignored/local. The provisioning script, fixed mapping, tracked scenario config, and synthetic fixtures can be committed; real values, source, database, and key cannot.
  5. How is LLM authentication delivered? Server provisioning resolves it before factory construction; `LLMFactory` retains config composition and creates an ephemeral `LLMConstructionContext`.
  6. Is an administrator identity required? No. Backend workload identity is server-to-custody authentication, not an AutoByteus user system; current Settings access remains unchanged.
  7. How do Kubernetes/company deployments work in first delivery? One Docker node or single Kubernetes server Pod/PVC may own one Local Store. Multiple replicas require a future separately installed adapter; no Vault/AWS/Kubernetes/company adapter ships now, and unknown kinds fail closed.
  8. Where is Local Store state held? The normal Store is below each server's configured data directory. Electron therefore uses `~/.autobyteus/server-data/secret-store/`; ordinary Docker uses `/home/autobyteus/data/secret-store/` inside its existing named volume. The host real-E2E pair remains in the host AutoByteus server-data domain. An in-process backend instance opens exactly one bootstrap-selected Store.
  9. Why separate databases rather than profiles? The approved host/local workflow needs default and real-E2E custody contexts, not arbitrary profile lifecycle. Separate database/key pairs remove profile schema/policy and improve test/default isolation without imposing Store sharing on Docker.
  10. Which proposed attributes survived use-case validation? Only attributes used by UC-001–UC-019 or an approved security/operational contract. The provisioning CLI request adds required `sourceAbsolutePath`, closed target `default|e2e`, `dryRun`, and `overwrite`; it has no target path, profile, Store address, definition list, value, remove/force flag, backend config, or caller environment bag. No automatic-import source/target/phase attributes survive the user's final decision.
  11. Does this ticket alter Docker deployment for E2E? No. The existing Compose topology, launcher, and named volumes stay unchanged. A normal Docker node persists its own default Local Store in its existing server-data volume; operators may customize deployments themselves, but AutoByteus does not prescribe a Docker E2E mount in this ticket.
  12. How does the node model scale to Kubernetes? A local Docker container or single Kubernetes server Pod may own one persistent Local Store. Multiple containers/Pods/replicas never share the writable SQLite Store; centralized multi-node custody is unavailable until a future adapter is implemented/installed.
  13. What first-delivery assurance is claimed? `LOCAL_HARDENED` only: built-in file-tool Store denial plus empty-base environments/descriptors for governed launchers and redaction. Codex is explicitly excluded from the environment non-inheritance portion because the user requires its established external-login launch behavior. Arbitrary same-user/all-in-one/Codex process denial and `STRONG_AGENT_ISOLATION` are deferred.
  14. How is an empty Store bound to its key? A random `store_id` and AES-GCM pair verifier under a domain-separated HKDF key are authenticated on every open before `READY`; swapped/partial/tampered pairs are `CORRUPT`, unsupported versions are `INCOMPATIBLE`.
  15. Does Claude Agent SDK receive the Anthropic definition? Only in explicit `managed-secret` mode. The existing generic `SecretManagementService.resolveForUse` is reused with `{kind:"agentRuntime",runtimeKind:"claude_agent_sdk",credentialSlot:"apiKey"}` and maps to the same `provider.anthropic.api-key` definition as native Anthropic consumers. Default `cli` mode performs no lookup. There is no `auto`, ambient raw-key, or fallback mode.
  16. How is the Claude value delivered? `ClaudeRuntimeAuthenticationService` resolves immediately before model-discovery/run child construction. `ClaudeSdkClient` builds an empty-base environment and supplies exactly `ANTHROPIC_API_KEY` through the SDK `env` option to that child only; it never mutates the parent environment or accepts an arbitrary caller environment.
  17. What security limit remains? The authorized Claude executable/SDK can observe its own environment, and JavaScript/SDK memory cannot be deterministically zeroized. Managed mode therefore removes supported descendant leak mechanisms (process/environment-inspection built-ins, user/project/local settings/hooks/plugins/external MCP config), redacts before diagnostic buffering, and reports only `LOCAL_HARDENED`.
  18. What existing behavior did CR-001 uncover? `AUTOBYTEUS_LLM_SERVER_HOSTS` activated remote LLM/audio/image discovery, and one `AUTOBYTEUS_API_KEY` authenticated both discovery and later `AutobyteusClient` requests. The explicit-auth implementation removed the ambient read but supplied no production replacement, so remote models disappeared.
  19. How is that behavior preserved cleanly? One `provider.autobyteus.api-key` definition is authorized to distinct discovery and construction consumers. A server-owned `AutobyteusRemoteModelDiscoveryService` resolves it and calls storage-neutral core discovery. Remote models keep their downstream provider metadata but declare `credentialProviderId=AUTOBYTEUS`; generic provisioning therefore resolves the gateway key for invocation.
  20. Is this product or test-only functionality? It is committed local operator provisioning functionality because target `default` changes normal local custody. Target `e2e` is test setup, but both share one trusted CLI/parser/mapping/batch implementation. Neither is normal product runtime.
  21. How are source and target selected? The operator supplies one absolute regular-file path with any filename/extension and separately supplies target `default|e2e`. Neither is inferred; there is no current/parent search. Security depends on file identity/access and strict content parsing, not a basename. The source receives regular-file/realpath/owner/private-access checks before values are parsed.
  22. How are accidental writes prevented? No target is the default. Target names resolve internally to fixed Store pairs, never caller paths. Dry-run is value-free; existing records are skipped unless `--overwrite`; every write requires target-specific TTY confirmation, with the stronger exact phrase naming the default Store.
  23. Does non-echoing mean no process reads the value? No. Import necessarily parses and transiently handles bytes. The guarantee excludes AI/chat, argv, ambient environment, shell evaluation, stdout/stderr, logs, exceptions, reports, evidence, artifacts, and plaintext temporaries; JavaScript/parser/SQLite runtime copies cannot be proven zeroized.
  24. What if the selected Store does not exist? Both files absent is importer-only `INITIALIZATION_REQUIRED`. Dry-run remains zero-write; a confirmed execution uses the existing staged Local initializer for that selected pair, then the one-transaction record batch. A one-file partial pair stays `CORRUPT`; a batch failure may leave a valid empty newly initialized Store but never partially committed records.
  25. Should any startup/app-data migration own legacy credentials? No. The user rejected not only automatic credential import but also automatic scrub/delete/rewrite/conversion. Remove the cutover call and add no migration framework.
  26. What happens to canonical application `.env` credential aliases? The file remains byte-for-byte operator-owned. A non-secret configuration projection admits approved non-secret names only; sensitive aliases never enter `AppConfig` state, generic getters, persistence, child environments, or runtime consumers. Parent aliases are ignored rather than deleted.
  27. What happens to custom-provider-v1? It remains untouched and is not converted or automatically preserved. The current provider store returns stable value-free reconfiguration guidance; the operator cleans up the legacy file and recreates providers through UI.
  28. How are working keys preserved? Only through explicit user action: UI/Settings, hidden input, or the separately invoked assignment-file importer. No startup behavior preserves them.
  29. What recovery state is needed? None. There is no automatic source mutation, Store transaction, cutover record, or phase ledger.
  30. Does the explicit importer remain? Yes. It is still the committed, operator-invoked absolute-source `default|e2e` tool approved earlier; startup and tests never invoke it.
  31. Which library is being updated? `repository_prisma` only, from the current `1.0.6` state to latest verified `1.0.8`. `prisma` and `@prisma/client` remain on `5.22.0`.
  32. Does `1.0.8` address the blocked `1.0.7` risks? Yes. Both packed entrypoints omit dotenv/config and `.env` discovery; query logging is default-off with documented environment and typed opt-ins.
  33. Does `1.0.8` replace AutoByteus database ownership? No. Current production source does not import `repository_prisma`; AppConfig/configured-client and reviewed lazy owners remain authoritative. Adopting the library in production would be a separate design.
  34. What local compatibility work is required? Move manifest/lock to exact `1.0.8`, delete obsolete patched-dependency metadata/file, create no replacement patch, and prove clean/frozen install, static/dynamic entrypoint safety, default-off log policy, build, and CR-009–CR-014 regressions without opening or logging real data.

  38. How are empty recognized placeholders handled? A recognized line must still be a syntactically valid static assignment. After unquoting and outer-horizontal-whitespace normalization, an empty value is absent/non-selected: no credential bytes, plan entry, warning, ignored metadata, count, or failure. ## Request Context

The user reported that ignored `.env`/`.env.test` credentials can be read by AI agents and can enter conversations, that copied ignored files break the worktree workflow, and that real provider credentials remain necessary for meaningful E2E. Through iterative discussion, the user selected a provider/backend architecture, corrected service-over-backend layering, required server-first deployment neutrality, rejected an unrelated administrator identity subsystem and OS-specific desktop keychain design, and requested a simplified AutoByteus local vault/store. The user initially explored profiles, then explicitly pinned down the cleaner target: the Local backend runs in Agent Server and normal versus real-E2E custody uses different encrypted databases. After initially approving Claude CLI-only cutover, the user reopened that decision and selected a universal-store design with exactly two Claude modes: external `cli` by default and explicit `managed-secret` using the same central secret service.

The agreed local operating model is:

```text
AutoByteus LocalSecretStorageBackend (inside Agent Server)
  ${serverDataDir}/secret-store/secret-store.db + secret-store.key
    -> normal Electron/direct/Docker server use

  host AutoByteus server-data/secret-store/real-e2e-secret-store.db + key
    -> host real tests reused by every worktree
```

The agreed worktree model is one-time machine provisioning followed by zero routine human involvement. A first machine/new provider/expired key still requires legitimate provisioning or rotation.

During live provisioning the user first considered an importer, withdrew it as local setup, then explicitly renewed and broadened the request: one script committed to the repository should parse the applicable `.env` or `.env.test` source and populate either default or E2E custody. The user still requires actual sources, values, Store databases, and keys to remain local/uncommitted. The design therefore treats the committed code as reusable operator tooling while leaving every real invocation and credential value under local operator control.

After that importer design, the user briefly asked whether existing installed application data should migrate automatically on upgrade. Architecture review confirmed MP-003 is reachable and an intermediate Store-first preservation design was explored. After seeing the required migration/recovery machinery, the user superseded that direction: keep the explicit importer, remove every automatic legacy data update—including the existing scrub/rewrite cutover—and accept explicit reconfiguration/cleanup.

Round-9 API/E2E then proved the intended current-application-file journey still failed after the recognize-first correction: the operator's selected file validly contains an empty `GEMINI_API_KEY` placeholder because Gemini uses the populated Vertex Express credential instead. The user confirmed the general software rule that empty current credential assignments should be ignored as absent while non-empty recognized assignments are imported. This is a bounded selected-value rule, not a fallback between providers or aliases.

After that correction passed, round-10 real-provider execution proved the Vertex Express credential was selected but its mode was discarded before Google SDK construction. Code review also traced Codex App Server through the ticket-introduced synthetic HOME and found it could no longer see the existing external login. The user resolved the only requirement choice by directing AutoByteus to leave Codex alone because `codex login` already owns that journey. The design therefore restores/preserves pre-ticket Codex launch semantics rather than adding another authentication subsystem, and separately repairs the shared Gemini mode data shape.

## Findings From Code / Docs / Data / Logs

### 1. Configuration and custody are distinct responsibilities

`SecretStorageConfigurationService` selects a typed backend configuration and persists only non-secret options. `SecretManagementService` owns catalogued values/status and uses the constructed backend. Provider/search subject services coordinate their metadata with lifecycle. This avoids both the old generic AppConfig blob and the previously invented user/admin scope.

### 2. One in-process backend with separate Stores directly solves the worktree problem

Agent Server constructs `LocalSecretStorageBackend` directly. Electron, direct, and normal Docker startup derive the default database/key below their configured server data directory. Host worktrees track the separate host real-E2E database/key selection and preflight value-free status. The user provisions that host real-E2E Store once per machine/provider, not per branch/worktree. No additional service is started and Docker deployment is not altered.

### 3. Physical Stores are stronger and simpler than arbitrary profiles

A backend instance is bound at bootstrap to one database/key pair, and normal resolve calls do not accept a Store selector. There is no fallback/inheritance. First-delivery E2E setup is constructed with only the writable E2E target and accepts dedicated test credentials directly; it cannot open or copy from the default Store. Separate host default/E2E files and keys improve operational and cryptographic isolation; they do not defeat arbitrary code running as the same unrestricted OS user and do not impose a Docker Store-sharing model.

### 4. Non-secret `.env.test` can be tracked, but should not own live-secret semantics

The user correctly identified that a credential-free file can be committed. The canonical live Store/scenario contract should be typed root JSON for validation and multi-package reuse. A tracked `.env.test` may remain for ordinary non-secret test settings or point to the typed config. Broad ignore rules need narrow exceptions and repository scans must prevent regression.

### 5. Capability contracts remain useful without pretending a production enterprise adapter ships

Writable backends support the existing Settings-shaped atomic save (create-or-replace) and idempotent remove. Externally managed backends support resolve/status/health while writes are disabled. First delivery proves the contract with InMemory, Local read-write/read-only, and a test-only externally-managed fixture. Concrete Kubernetes/Vault/AWS behavior is deferred until an adapter and its deployment identity are actually implemented; an unknown kind fails value-free without Local fallback. This preserves the user's company extension model without a placeholder production claim.

### 6. LLM construction needs two narrow shapes

Public factory input becomes `{configInput, authentication}` while the factory composes final `LLMConfig` and creates `LLMConstructionContext`. The context exists only between factory and concrete client constructor. Individual clients never import the server secret subsystem or backend.

### 7. Kubernetes/cloud custody is a future adapter boundary, not first-delivery behavior

Company infrastructure may later mount a value, let the server read Kubernetes API, or grant workload identity to Vault/AWS through a separately installed adapter. Environment injection remains rejected for provider keys. A mount or service account in the same container as an unrestricted agent shell is not a protection boundary. First delivery supports only one Local Store per Docker node or single Pod/PVC and reports `LOCAL_HARDENED`; multi-node centralized custody and strong identity/container/pod enforcement are future work.

### 8. First-delivery assurance is explicitly lower-tier

The agreed Local backend uses cross-platform encrypted SQLite databases and vetted authenticated encryption, not Electron/OS keychain APIs. Zero-touch server startup reads an owner-only machine-local key file. First delivery also removes plaintext custody, blocks Store paths through built-in file tools, and builds child environments/descriptors from empty allowlists. Without a separate OS identity or enforced agent sandbox, same-user code may still reach the database/key pair or trusted memory. The product therefore reports `LOCAL_HARDENED` only after the implemented checks pass and never reports `STRONG_AGENT_ISOLATION` in this delivery.

### 9. Use-case spines removed speculative contract fields

The UC-001–UC-017 audit found no product path for a generic organization/deployment/environment scope DTO, a caller-visible physical storage address, a Settings expected-version/CAS field, or a selectable Local Store connection alias. `SecretManagementService` receives one semantic consumer identity and owns catalog lookup; callers do not resolve a binding and pass a duplicate definition. Management returns healthy-only definition storage state, configuration/backend ownership returns complete five-state health, and provider/search subject services own validation state. These corrections remove boundary bypasses and attributes that the product cannot currently produce or consume.

### 10. Local Store persistence, concurrency, and reset are concrete

The normal Store directory is `${serverDataDir}/secret-store/`. Electron resolves that to `~/.autobyteus/server-data/secret-store/`; ordinary Docker resolves it below `/home/autobyteus/data` in the existing named volume. The host real-E2E Store uses `real-e2e-secret-store.db` plus `real-e2e-secret-store.key` in the host AutoByteus server-data secret-store directory. Each database holds format/pair-binding metadata and exact encrypted `(definition_id, nonce, ciphertext)` records; no profile table exists. Each Agent Server opens its configured Store directly. SQLite transactions, journal/busy handling where writable, and explicit read-only mode coordinate processes. Because current Electron `AppDataService` resets the complete `server-data` directory, ordinary reset behavior must preserve `secret-store/`; deletion requires an explicit reset naming exactly one Store.

### 11. Persistent Store formats require pair authentication and compatibility checks, not IPC

Electron, direct servers, and worktrees may open a Store created by another package version, while independent database/key files may be swapped or left partial before any record exists. UC-004/UC-005/UC-010/UC-011 therefore require a random `store_id`, format versions, and AES-GCM pair verifier authenticated under a domain-separated HKDF key before `READY`, including an empty Store. A wrong/swapped key, partial pair, missing current verifier, or verifier failure is `CORRUPT`; unsupported schema/encryption/verifier versions are `INCOMPATIBLE`. Neither is silently repaired, rewritten, or downgraded. There is no process protocol or connection handshake.

### 12. Corrupt and incompatible Stores are outward control-plane states

The approved failure states are operationally reachable through file-pair integrity, record authentication, persistent-version, lock, and dependency contracts. Health is exactly `READY`, `LOCKED`, `UNAVAILABLE`, `CORRUPT`, or `INCOMPATIBLE`. Per-definition `MISSING`/`CONFIGURED` exists only at `READY`. For every non-ready state the server starts a value-free Settings/configuration/health control plane, disables writes/validation/provider construction, and returns a stable instruction code without paths or values. This closes AR-004 without overloading definition state.

### 13. Claude can reuse the generic service only through a dedicated runtime-authentication owner

`SecretManagementService.resolveForUse(consumer)` already owns catalog lookup, authorization, backend resolution, and value-safe error mapping. Adding a Claude-specific resolution method or letting `ClaudeSdkClient` access the catalog/backend would duplicate or bypass that boundary. The clean extension is a precise semantic identity `{kind:"agentRuntime",runtimeKind:"claude_agent_sdk",credentialSlot:"apiKey"}` authorized to the existing `provider.anthropic.api-key` definition. `ClaudeRuntimeAuthenticationService` owns mode selection and is the sole Claude caller of `resolveForUse`; native Anthropic LLM/metadata retain distinct identities over the same definition.

### 14. Two explicit modes are safer and clearer than current `auto|cli|api-key`

Default `cli` mode performs no secret lookup and uses explicit external Claude CLI/account state. Explicit `managed-secret` resolves just in time and delivers only `ANTHROPIC_API_KEY` in the exact Claude Code child environment. Legacy `auto` and `api-key` are invalid configuration rather than aliases or fallbacks. This removes implicit ambient selection and makes the trust decision observable without adding a new UI requirement; `CLAUDE_AGENT_SDK_AUTH_MODE` remains non-secret startup configuration.

### 15. Managed child environment delivery is useful but deliberately bounded

The pinned SDK supports an explicit child `env`, so first delivery does not require a local broker, descriptor protocol, or custom SDK fork. The wrapper builds from an empty base, never mutates parent `process.env`, and does not accept caller `env`. Managed mode adds exactly `ANTHROPIC_API_KEY`; no config/session/log/CLI argument or readback API contains it. Because the authorized Claude process can observe its own environment, supported environment/process inspection and descendant-spawn paths are removed: empty user/project/local setting sources, no hooks/plugins/API-key helper/external MCP configuration, strict explicit MCP, and SDK `tools: []`. `allowedTools` contains only explicitly materialized AutoByteus MCP names. AutoByteus-owned tools execute server-side with sanitized environments. The design makes no deterministic JavaScript or upstream SDK-memory zeroization claim.

### 16. Claude diagnostics are a separate outward leak boundary

Current `ClaudeProcessDiagnostics` buffers raw stderr and redacts only while summarizing. With managed delivery, redaction must happen before text enters the buffer, then again at outward formatting. Spawn/provider-auth failures use stable value-free codes; raw child errors never enter logs, session events, GraphQL, support bundles, or test artifacts.

### 17. AutoByteus remote discovery is supported product behavior, not dead code

The base branch called AutoByteus remote LLM discovery from `LLMFactory` initialization and targeted reload, and called remote audio/image discovery from their factories. `AUTOBYTEUS_LLM_SERVER_HOSTS` remains a supported server setting, the built-in provider catalog still contains `AUTOBYTEUS`, the web client reloads all models after saving that provider key, and provider-scoped reload still declares AutoByteus reloadable. Removing those callers removes reachable user functionality rather than cleaning obsolete code.

### 18. Gateway credential ownership must be separate from model provider identity

Remote catalog payloads can describe an OpenAI, Gemini, or other model while all network traffic is sent to an AutoByteus host. Resolving by `model.providerId` would therefore use the downstream provider key rather than the gateway key. The minimal reusable correction is a required non-secret `credentialProviderId` materialized during registration: native models assign their credential owner once and `runtime=AUTOBYTEUS` models assign `AUTOBYTEUS`. Construction targets omit displayed provider, so LLM/media provisioning remains generic and has no provider fallback or AutoByteus branch.

### 19. Discovery has its own semantic consumers but shares one definition

The same upstream AutoByteus key authenticates LLM/audio/image catalog reads and runtime requests, so duplicating stored values would be wrong. The catalog maps `modelDiscovery/{llm|audio|image}/AUTOBYTEUS/apiKey`, `llm/AUTOBYTEUS/apiKey`, and `media/{audio|image}/AUTOBYTEUS/apiKey` to `provider.autobyteus.api-key`. A server-owned remote discovery service performs the JIT resolution and passes an ephemeral authentication value to storage-neutral core providers. If no hosts are configured it performs no lookup and clears only the matching model-kind AutoByteus runtime subset. Successful results synchronize only the corresponding AutoByteus-runtime subset, preserving native models with the same downstream provider. A transient pre-authoritative configured-host refresh failure preserves last-known-good, while explicit successful credential removal is authoritative and clears all AutoByteus runtime subsets without lookup.

### 20. Source-review local fixes do not change the approved product model

CR-002 maps the real existing Claude account location into the empty-base CLI child instead of a newly created empty app-data home. CR-003 applies explicit stdio MCP `config.env` as the authorized additions map over the sanitized operational base. CR-004 makes repeated custom-provider deletion successful. CR-005 corrects the handoff so managed-only tool/settings restrictions are not asserted for CLI. These corrections remain with implementation engineering after architecture re-review.

### 21. One importer implementation can serve two Stores only through a closed target enum

The user wants one PNPM command, not two unrelated scripts. The clean boundary is one importer with a required absolute source and required `default|e2e` target. The target enum is policy, not a path: it resolves internally to one of the two canonical database/key pairs. There is no implicit destination, target-path option, or cross-Store read. This reuses parsing/mapping/batching while preserving physical Store isolation.

### 22. No-replacement default and target-specific confirmation prevent accidental default writes

All mapped source values can be planned without readback. Existing target definitions are `SKIPPED_CONFIGURED` unless the operator supplies `--overwrite`; an absent source alias never deletes a target record. `--dry-run` validates and returns only definition/status/count data. A real write still requires a direct TTY and exact target phrase, with `IMPORT DEFAULT STORE` explicitly naming the more consequential normal Store. There is no `--yes` or noninteractive bypass.

### 23. Absolute source selection is compatible with safety when recognition precedes value parsing

The path itself may be in argv because it is non-secret; values may not. The CLI requires an absolute path but accepts any filename or extension. It rejects symlinks/non-regular files, verifies realpath/opened-file identity and private ownership/access, enforces bounded valid text, and never searches parents. It then scans assignment names against the positive registry. Only an exact recognized name activates strict static-value parsing; all other lines are skipped without right-hand-side interpretation. This is not generic dotenv execution, JSON/YAML/shell detection, or whole-file validation. Source bytes remain unchanged, while owned selected-value buffers are cleaned best-effort under the honest JavaScript zeroization limit.

### 24. Positive selection is the cohesive importer security boundary

The importer owns movement of current AutoByteus credentials, not validation of an operator's entire configuration file. The previous negative secret-like classifier duplicated policy outside the positive mapping owner, caused false rejection, and pressured the system to preserve irrelevant legacy aliases. Remove it rather than expanding it. One positive registry is sufficient: it defines what may enter the Store and resolves only current catalog definitions. Every definition has one supported source spelling; Qwen uses only `DASHSCOPE_API_KEY`. Unknown operational settings, unsupported provider names such as `QWEN_API_KEY`, legacy ZHIPU, arbitrary text, and malformed unknown lines remain outside the subject. File safety, selected-value integrity, target isolation, confirmation, atomicity, and leak prevention remain fail-closed.

## AR-009 App-Data Investigation And Final Decision

The existing general app-data migration framework was investigated because the user briefly asked whether installed credentials should move automatically. It is not a suitable owner for security-critical Store-first preservation: it depends on initialized AppConfig and Prisma, runs after secret bootstrap, records general migration output, and continues after failures. A correct automatic design would require disproportionate new orchestration. The user then explicitly rejected the entire automatic update path, including the existing scrub/rewrite behavior.

The user judged that machinery disproportionate and explicitly selected the simpler product outcome:

- no automatic import, copy, scrub, delete, rewrite, conversion, or other credential-bearing legacy data update;
- application `.env` and custom-provider-v1 remain byte-for-byte operator-owned;
- approved non-secret `.env` entries may be projected without retaining sensitive assignments; custom-provider-v1 is rejected value-free and not converted;
- users explicitly provision through UI/Settings, hidden input, or the importer, then perform cleanup themselves;
- the general `src/app-data-migrations` framework remains unchanged;
- no cutover writer, Store batch consumer, source-mutation parser, ledger, retry state machine, or new supplemental migration contract remains in scope.

This is an explicit persisted-data tradeoff, not an accidental omission: losing legacy credential and custom-provider-v1 continuity is acceptable. Approved non-secret application settings may remain directly usable through a non-retaining projection, but no legacy file is rewritten.

## Constraints / Dependencies / Compatibility Facts

- No actual secret value may enter artifacts, logs or conversation.
- The importer is trusted operator code that necessarily opens source values; this exception is bounded to explicit execution and does not authorize design/review agents or test runners to inspect the source.
- The absolute source path is non-secret CLI metadata, but the CLI must not echo it in normal output or embed it in evidence; values never enter argv or `process.env`.
- Every backend requires a bootstrap identity/key source; moving a credential-bearing bootstrap source into `.env` would recreate the problem. Local database/key paths themselves are non-secret bootstrap configuration.
- The real-E2E Store/scenario file is tracked configuration, not a credential authority.
- `LocalSecretStorageBackend` runs inside Agent Server and directly opens exactly one configured encrypted database/key pair. Runtime callers above `SecretManagementService` never open it.
- Real direct-provider tests require reviewed trusted execution and test-scoped credentials.
- Electron starts the embedded Agent Server; the server constructs the Local backend. Direct Node/test servers do the same without Electron.
- Existing Settings access is preserved; no user/admin model is part of this ticket.
- No environment or legacy-file credential fallback is permitted.
- Startup does not mutate or clean any legacy source or parent alias. Sensitive names are simply excluded from current configuration/runtime and purpose-built child environments.
- Legacy files remain plaintext residuals until operator cleanup; no secure-erasure claim is made for filesystem journals, snapshots, backups, SSD media, or prior copies.
- `AUTOBYTEUS_LLM_SERVER_HOSTS` remains approved non-secret configuration; `AUTOBYTEUS_API_KEY` remains untouched if present but normal runtime must not retain, expose, or use it.
- Codex remains an intentionally external-authenticated runtime. Its pre-ticket launcher inherits the operator environment and real HOME/CODEX_HOME so `codex login` state remains available; it has no managed Store binding and is expressly outside the `LOCAL_HARDENED` empty-base child-environment guarantee. This exception does not authorize credential lookup or fallback by AutoByteus.
- Claude `managed-secret` intentionally places one credential in the authorized Claude child process environment. This is not persistence or broad parent inheritance, but it is plaintext in trusted runtime memory and observable by that process/SDK.
- The first-delivery supported delivery mechanism is the pinned SDK's explicit `env` option. The package-internal file-descriptor mechanism is not adopted because it is not a stable public cross-platform contract.
