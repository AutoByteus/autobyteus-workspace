## Findings
1. Core Agent status pipeline is substantially retained, not reinvented. git diff origin/personal HEAD shows no changes to agent-status-payload.ts, runtime provider status projectors, lifecycle-status processor files, agent-run-status-projection-service.ts, frontend agentRuntimeStatusState.ts, AgentStatus.ts or status color utility. AgentRun itself has changed admission/shutdown structure, so this is not an assertion the entire runtime is identical. Its getStatusSnapshot still reconciles backend lifecycle and projects lifecycleState.status. Standalone history/prepared identity fallback remains Offline; active runtime status wins, startup/error command overlay covers absence of runtime.
2. Old MixedAgentMemberHandle supplied command overlay or AgentRun snapshot, falling back Offline, with coalesced first-work readiness. Current ConfiguredAgentExecutionHandle follows the same pattern, shared across direct Org and Team members. FlatTeamAgentExecutionHandle adds an adapter and supplies Offline until its shared handle exists. Live AGENT_STATUS clears temporary overlay in both old and new. New shared overlay is a single per-handle snapshot rather than old per-member map. Team-shaped status conversion and shared statusHint mapping overlap, adding adapter overhead but not separate competing runtime state machines.
3. Old MixedTeamManager collected configured leaf snapshots (recursively Offline for unmaterialized child Teams), plus task Agents/Teams. Current FlatTeamExecutionManager keeps leaf-first snapshots for flat configured members and recursive task runs. Org projector collects direct handles and structural root Teams, delegating descendant traversal to TeamRun; it deliberately does not iterate every Team directory entry, avoiding duplicate task leaves. Thus configured Team traversal moved up to Org, retaining leaf status ownership rather than inferring every Agent from parent activity.
4. Old workspaceHistoryNestedTeamStatus folded leaf statuses in precedence Running > Initializing > Error > Idle > Offline. New workspaceTeamAggregateStatus extracts precisely that precedence for both Team branch rows and Org-mounted Team rows. Org branches use tree identity and fold before expansion, not merely visible rows or coordinator status. Historical fold suppresses running/initializing; actual Org historical source supplies no runtime statuses so members are Offline. Running outranking Error is inherited policy, not a newly established defect.
5. Root activity is not member status: standalone Team header uses team.isActive, Org header uses run.isActive (emerald with running/stopped label); Org-mounted Team row uses aggregate status, individual Agent row uses actual status. A root can correctly be active while every member is Offline. Reusing green/activity labels for different concepts is a presentation/terminology ambiguity, not evidence of runtime activation. Agent green means Idle; branch green means aggregate Idle; root green means container active.
6. Earlier reported all-member-green behavior was eager configured readiness, not aggregation arithmetic. Current child implementation now uses prepareConfiguredAgents:false for standalone and mounted configured Team creation/restore; direct Org configured registration does not prepare candidates. Real assigned-task paths retain preparation. Current source therefore restores the old lazy principle; no claim here of independently executing restart/provider/browser validation.
