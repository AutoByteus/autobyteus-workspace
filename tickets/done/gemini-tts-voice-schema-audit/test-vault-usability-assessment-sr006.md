# Test-vault Import Usability Assessment — `SR-006`

## User Question And Direct Answer
The user asks whether `pnpm secrets:import` into the **test vault** is convenient/natural or involves so much workaround that it should be improved. **Answer:** the importer itself is a clear, safe primitive; an established real-E2E test instance has a documented path. For quick, exploratory provider checks, the *end-to-end workflow* is cumbersome. It is not yet a natural one-command experience. The initial one-off CJS/ESM module setup error during the voice probe was our probe-harness mistake, not an importer/production-vault defect.

## Evidence And Boundaries
- Root `package.json` runs `pnpm --filter autobyteus-server-ts build` before every `secrets:import`; preview and confirmed execution therefore rebuild separately. In a recent run, dry-run finished in roughly 16 seconds before any provider test. Build time is friction, not a correctness failure.
- The feature worktree's [`secret_management.md`](/Users/normy/autobyteus_org/autobyteus-worktrees/gemini-38-tts-upgrade/autobyteus-server-ts/docs/modules/secret_management.md) defines explicit absolute source and SQLite target, value-free `--dry-run`, direct-TTY `IMPORT` execution confirmation, no implicit current/production target and no test wrapper. These are deliberate credential-safety requirements worth preserving.
- `TESTING.md`, `test-support/live-e2e/run-live-e2e.mjs` and `pnpm isolated-app start` offer a dedicated real-E2E runtime/DB URL and an isolated app flow, so planned repeat testing is structured. But for recent one-off voice-list and basic-speech probes we manually created an ephemeral test directory/DB, ran dry-run and confirmed import, bootstrapped Prisma/vault/runtime, wrote a scoped ad-hoc invocation, verified result, then cleaned DB, adjacent key and generated audio. The importer loaded 10 recognized aliases from the source although the experiment used only Vertex Express. No secret values were exposed; production vault was not used.
- That setup is safe and workable, not a fragile or broken importer. The custom probe's first CJS/ESM duplicate-module bootstrap created a misleading local vault health error, resolved before the sole provider call. A canonical test bootstrap could prevent that kind of operator/harness mistake.

## Recommendation — Not Yet Approved
If the user wants this improved, scope a **separate test-only provider-probe workflow** (possibly an extension of current isolated-app/real-E2E tooling rather than a new command) that allocates an isolated target, invokes the existing reviewed dry-run, still requires direct-TTY confirmation, initializes one canonical runtime, executes an explicitly selected allowlisted probe, sanitizes output and cleans owned data in `finally`. Investigate scoped-secret import and non-stale build reuse as optional ergonomic questions. Do **not** introduce automatic import, implicit production target, secret logging, silent route/key selection or confirmation bypass. The user has asked for an assessment, not yet approved exact behavior or implementation.
