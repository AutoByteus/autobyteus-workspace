# Result — Gemini 3.8 TTS voice/schema parity investigation (`SR-003`)

## Short answer
**No: the app is current for Google's 30 featured prebuilt voice names and basic single-/two-speaker TTS payload, but it does not expose Google's full voice catalog or all documented speech options.** This is a scope gap relative to Google's capabilities, not a regression against the earlier approved `gemini-38-tts-upgrade` scope, which explicitly excluded library/design/replication and streaming. The 2026-10-01 real Vertex Express test proved a nonempty WAV for one basic 3.8 Flash request; it did not establish full voice-feature availability.

## Direct answer to “does generate image already support all the voices?”
No. `generate_image` is a separate image tool and has no voice setting; the relevant tool is `generate_speech`. Its exposed `generation_config.voice_name` is restricted to the 30 hardcoded names, and the Gemini audio adapter also rejects an Extended Voice Library ID if supplied manually. The tool schema is therefore **not** a transparent copy of Google's TTS schema.

For single-speaker synthesis, Google's [documented GenerateContent field](https://ai.google.dev/gemini-api/docs/generate-content/speech-generation) is `config.speechConfig.voiceConfig.voice`: the value may be a featured name or a provider-issued Extended/custom voice ID. Google's [Voices API](https://ai.google.dev/api/voices) can list available IDs and metadata on the Developer API. The sensible provider-aligned behavior would be to discover/accept IDs on routes that actually support them, pass the chosen ID to `voiceConfig.voice`, and let Google report route/model access failures—rather than pretending the current fixed enum is the complete provider catalog. This is an investigation recommendation, **not** an approved implementation decision.

Multi-speaker is not the same rule: Google's one-request `multiSpeakerVoiceConfig` is documented for at most two **prebuilt** voices. It would be incorrect to promise arbitrary Extended/custom IDs in that field without further evidence. Vertex Express's documented API still lacks voice-listing resources, so whether its key can discover or synthesize an extended ID remains unverified.

## Voice design and replication: what they add
- **What we already do:** Take text, choose one of 30 featured voices, optionally apply a single style instruction, and generate speech. Dialogue assigns one of those voices to each of at most two named speakers. Style controls *delivery on this request*; it does not create a voice identity.
- **Voice design:** Describe an imagined voice (for example accent, timbre and character) to Google's [Voice design API](https://ai.google.dev/gemini-api/docs/voice-design). Google creates a reusable project voice ID and a sample to audition. Later single-speaker TTS can use that ID. Autobyteus currently cannot create/manage the voice or pass its ID through its fixed 30-value validation.
- **Voice replication:** Provide recordings of a real adult speaker's voice **and the speaker's consent** to Google's [Voice replication API](https://ai.google.dev/gemini-api/docs/voice-replication). Google returns a reusable stored voice ID or short-lived client-managed voice key. Autobyteus currently has no consent/upload/storage/deletion workflow and also blocks those IDs in speech generation. This is a material privacy/identity feature, not just another style parameter.
- **Dialogue limit:** Google's one-call two-speaker dialogue supports prebuilt voices. Designed/replicated voices do not automatically work in that one-call configuration; [Google advises separate synthesis per turn](https://ai.google.dev/gemini-api/docs/generate-content/speech-generation) for custom-voice multi-character audio. We have not verified how Extended Voice Library IDs behave on the configured Vertex Express route.
- **Recommendation for discussion:** First permit provider-available catalog IDs and existing custom IDs in *single-speaker* `generate_speech`, with dynamic listing only on supported routes and explicit provider errors otherwise. Add per-turn style if dialogue control matters. Do **not** silently add voice creation/replication to `generate_speech`; consider separate opt-in workflows only if the user wants in-app creation and is ready to define consent, storage, expiry and deletion behavior. No implementation/approval is implied.

## Product decision before further work
Do you want a follow-on requirement for **voice catalog discovery and provider-supported synthesis IDs** (narrowest direct answer to the voice concern), or a broader **Google TTS capability expansion** including per-turn styles, output formats/streaming and voice design/replication? The latter has distinct access, consent and lifecycle implications. Either choice requires explicit approval before design/implementation. No changed intended behavior is approved in this audit.
