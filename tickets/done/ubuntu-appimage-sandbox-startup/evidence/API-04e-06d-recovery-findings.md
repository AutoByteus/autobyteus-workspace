Both observations used normal-user desktop launches on an owned Ubuntu 24.04.5 x64 overlay, Xvfb/Openbox/Zenity and the Ubuntu graphical polkit agent. The signed full fixtures were verified independently (API-05c-source-packages.log). Nothing below requires changing AppArmor, host permissions, real user data, app signatures or publisher trust.

**F-API-03 — Missing protected application: the refusal names a file but gives no recovery step.** In a healthy, enrolled, stopped 1.5.15 fixture, temporarily set aside only the canonical AppImage to represent an incomplete installation; leave the original, support program, service identity and private synthetic data intact. Launch the unchanged renamed .13 download as the normal desktop user, without the automation launch profile. Repeat with the same download's documented `--autobyteus-uninstall` action as an independent recovery control. Each opened an “AutoByteus installation” error dialog containing **only** `lstat /opt/autobyteus-desktop/1000/app/AutoByteus.AppImage: no such file or directory` and an OK button. Both exited 1. No new enrollment, authorization, running server, fallback or data loss; the rejection itself is correct. No wording says the existing installation is incomplete, that administrator repair is needed, or how to proceed. The uninstall control also cannot progress in this state. The criterion requires an explanation, **not** silent repair, bypasses or automatic removal. Restored the exact original protected inode in the fixture, confirmed its digest, launched the app and then used normal authorized removal successfully. Compare API-04e-repair-repeat.log, API-04e-repair-launch.png, API-04e-repair-uninstall.png and API-04e-removal.log. First capture used a corrected fixture filename; the two clean repeated launches in the repeat log are authoritative. Source lead, not ownership determination: internal/launch/managed_linux.go:34–36 returns the OS error before cmd/launcher/main.go dispatches uninstall or formats an actionable message.

**F-API-04 — Insufficient installation space: graphical user sees only a generic exit status after successful authorization.** On the now-unenrolled Noble fixture, confirm the dedicated install base is empty; provide it a temporary empty 32 MiB test volume. Leave the boot filesystem and all other mounts untouched. Open the genuine renamed .13, click Install, authenticate via the normal Ubuntu agent; the signed image is larger than the volume. The helper correctly reports `insufficient installation space` on stderr. The **only user-facing dialog** in a normal graphical launch instead says `Ubuntu authorization or installation refused: exit status 1`. It neither distinguishes storage failure from denied credentials nor suggests freeing space and retrying. All new installation directories, user, menu, profile, service/socket were absent afterwards; workspace hash remained unchanged, test mount removed. API-06d-rollback.log + API-06d-rollback.png show the distinction. Likely boundary: internal/install/provision_linux.go space preflight → internal/launch/authorize_linux.go error → graphical Explain. Request focused origin review; do not expose untrusted arbitrary helper output or change the authorization boundary as a shortcut. No product code was changed by QA.

Expected for both: deny safely **and** tell a desktop user a safe next action.
