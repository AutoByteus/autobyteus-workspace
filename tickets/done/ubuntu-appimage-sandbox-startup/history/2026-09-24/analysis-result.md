- **Supported scenarios:** SCN-001 normal AppImage launch; SCN-002 diagnostic `--no-sandbox` workaround. Misspelled `--no-sandobx` is not a valid workaround.
- **Finding:** Ubuntu 26.04's AppArmor unprivileged-userns restriction denies a capability Chromium needs for its namespace sandbox. The AppImage FUSE mount is `nosuid` and embeds a root-owned `chrome-sandbox` with mode 755, so Chromium's setuid sandbox helper cannot serve as fallback. Without either route Chromium exits before AutoByteus app startup. Correctly spelled `--no-sandbox` bypasses Chromium isolation and allows startup. Ubuntu introduced the applicable AppArmor default in 24.04; 20/22 behavior was user-reported, not locally reproduced.
- **Key evidence:** No-flag and typo probes both exit 133 with Chromium's setuid sandbox FATAL; kernel audit shows `unprivileged_userns` profile denying `sys_admin`; correct-flag probe logs app startup and embedded server running. `kernel.unprivileged_userns_clone=1` alone is insufficient because AppArmor separately denies capability use. Full commands, logs, checksum, source references and official Ubuntu/Electron/AppImage links are in `investigation-notes.md`.
- **Constraints and security:** Do not silently add `--no-sandbox` as a production fix or disable AppArmor globally; either removes security protections. No code, host policy, or release changes were made. The user's existing app process was left untouched.
- **Blockers/open risk:** None for the requested diagnosis. A production solution is intentionally not designed: package-format and OS-support scope are unapproved. A scoped AppArmor profile with an installed package is one potential direction; portable-AppImage behavior and fallback policy need user decision.
