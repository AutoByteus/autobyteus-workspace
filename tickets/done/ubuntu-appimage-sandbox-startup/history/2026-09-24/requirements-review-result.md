# Ubuntu AppImage Sandbox Startup — Requirements Review Result

- **Package ID:** `ubuntu-appimage-sandbox-startup`; current solution round `SR-001`.
- **Classification:** Ready for Approval; not implementation-ready.
- **Original request/context:** The user first asked why AutoByteus AppImage v1.4.78 requires `--no-sandbox` on current Ubuntu. Local Ubuntu 26.04 runtime and kernel audit established a Chromium sandbox/AppArmor plus AppImage-mount interaction. The user now rejects a manual CLI flag and says a no-sandbox default is acceptable if no perfect solution exists.
- **Proposed intended behavior:** An ordinary user opens the Linux AppImage with no flags. On a host where Chromium sandboxing works, it stays enabled. Where host policy blocks the sandbox, the AppImage automatically uses a no-sandbox fallback, logs the downgrade, and starts normally. No user flag, popup, manual AppArmor profile, or host-wide sysctl change is required. Existing Node-mode/CLI and explicit-argument behavior, Linux x64/arm64 package/updater lifecycle, and application data are preserved.
- **Approval basis/state:** The user's latest statement establishes willingness to accept a security tradeoff but does not explicitly approve the more specific conditional fallback versus an unconditional disablement. Approval is pending for `requirements-doc.md` SR-001; no design spec exists.
- **Scope:** AppImage launch behavior only. Additional `.deb`/other package formats, all-Linux unconditional no-sandbox, and host-policy changes are out of scope unless separately approved.
- **Why this proposal:** It solves the usability problem on restricted Ubuntu while avoiding unnecessary loss of Chromium isolation on Ubuntu 20/22 and other capable hosts. Upstream electron-builder v27 (currently alpha, not selected for direct upgrade) documents a similar conditional AppImage fallback. Current AutoByteus uses electron-builder 25.1.8 and AppImage-only Linux release assets; design must choose a compatible packaging mechanism only after approval.
