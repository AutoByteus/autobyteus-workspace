| ID | Finding | How established |
| --- | --- | --- |
| F-01 | **Where the content is lost: in the CLI's stream, not in our recorder.** The stream-json `step_update` of a `read_file`/`view_file` step carries `tool_info.output = "40 lines, 1005 bytes"`: the size of the **whole file**, not of the lines viewed (the probe asked for lines 5–9 of a 40-line file). Our converter passes `tool_info.output` through unchanged (`agy-stream-event-converter.ts:201,243`), so the raw trace holds what the CLI sent. | **Reproduced** with the real CLI (`evidence/INV-01-live-timing-probe.mjs`, output in F-04) and read. |
| F-02 | **Scope of the gap, measured on the founder's node (counts only; 202 runs with Antigravity results):** `view_file` 5,921 results, 4,820 size-only; `read_file` 244 results, 201 size-only; `grep_search` 400 results, 94 with no output (`None`) in the stream (its other results do carry text); `find_by_name` 442 results, 78 without output; `write_to_file` 3,879, `replace_file_content` 716, `write_file` 318: all `None` (the CLI sends a confirmation line only in its transcript; the journal already shows `→ ok` for those); `run_command` 8,819 results are full text (1,158 `None`); `list_dir` full text. MCP calls (`call_mcp_tool`) carry their result in the stream. | Measured (read-only scan of the raw traces). |
| F-03 | **The CLI does persist the full result of every tool step:** `<brain>/<conversation>/.system_generated/logs/transcript_full.jsonl`, one JSON row per step, `{step_index, source, type, status, created_at, content?, tool_calls?, …}`. A tool step is a `MODEL`/`GENERIC`/`DONE` row whose `content` is the result text; the `PLANNER_RESPONSE` row just before it holds `tool_calls[{name, args}]`. For `read_file` the content is the CLI's header lines (`Created At`, `Completed At`, twice) then `Showing lines 5-9 of 40` and the lines numbered `5: …`; for `view_file` the header then `File Path`, `Total Lines`, `Total Bytes`, `Showing lines a to b`, a sentence about the numbering, and the lines; for `run_command`, `grep_search`, `find_by_name`, `list_dir`, `write_to_file`: the header then the text (`Command exited with code N.`, `Found N results`, the lines, `Created file.`). Its size matches the stream's byte count plus the header (6,250 vs 6,048 bytes). | Measured on the founder's node (26 `read_file` steps in one run, all with content) and **reproduced** (probe: lines 5–9 and 1–3 with their text). |
| F-04 | **The row is already there when the DONE event arrives:** in 3 of 3 probe steps (`read_file` ×2, `run_command` ×1) the transcript row of step N was readable in the same millisecond as the stream's DONE `step_update` for step N. Not a guarantee: the implementation measures it on at least 50 live steps (D-3). | **Reproduced** (probe). |
| F-05 | **The backend already depends on this file for the same kind of gap:** `readAgyNativeToolArguments` (`stream/agy-native-tool-arguments-reader.ts`) reads the `PLANNER_RESPONSE` row of the previous step from `transcript_full.jsonl` through `scanAgyBrainJsonLinesReverse` (`agy-brain-file.ts`: guarded descriptor, newest-first rows, 2 MiB row bound, no symlinks, "every AGY brain read goes through here") because the stream's `parameters` are a lossy summary. It runs before `convert` in `AgyAgentRunBackend.handleMessage` (an awaited lookup, abortable, failure ⇒ `null` ⇒ the stream's summary is used). The generate_image path likewise reads `steps/<n>/output.txt` for the saved path (`agy-step-output-reader.ts`). So the architecture already has the owner, the safety rules and the failure mode this needs. | Read. |
| F-06 | **`steps/<n>/output.txt` is not the source for reads:** read steps have no `output.txt` (0 of 26 in the measured run); `run_command`, `write_file`, `edit_file` and MCP steps do. The transcript covers every tool step (26 of 26 `read_file`, 27 of 27 `run_command`). | Measured. |
| F-07 | **Parallel tool calls exist:** of about 3,900 planner responses with a call, 9% hold 2 or more calls; the tool rows follow as consecutive `GENERIC` rows in call order (`s+1…s+n`). The existing arguments reader accepts only a single call (null otherwise): a separate, smaller gap (follow-up FU-2). A results reader can identify a row by position: the nearest `PLANNER_RESPONSE` below it, the row's offset in that run of `GENERIC` rows, and the same offset in `tool_calls` with the same tool name. | Measured (465 conversations, counts). |
| F-08 | **Size:** the CLI bounds its own content: `view_file` median 2.8 KB, p95 13 KB, max 49 KB; `grep_search`, `run_command`, `find_by_name` p95 ≈ 10 KB, max ≈ 10 KB with the CLI's own `<truncated N lines>` marker (what the model saw). The raw-trace recorder has no cap: Claude's Read results are recorded in full (19,219 results, median 20 KB, max 681 KB). Recovering the AGY content adds on this node about 6,165 read results × median 2 KB ≈ 13 MB over 202 runs; a run's `raw_traces` file rotates as before. | Measured. |
| F-09 | **What the journal does with it today:** `viewFile` (`antigravity-translation.ts`) turns the size-only result into `Command: cat … → ok (content not recorded: N lines, M bytes)`, which for a ranged read states the file's size next to a range (misleading); `read_file` has its own converter since 561. `grep_search` and the other tools show `output` as recorded. Every AGY result starts with Antigravity's `Created At`/`Completed At` header in the stream for `run_command` (561's follow-up FU-1, not yet done). | Read and measured (journal lines). |
| F-10 | **ACP (autobyteus-386) is not delivered** (no ACP runtime on `origin/personal`; `agy acp` exists as a CLI subcommand). If it lands, its tool-result messages may carry the content at the source; this fix is independent of it and isolated in one reader plus the converter's use of it. | Read (`agy --help`; tickets on `personal`). |
| F-11 | **The founder's second screenshot (2026-11-23): `read_file` with `StartLine 501, EndLine 1000` shows `"3957 lines, 285596 bytes"`**: the same stream summary of the whole file, with the current tool name. | Read (task comment, image). |

| ID | Finding | How established |
| --- | --- | --- |
| F-12 | **Census over 465 stored conversations (transcript `tool_calls`) against the journal table and the recorded arguments** (counts): `call_mcp_tool` 1,618 (fine); `run_command` 920 (full result text; wrapper lines); `view_file` 814 and `read_file` 289 (size-only results); `replace_file_content` 186 and `write_to_file` 79 (in the table; arguments complete); **`edit_file` 130 and `write_file` 98: not in the table, so they render as generic lines, and their recorded arguments are only `Path`** while the transcript holds `Path, Target, Replacement` and `Path, Content, Append`; `grep_search` 124 (recorded arguments `Query, SearchPath` only; the transcript also has `CaseInsensitive, MatchPerLine, Includes`; result often empty); `find_by_name` 51 (result sometimes empty); `list_dir` 115 (fine); `manage_task` 13, `generate_image` 7, `read_url_content` 4, `search_web` 3, `list_resources` 1 (generic lines; `read_url_content`/`search_web` have clean equivalents). | Measured (read-only; `evidence/` scripts are scratch, not committed). |
| F-13 | **Why `write_file`/`edit_file` arguments are missing: parallel batches.** In one run's active file, 28 of 29 `edit_file`/`write_file` calls sit in a batch (the planner response made 2+ calls: 4 of them in a 3-call batch, 24 and 19 behind an earlier call's row), so `readAgyNativeToolArguments` (single-call only) returns `null` and the stream's `{Path}` summary is recorded. For an agent that works in batches this is most of its writes, not 9%. | Measured (the Task Manager's own run, counts). |
| F-14 | **A batch can be identified without waiting for its sibling rows:** the planner row is the nearest `PLANNER_RESPONSE` row below the step; the step's position in the batch is `stepIndex − plannerIndex − 1`; the planner's `tool_calls[position]` must carry the step's tool name. The measured batches (180+ two-call, 140+ larger) have exactly that layout (consecutive `GENERIC` rows after the planner row). | Measured (counts) and read. |
| F-15 | **Run command wrapper:** the stream result text of `run_command` is `Created At…`, `Completed At…`, `Command exited with code N.`, a blank line, `Command output:`, then the output (shape seen in the probe and in stored runs); the journal shows all of it (561's follow-up FU-1). | Read and measured. |
