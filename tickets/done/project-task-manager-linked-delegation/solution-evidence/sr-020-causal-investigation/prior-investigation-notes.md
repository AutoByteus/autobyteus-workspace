## Product And Domain Understanding
- Project: node-local named durable container with workspace links and embedded business Tasks.
- Project Task: description, optional Task-owned saved context and business status. Distinct from a runtime “task execution.”
- Delegated task execution: a fresh Agent or Team copy within a collaboration root, with its own run identity; Team ingress is coordinator AgentRun while the Team also has TeamRun identity.
- Collaborator: shared definition brought in by @; its normal per-root instance is not the copy created by delegate_task.
- Quiet shutdown: current reversible runtime release based on quiescence, not task acceptance/completion; run-ID delivery can wake it.
- Worktree: physical Git working copy. It is not synonymous with the execution tree.

## Follow-Up Feasibility Assessment — SR-002
Existing Team termination already enumerates and stops member and nested hosted execution resources (E-013), and provider Agent shutdown has concrete cleanup operations (E-014). Therefore an explicit Project Task identity can provide the stable business-to-runtime entrypoint the user describes. The missing behavior is reliable Task↔exact spawned execution linkage plus scoped completion/admission coordination, not a need to reinvent all runtime shutdown. A task Agent's follow-on delegations may be physically hosted alongside it, so assigned run ID alone is not sufficient proof of full ownership traversal (E-010). The “assigned execution root” must not be confused with its enclosing Agent/Team/Org collaboration root. Immediate trigger does not mean synchronous zero-time teardown; completed work must not be revived through existing reversible idle-wake behavior. These are current-state feasibility observations and unapproved technical concerns; no authoritative target design was authored.

## Cascading Collaborator Feasibility — SR-003
User explicitly requires more than delegated child copies: new brought-in collaborators are included recursively. The supported send_message_to bring-in path currently admits/reuses collaborators at the enclosing collaboration root (E-016–017); child Team recursive termination does not by itself cover these outer-root helpers. Both `addedViaAgentRunId` and `delegatorAgentRunId` provide provenance, but only the first admission is recorded for reused collaborators. Task-lifecycle ownership must not be inferred from runtime time windows, shared address or first creator alone. Complete cascade shutdown is feasible as new behavior, but cross-Task helper-instance sharing is a material product/contract decision. Proposed task-scoped runtime helpers would permit stopping all that Task's helper instances while preserving the same reusable definitions and unrelated work; alternative shared-runtime release semantics require user selection. No target design/schema/module assignment has been authored.

## Correction To SR-003 Sharing Framing — SR-004
The SR-003 proposed helper-isolation question must not be understood as changing or questioning delegate_task fresh-copy semantics: those already create independent runtime resources and IDs from the same definition. The issue is not reusable definitions. Normal collaborator admission through send_message_to(address) can reuse a runtime at enclosing-root scope; its helper lifetime remains an evidence-backed, separate integration question. A future design must distinguish these two operations before selecting any ownership/admission change. No blanket task-isolation refactor or accepted collaboration reuse change is authorized by this clarification.
