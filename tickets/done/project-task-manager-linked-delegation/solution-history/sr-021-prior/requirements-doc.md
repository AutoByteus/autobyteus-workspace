## Approved Focused Delta — SD-AP-002
1. Agent.md describes real Project Task Manager duties only: choose/clarify Project/Task, create/reuse Tasks, delegate, communicate about work using existing tools, use available results/user instructions to maintain business status. It does not discuss resources/providers/lifetimes/platform internals or supervise their release.
2. Ordinary Task tools expose relevant business content, exact assignments and truthful operation/status acknowledgements, **not raw resource/lifetime/cleanup payloads**. Saved work/context remains available and is delivered internally by Task ID. No requirement to remove business attachment metadata from Task reads or truncate business descriptions; that unapproved REQ-BL-007 restriction is withdrawn.
3. Platform performs all exact runtime closure/release and maintains truthful pending/failure/proven-success state plus safe existing explicit retry. Manager has no cleanup duty. DONE is an explicit business command, not a new platform determination that work is finished. No automatic completion-notification/retry scheduler/UI/protocol added.
4. Retain all prior runtime identity/scope/fence/data/no-migration/Delete/reopen/unlinked constraints and independent validation gates.

## Problem And Desired Outcome
Existing node-local Project Tasks have descriptions, saved context and TODO/IN_PROGRESS/DONE status, but no supplied Project Task Manager and no relationship to delegated Agent/Team executions. The user wants a manager to create or reuse a Task, delegate it to a worker Agent or Team, track it, and mark it DONE as the explicit resource-release boundary. The prior approved first version uses existing Chat/@, without Project-page chat. The scoped approved revision separates business-role Manager instructions from platform-owned lifecycle work without weakening cleanup. Completion awareness remains prompt/workflow communication, not a new platform detector.

Success means the exact business Task can be traced to the actual spawned execution, and completion releases that Task's owned execution resources without stopping its manager, enclosing organization or unrelated work. `DONE` is an intentional business decision, not inferred from an idle runtime or a worker's optimistic message.

### Out Of Scope (Prior Approved First Slice; Preserved In Proposal)
- Project-page embedded chat/panel, new assignment visualization or sidebar redesign; existing @/Chat is the first-slice entry.
- Scheduling, cron, unattended backlog polling/auto-dispatch, dependency graphs, batch tools, external issue trackers, new status vocabulary or automatic acceptance judgments.
- Project creation tools, attachment mutation agent tools, mobile Projects support, changing ENABLE_PROJECTS/default installation semantics.
- Deleting physical workspaces/git worktrees, output artifacts, conversations, run history or uploaded source files; any destructive expansion requires separate renewed user approval.
- New active-deletion blocking or delete-as-cancellation workflows; deletion keeps existing metadata/context semantics.
- Global rewriting of existing unlinked collaboration addressing/routing, or treating ordinary @ admission as fresh task-copy spawning. The approved Task-owned helper lifetime may require a bounded linked-Task admission/routing change; this is not a blanket collaboration redesign.

### Non-Goals
- No LLM platform architecture/resource inventory/cleanup supervision, automatic cleanup-retry or completion-notification scheduler, new diagnostic UI/tool, new worker self-DONE prompt protocol or blanket public exposure of internal stamps.
- Zero-latency cleanup across all providers; initiation is immediate, actual shutdown may take time and may fail.
- Proving arbitrary external processes/resources not owned by the execution framework were reclaimed.

### Preserved Boundary
BEH-001–010 preserve node/Project scoping, Task descriptions/context, exact run follow-up, unlinked execution behavior, default-off Projects UI, manager/root/sibling liveness and historical data. Existing manual Refresh remains read-only; no automatic board synchronization is proposed.

### Review Authority
Blocking technical corrections must protect the approved REQ/AC/BEH basis once approved. A new policy, migration obligation, compatibility guarantee, UI or destructive cleanup behavior is a Requirement Gap requiring user approval. Reviewer suggestions do not amend the scoped approved basis.
