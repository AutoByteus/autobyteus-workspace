## Proposed Delta For Explicit Approval
1. **Manager owns business work:** plan/create/reuse, delegate, follow the exact worker, check results/artifacts, then explicitly set IN_PROGRESS/DONE. It neither inventories physical resources nor monitors/retries cleanup as an LLM duty. Worker self-report, idle and shutdown still do not automatically mark DONE.
2. **Ordinary tool responses are business projections:** successful Task create/patch returns only Project/Task identity and recorded business status, without echoing description, attachments, execution/lifetime history or cleanup mechanics. Task listing retains business description/status and minimal exact assignment/dispatch information needed to select a Task and follow accepted work, not raw lifetime/cleanup detail or saved attachment metadata. Saved description/files still reach the worker internally by Task ID. Native/MCP semantics match. Exact envelopes/field names are technical design after approval, not silently accepted here.
3. **Server owns teardown and truthful diagnostics:** committed DONE atomically closes the lifetime and immediately starts the same exact protected cascade. Pending/failed release and exact retry authority remain server-maintained, separately observable in server diagnostic state/logs for engineering/operations, not ordinary Manager tool payloads. A DONE acknowledgement means business status was committed, never that every resource was released. Failed/indeterminate business operations return concise truthful errors; cleanup failures must not be erased or certified successful. Repeated explicit DONE remains a safe existing retry trigger; no automatic retry scheduler/new UI/Manager resource loop is added.
4. **Everything else is preserved:** fresh copies, helper ownership, late-input fences, Manager/root/Task-B/borrowed protection, durable data/history/worktrees, existing Delete/reopen/no-ID behavior, direct-use Project array/no migration and all independent gates.

## Problem And Desired Outcome
Existing node-local Project Tasks have descriptions, saved context and TODO/IN_PROGRESS/DONE status, but no supplied Project Task Manager and no relationship to delegated Agent/Team executions. The user wants a manager to create or reuse a Task, delegate it to a worker Agent or Team, track it, and mark it DONE as the explicit resource-release boundary. The prior approved first version uses existing Chat/@, without Project-page chat. The proposed revision separates ordinary business feedback/Manager decisions from server-owned resource diagnostics without weakening scoped cleanup.

Success means the exact business Task can be traced to the actual spawned execution, and completion releases that Task's owned execution resources without stopping its manager, enclosing organization or unrelated work. `DONE` is an intentional business decision, not inferred from an idle runtime or a worker's optimistic message.

### Out Of Scope (Prior Approved First Slice; Preserved In Proposal)
- Project-page embedded chat/panel, new assignment visualization or sidebar redesign; existing @/Chat is the first-slice entry.
- Scheduling, cron, unattended backlog polling/auto-dispatch, dependency graphs, batch tools, external issue trackers, new status vocabulary or automatic acceptance judgments.
- Project creation tools, attachment mutation agent tools, mobile Projects support, changing ENABLE_PROJECTS/default installation semantics.
- Deleting physical workspaces/git worktrees, output artifacts, conversations, run history or uploaded source files; any destructive expansion requires separate renewed user approval.
- New active-deletion blocking or delete-as-cancellation workflows; deletion keeps existing metadata/context semantics.
- Global rewriting of existing unlinked collaboration addressing/routing, or treating ordinary @ admission as fresh task-copy spawning. The approved Task-owned helper lifetime may require a bounded linked-Task admission/routing change; this is not a blanket collaboration redesign.

### Non-Goals
- Proposed: no LLM resource inventory/cleanup supervision or automatic cleanup-retry scheduler, new diagnostic UI/tool or blanket public exposure of internal stamps.
- Zero-latency cleanup across all providers; initiation is immediate, actual shutdown may take time and may fail.
- Proving arbitrary external processes/resources not owned by the execution framework were reclaimed.

### Preserved Boundary
BEH-001–010 preserve node/Project scoping, Task descriptions/context, exact run follow-up, unlinked execution behavior, default-off Projects UI, manager/root/sibling liveness and historical data. Existing manual Refresh remains read-only; no automatic board synchronization is proposed.

### Review Authority
Blocking technical corrections must protect the approved REQ/AC/BEH basis once approved. A new policy, migration obligation, compatibility guarantee, UI or destructive cleanup behavior is a Requirement Gap requiring user approval. Reviewer suggestions do not amend this proposed approval basis.
