## Intended Change
Provide the reusable Manager and add a business Task execution lifetime to the existing delegation pipeline. The external input is either a saved Task ID or described work, never competing payload authorities. New runs inherit a lifetime when created by a Task-owned worker. DONE atomically records business status and closes all current lifetimes, then immediately initiates scoped runtime release. Persistent ownership fences prevent late wake even after process restart and metadata deletion. Root runtime authorities perform release through exact public root boundaries; Task subject authority never walks physical runtime registries.

## Terminology
- **Business Task:** saved Project Task, globally generated taskId within current node; projectId still internal/context identity.
- **Lifetime:** immutable UUID identity for one open period of linked Task execution across all its reserved attempts and successful copies/roots. Closed by DONE; never reopened. Business status reopen does not revive it.
- **Owned execution:** new Task copy/helper with immutable lifetime stamp; a Team stamp includes its configured member tree. Separately created copies have their own stamp even when physically siblings.
- **Borrowed run:** already-existing non-task-owned configured/collaborator runtime consulted without transferring ownership. Does not pass a lifetime into its own subsequent work.
- **Assignment:** fresh delegate_task invocation explicitly using task_id. Internal helpers/follow-on copies are also owned executions, but distinguished by purpose, not presented as independent top-level assignment commands.

## Persisted Data / State Transition Decision
### Need gate and subjects
1. **Projects physical authority:** `<appDataDir>/projects/projects.json`, released/current physical container is an array (E-025 sample 1011 bytes/1 Project/2 Tasks). **Directly Usable — No Migration.** Existing Project entries retain their meaning and required keys. A new zero-or-one node-owned `ProjectTaskLifetimeCollection` entry is optional. Its absence truthfully means no Task-linked lifetimes; no historical executions are inferred. The next normal operation that creates a lifetime writes that new fact. No boot-time rewrite, new required historical fact, converter, schemaVersion or object-envelope decoder.
2. **Execution trees:** optional `taskLifetime` stamp on existing TaskExecution records. **Directly Usable — No Migration.** Absence means unlinked; present stamps validate and all writers preserve them. No history sweep or retro-binding.
3. **Context/conversations/files:** **Not Affected**; descriptions, statuses, IDs, attachments, outputs/history and Git worktrees retain their meaning. Existing deliberate context edit/delete rules unchanged.
4. **Built-in Manager definition:** normal new platform-owned template/bootstrap, no user definition migration.

**Correction of SR-008–010:** changing an array to an object made the former proposal incompatible, but that change was a designer choice, not a fact the feature requires. Guideline §2.1/§3 explicitly require avoiding such representational migrations. Keeping the existing array can still atomically store both DONE and closed lifetimes. ### One current physical array; tight logical projection
```ts
// Current physical JSON array. Existing Project rows remain valid current entries.
type ProjectStateRecord = Project | ProjectTaskLifetimeCollection;
type ProjectTaskLifetimeCollection = { taskLifetimes: ProjectTaskLifetime[] };
// Zero or one collection entry, omitted while no lifetime facts exist.
// ProjectStore's logical projection is not the physical JSON container:
type ProjectState = { projects: Project[]; taskLifetimes: ProjectTaskLifetime[] };
type ProjectTaskLifetime = {
  lifetimeId: string; projectId: string; taskId: string;
  openedAt: string; completedAt: string | null;
  executions: ProjectTaskExecutionLink[];
};
type ProjectTaskExecutionLink = {
  root: RootExecutionIdentity;
  execution: TaskExecutionReference; // exact agentRunId OR teamRunId
  ingressAgentRunId: string;
  purpose: 'assignment' | 'delegation' | 'helper';
  reservedAt: string;
  dispatch: 'reserved' | 'admitted' | 'delivered' | 'failed';
  cleanup: 'not_requested' | 'pending' | 'released' | 'failed';
  error?: { code: string; message: string };
};
// Optional current field on root TaskExecution, not a historical schema version:
taskLifetime?: { lifetimeId: string; purpose: 'assignment' | 'delegation' | 'helper' };
```
```json
[
  { "projectId": "project_A", "name": "A", "description": "...", "createdAt": "...", "updatedAt": "...", "workspaces": [], "tasks": [] },
  { "taskLifetimes": [ "...newly created current lifetime records..." ] }

```
The second entry is **node execution-lifetime state, not a fake Project, deleted-Project tombstone or UI row**. No `projectId` on the collection; each lifetime already carries its exact Project/Task identity. Logical splitting is internal to ProjectStore. Public metadata readers only see Projects; business lifetime methods get the complete logical state. Keeping this small explicit record variant avoids a second lifetime file/status-fence transaction protocol and retains old Project entries unchanged. Not equivalent to setting a JavaScript property on an array (JSON would discard it).

### Current reader / exact writer / invariants
- `project-state-schema.ts` defines one current `ProjectStateRecord[]` decoder and exact serializer. Require the top-level array; missing file decodes normal empty state, not an existing object/non-array file. A current Project row is recognized by its Project identity and projected through the existing metadata normalizer (optional tasks/context truthfully empty, unknown extras ignored). The lifetime collection is recognized by its dedicated `taskLifetimes` field on a non-Project row. This is **subject discrimination**, not a version or old/new decoder. A Project row remains a Project even if it has unrelated unknown fields; never reinterpret its data as a collection.
- Collection presence requires an array with valid lifetime/link fields and invariants; reject duplicate collection entries, duplicate lifetime identity, multiple open lifetimes for one Task, cross-lifetime execution ownership and closed-with-not_requested cleanup. Recognized invalid lifetime/fence facts are not filtered to empty. Invalid JSON/non-array authority or invalid lifetime facts give scoped actionable current-data errors, preserve the file, and never say “run migration recovery.” No implicit conversion of an object-envelope artifact.
- `serializeProjectState(state)` emits exact current Project keys and, only when lifetime facts exist, one `{taskLifetimes:[...]}` entry. Preserve all retained lifetimes on every metadata/service update. Empty ordinary metadata stays an array without a mandatory new entry. Parsing is side-effect-free; no rewrite on read/startup. First dispatch appends new facts through a normal locked atomic write, not a migration or opportunistic old-shape conversion.
- `ProjectStore.readState/updateState` own physical decode/serialize. Reuse existing `readJsonFile`/`updateJsonFile` with default `[]`, file lock and observed atomic commit callback; do not use nonarray→[] coercion or cast physical array as logical object. Updater receives logical state; validate/serialize before replacement. Commit callback receives the already-validated logical result without I/O/throw and closes lifetime gates immediately. Existing `listRecords/updateRecords` operate only on Project projection and preserve collection from full state. Root/Task callers do not see physical record variants or access JSON directly.
- DONE changes the Task row status and matching lifetime completedAt/cleanup fields in **one** physical array replacement; zero cross-store nested locks. Delete removes Project/Task metadata and current owned context but leaves the independent node collection, even after last Project deletion. A lifetime-only array is valid with empty Project listing; no fake Project/tombstone or deletion guard. History/closed fences retain identities without descriptions/files/member/provider duplication.
- Link identity remains `(root,execution)`; purpose and ingress validate against exact stamped tree on requested admission/release, not a new whole-history startup scan. Reserved/failed links without tree remain legal attempted-dispatch states, not release proof. New Task creation checks live plus retained IDs under the same lock; ambiguous existing IDs cannot silently bind; no renumbering.

5. **Commit/retry:** existing single-file lock/atomic replacement/observed commit sufficient. Retry reads current array and updates domain facts; no migration audit, original copy, hash/phase journal or second ledger. No source deletion/multi-file promotion.
