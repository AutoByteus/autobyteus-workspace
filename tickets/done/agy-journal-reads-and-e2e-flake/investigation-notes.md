## FU-2 — spilled outputs

| ID | Finding | How established |
| --- | --- | --- |
| F-03 | **The original tool's result carries the spill, not the later read.** When an Antigravity tool's output is long, its recorded result is the runtime text `The tool's output was truncated due to being too long. You can find the full output in a file at file://<app data>/brain/<id>/.system_generated/steps/<n>/output.txt`, a blank line, `Here is a preview with the middle of the output truncated:`, then the preview. 163 journal lines in 46 journal files hold this sentence (157 `run_command`, a few `grep_search`/`Bash`). The journal shows this runtime sentence and the path as the result's text. | Measured on the founder's journals and raw traces (read-only; counts and redacted shape). |
| F-04 | **The later read of the spill file is an ordinary read.** It is `view_file`/`read_file` (result size-only: **no content is recorded**) in 175 + 3 of the cases found, and a shell `cat`/`sed -n` through `run_command`/`Bash` (40 + 11, whose result carries the content that was read) in the rest. So "hiding" these reads loses no content that the journal holds; but a shell read does hold real content. | Measured (raw traces of the 60 runs that contain a spill path). |
| F-05 | **For MCP tools the original result already holds the complete output** (a 9,992-character `list_project_tasks` result recorded in full), and the agent still reads the spill file: that later read is redundant in the journal. For `run_command` the original result holds only the preview, and the shell read of the spill file holds the middle. | Measured (one run). |
| F-06 | **Precedent for the same concept in the neutral vocabulary:** Claude's translation turns its own "Output too large … Full output saved to: <path> … Preview" text into the preview plus `…[full output (<size>) was saved outside the raw trace: <path>]` (`runtimes/claude-translation.ts:30-45`, `PERSISTED_OUTPUT`). The marker names where the full output lives; a later read of that path is an ordinary read. Antigravity has no such rule today. | Read. |

## FU-3 — scripted-Antigravity E2E flake

| ID | Finding | How established |
| --- | --- | --- |
| F-07 | **Reproduced the hook timeout:** `work-journal-agy-schema-reads-scripted-agy.e2e.test.ts` alone, 6 runs at load average 37–45: 2 fail with `Hook timed out in 10000ms` at its `afterAll` while the test itself passes; 4 pass. The existing neutral-vocabulary file failed the same way in 1 of 5 combined runs. | Ran (`evidence/INV-01…txt`, `INV-04…txt`). |
| F-08 | **The teardown is the slow part, and it is variable:** timed per step in a scratch copy, 6 runs: `terminateAgentRun` 63–87 ms each (stable); `deleteAgentDefinition` 0.05–7.6 s; `app.close()` 0.3–12.9 s; the sum reached 16.6 s against vitest's 10 s default hook timeout. Quiet-moment runs finish the same steps in 0.6 s. | Ran (`INV-02…txt`, scratch copy, not committed). |
| F-09 | **The in-process server's event loop stalls for seconds:** an event-loop lag monitor over the same file shows a maximum lag of 4.5–15.5 s in every run; the CPU profile of the test process is idle during the stall (25 of 30 sampled seconds idle), so it is the machine, not our code, that holds the process. | Ran (`INV-03…txt`, `--cpu-prof`). |
| F-10 | **Host condition at the time:** load average 40–90 on 10 cores; `fseventsd` at 155% CPU; swap 19.8 of 21.5 GB used. This is the case TESTING.md calls "File watching on a busy Mac": closing the in-process server closes its recursive folder watchers on the main thread, which blocks for seconds when `fseventsd` is busy. | Measured (`ps`, `sysctl vm.swapusage`, `vm_stat`) and read (TESTING.md lines 187-199). |
| F-11 | **The project already owns the rule and the constant:** `tests/helpers/os-latency-under-load.ts` exports `IN_PROCESS_SERVER_HOOK_TIMEOUT_MS = 60_000` ("vitest hook timeout for a hook that starts or closes an in-process server or its folder watchers", autobyteus-517 FU-002). Only 7 of the 119 test files that call `startStudioE2eRuntimeServer` use it; 115 keep the 10 s default (113 of them have an `afterAll`). The scripted-Antigravity files are among them. | Read (`os-latency-under-load.ts`; `grep` over `tests/`). |
| F-12 | **A helper can set the hook timeout for every file that imports it:** `vi.setConfig({ hookTimeout })` at module load of an imported helper applies to hooks registered afterwards, in that file only (probe: a helper setting 3 s failed a 4.5 s `afterAll`; a file without the helper kept the 10 s default and passed the same 4.5 s hook). vitest 4.1.12. | Ran (scratch probe, removed). |
| F-13 | **The discovery timeout is not reproduced.** `AgyDiscoveryError: Antigravity model discovery timed out` (an unrelated failure at 22.2 s in the 560 API/E2E log, run 1 of `API-02-base-fails.log`; and in delivery's runs at load above 210) did not occur in 10 solo/combined runs of the same files here (load 37–90). The production probe already tolerates a stalled event loop for an exited child (`probe-time-bound.ts`, autobyteus-576: the timer defers its decision with `setImmediate` and gives an exited child a 1 s `close` grace); the run-start model check calls `listAntigravityModels()` with the usual bounds (10 s `--help`, 30 s `models`, no step deadline: `agy-agent-run-backend-factory.ts:154`), and the runtimes report's model step has an 8 s step deadline (`MODEL_LIST_READ_MS`). Which probe and bound fired in the failures is not recorded (the log lines are on the console, `RUNTIME_PROBE_TIMED_OUT { runtime, command, boundMs }`, but were not kept). | Ran (10 runs, no occurrence) and read. |
