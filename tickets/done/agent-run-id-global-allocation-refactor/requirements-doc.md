# Requirements Doc

## Status (`Draft`/`Design-ready`/`Refined`)

Refined

## Goal / Problem Statement

Simplify and unify concrete agent runtime identity by making every new concrete `AgentRun` receive one generated `<agent_definition_name_slug>_<uuid>` platform runtime identity.

The current codebase mixes canonical runtime identity with semantic information such as agent name/role, team run ID, member route key, and task ID. The target behavior is cleaner:

> Every concrete agent runtime receives exactly one canonical `agentRunId` allocated by one server-side owner before backend creation. New standalone, team-member, and task-agent runs all use the same `<agent_definition_name_slug>_<uuid-without-dashes>` shape. Team routing continues to use route keys/member paths, task lifecycle continues to use task IDs, and the readable slug is non-authoritative metadata for humans only; logic must not parse it.

This ticket remains independent from `send_message_to` global routing. Later routing work may use this invariant, but this ticket must not add new cross-agent message delivery behavior.

## Investigation Findings

The deeper inventory found all current concrete agent run ID generation and propagation points:

- Standalone service-created runs allocate IDs in `AgentRunProvisioningService.generateFreshRunId(...)`.
  - AutoByteus standalone runs use readable IDs through `generateStandaloneAgentRunId(...)` / `generateReadableAgentId(...)`.
  - Codex/Claude standalone runs use UUID candidates through the provisioning service.
- Codex and Claude backend factories still have local fallback UUID generation if `preferredRunId` is absent.
- AutoByteus server backend uses `createAgentWithId(...)`, but the lower-level `autobyteus-ts` `AgentFactory.createAgent(...)` still generates readable IDs if used directly.
- Team member agent run IDs are deterministically generated by `buildTeamMemberRunId(teamRunId, memberRouteKey)` unless an explicit `memberRunId` is present.
- Task-agent run IDs are deterministically generated by `buildTaskAgentInstanceIdentity(...)` from `teamRunId`, logical member route, and `taskId`.
- Team member and task-agent run creation bypasses standalone provisioning and calls `AgentRunManager.createAgentRun(..., memberRunId/taskAgentRunId)` directly.
- `AgentRunManager.registerActiveRun(...)` silently replaces an existing active-run registration for the same `runId` instead of rejecting duplicates.
- Final team-member context-file layout recomputes `memberRunId` from `teamRunId + memberRouteKey`, so non-route-derived member IDs require that path to stop deriving canonical IDs from route keys.
- Follow-up memory/projection investigation clarified that `origin/personal` keeps all leaf agent-member memory for a launched team run flat under the top-level/root `teamRunId`, while the current worktree has started moving nested leaves toward child-team-owned paths. The target design should use a cleaner forward layout: keep one root team memory locality boundary, but mirror nested team structure inside it with nested team-run folders.
- Team routing already has distinct identity surfaces: `memberRouteKey`, `memberPath`, `teamRunId`, and task-delegation `taskId`. These are the right owners for routing and task semantics; `agentRunId` does not need to encode them.

- Evidence basis: There are multiple canonical `AgentRun.runId` generation styles, backend fallback generation, deterministic team/task ID builders, route-derived context-file lookup, multiple competing team-member memory path authorities (root-flat, child-team-owned, consumer-local recomputation), task-agent memoryDir reuse risk, and no duplicate-active guard at the active registry boundary.
- Requirement or scope impact: The target should not merely centralize the existing semantic ID styles. It should remove semantic/deterministic agent run ID generation for new runs and replace it with one generated name-slug + UUID allocation path.

## Recommendations

- Treat the full `agentRunId` as a generated runtime identity: useful for identification, not a source for route/task semantics.
- Keep team routing on `teamRunId`, `memberRouteKey`, and `memberPath`.
- Keep task lifecycle identity on `taskId` and `TaskAgentInstanceIdentity` metadata.
- Introduce one server-side `AgentRunIdentityAllocator`/identity service for new concrete agent runtime IDs.
- Generate one canonical shape for new concrete agent run IDs: `<agent_definition_name_slug>_<uuid-without-dashes>`. The slug is readability-only; the UUID suffix is the uniqueness source.
- Remove production backend-local ID fallbacks. Backend factories should require the canonical generated ID from `AgentRunManager`.
- Remove new-run support for manually supplied canonical `memberRunId`; if a display/debug name is needed, use metadata fields, not canonical ID.
- Preserve historical run readability by continuing to restore stored historical IDs as stored, without rewriting old metadata. Existing historical team memory is direct-member/root-level only; historical nested root-flat team-member memory migration or fallback is out of scope because no nested team runs have existed in production data.
- Refactor context-file final owner handling so it uses stored/resolved `memberRunId` and an explicit `AgentMemoryLocation` instead of recomputing from route key.
- Add one reusable Agent Memory module API for path-sensitive write/read/projection paths. Its path rule should preserve root team locality while reflecting nested team structure: `agent_teams/<rootTeamRunId>/<...nestedTeamRunIdPath>/<agentRunId>`.

## Scope Classification (`Small`/`Medium`/`Large`)

Large

Rationale: The simplification crosses standalone provisioning, runtime backend factories, team member identity assignment, task-agent identity assignment, active run registration, team metadata, hierarchical-under-root team memory write/read projection paths, context-file final owner resolution, memory explorer paths, and tests.

## In-Scope Use Cases

- UC-001: New standalone agent runs receive a globally unique `<agent_definition_name_slug>_<uuid>` `agentRunId` before backend creation.
- UC-002: New team member agent runs receive globally unique `memberRunId` values before team backend/runtime context creation.
- UC-003: New task-agent runs receive globally unique `taskAgentRunId` values before task-agent backend creation.
- UC-004: Team routing continues to use member route keys/member paths rather than encoded agent run IDs.
- UC-005: Runtime backend factories consume required canonical IDs and do not allocate production run IDs locally.
- UC-006: Active run registration rejects duplicate canonical IDs and preserves the original active registration.
- UC-007: Existing persisted standalone and team-member histories remain readable under their stored historical IDs.
- UC-008: Context-file final team member storage resolves actual stored member IDs instead of deriving them from route keys.
- UC-009: Helper/evolver/compaction/application-launched concrete agent runs follow the same standalone ID path.
- UC-010: New team runs receive meaningful-but-unique `<team_definition_name_slug>_<uuid>` IDs rather than short-suffix `team_<label>_<8-hex>` IDs.
- UC-011: Memory write/read/projection paths for standalone runs, direct team members, nested subteam members, and task agents resolve the same concrete memory directory without parsing or regenerating run ID shapes.
- UC-012: Team memory explorer, run-history projections, application published-artifact reads, run-file-change reads, self-evolution target reads, external-channel reply recovery, and context-file final paths use stored opaque IDs plus a single authoritative `AgentMemoryLocationService`; they must not derive member IDs from routes or compute paths independently.

## Out of Scope

- `send_message_to` routing behavior.
- Global cross-agent message delivery by `target_agent_run_id`.
- Direct AgentRun message grants or message authorization policy.
- Rewriting existing historical run IDs or memory directories.
- Historical nested root-flat team-member memory fallback/migration. Current product data has no nested team runs; existing team-memory compatibility is limited to historical direct team members under `agent_teams/<rootTeamRunId>/<memberRunId>`.
- Changing external provider IDs such as Codex thread IDs or Claude session IDs into canonical `agentRunId` values.
- Redesigning team route-key/member-path routing semantics.
- Redesigning task delegation lifecycle beyond injecting generated task-agent run IDs.

## Functional Requirements

- REQ-001: The system must define a single server-side allocation boundary for new concrete `AgentRun` IDs. Its public allocation method must accept `agentDefinitionId` and resolve the agent definition name itself; callers must not pass precomputed slugs as authority.
- REQ-002: New canonical `agentRunId` values must use one generated shape based on `<agent_definition_name_slug>_<uuid>`, where the allocator derives the slug from `AgentDefinition.name` resolved by `agentDefinitionId`. They must not encode runtime kind, team run ID, member name, member route key, or task ID. The agent definition name slug is readability-only and must not be parsed for logic.
- REQ-003: The allocation boundary must check or guard against collisions with active runs, standalone persisted run IDs, team-member persisted run IDs, and in-flight allocations before approving a new ID.
- REQ-004: Standalone run preparation/creation must use the canonical allocation boundary rather than readable or runtime-specific candidate generation.
- REQ-005: Team member runtime identity assignment for new team runs must happen inside `TeamRunService.createTeamRun` before `AgentTeamRunManager.createTeamRun(config, teamRunId)`, using the canonical allocation boundary for concrete agent members and preassigned child team run IDs for `agent_team` members; new launch must not call `buildTeamMemberRunId(...)` for canonical run IDs.
- REQ-006: Task-agent identity creation for new task-agent runs must resolve the target logical agent member config from the active `TeamRun` to obtain `agentDefinitionId`, allocate `taskAgentRunId` through the canonical allocation boundary before identity binding, and must not derive `taskAgentRunId` from `teamRunId`, route key, or `taskId`.
- REQ-007: Runtime backend factories must require and use the canonical ID supplied by `AgentRunManager`; production paths must not rely on backend-local fallback allocation.
- REQ-008: `AgentRunManager` must reject duplicate active `agentRunId` registration and must not silently overwrite existing active registrations/listeners.
- REQ-009: AutoByteus backend creation must verify that the underlying AutoByteus agent ID equals the canonical run ID requested by the platform.
- REQ-010: New public/team-launch input must be a logical topology shape that does not expose `memberRunId` or `childTeamRunId` as caller-owned fields; any needed stable label must be metadata, not canonical runtime/team identity. `TeamRunService` must be the conversion point that creates the runtime-ready assigned config. Restore and persisted metadata reactivation paths may continue to carry stored IDs as data through a separate stored/runtime shape.
- REQ-011: Restore/read paths must continue to use persisted historical run IDs as stored, including readable or deterministic old IDs, without rewriting history.
- REQ-012: Team routing, roster selection, delivery within a team boundary, and task lifecycle decisions must continue to use route keys/member paths/task IDs rather than parsing or deriving meaning from `agentRunId`.
- REQ-013: Context-file final team-member ownership must resolve or carry the actual stored `memberRunId`; it must not recompute canonical IDs from `teamRunId + memberRouteKey`.
- REQ-014: External provider IDs such as Codex thread IDs and Claude session IDs must remain separate from canonical `agentRunId` values.
- REQ-015: The refactor must include durable unit/integration coverage for ID allocation, standalone/team/task-agent consumption, duplicate active rejection, removal of backend fallbacks, historical restore/readability, and context-file member ID resolution.
- REQ-016: New `teamRunId` values must use one generated shape based on `<team_definition_name_slug>_<uuid>`, with the slug derived from `AgentTeamDefinition.name` resolved by `teamDefinitionId`. Top-level `TeamRunService.createTeamRun` must generate and pass the ID through `AgentTeamRunManager.createTeamRun(config, teamRunId)` and `MixedTeamRunBackendFactory.createBackend(config, teamRunId)`. Existing historical team run IDs must remain readable as stored.
- REQ-017: Memory/projection/read paths must treat stored `runId`, `memberRunId`, `taskAgentRunId`, and `teamRunId` values as opaque path-safe identifiers. They must not validate historical IDs against, parse, or regenerate the new `<name_slug>_<uuid>` shape.
- REQ-018: The system must define one reusable Agent Memory location boundary, `AgentMemoryLocationService`, for path-sensitive memory location resolution. It must expose a lightweight write-time team-agent run location shape carrying `rootTeamRunId`, `teamRunPath`, concrete `agentRunId`, and resolved `memoryDir`, and a metadata-rich team-member location shape for read/projection paths carrying the member metadata plus the same resolved memory directory. Direct root members use an empty `teamRunPath`; nested members append each nested `agent_team.teamRunId` / `childTeamRunId` to the path. The location path rule is `agent_teams/<rootTeamRunId>/<...teamRunPath>/<agentRunId>`.
- REQ-019: New write paths must assign `AgentRunConfig.memoryDir` from the same `AgentMemoryLocationService` location rule that read/projection paths use: standalone runs write under `agents/<agentRunId>`; direct team members under `agent_teams/<rootTeamRunId>/<memberRunId>`; nested team members under `agent_teams/<rootTeamRunId>/<childTeamRunId>/<...>/<memberRunId>`; and task agents under the same team path as their logical member, using their own `taskAgentRunId`.
- REQ-020: Team-member read/projection consumers must use `AgentMemoryLocationService` or an equivalent explicit `memoryDir`; they must not recompute `memberRunId` from route keys, flatten away `teamRunPath`, or choose between root-flat and child-sibling paths independently. This includes team-member run projection, team memory explorer, run-file-change projection, application published-artifact member reads, self-evolution target resolution, external-channel reply recovery, and context-file final owner resolution.
- REQ-021: Durable coverage must include historical standalone memory projection, historical direct team-member memory projection, new nested subteam member projection/explorer, opaque historical ID acceptance, and new-run write/read path symmetry for direct team members, nested members, and task agents. Historical nested root-flat projection coverage is not required because no such production data exists.

## Acceptance Criteria

- AC-001: Creating standalone AutoByteus, Codex, and Claude runs produces a new `<agent_definition_name_slug>_<uuid>` `agentRunId` allocated before backend creation and records that same ID in active-run state and metadata.
- AC-002: New team member runtime contexts contain `memberRunId` values assigned by `TeamRunService` before runtime creation: concrete agent members use allocator-produced `<agent_definition_name_slug>_<uuid>` IDs, `agent_team` wrapper members use their preassigned child `teamRunId`, and route keys/member paths remain unchanged and still drive team routing.
- AC-003: New task-agent identities contain `taskAgentRunId` values allocated by the canonical boundary after resolving the target logical member `agentDefinitionId` from the active `TeamRun`, while `teamRunId`, logical member route, and `taskId` remain metadata fields.
- AC-004: Attempting to register a second active `AgentRun` with an existing active `runId` fails loudly and leaves the original active registration/listeners intact.
- AC-005: Codex and Claude backend creation fail if no canonical ID is supplied instead of silently inventing one.
- AC-006: AutoByteus creation fails if the underlying agent factory returns an ID different from the requested canonical ID.
- AC-007: New team launch/config input DTOs do not contain canonical `memberRunId` or `childTeamRunId` fields; `TeamRunService` assigns them before runtime creation, and restore from stored metadata still uses stored IDs through the restore path.
- AC-008: Existing standalone and team-member history lookup/restore works for historical IDs without rewriting historical memory directories.
- AC-009: Final team-member context-file paths resolve through stored/resolved member identity and no longer rely on deterministic `buildTeamMemberRunId(teamRunId, memberRouteKey)`.
- AC-010: Tests prove that team route-key selection still works after member IDs become generated, non-route-derived runtime IDs.
- AC-011: Tests prove that task delegation still binds, activates, targets, and settles task agents using generated `<agent_definition_name_slug>_<uuid>` `taskAgentRunId` values plus separate task metadata.
- AC-012: No `send_message_to` global routing behavior is added or changed by this ticket.
- AC-013: Creating a new team run produces a `<team_definition_name_slug>_<uuid>` ID in `TeamRunService`, passes it explicitly through manager/backend creation, and team member/task-agent metadata stores this team ID separately from `<agent_definition_name_slug>_<uuid>` runtime IDs.
- AC-014: Historical standalone memory projection reads stored metadata `memoryDir`/`runId` opaquely and still works for old readable or deterministic IDs that do not match the new generated shape.
- AC-015: Historical direct team-member memory projection and explorer reads use stored top-level `teamRunId + memberRunId` opaquely and do not call any route-derived member ID builder.
- AC-016: New nested subteam member projection/explorer reads load from `agent_teams/<rootTeamRunId>/<childTeamRunId>/<...>/<memberRunId>` and tests fail if implementation places nested member memory as a top-level sibling under `agent_teams/<childTeamRunId>/...` or loses the nested path. Existing historical direct team-member root-level reads remain readable; historical nested root-flat fallback is not required.
- AC-017: New direct team-member, nested team-member, and task-agent runtime writes use the same memory directory that their projection/read path later resolves.
- AC-018: Read-side services that need team-member memory locations consume `AgentMemoryLocationService` output containing `rootTeamRunId`, `teamRunPath`, and explicit `memoryDir`; no in-scope write/read service owns its own team-member path derivation.

## Constraints / Dependencies

- Base branch must be `origin/personal`; this ticket is separate from `codex/send-message-global-run-routing`.
- The implementation should not rewrite existing persisted run histories or memory directories. New team runs use the hierarchical-under-root layout. Existing historical direct team-member memory remains readable as stored because direct-member paths are unchanged. Historical nested root-flat fallback/migration is not required because current product data has no nested team runs.
- Historical restore/read may need to register or display non-canonical historical IDs; new allocation must still produce only the new canonical name-slug + UUID shape and read paths must remain shape-agnostic.
- Runtime provider IDs must remain distinct from canonical platform `agentRunId`.
- Team route keys/member paths are authoritative routing metadata and should not be replaced by `agentRunId`.

## Assumptions

- The platform does not need route/task/debug semantics encoded in canonical run IDs; the definition-name slug is only lightweight human readability, while display/debug fields remain metadata.
- Route key/member path are already sufficient for team-internal logical routing.
- Task-agent lifecycle already has `taskId`; it does not need `taskId` encoded in `taskAgentRunId`.
- Existing tests or imports that inject `memberRunId` are either historical/restore fixtures or should be updated to use metadata/route keys instead of manual canonical ID selection.
- Existing team metadata already stores nested `agent_team.teamRunId`, so new hierarchical-under-root memory locations can be derived without adding duplicate per-leaf memoryDir fields to the durable metadata schema. Current production data has no historical nested team runs, so the design does not add a metadata layout marker or filesystem fallback for historical nested root-flat memory.

## Risks / Open Questions

- Should new IDs use UUID-without-dashes, ULID, or another token? Recommendation: choose the simplest safe implementation already available in Node: derive slug from `AgentDefinition.name` / `AgentTeamDefinition.name`, then append `randomUUID().replace(/-/g, "")`.
- Should the allocator maintain only in-process reservations plus persisted scans, or add a durable global identity index? Recommendation: start with UUID-backed name-slug IDs, active duplicate guard, persisted scans, and in-process reservations unless implementation discovers a real multi-process requirement.
- Context-file decision: keep route-key-facing APIs/URLs if useful, but resolve route key to actual stored `memberRunId` and hierarchical agent memory location through `AgentMemoryLocationService` before storage layout.
- Public new-launch ID policy: the public launch DTO is logical topology only and does not expose caller-owned `memberRunId` or `childTeamRunId`; restore/import-from-stored-metadata remains internal/restore-only.

## Approval Status

Refined based on the user's explicit design direction and architecture review feedback on 2026-06-11: simplify `agentRunId` into a unique `<agent_definition_name_slug>_<uuid>` identity resolved from `agentDefinitionId`, use the same rule for task agents after resolving target member config, use `<team_definition_name_slug>_<uuid>` for team runs passed explicitly through launch/backend APIs, narrow new-launch input to logical topology with server-assigned runtime IDs, keep team routing on route keys, and make `AgentMemoryLocationService` the coherent Agent Memory boundary for hierarchical-under-root memory paths that preserve folder locality and nested team structure. Round 6 clarification from the user narrows historical team-memory compatibility to existing direct team members only because no historical nested team runs exist; the design also separates lightweight write-time team-agent memory locations from metadata-rich read/projection member locations.
