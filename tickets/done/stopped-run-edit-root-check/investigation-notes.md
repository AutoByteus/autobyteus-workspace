| --- | --- | --- |
| F-01 | The single-agent stopped-run edit (`StandaloneStoppedRunSelectionUpdater.update`, run inside the run's transition lane) refuses only when `agentRunManager.getActiveRun(runId)` is set, i.e. the host runtime is live. It never asks whether the run's root is registered. | Read: `autobyteus-server-ts/src/agent-execution/services/standalone-stopped-run-selection-updater.ts` lines 58-65. |
| F-02 | A registered root with an offline host is a supported, tested state: "a host crash does not end it (the next use makes the host ready again)"; "The host crashes: the root and its children survive; a delegated copy's report wakes the host (DS-009)". | Read: `standalone-agent-run-root.ts:90-93`; `tests/unit/standalone-agent-run-root/standalone-agent-run-root.test.ts:45,79,189,215` (fixture `f.host.crash()`). The root also stays after idle shutdown of a peer-delegated host (`standalone-agent-run-root-manager.ts:243-245`). |
| F-03 | The root captures the host's inherited launch once, when it is loaded: `rootLaunchConfiguration: launchConfigurationOf(metadata)` (runtime, model, model settings, auto-approve, workspace). `StandaloneRootCollaborators` hands this fixed object to `launchBase()` ("inherited"), from which catalog copies snapshot (REQ-004). Nothing updates it afterwards. | Read: `standalone-agent-run-root-manager.ts:84-90,428`; `standalone-agent-run-root.ts:159-162`; `standalone-root-collaborators.ts:30,44-72`. |
| F-04 | The host itself is not affected: each activation builds its member context from the CURRENT metadata (`buildMemberExecutionContext` reads `host.readMetadata`), so a saved model or runtime applies to the host when it resumes. Only the copies delegated afterwards from the lingering root take the OLD launch. With a pending runtime switch the old runtime is inherited too, while the host starts on the new one. | Read: `standalone-agent-run-root-manager.ts:430-440`. Not reproduced (see U-1). |
| F-05 | Editability shown to the user comes from the host's status (`runModelConfigEditability({isActive...})` from `statusProjectionService`), so a run with a lingering root and an offline host is editable in Settings. | Read: `run-history/services/agent-run-resume-config-service.ts:52-58`. |
| F-06 | The edit of a stored delegation tree (`updateStoredTree`) refuses with RUN_ACTIVE when `hasRoot`, because it writes the tree under a live root. That is a different write (the tree), not the host's metadata, so it is not a model for the host edit. | Read: `standalone-agent-run-root-manager.ts:336-345,369`. |
| F-07 | The root manager is the process's `StandaloneRunLifecyclePort`; `AgentRunService` already holds it as `standaloneRuns` and uses it for `stopRoot` ("even when the host's own runtime already died"). The updater itself lives in `agent-execution`, which must not import the root (ports exist for that). | Read: `standalone-run-ports.ts:1-35`; `agent-run-service.ts:90,106,132`; `agent-run-lifecycle-service.ts:120-131`. |
| F-08 | **FU-005 (order of the restart notice and the hand-over notice) is covered; nothing to build.** The restart notice is a SYSTEM input built with `platformInputPrefaceMetadata` (`restart-notice.ts:40-45`); `canCarryPreface` returns false for any message that already carries a platform preface (`agent-run-input-preface-dispatch.ts:16-19`), so the hand-over notice (a platform notice source, `runtime-handover-notice-service.ts`) is not attached to it and stays pending until the next external input. `AgentRunPlatformNotices` also hands over at most one notice per dispatch (`agent-run-platform-notices.ts`). Result: restart notice first, hand-over notice with the next input; both cannot collide. The restart notice is posted only as the run's first input (`onlyAsFirstInput`), after the restore that performs the switch. | Read; not run. The restart chain (autobyteus-285) is on the base (`tickets/done/restart-resume`). |
