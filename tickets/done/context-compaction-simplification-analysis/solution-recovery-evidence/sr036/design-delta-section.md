### Decision, root cause and design health

**Select forward retention of the existing accepted `message_id` and `dedupe_key` in native user raw facts, then normal typed projection into `messageId` / `dedupeKey`.** Do not allocate another identity, overload raw `id`, repurpose `correlation_id`, synthesize identity from a turn or add a live-history lookup ledger. A raw ID identifies a trace, not an accepted input. The original event metadata, already used by AgentRun's pending snapshot, is the source of the accepted keys.

Root cause: a missing correlation invariant across an existing native writer → ordinary reader → saved conversation → live input boundary; not a wrong queue owner. **Refactor needed now, bounded:** extend the existing value contracts and eliminate lossy mappings and identity-blind merges in the affected paths. Keep input execution/FIFO/recovery ownership unchanged. No new orchestration service, admission registry, cache, startup scan or parallel format. Centralize the presentation identity comparison as a pure value concern in the existing presentation-contract package; core persistence parsing remains core-owned and must not depend on server/web or that presentation package.

Rejected alternatives: body/media/time equality is not identity; latest-position matching guesses; runId+turnId is not unique across retained runs (fresh TurnTracker on restore, with no raw run_instance_id) and generic append-capable runtimes need not have one input per turn. These are reasons not to choose those mechanisms, not new restart product failures. An ephemeral index would require new facts/lifetime/coordination without benefit over preserving keys already available at ingestion.

### Matching, deduplication and presentation

**Scope first:** one exact node binding/AgentRun conversation; never match between root host and child, two children, another node, or another loaded context. Within a saved projection, require the same message kind/role and sender provenance (`senderId` / `senderAgentRunId` / `senderAddress`, as applicable). A user bubble and an inter-agent delivery are never interchangeable. Context/run ownership remains the existing caller's responsibility, not a new persistent identity component.

**Typed-key relation:** a pair matches iff at least one same-named usable key is equal and no same-named usable key on both sides disagrees. Thus:
- same messageId, equal or absent dedupeKey → match; same dedupeKey with one/both messageIds absent and no conflicting present key → match;
- different present messageIds **never** merge, even with equal dedupeKey; equal messageId with conflicting present dedupeKeys does not merge;
- messageId "x" never matches dedupeKey "x" by cross-field equality;
- no key on one side → no exact match. Do not borrow an identity for an anonymous row from content, time, attachments, turn or position.

A partial-key input matching more than one existing candidate is ambiguous: do not choose the first or transitively bridge those candidates; retain separate entries. This is a deterministic comparison safety rule, not a newly claimed product failure or a new reconciliation registry. Implement one pure `sameAcceptedInputIdentity` value comparison (and, if useful, unique-match selection) in `autobyteus-agent-presentation-contracts/src/accepted-input-identity.ts`, exported normally. Server and frontend projection/live callers use it with explicit sender/context scoping. It has no queue/network/store/framework dependency. Core needs only equivalent primitive decoding, not a dependency on presentation or a second matching algorithm.

Both server `run-projection-dedupe.ts` and browser `runProjectionConversation.ts` must honor identity before considering their existing semantic merge path. For a user/inter-agent entry with either accepted key, only an unambiguous exact match can merge; neither different-key entries nor keyed/anonymous pairs enter body/time dedupe. Identity-less entries retain the current generic projection policy, but sender provenance must participate so different senders cannot collapse. Do not change unrelated tool/activity/provider dedupe or enable old snake_case/metadata aliases for this new typed path. Existing unrelated identity handling remains separately scoped. Merge retains nonmissing keys and all attachment/provenance facts; never erase a known key with undefined/null or select across conflicting senders.

Frontend `userMessageProjection.ts` remains the one user upsert owner. Its existing OR matcher must use the conflict-safe relation; `agentInputStateHandler.ts` must not independently repeat the old OR expression when finding a timestamp. Centralize lookup there, return/use the same matched message, or export its pure lookup. Pending snapshots still ignore non-user senders and never fabricate user bubbles for them.

For matched A, preserve saved timestamp and retained presentation facts; overlay original live input text and current pending label rather than appending. Reconcile attachments within this matched message by exact existing attachment locator/type, retaining media plus non-media references, original URI/type/name and existing non-executable composer references. The pending projection can contain only recorded non-media references while history includes media; absence there must not delete saved media. Preserve richer stored file names and mention/local attachment facts rather than replacing them with absent values. Use current attachment hydration/identity conventions, not basename/body similarity or a new attachment authority. Keep this preservation scoped to history/live pending reconciliation; do not broaden unrelated echo/send semantics unnecessarily.

For unmatched B, add one pending bubble in snapshot order; repeat same/newer snapshots upsert it once. Existing revision guard ignores same-instance stale/equal revisions. Removing an entry clears its pending label, not its conversation history. New run instance still obeys existing exact-context/rebinding guards; no persisted pending label or restored queue is inferred from the newly saved identity. All SR035 atomic publication and terminal retention remain mandatory.

### Persisted-data transition — Directly Usable — No Migration

**Stored raw user format IS affected additively; existing stored data is Directly Usable — No Migration.** This explicitly supersedes the earlier all-raw-writers-unchanged decision. It does not contradict the approved no-history-rewrite/no-new-migration/no-durable-queue constraints. Optional absence has a truthful meaning: the row contains historical content/provenance but no evidence of its accepted command key. Such rows remain readable in normal current runtime; they cannot satisfy an exact history/live match. Do not backfill or relabel them, including the frozen API009 responses. Ordinary new writes retain the already-present accepted keys.

1. **Need:** no conversion required; recognized optional keys enrich new facts without changing old content. No available old fact reliably supplies the lost key. Fabricating it would be wrong, not a useful migration.
2. **Availability:** no new startup/capability/run gate; old identity absence never blocks application/new work/history. Existing invalid-package/file/attachment admission is not weakened.

No installed private-profile census or claim that generated fixtures prove released upgrades. Core/store and server normalizers are the normal reader boundaries.
4. **Dispositions:** existing keyless rows preserved/read as unknown; new keyed rows read with exact identity; absent/invalid optional keys never establish a match. Existing predecessor preserved exclusions stay excluded, never recreated by this change. No migration aggregate status introduced/reinterpreted.
5. **Commit/retry:** existing one raw append and existing archive commit boundaries only. No extra journal/backup/hash/transaction, queue-durability promise or second ingestion on compaction retry.
6. **Current-only:** one structural current reader, no version branch, dual writer or old-file fallback. Released rotation migration copies complete segment bytes, preserves/excludes pending residue and leaves orphan non-authoritative files untouched; its missing-complete-file failures remain. No changed strict row classifier imported from RawTraceItem was found there. No released migration or Prisma change is selected.
7. **Cost:** zero corpus rewrite, zero new startup passes/syncs. Bounded extra key strings in new user rows and existing requested projections only. 8. **References:** accepted keys are correlation values, not path locators/authorization. Attachment and sender ownership still use existing exact execution/run contracts. Trees, message stores, manifests, snapshots and provider-native records retain their meanings.
9. **Evidence:** reader/writer round-trip, mixed old/new history and real producer-through-hydration regression below are required, not already Pass. Ordinary archive and attachment protections must remain exercised.
10. **Lessons/review:** no historical lockout, whole-corpus readiness, per-trace journal or guessed ownership. Independent architecture review must cover this new persisted-field decision; ARCH005 reviewed SR035 only.

**Rollout/lifetime:** build core/server/contracts/web together through the existing process. The guarantee applies to inputs ingested by the revised native writer. Ordinary code update starts the revised backend/native instances; mixed binaries writing a run, hot-patching a held old instance and repairing lost keys in already-captured old responses are not supported deployment contracts. Pending queues already do not survive backend restart; do not terminate user work solely for a data conversion (there is none), nor invent replay to preserve it. Existing historical rows may coexist with new ones after normal restore. Identity-bearing old history does not authorize a new instance to replay old input. Retained native activity remains in-memory only; this is not cold-history compaction-state persistence.
