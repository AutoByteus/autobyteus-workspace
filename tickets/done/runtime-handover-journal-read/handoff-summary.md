## Delivery Summary

- Delivered scope:
  - **After a runtime switch, the new agent's first input names the journal file with the previous agent's most recent work and asks for a complete read.** The file is the newest closed journal file with at least one work entry (any entry that is not a notice). The text says: before you reply or continue the work, read `<journal folder>/<file>` completely, from its first line to its last; if it is long, read it in parts until you reach the end. The notice no longer calls `work_journal_active.md` the latest work; it says that file starts with this hand-over. Every file stays listed, oldest first, in the existing format ("the earlier ones are there if you need to look further back"). A switch before any work leaves no closed file with work, so the notice has no read instruction and lists the files as before. It still names no runtime or model, repeats no request, and is delivered once, first, with the marker presentation.
  - **Why the old text failed (the root cause).** At the moment the notice is built, the open file holds only the switch marker: the previous agent's work is in the newest closed file. The old text called the last file in the list the latest work, so agents started from a file with one line in it and often never read the work. The founder saw a clear drop in quality after every switch.
  - **One new fact with one owner.** `WorkJournalFileSummary.workEntryCount` (entries that are not notices) is computed in `listJournalFiles`, which already parsed every file; the builder only reads it, and an explicit rule in one pure function chooses the file. Three source files changed (one type field, one line, the builder). No persistence, API or GraphQL change: the journal view maps its fields explicitly, so the count is not exposed.
- Docs synced (`docs-sync-report.md`): the implementation updated `GLOSSARY.md` ("Work entry", "Hand-over notice") and `run_history.md`; the Solution Designer added design Case 25; delivery updated `agent_work_journal.md` (the `listJournalFiles` bullet) and checked `DESIGN.md`, `TESTING.md`, `RELEASE.md`, `agent_episodic_catalog.md` and the web docs: no change.

## Residual Risks For The User

- R-1 (**FU-001**): a run switched to the **Claude Agent SDK** does not read the whole named journal. In three of three live runs the agent read the start and the end of a 2,405-line journal and skipped the middle. The founder's goal (the new agent continues with the full context) is therefore met by Codex and native AutoByteus agents and, as far as these checks show, not yet by Claude Agent SDK agents on long journals. The server text is as approved. The follow-up asks what helps (the line count beside the instruction, a hint for that runtime). Journals of the founder's switched runs measured 32 to 3,001 lines, so a long journal is the normal case.
- R-2 (not tested live): Antigravity and Grok as the switched-in runtime. The notice text is the same for every runtime (no runtime name in it); the built-server E2E runs MS, native and AGY switch-back, and Grok as a switch target (RS-06, RS-07, EX), run the notice's delivery and echo on scripted runtimes.
- R-3 (host): this Mac is out of memory (swap about 96%) and its `fseventsd` holds 20 to 24 GB and delivers file events late or not at all. Tests that wait on file events, and tests with tight fixed waits, fail here under load and pass alone. Restarting `fseventsd` or rebooting needs root and was not done. This is the same condition as autobyteus-576's DEC-005.
- R-4: the model's compliance is not guaranteed by any server text (Non-Goal of the requirements); the live check measures it for three runtimes only.
