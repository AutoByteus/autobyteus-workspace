# Investigation Notes

## Investigation Status

- Bootstrap Status: `Complete`
- Current Status: `CR-005 Design Impact investigated and corrected — ready for architecture review round 6`
- Investigation Goal: Identify why a selected local video opens in the packaged Electron Files preview but remains black at `0:00`, prove the cause against the user's actual media and Electron version without disturbing the running app, and establish the smallest secure production-path fix and validation boundary.
- Scope Classification: `Medium`
- Scope Classification Rationale: The visible symptom is confined to one viewer, but the correct fix crosses renderer preview state, raw context-locator hydration/submission, Electron's pre-ready custom-scheme lifecycle, main-process filesystem validation, MIME and byte-range response behavior, and realistic Electron execution.
- Scope Summary: Repair supported local-video metadata loading, play/pause, seek, and failure recovery in the Electron Files preview; preserve valid external local-file context locators; quarantine unsupported context locators from executable media; retain the trusted local-file validation boundary and unrelated viewers.
- Primary Questions Resolved:
  1. What exact URL and production path does the video element use? `local-file://` from File Explorer state through `VideoPlayer.vue` to the Electron protocol handler.
  2. Is the reported video absent, corrupt, badly encoded, or not fast-start? No; the exact H.264 MP4 is readable, decodable, and fast-start.
  3. What concrete media error occurs under the shipped runtime? Electron 42.4.1 produces `MediaError.code = 4`, `readyState = 0`, and `duration = NaN` with current protocol semantics.
  4. Why does it occur? The custom scheme is never registered with Electron's required streaming privilege before ready.
  5. Is adding `stream: true` alone sufficient? It fixes metadata and playback from the start, but not seeking because the current handler drops `Range` and returns an ordinary `200`.
  6. Is standard+stream plus range behavior sufficient with the old URL? No. API/E2E proved the standard parser rewrites `local-file:///Users/...` to `local-file://users/...`, so the absolute POSIX path identity is lost before decoding.
  7. Can the old opaque shape use stream-only plus correct ranges instead? It preserves case and handles the reported 13 MB file, but the approved 607 MB later-range seek fails with `PIPELINE_ERROR_READ`.
  8. What contract is sufficient for media identity/ranges? Pre-ready `standard + stream`, a fixed lowercase `local` authority with the complete case-preserving encoded absolute path in `pathname`, validated MIME-correct full/single-range responses, and the existing cancel-safe stream owner.
  9. Does the refreshed task base retain the original defect? Yes; the base handler is identical to the user's running source. The first implementation commit `f60718a63` correctly implemented the initial reviewed design but exposed the URL-identity conflict only at realistic Electron execution.
  10. Is File Explorer the only reachable URL producer? No. `contextAttachmentPresentation.resolveWorkspacePreviewUrl` independently interpolates the same obsolete scheme for embedded absolute workspace-image thumbnails. The target therefore needs one process-neutral URL codec used by both renderer producers and Electron main, not a paired one-off patch.
  11. Can a local-file locator enter without either derived builder? Yes. Supported Context Files text paste and runtime message/projection hydration call `hydrateContextAttachment`, which explicitly retains `local-file://` as `external_url`; send and presentation retain it. Valid legacy empty-authority POSIX and drive-authority Windows locators need an isolated transition to canonical form before current-model presentation. Arbitrary opaque hosts were already rejected as filesystem identities by the current main decoder and must not be guessed into paths.
  12. Which raw URL adornments can the handler enforce? Under exact Electron 42.4.1 standard+stream, port and credentials are erased and authority case is normalized before `protocol.handle`; query and fragment remain visible. Raw context-locator ingress can reject all adornments before DOM assignment, but the handler contract must accept an indistinguishable canonical request after Electron erases port/credentials and continue to rely on filesystem validation.
  13. Can unsupported current attachment metadata remain generic at send? No. `partitionContextAttachmentsForStreaming` branches only on inferred type, so `local-file://opaque/image.png` becomes `unsupported_local_file(type: Image)` and still enters `image_urls`, server `ContextFile(IMAGE)`, LLM media arrays, and media normalization. The local optimistic user message already stores full attachment objects separately, so a bounded submission plan can retain current UI/message metadata while excluding unsupported state from executable arrays; existing historical records remain readable, but newly quarantined unsupported input will not be written to durable runtime projection without a new metadata-only transport.
  14. Is current-session-only retention and fresh-reload disappearance of newly unsupported metadata approved? Yes. After the architecture reviewer isolated AR-004 and the user was offered current-session quarantine versus a larger durable metadata feature, the user explicitly chose Option 1 on 2026-07-18. Valid attachments/locators remain durable normally; executable-media quarantine remains mandatory.
  15. Does the reviewed two-privilege lifecycle preserve PDF and Excel? No. API/E2E round 3 proved that real PDF.js XHR and Excel Fetch fail before `protocol.handle` from both HTTP and packaged-representative `file://` shell origins. `corsEnabled` alone serves PDF XHR but not Fetch; `supportFetchAPI` alone serves neither cross-protocol consumer; both serve the established consumers.
  16. Can both additional privileges be enabled safely without another boundary? No. An exact Electron 42.4.1 probe showed foreign-HTTP and same-origin Blob child frames then receive local-file bytes. The handler `Request` omits usable origin/referrer/fetch metadata, so handler-only filtering cannot distinguish them.
  17. What is the smallest owned security correction? Register exactly `{ standard, stream, supportFetchAPI, corsEnabled }`, then use one default-session `webRequest.onBeforeRequest` filter to permit only the exact main `WebFrameMain` of a live registered `WorkspaceShellWindow`. Top-frame HTTP/file Fetch+XHR still pass; foreign-HTTP and same-origin Blob child requests are canceled before `protocol.handle` with zero bytes. Browser tool content remains in a separate session with no handler.

- Public API / spec / issue / upstream source: [Electron `protocol` API](https://www.electronjs.org/docs/latest/api/protocol/), [CustomScheme structure](https://www.electronjs.org/docs/latest/api/structures/custom-scheme), [WebRequest](https://www.electronjs.org/docs/latest/api/web-request), [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security), and [Electron release PR #51270](https://releases.electronjs.org/pr/51270).

- Relevant contract, behavior, or constraint learned:
  - `protocol.registerSchemesAsPrivileged` must be called before the application ready event and may be called only once.
  - The `stream` privilege defaults to false.
  - Custom protocols used by `<video>` and `<audio>` require `stream: true`.
  - `standard: true` supplies generic URI semantics; the same-version probe verified that `standard + stream` works with the expected media range/cancellation lifecycle here.

  - `webRequest.onBeforeRequest` exposes optional `webContentsId` and requesting `WebFrameMain`, can cancel the request, and supports only one active listener per event.
  - Electron recommends sandboxing, context isolation, retained `webSecurity`, navigation/window restrictions, and custom-protocol scoping.
- Why it matters: The protocol must combine the exact four capabilities required by media, PDF XHR, and Excel Fetch with both a valid standard authority/path split and a pre-handler frame-authorization owner. Node-only parsing, handler Request headers, and privilege-only tests are not adequate witnesses.

1. **The exact file is healthy.** Its bytes, metadata layout, codec/pixel format, and sampled decoding all succeed. Its `moov` atom precedes `mdat`, so this is not a download-progressive-metadata problem.
2. **The renderer production route is behaving as currently written.** File Explorer recognizes the video, opens a tab, builds an encoded opaque `local-file://` URL, maps it to `VideoPlayer`, and supplies it directly to Chromium.
3. **The Electron media contract is incomplete.** `installProtocols()` runs only after ready and calls only `protocol.handle`. Electron therefore never learns that `local-file` may stream media. The current `net.fetch(file:)` response also does not propagate Chromium's incoming range.
4. **The missing privilege is causally proven.** With the exact same Electron binary, file, and handler shape, adding `stream: true` changes the result from media error/code 4/duration NaN to correct 330.533333-second metadata and playable media.
5. **A flag-only fix would be incomplete.** Native video controls include seeking. A streaming-only `200` response played from zero but reset a 120-second seek to zero. Correct single-range `206` behavior fixed it.
6. **The response must be streaming and cancellation-safe.** Chromium cancels an initial stream and opens later byte ranges during large seeks. Whole-file Blob/buffer loading or a fragile Node-to-web stream adaptation would add memory or correctness regressions.
7. **Existing validation is not the defect.** `validateReadableRegularFile` correctly gates absolute readable regular files. It should remain the only filesystem validation policy owner and execute before any source bytes are returned.
8. **The UI hides all native media failures.** `useAuthorizedObjectUrl` cannot report errors for directly assigned custom URLs, and `VideoPlayer.vue` does not subscribe to the media element's `error` event. Unsupported codecs and unavailable files therefore remain black even after transport is fixed unless the viewer adds an error/retry state.
9. **The problem is broader than this one exact file but the task should stay bounded.** Local audio shares the same scheme and requires streaming privilege. Image/PDF/Excel use the scheme but not native media seeking. Remote/browser content uses other paths and must not be reworked.
10. **The running log is not a sufficient media diagnostic.** Current renderer code does not log/propagate the native video error, so absence of an application-log error does not contradict the same-version probe. Implementation should provide user-visible state; it need not expose absolute paths or Chromium pipeline detail.
11. **The first implementation is structurally faithful but technically contradicted.** Source review found no deviation; realistic Electron execution alone exposed standard-scheme URL canonicalization. This is Design Impact, not a stale test or local fix.
12. **The old triple-slash URL is incompatible with `standard: true`.** Chromium promotes the first POSIX segment to authority and lowercases it. Decoder acceptance cannot recover original case or the leading segment safely.
13. **Stream-only is not a complete alternative.** It preserves exact URL identity and handles the reported file with correct ranges, but the large later-range seek fails under Electron 42.4.1.
14. **A fixed authority solves both identity and seek.** `local-file://local/Users/...` stays exact across authored attribute, media property/current source, and handler. Standard+stream then passes exact/significant/large playback and seek with the current response/stream implementation.
15. **The clean security contract is boundary-scoped exact identity plus the existing validator.** Raw supported context ingress rejects credentials/port/query/fragment and old/wrong/opaque authorities before DOM assignment. The normalized handler requires `local`, rejects the wrong authority and surviving query/fragment, decodes pathname once, requires/normalizes `/C:/...` on Windows, then calls the unchanged validator. It cannot claim rejection of an authored port/credential that Electron erased. The builder accepts only a POSIX absolute or Windows drive-letter path. No arbitrary hostname-to-path mapping is needed.
16. **File Explorer is not the only production URL producer.** `contextAttachmentPresentation` derives a local-file URL for an absolute workspace-image thumbnail in embedded Electron, and an existing component test exercises that normal path. Fixing only the File Explorer builder would leave this reachable consumer broken.
17. **The URL wire shape needs one owner, separate from trust and response policy.** `autobyteus-web/shared/` already contains pure renderer/main contracts and both build systems can consume it. A subject-specific codec can own constants/build/parse while routing stays in renderer owners, filesystem validation stays in `localFileValidation.ts`, and range/stream policy stays in the Electron protocol owner.
18. **Derived local resource URLs are ephemeral, but external locators are not necessarily derived.** File Explorer open-file state and `workspace_path` thumbnail URLs are runtime state. Separately, pasted/projected `external_url` attachments can retain an already-authored local-file locator and require a transition decision.
19. **A third supported raw-locator path is persisted-capable.** Text paste and runtime projection can produce `external_url` context attachments whose locator already begins `local-file://`; send/projection retains the raw string. One user's current data having no hit does not eliminate this product contract.
20. **Valid legacy locator meaning is recoverable before Chromium.** At raw hydration, an empty authority plus absolute pathname preserves the exact POSIX path, and a one-letter drive-authority form preserves the Windows drive/path. These can be decoded once and rebuilt through the canonical current codec before presentation. After standard-scheme DOM assignment, that information is no longer recoverable.
21. **Opaque multi-host locators are retained data but not valid filesystem identities.** The first implementation and current decoder reject `local-file://opaque...` before validation. Durable tests using opaque strings prove retention/hydration, not successful file serving. Target code must retain their attachment metadata while preventing unsupported identities from media assignment; it must not guess a hostname into a path.
22. **Electron erases some authored adornments.** The exact renderer probe showed `local-file://local:99/...` and `local-file://user:pass@local/...` become canonical property/handler URLs with empty port/credentials; uppercase authority becomes lowercase. Query and fragment remain in the handler Request and can be rejected there.
23. **Security promises must follow observable boundaries.** Supported raw context ingress can reject credentials/port/query/fragment/wrong/opaque forms before DOM assignment. File Explorer/context derived builders never create them. The handler can reject wrong authority and surviving query/fragment, but a manually authored erased port/credential URL is indistinguishable from canonical and simply proceeds through the unchanged absolute/readable/regular-file validator.
24. **Presentation containment alone is insufficient.** The proposed `unsupported_local_file` kind prevents `<img>` and open actions, but `partitionContextAttachmentsForStreaming` ignores `kind`. With inferred type `Image`, `local-file://opaque/image.png` enters `image_urls` and remains executable downstream.
25. **The failure consequence is concrete.** Agent/team stream handlers construct `ContextFile(IMAGE)`, `buildLLMUserMessage` maps it into `image_urls`, memory ingestion records it as media, and the current-message client normalizes media sources. An unsupported local-file URL can therefore fail an otherwise valid user message and persist through the wrong executable channel.
26. **Current message metadata already has a separate owner.** `beginLocalUserSubmission` and `finalizeLocalSubmissionAttachments` store full `ContextAttachment[]` in the optimistic/local `UserMessage`; the WebSocket arrays are derived separately. No metadata-only server field is needed to keep the label in the current UI.
27. **Live team echo needs a mixed-case merge.** `memberInputMessageHandler` preserves existing attachments only if the incoming list is empty. When valid and unsupported attachments are sent together, the echo contains the valid executable entries and would replace the local list. The target must merge existing non-executable current kinds into the matching echo and dedupe them.
28. **Durable new-invalid retention is not available without a new transport.** Server/core run projection stores executable context/media, not arbitrary client attachment metadata. The bounded design quarantines new unsupported input from durable runtime writes while preserving existing historical invalid records on read. Cross-restart persistence of newly rejected locators would be a separate product/API/memory-schema requirement, not a reason to misuse executable arrays.
29. **Quarantine does not create an empty-message execution edge.** `AgentUserInputTextArea` disables Send unless trimmed message text is nonempty. A reachable send with an unsupported attachment therefore still carries text; excluding the invalid locator lets that text and any valid attachments proceed through the existing executable path.
30. **AR-004 is resolved by an explicit bounded-retention choice.** The user chose Option 1 after the current-session/fresh-reload consequence and the alternative metadata-only persistence feature were explained. Newly unsupported metadata may disappear after fresh reload; valid files/locators remain durable; executable arrays remain reserved for executable context/media.
31. **The reviewed two-privilege lifecycle cannot preserve established document viewers.** Real PDF.js XHR and Excel Fetch fail before `protocol.handle` from both representative shell origins. The implementation follows design; response, validation, fixtures, and viewer routing are not the cause.
32. **Both Fetch and CORS capabilities are necessary, but privileges alone are unsafe.** The exact differential proves no one-flag variant serves both consumers. The ungated four-privilege probe also proves ordinary foreign-HTTP and same-origin Blob child frames can read scheme responses.
33. **Handler-only requester filtering is impossible in Electron 42.4.1.** At `protocol.handle`, the request headers omit origin, referrer, and fetch metadata in the relevant cross-protocol requests. Authorization must occur at an earlier boundary that retains request-frame identity.
34. **The default-session webRequest boundary retains sufficient identity.** `onBeforeRequest` provides `webContentsId` and the requesting `WebFrameMain`; exact object comparison to a live registered workspace shell's `webContents.mainFrame` distinguishes authorized top-frame HTTP/file Fetch+XHR from both tested child frames. Cancellation prevents handler invocation and bytes.
35. **A second byte transport is not the smallest correction.** Viewer-specific binary IPC/Blob delivery would duplicate response/validation ownership and still trust the same top shell. Per-path tokens minted from that shell's own path input do not reduce its authority but would complicate canonical persisted locators and range/retry lifecycle. The evidence-backed extension is one protocol with a pre-handler main-frame gate.

## Constraints / Dependencies / Compatibility Facts

- Electron privilege registration is a one-time pre-ready operation and must contain exactly `standard`, `stream`, `supportFetchAPI`, and `corsEnabled`; request-gate and handler installation remain post-ready.
- The app shell uses Electron's default session, so app-level scheme registration/handling plus one filtered `webRequest.onBeforeRequest` authorization owner are required. Browser views use `persist:autobyteus-browser`, where the handler is absent.
- The pre-handler authorization predicate must require a live registered `WorkspaceShellWindow` and exact equality between the request's `WebFrameMain` and that shell's `webContents.mainFrame`. URL/origin string comparisons are not an adequate substitute; missing/destroyed/unregistered/subframe requests fail closed.
- The shell must retain `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, blocked navigation, denied new windows, and enabled `webSecurity`. Do not add `secure`, `bypassCSP`, service-worker, code-cache, or extension scheme privileges.
- The internal URL shape must change cleanly to `local-file://local/<encoded absolute path>`; old empty/drive authorities are obsolete and must not receive a compatibility decoder.
- The fixed authority must preserve uppercase/case-sensitive segments, spaces, Unicode, percent signs, hashes, Windows drive letters, and other URL-significant characters entirely in pathname.
- Both supported renderer producers and Electron lifecycle/response code must consume one subject-specific shared codec; no endpoint may retain its own scheme/authority concatenation or hostname-to-path decoder.
- A successful codec parse is not authorization. The existing main-process validator must still accept the decoded candidate before any open/read.
- Context hydration is the only owner allowed to understand valid legacy empty/drive-authority locator shapes. Ordinary attachment presentation and the Electron handler accept canonical current identities only.
- Context attachment submission must derive executable arrays from current kind, not inferred file type alone. `unsupported_local_file` remains local metadata and cannot enter `context_file_paths`, `image_urls`, server `ContextFile`, or runtime media arrays.
- Existing agent/team WebSocket and runtime-memory schemas remain executable-only. No metadata-only transport is added; new unsupported input is intentionally client-quarantined rather than durably persisted, while existing historical records remain readable.
- Handler-visible URL identity is already canonicalized by Electron. Port/credentials and raw authority case are not enforceable there; query/fragment and wrong authority remain enforceable.
- The response owner must determine a MIME type for every existing local-file media/document route or preserve a safe fallback; supported video/audio types must not become `application/octet-stream` accidentally.
- Only a single byte range is needed for Chromium media in scope. Malformed, multi-range, and unsatisfiable ranges must not return bytes and should produce deterministic failure responses.
- Streams/file handles must close on completion, cancellation, and error. Large video should not be materialized entirely in renderer or main-process memory.
- Codec support remains bounded by the shipped Chromium/Electron build. The fix promises correct transport for supported content, not new codec availability.
- English and Simplified Chinese UI strings must follow the repository localization generation/audit workflow.
- Implementation-owned local checks can cover pure protocol helpers/component state; realistic custom-protocol playback and seek belongs in API/E2E after source review.
