## Problem / desired outcome
A converted historical Org resumes its selected agent, then stops because the saved token summary still claims a Team root. The same family migration also reads expensive standalone/flat-Team histories unnecessarily during locator conversion. Complete token-statistics ownership conversion as part of the existing unreleased feature migration so valid converted conversations continue without this failure and their accumulated usage is preserved.
Stakeholders: user continuing old conversations; data owner preserving usage/history; developers integrating the unreleased feature. Observable success is a continuation response with valid token events, not merely disappearance of a warning or a successful migration status.

## Supported scenarios / use cases
- UC-001 / SCN-001 / Supported Normal Scenario: user first launches the feature with an existing supported nested Team history and saved usage; migration converts it; user opens resulting Org and sends a continuation; response and usage update succeed with prior data preserved. Supported by original feature history-continuity contract and current user request.
- UC-002 / SCN-002 / Supported Explicit Edge Scenario: the same migration is invoked again through its ordinary supported retry/test entry. History source conversion has no remaining candidates, but saved token source attribution remains. History work is a no-op; token candidates are converted; the conversation then continues. No shipped success-record detection/replay mechanism. Manually preparing a development profile for this test is a separate operational action, not a customer migration requirement.
- UC-003 / SCN-003 / Supported Normal Scenario: user continues an existing native flat Team, standalone Agent or already-correct Org; this correction does not reclassify its valid ownership or change its totals. Original feature preserves flat Teams and distinct root families.
- UC-004 / SCN-004 / Supported Explicit Edge Scenario: migration is retried after a supported failed/interrupted startup; completed work is not double-counted and unresolved ownership/persistence failures are reported rather than treated as success. Existing runner retry contract supplies the basis. Success records keep the existing skip semantics; local development ledger preparation is outside shipped migration logic.

- UC-005 / SCN-005 / Supported Normal Scenario: user upgrades with many standalone/flat-Team histories and a smaller nested-Team cohort (or none). The family migration reads only lightweight root metadata/index data to classify candidates; it does not enumerate/parse non-candidate traces, complete archives, attachment bytes or formal sidecar content. Selected source histories still convert safely. User U-SCOPE-004 and observed locator inventory provide independent basis. No universal wall-clock target or guarantee about other startup phases.

## Scope guardrail
In scope: UC-001–005, candidate discovery and candidate-scoped locator/runtime/cleanup/history-index conversion, exact token attribution needed for the converted root and its supported configured/task participants, relevant derived summaries/readers and repeat-safety evidence, all as part of the existing family migration.
Out of scope: a second migration ID for this correction; general token analytics/UI redesign; changing token pricing/counting semantics; weakening root-family event validation to hide this defect; missing-tree reconstruction, separate startup-wide readiness/attachment validation, startup timeout, thread-writer conflicts, definition package conversion or external repository changes; arbitrary corrupt-data reconstruction; production release or integration into personal.
Non-goals: automatic replay of successful migrations or migration version markers/hooks solely for development builds; global repair of cross-cohort links; reset statistics, recreate conversations, restart settled tasks, or launch/replay the user's real profile for testing without separate operational approval.
Preserved boundary: BEH-001–005 and REQ-003/004. No acceptable loss of user content or accumulated usage.
Review authority: blocking findings must trace to approved REQ/AC/preserved behavior. New migrations, broad compatibility policy or new product behavior require renewed approval; reviewers cannot silently expand scope.

## Requirements
- **REQ-001 / BEH-001:** Extend existing `20260901_agent_org_flat_team_families_v1` migration to complete supported converted runs' token-statistics ownership. Do not register a second migration or increment this ID for this fix. Eventual target is `origin/requirements/flat-agent-organization-model`, not personal.
- **REQ-002 / BEH-002:** Treat this as one unreleased first-time source→target migration. On ordinary rerun, independently process remaining history and token candidates without development-build detection or automatic reset/reopening of successful ledger entries. No history candidate means no history conversion; old token ownership may still require correction, validated against exact execution ownership. No invented usage for absent records.
- **REQ-003 / BEH-001/003:** Preserve exact existing accounting totals, cost values, conversation/run/platform identities, messages, references and task history. Ownership correction must remain consistent across the authoritative stored summary and relevant derived readers; it must not be undone by the next usage observation. Native flat-Team/standalone/native valid Org data outside the affected cohort is unchanged.
- **REQ-004 / BEH-004:** The migration's correction is idempotent and recoverable through supported startup/retry behavior, reporting actual completion/failure. Do not count migrated usage again or report completion before required ownership work succeeds. Unresolved/conflicting ownership must not be guessed. Preserve genuine runtime safety validation and unrelated migration recovery policy.

- **REQ-005 / BEH-005:** Candidate selection governs all history-conversion phases. Permit root-directory enumeration and execution-tree/history-index metadata reads to classify supported nested-Team sources and incomplete work. Exclude standalone Agent histories entirely; once metadata establishes a flat Team, do not enumerate/read its member traces, archives or attachment/sidecar contents for this migration. Do not rebuild/revalidate every existing Org history when no source/index work remains. Preserve non-candidate rows/files, and preserve candidate-contained references, tasks and attachment bytes. Missing/invalid metadata is diagnosed, not guessed into a conversion candidate. Separate startup readiness validation is unchanged.

## Constraints / assumptions / open technical questions
No public API, UI or database schema change is prescribed. Metadata classification is lighter than history parsing but not free; no unmeasured timing claim. Correctness must include prior token materialization order, cumulative state and derived readers. Source candidates, not “previously run build” detection, determine work. The existing migration ID and ordinary runner status policy stay unchanged. If a development rerun is requested later, stop the app and back up the profile before a separately approved exact ledger operation; do not ship that operation in application logic. Do not claim removing this migration scan removes the separate startup readiness scan. Outside-cohort synthetic typed URLs are not an approved reason to traverse standalone/flat histories; if a real supported cross-cohort preservation gap is demonstrated, return it to the user rather than adding a global scan or runtime fallback.
