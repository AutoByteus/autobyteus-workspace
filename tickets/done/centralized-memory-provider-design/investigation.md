## Current Behavior / Current Flow

- Current local runtime memory root contains:
  - `memory/agents/<runId>/...`
  - `memory/agent_teams/<teamRunId>/...`, including team metadata files and member agent run memory below the team-run path
- These paths are actively used by runtime, run-history, memory-view, and team services.
- Current local node behavior is acceptable and should not be disrupted.
- There is no current cross-node import namespace.
- Current homepage Memory menu displays local node memory only through `MemoryHome`, `memoryExplorerStore`, and local memory explorer GraphQL queries.
- Current `/memory` route state carries local view/tab/agent/team/run identifiers but no source selection, so source-aware browsing must explicitly add and preserve source route/store state.
- Current memory detail and inspector queries read from the local memory root only; they do not accept a local/imported source input.
- There is no current memory source selector for Local vs imported source nodes.
- There is no current Memory Hub ingestion endpoint or source-node sync worker.
- There is no current durable sync manifest/file fingerprint state for pushing memory to another server.
- There is no current Memory Hub advertised URL configuration, source credential store, token creation flow, or token-to-source authorization mapping.
- Existing frontend Nodes functionality is a UI registry/control surface, not a backend identity system: `NodeProfile.id` is frontend-generated and local to the registry, `NodeProfile.name` is editable display text, and `NodeProfile.baseUrl` is a network endpoint used for node-bound routing.
- Current backend startup already separates `--host`/`--port` binding from `AUTOBYTEUS_SERVER_HOST` public/client-facing URL and `AUTOBYTEUS_INTERNAL_SERVER_BASE_URL` internal runtime URL. However, `AUTOBYTEUS_SERVER_HOST` is still a single configured public URL for one caller context, not a guarantee that Docker/Kubernetes sources can reach it.

## Revised Architecture Direction From Investigation

The design is now:

```text
Source node local memory:
  memory/agents/**
  memory/agent_teams/**

Memory Sync source subsystem:
  scan + plan full-file replacements for changed files + push batches

Hub node embedded Memory Hub:
  memory/imports/<sourceNodeId>/source-node.json
  memory/imports/<sourceNodeId>/sync-manifest.json
  memory/imports/<sourceNodeId>/agents/**
  memory/imports/<sourceNodeId>/agent_teams/**
```

Important decisions:

- Feature name: Memory Sync.
- Receiving role: Memory Hub.
- Current server embeds both source and hub capability.
- No separate project in v1.
- Keep current local runtime memory paths unchanged.
- Imported memory is separate and read-only by default.
- Source identity is stable configured `sourceNodeId`.
- IP/port/service URL is metadata and may change.
- Do not sync `imports` recursively.
- Do not require v1 raw-trace index or analytics index. Future indexes can be derived from imported memory later.
- Extend the current Memory menu with a source selector: Local Memory plus imported source nodes.
- Add runtime-updatable Memory Sync configuration so users can make the current node a hub or configure it as a source after startup.
- Add source-aware Memory menu routing so Local Memory remains default, imported sources are explicitly selected, and source choice persists through list/detail/inspector/back navigation.
- Hub setup owns an editable advertised hub base URL. The UI should seed candidates from the configured public/client-facing server URL (`AUTOBYTEUS_SERVER_HOST` / `getBaseUrl()`) first, then current bound frontend node/runtime/LAN/tailnet/manual candidates. Source-side `Test Connection` validates the actual URL reachable from Docker/Kubernetes/local sources.
- Hub source credentials are generated by the hub backend with secure random tokens, stored only as hashes plus metadata, displayed only once, and revocable/regenerable from the Memory Sync tab.
- Reuse the existing frontend Nodes page to open/configure registered source nodes. Do not create a second parallel frontend node registry for Memory Sync.
- Keep `sourceNodeId` backend-owned and stable; frontend node registry fields can help the user find a node or prefill a suggested label but must not silently rename hub imports.

## Runtime-Native Session Portability Finding

Imported memory is not active runtime state.

- AutoByteus may later design explicit import/replay/analysis features, but v1 Memory Hub does not make imported runs runnable.
- Codex and Claude native sessions are runtime-owned and cannot be restored merely by copying AutoByteus memory artifacts.
- Therefore imported memory must not appear in normal local runnable run history and must not be presented as a native session restore source.

## Findings From Code / Docs / Data / Logs

1. The existing local memory layout is already the right source artifact set.
2. The least risky storage addition is `memory/imports/<sourceNodeId>/`, not a new top-level project and not a relocated local memory root.
3. A stable source id is mandatory for repeated sync. IP/port can be used in display metadata, not as durable folder identity.
4. Push sync is best for Docker/Kubernetes/local mixed deployments because source nodes can reach a hub URL and the hub does not need access to each source filesystem.
5. File-level mirroring preserves future optional analytics value better than raw-trace-only sync when the future use cases are unknown. The same canonical file map covers both `agents/...` and `agent_teams/...` entries using a `kind` plus relative path.
6. A sync manifest is necessary for idempotency and unchanged-file no-ops. An analytics index is optional and should be deferred.
7. The current Memory menu is the right first browsing surface for imported memory, as long as imported memory is explicitly selected/labeled and read-only.
8. Source/hub configuration must be mutable from UI/API after startup so local Docker nodes do not need to be recreated only to set hub URL/token.
9. Existing frontend Nodes functionality should participate in setup/navigation: open a registered source node, then configure Memory Sync against that node's bound backend.
10. Existing frontend Nodes functionality should not define hub storage identity: frontend registry ids and labels are local UI metadata, while `sourceNodeId` is node-local backend configuration and hub import identity.
11. The hub URL in copyable setup information is an advertised base URL, not a guaranteed backend-generated truth. The backend can suggest `http://127.0.0.1:<port>` or the current bound node URL, but Docker sources may require `http://host.docker.internal:<port>` and Kubernetes sources may require a Service/Ingress URL.
12. Memory Hub source tokens should be generated using the same class of server-side random credential and hash-at-rest pattern already present in remote access. Plaintext token display is one-time only.
13. Source nodes still need to persist the copied hub token locally for background sync after restart, so source-side config must treat that token as sensitive and mask it in UI/status responses.
14. Existing remote-access pairing already follows the industry pattern for network-dependent URLs: generate/list candidate addresses, let the user choose or enter a manual URL, then bind credentials to that client-facing URL. Memory Hub should follow that same pattern instead of treating startup `AUTOBYTEUS_SERVER_HOST` as universally correct.
15. For a local Electron hub plus local Docker source, the most useful candidate is usually `http://host.docker.internal:29695`, because `127.0.0.1:29695` from inside the container points at the container itself. A LAN IP candidate such as `http://192.168.1.20:29695` may also work only if the embedded server is bound beyond loopback and host firewall/network policy allows it; it exposes the hub more broadly than the Docker-host alias.
16. Memory source selection is not just a home-list concern. Current route/detail/inspector flows carry run ids without source scope, so source-aware routes and backend detail readers are required to prevent imported details from accidentally reading local runs with the same ids.
17. Background sync for active raw traces should stay file-level and simple. Active `raw_traces.jsonl` may change frequently, but v1 should compare fingerprints and upload the whole file when changed. When compaction/archive rewrites files, Memory Sync does not care which records moved; it treats new run-root archive segment files such as `raw_traces_000001.jsonl`, changed raw-trace manifests, and rewritten active files as changed files and mirrors them.

## Constraints / Dependencies / Compatibility Facts

- Current runtime code expects local `memory/agents` and `memory/agent_teams`; do not move them.
- Imported memory must not be confused with local runtime memory.
- Source-node relative paths must be normalized and validated to prevent path traversal.
- Sync must handle Docker/Kubernetes/local deployments with stable source ids.
- Sync must avoid echo loops by excluding `memory/imports` by default.
- Hub URL reachability is deployment-specific; advertised hub base URL must be editable and validated by source-side test connection.
- Memory Hub tokens are sensitive and must not be stored in imported memory artifacts or exposed by normal status/list queries.
- Source-side saved hub tokens are also sensitive and should be stored in Memory Sync config/secret storage, not in exported memory artifacts.
- Selected Memory source must be part of Memory page state and backend query identity whenever browsing imported details or inspectors.

## Open Unknowns / Risks

- File sync protocol detail now has a concrete v1 shape: compare file fingerprints and upload full-file replacements for changed files only. There are no append/range deltas in v1. Compaction/archive is not modeled at record level; it appears to Memory Sync as changed files to mirror. Implementation can still tune batch size, stable-read behavior, and hashing performance.
- Delete propagation: recommended default is no automatic hard delete propagation in v1 to protect hub corpus.
- Imported memory browsing is now designed as a Memory menu source selector plus imported/read-only detail views; exact visual placement can still be refined during implementation without changing the architecture.
- Exact GraphQL field names and DTO details remain implementation choices, but hub URL/token ownership is no longer open: advertised URL is editable hub config, hub tokens are backend-generated and hash-stored, and source nodes save copied tokens as masked sensitive config.
- Redaction/retention is important before production enterprise usage.
- Future analytics/index shape is unknown and should be derived after real memory corpus usage.
