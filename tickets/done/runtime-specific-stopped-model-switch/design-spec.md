## Supported Behavior And Production Reality
The existing stopped Agent/Team/Org Settings path already enforces external catalog membership and schema validity without an AutoByteus context-capacity gate (SR-003 delivery). The new issue is not missing Claude choices: the packaged backend returned 11 SDK rows and the scrollable picker contained them plus a saved historical ID (E17–19). It is **split alias authority**: the Claude SDK adapter marks `default` as an alias of listed `opus`, the backend catalog still sends both, the launch-oriented Web grouper folds `default`, and the stopped picker then reintroduces the unmatched exact ID under a mixed “Saved / runtime-offered” heading. A direct frontend hide would leave the backend offering/validating the duplicate.

The approved change is exact and narrow: for Claude, when SDK evidence unambiguously resolves `default` to the same concrete model as another listed ID, **one backend catalog owner omits `default` from newly selectable offered rows**. The sibling and all other distinct models remain. If the relation cannot be established, `default` remains offered. The pre-existing saved exact `default` value remains a separate current value; unchanged-model settings and provider continuation stay possible when SDK still reports that raw ID. No implicit rewrite to `opus`, no frontend alias policy, no new context-size veto, no runtime switching, no active hot-swap, no Save-time history reset.

Scenario basis: SCN-007 is a Supported Normal Scenario for a user opening stopped Claude Settings after real SDK discovery, and a Supported Explicit Edge Scenario for a run saved as exact `default`. SCN-001–006 remain approved. **BEH-007 is preserved out-of-scope behavior**, not a new product entitlement: Agents/Agent Teams → Run from a saved definition and Applications → Launch Setup/readiness from a saved/effective profile must continue to accept an exact SDK-reported current `default`. ARCH-REV-002 MP-001/002 trace the exposed triggers and forward paths; prior live E2E-02–07 exercised definition-to-Run. E23 additionally found one Agent and four Team indexed local histories with exact Claude `default`, though manual selection and current-definition prevalence are unknown. No synthetic alias chain, hidden-state tampering or migration is needed.

## Task Size, Risk, And Escalation
- `task_size=Medium`: refactor existing Claude catalog, shared run-selection evidence/option DTO, GraphQL projection, shared Web picker plus bounded launch/application exact-current consumers, localized labels, tests and docs. No new runtime, storage schema, writer, provider session mechanism or new subsystem.
- `architectural_risk=High`: provider snapshots and Agent/Team/Org options share catalog ownership; changing offered rows also affects launch/platform consumers and fresh Save validation. Replacing the current two-list frontend intersection with a server-provided option descriptor changes the GraphQL/Web contract. Existing exact `default` run settings, definition-to-Run seeds, application readiness and provider identity must survive. These are cross-boundary invariants, not mere string cleanup; hence the requested repeat architecture review.
- Escalate a proven consumer contract or persisted-data conflict as Design Impact/Requirement Gap; do not add a client-only filter, accept an unlisted changed target, silently remap a saved ID, or reintroduce capacity gating. Representative provider continuation remains a downstream validation risk, not a universal success guarantee.

## Authoritative Ownership, Interfaces, And Dependency Direction
1. **Raw Claude SDK adapter:** `ClaudeSdkClient.listModels()` faithfully adapts all supported SDK rows, including exact `default`, its resolved-model evidence and schema. It does not silently remove a runtime ID; the Claude session manager's direct raw SDK use and provider continuation remain intact. The existing presentation derivation supplies *internal* alias/recommendation evidence but no longer exposes a client-side alias contract.
2. **Claude provider catalog:** `ClaudeModelCatalog` is the single owner of selectable-row normalization. From one raw SDK snapshot, its focused normalizer yields offered rows and an exact-ID current lookup. Drop `default` only when its unambiguous canonical resolution equals a *different listed* row, retaining SDK order when choosing that sibling; mark the sibling recommended. Otherwise retain `default` and its recommendation. Do not deduplicate other equal canonical labels or guess from names, context sizes or model-family strings; IDs such as `claude-fable-5-1` and `claude-fable-5-1[1m]` are distinct unless the specific approved default-alias rule applies.
3. **Runtime catalog boundary:** `ModelCatalogService` exposes normalized **newly offered** rows for both `listLlmModels` and provider snapshot queries. Its one runtime-scoped catalog view has `offeredModels` and `findExactCurrent(id)` from the same raw snapshot. A named `resolveExactCurrentLlmModel(runtime,id,cwd?)` entrypoint delegates to that view for existing effective selections outside stopped Settings; it returns the exact row or null, **not** an offered-choice eligibility verdict. Codex, Antigravity and AutoByteus use offered=raw. The raw collection remains encapsulated; neither selection service nor application validator calls ClaudeSdkClient/ClaudeModelCatalog directly. `listLlmModels` must not be used to reject a persisted/effective current ID.
4. **Run selection owner:** `RunModelSelectionService` uses one fresh catalog view per runtime/workspace key per batch. `listOptions` emits replacement descriptors only from offered rows, excluding the saved exact ID, plus a separately resolved current descriptor if the SDK still reports it. For `validate`, changed selection must match an offered row; unchanged ID must equal the fresh persisted current ID **and** resolve exactly from the raw runtime snapshot. The matching row's schema governs config validation. AutoByteus capacity proof still applies only to changed native selections. Unknown future runtime fails closed. Thus alias removal does not become an arbitrary historical-ID bypass.
5. **Transport/presentation:** GraphQL maps stopped run-option descriptors; provider snapshots contain normalized offered rows. A separate batched `runtimeCurrentModelDescriptors(runtimeKind, identifiers)` read-only GraphQL query maps exact backend descriptors; launch/application callers pass only their server-origin persisted/seeded current IDs. The query itself is a descriptor lookup, not a provider-choice list or authorization to Save a changed ID. The Web existing-run picker uses self-contained run options. Agent/Team definition editor and Run creation, mobile launch, Team member inheritance, and Application Launch Setup request exact-current detail for their server-origin seed/baseline/saved override while using snapshots only for new offered choices. In shared picker logic, exact offered ID wins normally; if a seeded current ID is absent from offered rows but exact descriptor exists, show its canonical/provider label as a **current-value display only**, with its schema, not as a new clickable `default` choice. Selecting listed sibling `opus` is explicit and changes the stored ID; merely opening/re-clicking current display does not. If no exact descriptor exists, show raw saved ID and truthful unavailable state. Frontend formats/describes backend data but never infers alias equivalence, adds a hidden ID to offered groups, or treats a new arbitrary draft ID as saved current.

**Boundary rule:** Web → GraphQL run options/provider snapshots/exact-current descriptor query, not Web → SDK alias policy; selection and application readiness → ModelCatalogService, not its internal Claude SDK; lifecycle managers → selection validator, not raw catalog; restore adapter → saved provider/session, not normalized picker list. The shared view has one meaning per field: offered choices and exact current resolver. Exact-current resolution is for the caller’s server-origin saved/effective identity, not a fallback way to offer `default` anew.

### Target Contracts
```ts
type RuntimeModelSelectionCatalog = Readonly<{
  offeredModels: readonly ModelInfo[];                    // new selections only
  findExactCurrent: (savedIdentifier: string) => ModelInfo | null; // same raw snapshot
}>;
type RunModelChoice = Readonly<{
  llmModelIdentifier: string;
  providerName: string;
  displayName: string;
  canonicalName: string;
  description: string | null;
  configSchema: Record<string, unknown> | null;
  recommended: boolean;
}>;
type RunModelOptions = Readonly<{
  currentModelIdentifier: string;             // persisted ID, even if currentModel is null
  currentModel: RunModelChoice | null;         // exact current descriptor, not an offered row
  replacements: readonly RunModelChoice[];    // backend-authorized offered rows
  unavailableReason: string | null;
}>;
```
GraphQL `RunModelOptionsObject` and Agent/Team/Org operations mirror these fields; regenerate Web types in lockstep. Reuse one `RunModelChoice` mapping for current and replacement rather than overlapping optional fields. `currentModelIdentifier` is intentionally separate because a removed SDK row still has a persisted ID. `currentModel=null` is distinct from an available model with `configSchema=null` (no adjustable settings). The separate launch-current descriptor query returns the same bounded display/schema fields with the requested exact ID and nullable descriptor; it does not change provider snapshot `llmModels` membership. Batch/dedupe by runtime plus exact ID for Team/application leaves; verify runtime-scoped cache invalidation and do not cache across Save freshness. Do not send raw SDK internals to Web. The change is an explicit run-options contract revision; no fake numeric capacities or dual old/new DTO.

## Design Health, Refactor And Clean-Cut Removal
- Posture: user-directed behavior correction plus bounded refactor. Root causes: **Boundary/Ownership Issue** and **Duplicated Policy** (backend returns duplicate while Web folds it), plus **Shared Structure Looseness** (ID-only run options force a separate frontend catalog/schema lookup and an unmatched-ID fallback that conflates saved and offered). The reviewed old capacity refactor remains correct.
- Refactor now: **Yes**. Centralize Claude alias normalization in its backend catalog; make run options self-contained for stopped-run picker and model schema; retain only presentation formatting in Web. This prevents a frontend-only hide while avoiding repeated catalog disagreement. Do not add a new subsystem or general alias registry.
- Remove/decommission: frontend `resolveAliasTarget` / `aliasIdsByTarget` folding, `SelectItem.aliasIds` / `selectItemMatches` alias matching if repo-wide call-site audit confirms no other owner, GraphQL `aliasOfModelIdentifier` and Web generated/client mirror, and the stopped-run `groupedModelOptions`/server-ID intersection plus mixed “savedOrOfferedGroup” fallback. Retain a **separate saved-current display** for stopped and launch/application surfaces, not a compatibility picker choice. `SearchableGroupedSelect` needs a selected-value display override when the exact current ID is absent from offered items; it must not alias-match the sibling as selected. Keep `recommended` as truthful server-provided presentation metadata; if only Claude emits it, other catalogs return false/null as existing semantics require. Remove obsolete tests/docs describing frontend alias folding; add tests of backend normalization/current resolution.
- Not legacy retention: exact saved `default` lookup is the **current-value invariant** for any saved ID, not a version-specific branch. Existing persisted values remain directly usable. Do not keep a second “raw offered” API or accept `default` as a fresh changed stopped-run target once filtered.
- Technical tradeoff: richer run-option descriptors are a modest GraphQL/type change but eliminate the frontend's second catalog authority and preserve settings schema for historical current values. The separate exact-current lookup is used only on launch/application paths that already have a provider snapshot; the stopped picker retains self-contained run options to avoid its old dual-catalog intersection.

## Persisted Data Transition
Decision: **Directly Usable — No Migration**. AE-07 inspected representative Agent metadata and Team/Org trees; E23 found five currently indexed exact-`default` Agent/Team runs (local point-in-time inventory); current readers/writers store exact model ID/config and provider binding. The new filter changes *selection-facing offered rows*, not stored shape. Raw exact lookup, definition/launch current display, application readiness and normal restore continue to understand a saved `default` without converting it to `opus`; an explicit switch persists the chosen exact ID. No bulk rewrite, dual read/write, version branch, data loss, workspace change or Save-time compaction. If the SDK no longer reports that exact ID, current value remains visible but settings schema is unavailable and Save must not claim validity; normal provider outcome remains observable.

## Concrete Example
SDK rows `default → claude-opus-5-5`, `opus → claude-opus-5-5`, `sonnet → claude-sonnet-5` yield provider snapshot and new replacement IDs `opus, sonnet`; `opus` carries the recommendation. A saved definition seeded as exact `default` appears in Agent/Team Run with a current-only Opus label/schema, but the offered Anthropic list contains only `opus, sonnet`; leaving it unchanged creates the run with exact `default`, whereas selecting `opus` explicitly persists `opus`. Application Launch Setup/readiness resolving that effective saved leaf receives the raw `default` model descriptor for credential authority rather than `MODEL_UNAVAILABLE`. An old stopped run saved as exact `default` receives `currentModelIdentifier=default`, current descriptor/schema from the raw SDK row, and replacements `opus, sonnet`. Editing thinking settings while leaving ID `default` validates that exact raw row and preserves ID; clicking `opus` validates/persists `opus`. If `default` has no proven listed sibling, it stays in offered rows. A distinct `[1m]` model is not removed merely because its canonical display label resembles another ID. Bad shape: server offers `default` while Web hides it, or Web reports saved `default` unavailable because it only searched offered provider rows.
