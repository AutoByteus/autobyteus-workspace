# Token Usage: One Cumulative Row Per Agent Run — Requirements

## Status (`Design-ready`)

Approved by the user on 2026-08-19 after repository, release-tag, representative production-data, historical-upgrade, and production-shaped Electron verification. The approval adopts the strict one-row model and `REQ-011` run-created-in-range/lifetime-total semantics, and directs the design to follow `autobyteus-server-ts/README.md` production data-migration conventions. `SR-002` through `SR-007` resolved bounded-state, direct/skip-version, forward-only-runtime, failure-classification, and deterministic Prisma/SQLite transport findings. That reviewed implementation subsequently completed live consolidation successfully. User-directed `SR-010` restores this ticket to the completed `SR-007` boundary: the later `SR-008`/`SR-009` migration-audit summary projection, stored-summary compaction, and historical-log work are withdrawn as a separate migration-framework concern. `SR-011` removed the retained consolidation's false manual Retry. `SR-012` supersedes the boolean-only presentation and completes that already-approved degraded journey with one generic runner-owned recovery action carried to localized Settings guidance, so users can distinguish “restart to retry” from “no retry” without the UI inferring migration policy. The two observed oversized historical `summary_json` values, the current status-response size, `log_path`, and historical log files are explicitly accepted residuals for this ticket and must remain untouched here.

## Goal / Problem Statement

Deliver two explicit upgrade-safe change groups in the same ticket. First, repair the already-released `20260730_token_usage_provider_name_snapshot_backfill` **in place under the same migration ID** so an installation whose upgrade is currently stuck at that historical migration can install the newer version, retry it with the corrected bounded implementation, and start successfully; the transition-critical sibling model-value definition must be bounded under its unchanged ID for the same direct/skip-version path. Second, replace the append-per-notification token-usage ledger with one authoritative cumulative token-usage row per canonical agent run through a separate new migration. The invariant applies equally to standalone runs, direct/nested team members, and delegated/task-created agent runs. Existing installations must consolidate safely without losing lifetime run/team totals.

The current representation is not merely inefficient. It models cumulative run state as immutable wide events, repeats raw and pricing JSON, requires readers to reconstruct totals by summing rows, and lets a nonessential display-metadata migration materialize the entire table through Prisma/NAPI.

## Investigation Findings

- Current schema: `TokenUsageLedgerEvent` has 83 columns, unique per-event/idempotency keys, no uniqueness on `run_id`, and wide raw/pricing JSON fields.
- Current writer: `TokenUsageEventPersistenceProcessor -> TokenUsageLedgerStore.appendTokenUsageEvent -> SqlTokenUsageLedgerRepository.appendUsageEvent` schedules one insert for every enriched update.
- Current accounting is mixed-shape:
  - native AutoByteus: `per_call` deltas;
  - Claude SDK: `per_turn` deltas;
  - Codex: `cumulative_snapshot`, normalized against the preceding snapshot into an accounting delta before append.
- Therefore, “upsert the latest incoming payload” would be incorrect. The target row must accumulate normalized deltas and keep compact per-series reconciliation state for cumulative sources.
- Representative local production evidence on 2026-08-19:
  - database file: ~806 MiB;
  - ledger: 154,096–154,108 rows while the running app continued writing, 1,269 distinct runs, average 121.43 rows/run, maximum 4,499;
  - 148,391+ Codex cumulative rows;
  - table plus indexes: ~774.5 MiB (table alone ~690.1 MiB);
  - raw-event, raw-usage, and pricing JSON payloads alone total ~475 MiB;
  - the current `SELECT *` shape contains ~635.8 MiB of text across the ledger and ~620.8 MiB among null-name candidates;
  - all 149k null-name candidates in this sample are non-AutoByteus, so a correctly filtered provider-name query would read zero rows;
  - 228 runs cross UTC-day boundaries, proving strict one-row storage cannot preserve the existing “usage deltas observed during arbitrary period” result by itself;
  - two observed runs contain more than one cumulative snapshot series, so the target must reconcile per source series even though the authoritative subject remains one run row;
  - all 1,269 observed runs use one runtime/model identity, but 48 runs contain more than one pricing tuple and aggregate price/status semantics must not be replaced with the latest event's price.
- Release tags `v1.4.49` and `v1.4.52` both contain the full-wide provider-name migration and startup-fatal dependent provider gate. Current `origin/personal` still performs full-table `SELECT *` pre/post snapshots and retains the fatal prerequisite coupling.
- Current `origin/personal` also makes the earlier custom-provider model-value backfill transition-critical: it reads all ledger rows before and after, builds whole-ledger invariant arrays, and stores a skip detail for every non-target row. A supported direct/skip-version upgrade can therefore fail before reaching a bounded consolidation unless this unchanged-ID sibling is repaired too.
- Canonical run identity is already global and opaque: standalone and team topology creation use `AgentRunIdentityAllocator`; team and delegated executions carry exact agent run IDs plus separate root/task/address metadata.
- Production-shaped Electron verification reached healthy degraded startup but `20260819_token_usage_run_records_v1` failed three times before scanning/importing. Exact backup reproduction proved the first ordered run had leading `NULL` JSON-expression rows followed by valid integers that Prisma returned as strings. SQLite integrity was healthy and every non-null cumulative-source value was a nonnegative in-range integer; this is an adapter-representation boundary defect, not corrupt or unsafe production data.
- The corrected Electron package subsequently consolidated 158,025 legacy rows into 1,283 unique run rows and served current statistics successfully. The same read-only verification found terminal old source-shaping summaries of 13,964,274 and 14,318,058 bytes and a 31,387,995-byte migration-status response. The user explicitly classifies migration-summary/log storage redesign as a separate future ticket; this ticket neither reads differently nor mutates those historical audit bodies or log files.

Detailed evidence and the period-semantics decision table are in [`token-usage-data-model-analysis.md`](./token-usage-data-model-analysis.md).

## Design Health Assessment (Mandatory)

- Change posture: `Larger Requirement` combining `Bug Fix`, `Performance`, `Behavior Change`, `Refactor`, and persisted-data contraction.
- Initial design issue signal: `Yes`.
- Root cause classification: primary `Boundary Or Ownership Issue` plus `Missing Invariant` and `Shared Structure Looseness`.
- Refactor posture: `Likely Needed` / required in this change.
- Evidence basis: the persistence boundary owns events rather than the cumulative agent-run accounting subject; the 83-column event shape mixes current state, reconciliation state, audit/debug payloads, price inputs, derived costs, display snapshots, and topology metadata. Every reader compensates by rebuilding summaries from arrays. The migration independently bypasses bounded repository behavior with full-wide raw queries.
- Requirement or scope impact: replace the persisted subject and repository APIs, move cumulative folding into the authoritative token-usage boundary, update run/team/statistics readers, add an isolated released-data transition, and decommission append-only paths and full-ledger migration queries.

## Recommendations

1. Repair both released 20260730 token-ledger source-shaping migrations under their existing IDs before introducing or running the new ledger-consolidation migration. This lets a database already marked `FAILED` retry corrected code immediately after upgrading and prevents a still-`NOT_RUN` sibling from blocking a direct/skip-version upgrade.
2. Make the current persisted subject a `TokenUsageRunRecord` (exact final name belongs in design) with a database-enforced unique `run_id`.
3. Treat incoming event DTOs as transient observations. Fold normalized deltas into cumulative numeric/cost fields and keep only compact reconciliation/display/status state necessary for future updates and queries.
4. Do not create a replacement durable per-event audit table in this ticket. Event history is not required by the user's requested model; raw runtime traces remain a separate concern.
5. Approve run-created-period/lifetime-total semantics for Settings statistics. Preserving exact “usage during arbitrary period” requires additional time-bucket/history rows and conflicts with a strict one-row-only token-usage store.
6. Decouple provider-name display backfill from the startup-fatal provider-identity prerequisite. Do not weaken independent secret/provider identity safety.

## Required Upgrade Sequence

1. The newest application version ships corrected implementations for the existing migration IDs `20260730_token_usage_custom_provider_model_value_backfill` and `20260730_token_usage_provider_name_snapshot_backfill`.
2. On a direct/skip-version or previously blocked installation, the migration runner executes or retries those corrected definitions in their existing registry order against the still-present legacy ledger.
3. Both released backfills operate through narrow SQL eligibility, bounded keyset batches, compare-and-set updates, scalar validation, and capped details; neither materializes a full-ledger result.
4. A separate newly identified consolidation migration, with successful-or-warning completion of both repaired source-shaping backfills as prerequisites, then aggregates legacy rows into the one-row-per-run current store and validates them before legacy-table removal.
5. If a source-shaping backfill or consolidation returns a capability-scoped failure after the current schema exists, the legacy source remains intact, the application and new work may start, historical token reads are unavailable when consolidation is incomplete, and status evidence remains bounded. Restoration of pre-existing canonical runs is rejected before provider startup only while consolidation is incomplete. Newly allocated runs write only the current table; normal runtime never reads or writes legacy rows.
6. On consolidation retry, migration code validates that current target `run_id` values are disjoint from legacy `run_id` values, imports the entire legacy aggregate once, validates, and deletes the source in the same transaction. Any overlap or missing required current schema fails before cleanup. If Prisma/current platform schema deployment itself fails, global startup failure is acceptable and a corrected externally installed release retries without a legacy runtime fallback.

## Scope Classification (`Large`)

The change crosses live event ingestion, persisted identity/invariants, cost and component aggregation, GraphQL statistics semantics, released-data transition, migration diagnostics, and application startup availability.

## In-Scope Use Cases

- Fold native AutoByteus per-call token deltas into one standalone/member/delegated agent-run row.
- Fold Claude terminal per-turn token deltas into that same run-owned model.
- Reconcile frequent Codex cumulative snapshots, including restart/resume and more than one snapshot series, without adding a row per notification.
- Read standalone and team-member lifetime summaries directly from cumulative run rows.
- Derive root-team totals by summing concrete member/delegated agent-run rows.
- Show task/team and model statistics under the approved date-range semantics.
- Transition existing event-ledger data into one cumulative row per distinct canonical run with bounded work, forward-only degraded capability gating, ordinary relaunch safety, validation, and legacy-table decommission.
- Correct and isolate `20260730_token_usage_provider_name_snapshot_backfill`.
- Correct the transition-critical sibling `20260730_token_usage_custom_provider_model_value_backfill` under its unchanged ID so it cannot block a large direct/skip-version upgrade before consolidation.

## Out of Scope

- A new durable detailed token event-history/audit table.
- Preserving raw event, raw usage, or raw pricing snapshot JSON in the authoritative run-total table.
- Exact arbitrary-time “usage deltas during period” reporting if the recommended strict-one-row period semantics are approved.
- Changing provider token-source normalization (for example, choosing Claude `modelUsage` over `usage`) beyond what is necessary to fold already-normalized accounting facts.
- Rebuilding TeamRun execution topology inside token usage; TeamRun remains the topology authority.
- Automatically running a full-database `VACUUM` on the critical startup path. Freed pages must be reusable; optional physical-file compaction is a separate maintenance concern.
- Physically dropping the legacy table/model/index contract in the same release. Because Prisma schema migrations run before app-data migrations, the safe current-ticket contract phase is to empty and decommission the legacy table after validated consolidation while retaining its dormant migration-only schema declaration. Physical contract removal requires a separately sequenced future mechanism that cannot destroy data for skip-version upgrades.
- Weakening independent secret-vault or custom-provider identity safety gates.
- Manual editing of production migration records or token rows.
- Any migration-framework redesign of `summary_json`, summary read projection, structured summary/detail API, count columns, or per-migration diagnostic-log ownership.
- Any compaction, rewriting, relocation, deletion, or interpretation of existing migration-record summaries, `log_path` values, or historical migration-log files. The observed 31,387,995-byte status response is an informed accepted residual for this ticket and belongs to a separately bootstrapped future ticket.

## Functional Requirements

- **REQ-001 — One authoritative row per run.** The current token-usage persistence store shall contain exactly one authoritative cumulative record for each canonical agent run ID, enforced by a database uniqueness constraint on `run_id` (or an exactly equivalent canonical agent-run identity column).
- **REQ-002 — Uniform run-kind invariant.** `REQ-001` shall apply without identity special cases to standalone, direct team-member, nested team-member, delegated task-agent, and task-team member agent runs. Root team and task metadata remain attributes; they do not replace the concrete agent run key.
- **REQ-003 — Correct update-shape folding.** The persistence owner shall add normalized `per_call`/`per_turn` accounting deltas and shall reconcile `cumulative_snapshot` sources against compact per-run/per-series checkpoints before adding only the non-regressing advancement.
- **REQ-004 — Atomic rapid-update safety.** Concurrent or rapidly scheduled updates for one run shall not lose increments, create duplicate run rows, or let an older cumulative snapshot regress stored lifetime totals. The update and reconciliation checkpoint shall commit atomically.
- **REQ-005 — Bounded deduplication state.** Supported replay of the same cumulative snapshot or immediately repeated update within the current store shall not double count. Cross-schema replay shall be prevented by `REQ-023` gating pre-existing-run restoration before its provider starts while consolidation is incomplete; current runtime shall not inspect legacy facts. Reconciliation bookkeeping shall have enforced entry-count and serialized-size limits: at most eight cumulative-series checkpoints and at most 64 fixed-length idempotency-key digests per run. Series and event identifiers shall be stored as fixed-length digests, not provider-sized raw keys. When a ninth distinct cumulative series is admitted, the least-recently admitted checkpoint shall be evicted deterministically, the incoming series shall establish a baseline without charging its first cumulative snapshot, and a bounded quality flag shall disclose possible undercount; subsequent advancements for the retained series remain independently correct. The encoded checkpoint and idempotency state shall also have hard byte caps and shall never reintroduce one durable wide row per notification.
- **REQ-006 — Cumulative facts retained.** The run row shall retain cumulative token components, cumulative estimated component/total costs, aggregate pricing/currency/status semantics, usage-report count, latest prompt/context values, first/latest observation timestamps, runtime/model/provider display identity, run/team/task display attribution, and quality/missing-dimension state required by supported APIs.
- **REQ-007 — No repeated raw audit payloads.** The authoritative run row shall not retain per-notification `raw_event_json`, `raw_usage_json`, or `pricing_snapshot_json`. Only compact source checkpoint or summary state demonstrably required for correct folding/querying may be persisted.
- **REQ-008 — Direct run summary.** `getAgentRunTokenUsageSummary(runId)` shall return the same lifetime token/cost meaning from the single cumulative run row without loading or reconstructing an event list.
- **REQ-009 — Team/member aggregation.** Member summary shall select the exact root/run record. Root-team summary shall sum each included concrete agent-run record once, including delegated/task-created runs, and shall not store a separate duplicative team-total row.
- **REQ-010 — Public summary stability.** Current GraphQL field names and live websocket token-update behavior shall remain stable unless explicitly changed here. Cache read/write, standard/gross input, output/reasoning, billable output, nullable/mixed cost, unit-price explanation, usage-report count, current prompt, and context-window meanings shall remain truthful.
- **REQ-011 — Statistics period semantics.** Settings > Token Statistics date controls shall select runs by `run_created_at`, falling back to `first_usage_observed_at` with the existing truthful fallback label. Task/team and runtime/model results shall show the selected runs' lifetime cumulative totals. The UI copy shall no longer claim “Usage during period.” No separate time-rollup/event-history table is in scope.
- **REQ-012 — Historical migration repaired in place.** The corrected provider-name implementation shall remain registered as `20260730_token_usage_provider_name_snapshot_backfill`, so existing `NOT_RUN`, stale `RUNNING`, or `FAILED` records retry the corrected code after application upgrade. It shall select only null/blank-name AutoByteus candidates and only the columns required to classify/update them. Non-AutoByteus null-name rows shall be excluded in SQL.
- **REQ-013 — Provider backfill batching.** The provider-name backfill shall use bounded keyset batches and compare-and-set updates. It shall never materialize the full ledger, full candidate set, or full before/after row snapshots in Node/Prisma.
- **REQ-014 — Bounded validation and diagnostics.** Migration invariants shall use scalar/database-enforced checks appropriate to the actual single-column update. Per-reason counts and example/failure details shall be capped; the corrected token migrations shall not create logs or result summaries that grow linearly with ledger row count. They shall not materialize the full ledger merely to produce validation or diagnostic evidence. General migration-record summary representation, current status-read projection, and historical log retention are outside this ticket.
- **REQ-015 — Provider backfill retry/isolation.** A normal migration failure or an attempt that ends before completion shall leave the migration idempotently retryable through the existing runner with truthful status/error evidence. All abrupt-termination labels share this one ordinary relaunch disposition; no cause-specific recovery machinery is required. A failed provider-name display backfill alone shall not terminate global application startup.
- **REQ-016 — Dependency decoupling.** The nonessential provider-name snapshot backfill shall not remain a hard prerequisite of the independently safety-critical readable custom-provider identity migration. Independent provider/secret safety failures may retain their current gate; statistics labels fall back truthfully when the backfill is pending.
- **REQ-017 — Separate legacy consolidation required.** A new migration with its own later ID shall transform existing `token_usage_ledger_events` data into the current one-row-per-run store. Successful or warning completion of both repaired 20260730 token source-shaping steps shall be its prerequisite so a failed historical retry leaves the legacy source intact for another retry. Direct use without transformation is insufficient because duplicate rows violate the target invariant and contain delta facts that cannot be replaced by selecting only the latest row.
- **REQ-018 — Aggregate-preserving transition.** For every migrated run, pre-transition lifetime accounting-token components and estimated component/total costs shall equal the post-transition cumulative facts, subject only to already-null/unknown semantics. The transition shall also preserve root/team/task attribution, display fields, report count, observation bounds, latest prompt/context values, and truthful mixed/unknown identity or pricing state.
- **REQ-019 — Bounded relaunch-safe transition.** Consolidation shall process bounded source/result sets inside one SQLite transaction and shall not add a bespoke per-row journal. If the transaction does not commit, standard SQLite rollback shall leave the source intact and permit the existing runner or a corrected later release to retry; no shutdown-, power-, kernel-, device-, or filesystem-specific branch is required. Current rows admitted after a capability-scoped failure shall belong only to newly allocated run IDs. A later retry shall validate zero `run_id` intersection with legacy rows before importing the complete legacy aggregate once; any intersection fails before source cleanup. Automatic startup scheduling and public recovery capability are distinct. `AppDataMigrationRunner` shall derive one nonpersisted recovery action from the definition, record status, and active/stale-running state: `MANUAL_RETRY`, `RESTART_TO_RETRY`, or `NONE`. `AppDataMigrationStatusSnapshot.canRetry` shall be derived only as `recoveryAction === MANUAL_RETRY`. Required `STARTUP_ONLY` definitions in `NOT_RUN`, `FAILED`, or stale `RUNNING` state publish `RESTART_TO_RETRY` and `canRetry=false`; active `RUNNING` and terminal success/warning states publish `NONE`. `runPending()` remains the next-startup executor, direct `runMigration()` remains restart-required, and a startup-only definition not scheduled by `runPending()` shall not falsely advertise restart recovery.
- **REQ-020 — Validation before decommission.** The legacy table shall be absent from all normal runtime readers and writers immediately in the target code. Only migration-owned code may query or decode it. After migration validation proves distinct-run coverage and aggregate preservation, the same transaction shall delete all supported legacy event rows so the table is empty and its pages are reusable. The dormant physical table/model declaration remains migration-only because normal Prisma schema migrations execute before app-data migration; physical contract removal is deferred. Failure shall leave recoverable source evidence and shall not present partial historical statistics as complete.
- **REQ-021 — Reusable space, nonblocking physical compaction.** After successful validation the legacy pages shall be reusable by SQLite. Any physical file shrink/VACUUM mechanism shall be explicit, disk-space-aware, retryable, and outside the global startup critical path.
- **REQ-022 — Sibling source-shaping migration repaired in place.** `20260730_token_usage_custom_provider_model_value_backfill` shall remain registered under that unchanged ID but replace both whole-ledger reads, whole-ledger invariant arrays, and linear skip details with SQL-filtered potential candidates, a minimal projection, bounded keyset batches, compare-and-set `model_value` updates, scalar row-count/update invariants, per-reason counters, and capped examples. An attempt that ends before completion and the later same-ID runner retry shall remain idempotent; all non-`model_value` fields remain protected by the update statement rather than copied into Node snapshots.
- **REQ-023 — Forward-only degraded transition gate.** When consolidation is not successful, stored historical token reads and restoration/continuation of any pre-existing canonical agent run shall be unavailable before provider startup. The application, settings, unrelated capabilities, and newly allocated runs remain available when the current schema is valid; new runs write only `token_usage_run_records`. Settings shall consume the server-owned recovery action and present a failed startup-only consolidation as restart-retryable with localized visible guidance, without enabling or dispatching the generic manual Retry action. It shall not infer this state from migration ID, `requiredOnStartup`, execution policy, or local status combinations. Admission is based on migration readiness and the supported restore/new-run lifecycle, not on runtime queries against legacy rows. The migration retry shall validate zero legacy/current `run_id` intersection before import. No runtime legacy reader, legacy writer, checkpoint seed, overlap marker, dual read/write, or compatibility fallback is permitted.
- **REQ-024 — Deterministic, proportionate migration boundary.** All ticket migrations and migration-adjacent fallbacks shall comply with [`data-migration-conventions.md`](./data-migration-conventions.md): treat known supported released source shapes to one fixed current target as a deterministic transformation; assume one writer, a stable normal attempt, sufficient permissions, and normal SQLite/filesystem behavior; use the existing runner and real transaction semantics; and add recovery/lifecycle machinery only for an independently supported reachable product path. Quit, kill, shutdown, and power-off are one incomplete-attempt category, not separate product requirements. Hostile tampering, theft, arbitrary corruption, kernel/device/syscall failure, compromised processes, and adversarial writers shall not drive in-scope code or tests absent a separately approved contract. `REQ-023` is the smallest current-only capability gate that makes cross-schema replay Not Reachable.
- **REQ-025 — Classified failure and corrected-release recovery.** Every migration outcome shall record truthful bounded evidence and be classified against the schema, current-format data, and integrity/safety invariants actually required by the forward-only current application. When the current platform/schema is valid and only token history or provider display is unavailable, bootstrap/health, settings, unrelated capabilities, and new runs shall remain available while affected reads/restores are gated. Any exposed recovery action shall be executable through the entrypoint it advertises: the runner publishes `MANUAL_RETRY` only when the generic command can execute, `RESTART_TO_RETRY` only when ordinary startup is a supported executor, and `NONE` otherwise. Settings renders localized restart guidance only for `RESTART_TO_RETRY`. When required current tables/columns/constraints, required current file attributes, or another core current invariant are unavailable, global startup failure is acceptable and no legacy runtime fallback shall be added. `SUCCEEDED_WITH_WARNINGS` is permitted only when the required current target is independently validated and any remaining old column/table, obsolete structured-file attribute, superseded file, stale legacy value, or other cleanup residue is bounded, unreachable from current code, and not prohibited by an independent security/privacy/retention/storage contract. It shall not hide an incomplete required target, an observable source/target ambiguity, or cleanup failure that rolled back the target transaction. ## Constraints / Dependencies

- SQLite is the production store; local evidence has `auto_vacuum=NONE`, so deleting/dropping rows does not automatically shrink the physical file even though pages become reusable.
- Prisma/NAPI and V8/Node string-result limits prohibit unbounded wide result materialization.
- Current event enrichment is serialized per run, but persistence is scheduled asynchronously; target persistence must supply its own atomicity/ordering guarantee.
- The target must handle delta and cumulative source shapes; “replace row with latest payload” is not correct for native/Claude deltas or for legacy aggregate preservation.
- TeamRun execution tree remains authoritative for topology; token usage stores only root/run/task/display attribution needed by statistics.
- The app-data migration registry/runner already records statuses/retries and is the required relaunch mechanism; this ticket shall not add a durable per-batch recovery journal. Capability-scoped degradation is enforced by current readiness/restore admission, not by legacy reads. Existing-run restoration reuses canonical run/provider identity and is therefore unavailable until consolidation succeeds.
- Canonical IDs allocated for genuinely new runs are globally unique. Consolidation migration code must validate that current run IDs admitted during degradation do not intersect legacy run IDs; current runtime must not inspect legacy identity/event indexes.
- Prisma schema deployment precedes app-data migration. Absence of the required current table/columns is a platform-critical failure and shall not activate an old-schema runtime path.
- SQLite computed expressions have dynamic storage classes and Prisma raw-query decoding can vary with nullable result-set shape. All migration-derived scalars therefore need an explicit transport representation validated through the actual production ORM/driver boundary; TypeScript result annotations do not establish runtime representation.
