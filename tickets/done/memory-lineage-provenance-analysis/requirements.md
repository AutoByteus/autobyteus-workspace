## Goal / Problem Statement

Define and then implement a unified, evidence-grounded memory contract in which:

- existing runtime raw traces remain immutable original activity evidence; explicitly typed operational records remain distinguishable and are not projected as user activity;
- work evidence is the earliest memory-ready view, resolved from referenced authoritative raw records rather than persisted as copied content;
- every successful compaction retains explicit direct lineage to the preceding successful compaction whose output influenced it and to newly selected original work;
- WorkingContext and its persisted snapshot represent what the LLM currently sees/remembers;
- recurrent compaction consumes the current compaction output plus newly selected settled activity and produces one quality-first complete replacement output whose episode and fact counts are chosen naturally by the LLM;
- the compactable logical WorkingContext prefix—including the existing compacted-memory user region when present—is supplied to the compactor as one naturally ordered conversation history that omits private reasoning;
- native compaction and generated Work Evidence reuse one core-owned, deterministic readable-tool/text presentation policy for redaction, serialization, and explicit head/tail omission while retaining separate sources, envelopes, and consumer bounds;
- Event Monitor projection remains an active-raw-activity view rather than a memory/context view; and
- cross-runtime source identity and higher-memory provenance remain truthful.

The detailed intended behavior is normative in `memory-context-and-lineage-contract.md`, `use-case-data-flow-spine-map.md` makes every use case traceable through its complete production or approved target-production path, and `memory-compactor-prompt-content-contract.md` is the exact wording authority for the two LLM-facing prompts. This stage establishes the requirements basis; implementation design begins after approval of those normative artifacts and this document.

This is a bounded change to native AutoByteus structured memory compaction, compactor conversation-history rendering, shared readable-tool/text presentation used by generated Work Evidence, lineage lookup, canonical `WorkingContext` finalization, snapshot persistence/restore, one native-only startup snapshot migration, and the exact request-recovery capture point around a durable compaction. It is not a general memory-evolution or external-runtime compaction project.

### Explicitly unchanged

- Existing runtime user/assistant/tool records remain immutable original activities; their IDs/content are not rewritten into summaries. The migration does not append, rewrite, or delete raw-trace records.
- Successful compaction may move newly selected non-compacted-memory original raw evidence from active storage to archive exactly as today. Prior-memory ancestry is never re-archived as though newly selected.
- Event Monitor continues to read and page active raw traces only.
- Readable server work-trace Markdown remains a separate generated presentation artifact and is not read as the native compactor input. Its source enumeration, timestamps, Markdown/file/manifest contract, reasoning omission, and generated-artifact ownership remain; only visible-value serialization/redaction and oversized-field presentation move to the shared core policy, replacing silent prefix-only loss with explicit head/tail omission.
- Storage-only external runtimes continue recording normalized raw activity and provider/session boundaries; this ticket does not add AutoByteus episodic/semantic compaction to them.
- There is no separate tool-result condenser: settled tool-call/result groups continue to be rendered directly into normal compaction input, while live/incomplete groups remain protected. Each selected group appears as one `Tool` block with `name`, `status`, `arguments`, and `result` or `error`; rendering changes from whole-item prefix-only clamping to explicit bounded variable-field head/tail omission.
- A one-time registered startup migration preserves and converts only exact metadata-classified native AutoByteus WorkingContext snapshots, removes obsolete pre-lineage episodic/semantic rows and the compacted-memory manifest after valid v5 publication, and leaves external/imported/unclassified/unsupported locations untouched. Historical decoding exists only inside that migration. Normal runtime recognizes strict v5 snapshots/current lineage only.
- Current runner/parser failure and retry behavior remains: no candidate output or lineage record is published, the lineage head remains unchanged, and the same pending `compactionId` is retried on the next normal request.

## Recommendations

- Adopt the complete foundation contract without introducing a raw-memory persisted alias.
- Use a recurrent compaction lineage chain with direct `previousCompactionId`/raw-trace-archive-file inputs, cycle-safe traversal, and rebuildable transitive closures.
- Use one reference-only `CompactionLineageRecord` per success: existing `compactionId` + optional `previousCompactionId` + run-relative native-compaction archive `file_name` + produced episode/semantic IDs.
- Let the model choose the natural number of episodes and facts needed for reliable continuation; keep unrelated phases distinct and remove chatter/repetition/obsolete state without prescribing item counts or a ticket-specific token ceiling.
- Record already-known input/output IDs automatically; retain prompt/selection policy versions and optional integrity hashes, but do not duplicate rendered task or evidence content and do not ask the LLM for citations or storage IDs.
- Preserve the implemented run-scoped resolver and extend coverage so natural-count and mixed prompt-version membership reports direct inputs and recursive roots truthfully.
- Make the output listed by the lineage head a required recurrent compactor seed, append only a successful new record whose `previousCompactionId` matches that head, and finalize its natural memory/current-user composition inside WorkingContext before snapshot/render.
- Keep Event Monitor active-raw only and keep work-evidence/archive access separate.
- Replace the destructive reset with a new-ID native-only snapshot migration: reuse exact current metadata classification; touch only `RuntimeKind.AUTOBYTEUS`; preserve/convert snapshots first; validate strict v5; then delete only obsolete episode/semantic/manifest state. Preserve valid current lineage-aware runs directly and leave external/imported/unclassified/unsupported locations untouched.
- Keep migration proportional: use the completed corpus audit as feasibility evidence, project and validate one eligible run at a time, keep only convertible truthfully sourceable units, report omission reason/count metadata, and allow `messages: []` when nothing survives. Do not add global planning, inventory fingerprints, a second conversion pass, generated recovery text, synthetic tool outcomes, or migration-authored raw evidence.
- Remove raw-trace-based WorkingContext reconstruction. During migration, exact eligible active raw records are loaded only as bounded reference facts for validating already-stored source references; they are never searched to repair Tool protocol or reconstruct missing content. Normal restore never fabricates recent context from raw traces.
- Preserve pre-write compactor failure/retry, and move LLM request-recovery capture to the stable post-compaction/pre-request boundary so a provider failure cannot restore context behind a durable lineage head.
- Render the planner-selected recurrent WorkingContext prefix as one natural `<conversation_history>` block: projected M(n-1) in its model-visible user-role position followed by selected R(n), with reasoning/backend metadata omitted and each settled call/result represented as a straightforward `Tool` block containing `name`, `status`, `arguments`, and `result` or `error`.
- Reuse the implemented shared readable presentation core unchanged. Keep WorkingContext planning/XML prompt construction and raw historical replay/timestamped Markdown generation in their current authoritative subsystems.

## Functional Requirements

- `REQ-001`: The solution package must maintain an evidence-backed current production map for raw activity, active/archive storage, Event Monitor projection, WorkingContext/snapshot, native compaction, episodic/semantic memory, and external-runtime recording.
- `REQ-002`: The implementation contract must preserve the terminology and authority boundaries in the foundation contract: ordinary raw traces are original runtime activity/content and typed operational records are explicitly distinguishable; work evidence is a reference-resolved memory-ready view rather than another content store; WorkingContext/snapshot is current model context; Event Monitor is active activity; durable memory is derived.
- `REQ-003`: The lineage contract must model one immutable derivation record per successful compaction, keyed only by the existing `compactionId`, with explicit reference-only inputs/outputs and stable run/member scope independent of absolute paths or timestamps. The record must not add parallel activity or generation identities for the same one-to-one successful operation/output bundle.
- `REQ-004`: Every successful native structured compaction must archive exactly its selected raw records in one immutable native-compaction raw-trace archive file and publish exactly one immutable `CompactionLineageRecord` containing the existing successful `compactionId`, optional `previousCompactionId`, the archive manifest entry's existing run-relative `file_name`, produced episode/semantic IDs, derivation/execution metadata, schema/prompt/selection-policy versions, and optional integrity hashes. The strategy returns an IDless content/selection/execution proposal. `MemoryManager` acceptance reuses the pending `compactionId`, verifies that the captured baseline lineage head is unchanged, assigns output IDs, builds and validates the accepted candidate, and its internal committer performs the normal sequence: complete exact raw archive -> persist output rows -> append lineage as the new head -> install finalized context -> persist v5 snapshot -> clear pending. The lineage store must accept only a unique next record whose `previousCompactionId` equals the existing head, or `null` when the file is absent/empty. The record must not repeat raw IDs/content, copy prior-memory content, copy rendered compactor-prompt content, flatten ancestral refs, add a separate activity/generation ID, fabricate a segment ID, or expose the internal archive boundary key. The resolver obtains selected raw membership and direct source interval from the referenced completed file/manifest entry. An absolute filesystem path is forbidden. `execution.promptContractVersion` is producing-contract audit metadata: existing SR-004 records with value `1` remain immutable and directly readable; new compactions using the approved natural system prompt/history-only payload write value `2`. The current schema reader accepts and preserves both values in mixed chains without decoding content differently or rewriting records; unknown values remain unsupported.
- `REQ-005`: The structured compactor must receive one naturally ordered conversation-history rendering of the compactable logical WorkingContext prefix—projected prior memory when present followed by selected new natural history—and return a self-contained complete replacement output bundle, not a delta. The LLM chooses the natural number of episodes and facts. The output uses the smallest sufficient episode structure to preserve distinct task phases, important outcomes, and current state; it does not combine unrelated work merely to reduce count or create episodes for chatter/repetition. It preserves continuation-critical facts, prioritizing constraints, decisions and rationale, unresolved work, user preferences, and important artifacts, while retaining the existing JSON categories and per-entry safeguards. The ticket adds neither an item-count target nor a numeric output-token ceiling. The proposal carries content, selected new raw IDs, retained continuation, and execution metadata but no compaction/output IDs or persistence objects. `MemoryManager` retains the application-owned baseline lineage head outside the LLM strategy, reuses the pending `compactionId`, assigns episode/semantic IDs during acceptance, and appends their reference-only lineage only after the output rows exist. The appended tail is the sole current-compaction authority. The LLM emits no evidence citations, compaction IDs, or storage identifiers.
- `REQ-006`: A cycle-safe run-scoped resolver must accept a typed `MemoryArtifactRef` containing `kind: "episode" | "semantic"` plus `id`, locate its producing `CompactionLineageRecord` in the matching output list, validate and read the directly referenced raw-trace archive `file_name` through the archive manifest, and return its selected raw records/interval plus optional direct `previousCompactionId`, derivation time, and recursively deduplicated original raw roots/root interval. Unknown artifacts return `not_found`; a missing or inconsistent record/file in a referenced current-format chain is an integrity error. The implementation must not guess the artifact kind, guess sources, or claim transitive roots were direct inputs.
- `REQ-007`: Repeated compaction must implement `M(n) = compact(M(n-1) + R(n))`: consume the output listed by the last successful lineage record as a direct seed, set that head ID as the new record's `previousCompactionId`, require a non-empty newly selected non-compacted-memory prefix R(n) backed by archive-eligible active raw evidence, archive only that eligible original settled activity, generate one complete bounded successor, and keep older compaction outputs immutable/inactive. Migration creates no substitute/baseline raw unit, so later R(n) may select only retained non-system input already backed by real eligible active evidence. Appending the successful new record makes it the sole new lineage head; no separate activation pointer exists. M(n-1) alone never makes a new compaction eligible and is never re-archived. Canonical provider-neutral `WorkingContext` finalization before snapshot/render must preserve typed memory/retained/current sections, system/media, and complete tool protocol. Renderers must not own semantic repair.
- `REQ-008`: Raw activity and current model context must remain separate. Event Monitor reads active raw only; newly selected original records archive unchanged; a strict current-schema snapshot is the sole normal resume source. New startup migration `20260731_migrate_native_working_context_snapshots_v5` runs after delivered external cleanup and transforms only exact metadata-classified native AutoByteus standalone/team-member targets with absent/empty lineage; every nonempty-lineage location is skipped untouched. All external, imported, unsupported, missing/invalid-metadata, unclassified, and conflicting locations remain untouched. The classifier supplies the exact expected strict-v5 snapshot identity: standalone `runId` or team `memberRunId`. The server migration loads source bytes plus bounded same-subject eligible-active raw reference facts; one pure migration converter owns historical decoding, parseable-source `agent_id` equality, and message role/content/media/tool/ref matching. A parseable source with missing/blank/mismatched `agent_id` is rejected with no mutation; parse-invalid input has no contrary source identity and serializes the empty current candidate with the metadata-derived expected identity. For an eligible source, preserve valid current-representable system messages; preserve each valid non-system logical unit or complete Tool group only when its content/media/tool structure is valid and every required stored reference matches an eligible active fact; ignore unknown optional fields; omit invalid, incomplete, ambiguous, old-compacted-memory, or unsourced non-system units without repair.
