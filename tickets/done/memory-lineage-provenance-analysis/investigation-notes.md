**Decision:** Preserve/decode only exact current-metadata native AutoByteus snapshots with absent/empty lineage inside the startup migration, convert them to strict v5, then delete their obsolete episode/semantic/manifest state. Skip every nonempty-lineage location byte-for-byte and leave external/imported/unclassified/unsupported locations untouched. Use the existing nonblocking runner lifecycle without adding physical-failure semantics. Remove raw-history restore entirely. Separately, preserve durable compaction across provider failure by capturing request recovery after compaction.

## Findings From Code / Docs / Data / Logs

Complete synthesis is in `provenance-methodology-analysis.md`.

Key conclusions:

1. Direct artifact/activity lineage must be persisted during compaction, not reconstructed later.
2. Raw leaf IDs already exist, but current episode/semantic models lose them.
3. The implemented SR-004 planner includes the compacted-memory message-local constituent in the natural compactable prefix while collecting archive membership only from newly selected raw-backed natural units. `MemoryManager` separately captures the current lineage tail outside the strategy and maps that unchanged baseline to `previousCompactionId`; absent/empty lineage means no current memory and a null predecessor.
4. The target recurrence is `M(n) = compact(M(n-1) + R(n))`; output is one complete bounded successor, not a delta.
5. Only the newest successful compaction output bundle is current; older outputs remain immutable/inactive history.
6. One `CompactionLineageRecord` stores only the existing successful `compactionId`, optional `previousCompactionId`, one completed raw-trace archive file's existing run-relative `file_name`, and produced episode/semantic IDs—not a parallel activity/generation ID, raw membership/content, fabricated segment ID, internal boundary key, rendered prompt, or copied transitive closure. Success requires non-empty newly selected raw-backed R(n); M(n-1) alone is not eligible and is never re-archived.
7. Recursive origin accepts run/member scope plus explicit artifact kind and ID, distinguishes direct inputs from ultimate raw roots, uses cycle protection/deduplication, and may use rebuildable indexes without changing authority.
8. Unknown typed artifact IDs return `not_found`; a missing/inconsistent relation inside a referenced current-format chain is an integrity error. No resolver reads discarded row files.
9. The directly referenced raw-trace archive file's source interval, recursive root interval, derivation time, and lineage append/derivation ordering are distinct.
10. Every episode and accepted semantic fact in the model-decided complete replacement shares one direct recurrent-input pointer; detailed localization/fine citations remain outside scope. No application layer may discard a valid item solely because it is fourth or twenty-first.
11. The strategy returns an IDless proposal containing selected new raw IDs, retained messages, normalized content, and execution metadata; it carries no prior compaction or output identity. `MemoryManager` reuses the pending `compactionId`, validates the separately captured baseline lineage tail, assigns episode/semantic IDs, constructs/validates the accepted candidate, and maps the baseline head to `previousCompactionId`.
12. Current compacted-memory/current-user adjacency is not a safe provider-neutral assumption; WorkingContext finalization owns natural composition and typed constituent provenance.
13. Raw IDs/content remain immutable across archive movement, and prior-memory ancestry is never re-archived as new raw activity.
14. Derived compaction outputs do not belong in raw traces; Event Monitor remains active-activity only.
15. Runner/parser failure leaves the lineage tail and baseline installed/snapshotted WorkingContext unchanged while retaining the pending `compactionId`; no staged publication journal is introduced.
16. Valid schema-v5 snapshot remains normal resume authority for finalized messages, media/tool structures, and message-local constituent ranges only. It contains no compaction/output/current-state identity. Separately, absent/empty lineage means no current compacted memory; otherwise its last valid record lists the exact current output IDs. One required new-ID startup app-data migration preserves/converts pre-lineage snapshots to strict v5 before deleting only episodic/semantic JSONL and the compacted-memory manifest. Normal runtime contains no historical decoder or raw-history reconstruction fallback.
17. After one thousand compactions, WorkingContext contains only M1000 rather than an accumulation of M1..M1000; the LLM chooses M1000's natural item count, while durable older outputs/provenance may grow separately.
18. Delivered SR-010 preserves the SR-004 reasoning-free XML-bounded User/Assistant/Tool history and now reuses the existing finalizer before labels, so internal constituent ranges do not split one canonical user turn. There is no remaining prompt/rendering implementation defect in SR-012.
19. SR-004 already implemented the tight shared core Tool/value renderer and explicit head/tail omission for both compaction and generated Work Evidence while preserving separate source/envelope ownership. SR-010 leaves that boundary unchanged.
20. Normal accepted publication has one order: archive R(n), persist output rows, append the validated successful lineage record as the new current head, install finalized context, persist message-only v5, then clear pending state. Strategy/LLM cannot assign produced IDs or publish any of those artifacts.
21. `compaction_lineage.jsonl` is the only persisted compaction-history/current-state authority: successful records only, absent/empty means no current compaction, and the last valid record is current. Appending requires a unique `compactionId` and `previousCompactionId` equal to the prior tail. No `compaction_state.json`, snapshot-level output IDs, replacement manifest, or activation field is added.
22. The native snapshot migration, migration runner, and `startConfiguredServer` have separate responsibilities. The migration applies one structural gate: every nonempty-lineage location skips untouched; absent/empty-lineage content problems become `converted_with_omissions` and a validated v5 candidate. The runner and caller keep their existing nonblocking lifecycle. No migration-specific or historical behavior leaks into runtime restore.
23. Semantic sizing has four relevant owners: `agent.md` owns the concise origin/personal-style natural task and stable quality/schema policy; the operation user message owns only renderer-produced canonical history turns; parser/normalizer own structural/per-entry validation and cleanup without count caps; acceptance owns non-empty/application identity invariants. The LLM chooses the natural item count. Internal message constituent ranges remain available for planning but do not create artificial model-visible turns. Launch/provider output-token configuration is unchanged. This is a bounded local extension to DF-L02/DF-L08, not a new primary spine or persistence model.
24. Delivered SR-010 lineage normalization has no 3/20 maximum and retains non-empty episode, uniqueness, safe archive filename, scope, predecessor, timestamps, execution metadata, and integrity validation. This is regression-protected current behavior.
25. `promptContractVersion` audits the producing LLM contract, not the lineage JSON shape. Existing value `1` truthfully identifies historical SR-004 fixed-count/system-plus-duplicated-operation records. Current SR-010 writes value `2` for the natural system prompt, history-only operation payload, and canonical-turn contract. Mixed `1 -> 2` current-schema chains are direct-use and require no rewrite.
26. Message-local constituent metadata contains only local kind/range and raw-backed natural references. `MemoryManager` separately captures the lineage tail and maps it to `previousCompactionId`; neither rendering nor snapshot carries that ID.
27. The user-observed restore failure is reachable; generic snapshot disappearance is not. Normal creation persists snapshots, explicit restore consumes them, and no supported product action deletes one. Therefore the last-twelve/raw-history projector must be removed rather than expanded; explicit restore without a snapshot fails while new-run initialization remains separate.
28. A pre-lineage snapshot can preserve truthful context without fabricating historical compaction lineage or migration evidence. Valid system messages may be retained without raw provenance. A non-system logical unit or tool group is retained only when current structure is valid and every required source is truthfully backed by eligible active raw records; otherwise it is omitted. The migration never appends or rewrites raw records. The first later current-format compaction therefore consumes only genuinely sourceable retained input.
29. An LLM request-recovery checkpoint is an ephemeral context rollback point, not a compaction transaction. It must be captured after any successful pending compaction and before current-request mutation. Provider failure restores that compacted stable base; raw/archive/output/lineage/tool facts remain durable; success or supported interruption settles the checkpoint.
30. The completed 347-file read-only audit is sufficient feasibility evidence for the known corpus. The production migration builds/finalizes/strict-validates each eligible absent/empty-lineage candidate before replacing its snapshot. No runner lifecycle extension, global prepared plan, inventory fingerprint, second scanner, or delivery-only converter is justified.
31. Migration quality is simple, truthful, and availability-aware. Every eligible absent/empty-lineage file is convertible because the converter retains only valid current-representable units and omits unsupported, incomplete, ambiguous, old-compacted-memory, or unsourced non-system units. If parsing fails or no message survives, strict v5 with `messages: []` is the valid minimum. The converter generates no recovery notice, placeholder, synthetic tool result, or raw evidence. Omissions yield `SUCCEEDED_WITH_WARNINGS`; every nonempty-lineage location skips before conversion.

  - delivered lineage records with supported prompt-audit values `1 | 2`: `Directly Usable — No Migration`; current SR-010 writers use value `2`.
- Migration mechanics required by evidence: use a new durable ID because the old destructive ID is already recorded `SUCCEEDED`; decode historical snapshot shape only inside a focused migration converter; gate conversion on absent/empty lineage and skip every nonempty location untouched; retain valid current-representable system messages and complete non-system units/tool groups whose stored references resolve truthfully to eligible active raw records; ignore unknown optional fields; omit unsupported, incomplete, ambiguous, old-compacted-memory, or unsourced non-system units; use `messages: []` when parsing fails or nothing survives; finalize/serialize/strict-v5 validate; replace the snapshot; then delete only `episodic.jsonl`, `semantic.jsonl`, and `compacted_memory_manifest.json`; leave lineage absent/empty.
- Per-run validation mechanics: the migration reads one eligible absent/empty-lineage source, constructs its v5 candidate and bounded omission diagnostics in memory, finalizes and strict-validates the complete candidate, then replaces that run's snapshot. It never mutates raw traces. There is no aggregate prepared plan or runner interface extension.
- Why omission is proportionate: a later compaction must source every non-system input it actually consumes, but an old compacted summary or unsourced unit cannot truthfully point to unknown historical raw activity. Omitting that unit is simpler and more truthful than inventing evidence or retaining compatibility fields. Valid system messages and exact active-backed units remain usable; an empty-message v5 keeps the run structurally restorable when nothing can be retained.
- Startup/result contract: content-shape problems yield a valid v5 plus `SUCCEEDED_WITH_WARNINGS`; they do not leave the run unrestorable merely because exact preservation failed. Every nonempty-lineage or excluded location is `SKIPPED`. The existing runner/caller lifecycle remains unchanged; this ticket adds no physical-failure, compatibility, repair, backup, or rollback semantics.
- Product-reachability boundary: a discovered directory with no snapshot is skipped by migration, and explicit restore without a snapshot fails. No cleanup or reconstructed context is designed for that premise because no supported product lifecycle produces it. Raw traces are consulted only to validate stored source references during migration, never to reconstruct missing context, synthesize tool results, or serve normal WorkingContext restore.
- Test-environment constraint: API/E2E must bind memory and migration database/ledger to the same isolated app-data root. The product runtime receives no multi-root compatibility branch.
- Provenance backfill remains rejected: the migration creates no historical compaction record and does not claim old episodes/facts are current. The first later successful compaction has `previousCompactionId: null`; prospective recurrent edges are authoritative from then on.
- Storage/privacy/operational constraints: conversion scans the bounded exact native target set and its raw files, so process one run at a time and avoid whole-root loading. Raw evidence may contain sensitive content; normal authorization/redaction remains.

## Constraints / Dependencies / Compatibility Facts

- Raw trace file paths and `active` source labels are not stable logical identities.

- Raw trace `seq` is per turn, not a run-global order.
- Work trace summary hash covers visible/redacted rendered content and deliberately excludes separate reasoning; it is not a complete raw-corpus fingerprint or evidence-selection record.

Its reasoning omission and combined `tool:` body inform the contract, but native compaction renders planner-selected WorkingContext without raw timestamps or the file/manifest wrapper.
