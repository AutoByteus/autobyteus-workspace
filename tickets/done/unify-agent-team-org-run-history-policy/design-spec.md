## Current-state read and intended change

Team initializes a memory-directory-shared catalog from the admitted index without writing; Org initializes each instance by scanning all admitted trees and rewriting the index. The latter causes first-read mutation, repeated work with new instances, hidden pre-create ordering, and a store bypass in the unmerged Org memory source. Both families already share admission readiness. Existing lifecycle owners and index/tree stores are usable; the policy split is in catalog initialization/state/writes, not the persisted schema. Team archive also lacks the Org archive's compensation when its index update fails, and its pre-queue `hasManagedTeamRun` check is not protected by the manager's per-root transition lane. A concurrent restore can make that check stale (ARCH-REV-001/DR-001, PM-001). See the source log and architecture findings in `investigation-notes.md`.

**SR-005 current-branch Memory reality:** the existing Team Memory explorer already uses the catalog owner, but after reading each admitted root tree it asks its member-target builder to enumerate member locations through an unscoped all-root lookup. That rereads every stored root per root being summarized (N + N² reads); API-REV-001 measured 12 reads for three roots after readiness. The previous DS-004 wording described a one-read path while its file map deferred Memory integration to the unmerged branch. The Team correction is required now under unchanged AC-003; only the Org root-memory adapter remains merge-conditional. This is a design-route correction, not an expansion of the history index's authority or a data-format change.

**Target authority:** the per-family index is authoritative for **history-row membership and index-only facts** (summary and termination); execution trees remain authoritative for run packages/details and tree-owned archive facts at an explicit lifecycle mutation or repair. A tree without a row is not automatically a history row. Catalog queries are always index-backed, admitted, summary-normalized, and read-only. Lifecycle events make index changes. Exceptional tree-based repair is a separate offline/local maintenance command, never first-read or routine startup behavior.

## Supported user path anchoring DS-003 (ARCH-REV-001 / PM-001)

A user sees a stopped retained Team in workspace history and clicks **Archive**. The actual path is `useWorkspaceHistoryMutations.onArchiveTeam` → `runHistoryMutationActions.archiveTeamRunInHistoryStore` → `ArchiveStoredTeamRun` GraphQL → Team history resolver/service → `TeamRunHistoryCatalogService.setArchived`. Separately, a user can send a message from that stopped Team context; `agentTeamRunStore` issues `RestoreAgentTeamRun` GraphQL → `TeamRunService.restoreTeamRun` → `AgentTeamRunManager.restoreTeamRun` and then `recordTeamRunRestored`. These are independently supported actions on the same root, not manual corruption or a synthetic call. Their overlap is within approved SCN-002, BEH-002, REQ-002/004 and AC-002.

Current failure interleaving: Archive checks `hasManagedTeamRun=false` **outside** both queue and manager lane → Restore enters `withRootTransition`, registers the Team as managed → Archive later enters catalog queue and writes archived tree/index → success is reported for a now-managed run. Target interleaving: Archive enters catalog queue, then `manager.withInactiveHistoryMutation(rootId, callback)`; the manager checks `hasManagedTeamRun` **inside** `withRootTransition` and runs the complete archive/unarchive callback only if still unmanaged. If Restore registered first, Archive returns the existing managed-run refusal and neither tree nor index changes. If Archive entered the lane first, Restore waits until archive/unarchive fully commits or compensates, then follows its existing restore policy. This is the real-user outcome the lock order exists to protect.

## Supported user path and bounded read design for DS-004 (API-REV-001 / CRR-002)

A user selects an **imported** source in Memory and opens **Agent Teams**, then may open a Team's run list. `memory.vue` / `memoryExplorerStore.fetchTeams` or `fetchTeamRuns` issues the corresponding Memory GraphQL query. The resolver resolves that source to its imported root and makes a fresh `TeamMemoryExplorerService`; both query methods call `buildGroups()`. This real request path, not a standalone location-service benchmark, is the AC-003 boundary. For each admitted root, the explorer queries catalog metadata through `TeamRunHistoryCatalogService.listCatalogRows()` and reads its execution tree once. It must pass that **same validated snapshot** to member-target construction. The member-target builder obtains configured placements and physical memory paths from a pure tree-scoped projection in `TeamRunExecutionTreeLocationService` (reusing its `TeamExecutionIndex`, `listInTree`/`toLocation` logic) via `AgentMemoryLocationService`, then reads only memory files/stat metadata needed for the existing availability cards. It must not call the existing unscoped `listTeamMemberLocations({teamRunId})` from the per-root loop, because that method calls `listAgents()` across every root again.

Make the tree-scoped API explicit rather than an optional fast path: e.g. `listAgentsInTree(tree)` with no store/manager/readiness I/O, `listTeamMemberLocationsFromTree({teamRunId, tree})`, and `TeamMemoryMemberTargetBuilder.buildFromTree(teamRunId, tree)`. The latter is the only builder entry used by `buildGroups()`. The tree's root ID must match the requested root (or fail/skip through the existing safe-read/error policy), and `matchesTeam` must retain current root/containing/ancestor filtering so nested Team/task-agent member targets, configured placement, path layout, search, counts, sorting and memory availability stay unchanged. Existing general location APIs may remain for their independent callers; do not broaden this ticket into changing runtime location lookup semantics. A root whose tree cannot be read remains skipped as today; admission exclusion and catalog failure fallback remain as approved. No extra cache or persisted data is introduced.

The measured performance contract is at most one execution-tree store read per admitted root **per GraphQL request**, after explicit readiness work; a fresh service object does not reset that budget. Team list and Team-run list each need their own proof. Catalog metadata still comes from the read-only owner and must not mutate imported indexes. When the separate Org memory branch merges, its root source must use `AgentOrgRunHistoryCatalogService.listCatalogRows()` without increasing its one-tree-per-root traversal; that adapter does not exist in this current branch and receives no present validation credit.

## Terminology and authority

- **History row authority:** the admitted, current-format per-family index array for listing membership, summary and termination; it is maintained by lifecycle events.
- **Execution-tree authority:** current run package/detail and archive state at explicit lifecycle or maintenance steps; it does not trigger row creation during a query.
- **Repair:** explicit offline/local, dry-run-first operation adding missing rows from admitted trees. It does not silently reproject existing rows or overwrite corruption.
- **Admission:** the already-shared `RootRunPackageReadinessIndex`; it determines whether a row is eligible for exposure, not the row's content.

## Legacy removal and persisted-data decision

- Policy: **No backward compatibility; remove legacy code paths.** Remove old Org `listRows()` and `initialize()` runtime methods/calls rather than preserving aliases; update all callers/tests. Remove runtime tree-scan/rewrite initialization. Remove runtime use of `AgentOrgRunHistorySummaryWriter` (retain it for its historical migration import). Remove `TeamRunHistoryIndexService` and its unit test if final repository search still shows only self/test imports; do **not** remove migration `TeamRunHistoryIndexReconciler` with the similar name.
- Stored subjects: `memory/team_run_history_index.json`, `memory/agent_org_run_history_index.json` arrays plus package trees under `agent_teams/<id>` and `agent_orgs/<id>`. Representative isolated fixture has 1 Team and 4 Org current-shape rows, including termination facts; approximate real-user volume is unknown, so avoid routine full-tree scans and rewrites.
- Semantic/physical change: **none to row schema or file locations**. Only authority and when reading/writing occur change. Summary/termination remain index-only; existing row values must not be discarded by repair. Team catalog changes from tolerant to its existing strict reader for corruption, an approved behavior decision, not a format migration.
- Decision: **Directly Usable — No Migration.** Team `readIndexStrict()` and Org `readIndex()` already parse current arrays; both treat ENOENT as empty, and throw on malformed current data (Team strict path). Current version-agnostic readers retain the eight fields, with shared in-memory summary compaction. No old/new dual readers or startup rewrite. Existing one-time migrations are left intact as historical transformations and run only according to their own ledger.
- Repair is **not** a migration. It may add absent rows from current admitted trees. A wholly missing index lacks recoverable summary/termination; dry-run must diagnose this, apply must require explicit loss acknowledgement, and result must not claim lossless recovery. A corrupt index must stop with no overwrite and refer to backup/manual restoration. Valid existing rows are not reprojected or pruned merely because a tree differs.

### Primary spine notes

DS-001 and DS-004 are read-only at the history boundary; detail/root tree reads are separate downstream work for visible roots, not catalog reconciliation. For DS-004, admission readiness is excluded from the measurement; `buildGroups()` may load **one** validated snapshot per admitted Team root, but member lookup must project from that snapshot and never invoke an unscoped `listAgents()` that rereads roots. Both Team-list and Team-run-list requests traverse independently; each must meet the bound. DS-002's manager completes package admission before event recording, so Org create no longer preinitializes. DS-003 acquires the shared family queue **before** the manager per-root transition lane for Team and Org archive/delete. Team archive/unarchive must use a generalized inactive-history manager callback, not a pre-queue status check. This holds the inactive decision, tree/index writes and compensation in the same lane as restore; the family queue serializes row writes across roots. Create/restore release their manager lane before recording history, so they do not hold lane → wait queue and deadlock. DS-005 is deliberately an operator-triggered separate spine; no startup/list caller reaches it. DS-006 is a shared bounded state/queue mechanism inside the catalog owner, not a new top-level service.

## Shared core contract and lifecycle boundary

Create `CollaborationRunHistoryCatalogCore<Row>` in run-history services, with a state registry keyed by resolved memory directory **and explicit family** (`agent_team` / `agent_org`). The core receives narrow family adapters: `idOf(row)`, strict `readRows`, `writeRows`, `awaitReady`, `isAdmitted`. Family tree projectors are passed only to family event methods, never to core initialization or query. It stores no per-instance manager, tree store or removal callback. Keep the generic row shape tight: it only needs ID, `summary`, `createdAt`; family-specific fields stay in family row records, not a nullable union of Team/Org attributes. Do not replace public family catalogs with a generic ambiguous-ID API.

- `listCatalogRows()` and `getCatalogRow(id)` await the shared initialization promise, use index-only cached rows, compact summaries in returned snapshots at this **catalog boundary**, filter admission at query time, return sorted defensive/immutable row snapshots, and never call `writeRows` or tree stores. Initialization keeps every valid persisted row internally, including currently unadmitted ones, so later unrelated writes do not delete them; exposure is filtered by current admission. Missing index loads `[]`; strict parse failure resets the init promise and propagates error without writing.
- All runtime row mutations enter the same family-keyed queue. Simple create/restore/first-summary/termination operations copy current rows, apply a family projector where appropriate, compact only the affected summary through the core (untouched summaries are not silently truncated), write the current index atomically, then publish new in-memory rows only after success. First nonempty summary wins in queue order. No-op summary/termination does not flush.
- For archive/delete, the family adapter enters the core family queue **first**, then the manager's per-root inactive-history transition lane. Org already has `withInactiveHistoryMutation`; Team must generalize/rename `withUnmanagedHistoryDeletion` to the equivalent `withInactiveHistoryMutation`, using `withRootTransition` and checking `hasManagedTeamRun` **inside** that lane. Remove Team archive/unarchive's pre-queue `hasManagedTeamRun` check. The manager callback must enclose the entire tree read/write, index write/readback, compensation and final state publication; it is not just a check that returns before mutation. Only after the manager gate admits an unmanaged run does the core expose a locked row snapshot and a controlled durable index-write/publish operation; the adapter coordinates tree/package steps and compensation. Candidate rows are not published to queries until the multi-file operation succeeds. Failure restores/validates the prior tree/index snapshot or reports an indeterminate outcome; it must not silently claim success. Team archive/unarchive gain the same inactive-only transition guarantee and rollback required by AC-002. If restore acquired its per-root lane first, the queued archive/unarchive rechecks managed status inside the lane and returns the existing managed-run refusal with no tree/index write. If archive/unarchive acquired the lane first, restore waits until the full commit or compensation finishes.
- Admission readiness is awaited at load and current admission is checked at query; unadmitted rows stay persisted but are excluded from responses. `recordCreated` requires its manager-admitted package; the manager calls admission before the event. No query needs a tree to determine row membership. Family-specific projectors remain `projectTeamRunHistoryIndexRow` and `projectAgentOrgRunHistoryRow` for event/repair creation only. Org projector must compact recovered summary through the catalog boundary at runtime.
- `resetTeamRunHistoryCatalogState(memoryDir)` delegates to the new Team-family state reset for the existing migration/test contract; provide a matching Org reset for tests/maintenance. Reset is not a normal query operation and must not run while a family mutation is active.

**Non-obvious creation example:** On a fresh process, `manager.create(orgTree)` persists and admits run `R`; `recordCreated(R)` then initializes from the Org index **only**, sees no `R` row, writes one projected row. The existing Org preinitialize-before-create line is deleted. The bad shape—first read scanning the newly persisted tree and inserting `R` before the event—is removed.

## Return/event flow, boundary checks and removal plan

- DS-002 return/event: index commit succeeds → family catalog publishes the row map → run service returns the created/restored run; on commit failure, family service terminates the just-created/just-restored run and propagates the error. This is not an alternate source of row authority.
- DS-003 return/event: catalog queue → manager per-root gate/inactive recheck → full transaction/compensation → success/failure result → caller refreshes retained history only after success. On a determinate failure, prior tree/index/state are restored and verified; an indeterminate failure remains an error, never a success response.
- DS-006 bounded local: one initialization promise per `(directory, family)` → strict index load → admission-filtered read snapshots; mutation requests chain through one queue → candidate file write → committed in-memory publication or compensation.
- Thin facades: `CollaborationRootHistoryService` combines family lists but owns neither family catalog; memory root sources translate family rows into memory metadata but do not own history persistence. `getTeamRunHistoryCatalogService()` is a convenience factory, not a second policy owner.
- Identity/interface check: public methods stay Team-ID or Org-ID specific. The generic core is internal and always keyed by an explicit family plus resolved directory; no method guesses which family a bare ID names. The existing domain names `TeamRun` and `AgentOrgRun` remain natural; the core name denotes a shared catalog policy, not a new domain subject.

## Explicit repair design

The maintenance command is dry-run by default, requires an explicit local app-data profile, resolves its configured memory directory through `AppConfigProvider`, and requires `--apply` for any write, and has a stopped/quiescent local server as an operational precondition. It first rebuilds/awaits strict readiness for that local root, strictly reads both current indexes, computes **only admitted IDs absent from each valid index**, then reads/project trees only for those IDs. It reports family/ID counts, existing-index status, and the inability to recover index-only summary/termination for new rows. It never changes an existing valid row or prunes unadmitted rows. On apply, it backs up each existing index before writing one family's merged current-shape array, strictly rereads/verifies, then proceeds to the next; failures are reported per family with backup path and no false all-or-nothing claim. A corrupt index aborts that family without overwrite; a wholly missing index requires explicit acknowledgement of unavailable index-only facts. This command is not injected into the server, startup, GraphQL, or any memory-explorer source. It is an operational exception to index authority, not a normal second authority.

The command rejects an ambiguous/default target: require an explicit `--app-data-dir` for the **owned local profile**, derive its memory root from initialized app configuration, and print that exact resolved root for confirmation. Do not accept a `--memory-dir` or the memory explorer's arbitrary folder selector for apply. It is not a remote API. Documentation must state the offline/quiescence and backup prerequisites. If implementation cannot enforce/verify a local-owned target adequately, return `Design Impact` instead of allowing writes to imported sources.

## Task size and architectural risk

- `task_size`: **Medium**. Several files across the existing run-history capability and direct service/memory consumers, plus an offline repair entrypoint and tests; SR-005 adds a bounded existing Team Memory read path in current ownership, not a new product subsystem or broad UI/API rewrite. Payload inventory is two existing JSON arrays and representative fixtures; the size comes from runtime ownership and lifecycle refactoring, not row count.
- `architectural_risk`: **High**. The solution changes history-row authority, persisted read/write timing, shared state/queue scope, archive compensation and Org creation sequencing; SR-005 also touches Team member-location projection on an imported read path. A mistake has a cross-family data-integrity, wrong-member-path or imported-folder write blast radius. Independent architecture review is warranted even with no schema migration.
