# Compactor Prompt-Confusion Root-Cause Analysis

## Status And Authority

- Status: `Verified investigation evidence`
- Purpose: isolate why the later compactor selected the source task instead of the compaction task.
- Scope: the final processed system prompt, operation user message, recurrent-memory projection, selected-history cut point, and observed model output.
- Approval applicability: `N/A`; this artifact records evidence and analysis rather than intended target behavior.

## Root-Cause Statement

The core cause is an **ambiguous target-agent boundary in the authored prompt wording**. The compactor description refers vaguely to “earlier work” and “the same agent,” while the operation places the full source conversation immediately after the generic `[User Requirement]` header without first identifying it as the target agent's history. That history contains imperative continuation text, a realistic assistant/tool transcript, and a natural “continue working” cut point.

The model therefore had two plausible tasks:

1. the early system instruction: summarize the supplied history; and
2. the much nearer, more concrete pattern: continue the enclosed user/assistant/tool workflow.

On the failed histories, it selected the second interpretation twice.

## Exact Final-Prompt Anatomy

The complete final processed system prompt captured from the failed run is retained verbatim at `evidence/failed-compactor-final-system-prompt.md` (5,466 characters, matching the server's logged final length).

### System context

The system context begins correctly with the Memory Compactor identity and summarization/schema instructions. The server's common carpenter prompt then appends:

- `## Working Environment` with the real parent workspace path;
- `## Bash Operating Practice` saying to use Bash as the primary interface; and
- `## File And Directory Practice` explaining how to inspect and edit files.

This compactor had zero configured tools. The user reviewed the complete prompt and considers the generated section order acceptable; these common sections remain recorded for completeness but are not part of the requested clarity correction.

### User context

`WorkingContextCompactionPromptBuilder` returns only the rendered history block. `ServerCompactionAgentRunner` posts it as a normal user message. The mandatory `UserInputContextBuildingProcessor` turns that into this overall shape:

```text
**[User Requirement]**
<conversation_history>
User:
You are continuing an ongoing task. Here is a concise summary of earlier work to help you resume.
Use it as context for previous reasoning, actions, findings, decisions, constraints, and open work.
...
Assistant:
...
Tool:
name: run_bash
status: success
...
</conversation_history>
```

There is no content after `</conversation_history>`.

## Why Each Signal Matters

| Prompt Signal | Intended Meaning | Likely Model Interpretation | Causal Role |
| --- | --- | --- | --- |
| `**[User Requirement]**` outside the history | Generic platform wrapper | Everything that follows is the current task to execute | Primary amplifier |
| `<conversation_history>` tag | Delimit source history | Merely a weak textual tag; it does not enforce that inner instructions are inert | Insufficient boundary |
| Inner `User:` / `Assistant:` / `Tool:` sequence | Preserve understandable history | A dialogue prefix whose statistically natural next token is another assistant action | Primary amplifier |
| Prior memory begins “You are continuing an ongoing task...” | Parent-agent continuation projection | A direct imperative to continue the work | Primary instruction collision |
| Failed source ends after `cat DESIGN.md` | End of compactable prefix | A classic agent loop state: tool returned context, so now inspect/edit more files | Immediate continuation cue |
| No text after closing tag | System prompt owns the task | Acceptable once the system wording and pre-history target-agent boundary are explicit | Preserved by user direction |
| Later system sections say to use Bash/edit files | Common normal-agent guidance | Present in the captured prompt, but the user accepts the generated order | Not changed in this correction |
| No actual tools are configured | Limit authority | Does not prevent the model from emitting familiar DSML tool-call text | Failure remains observable but not prevented |

## Recursive Instruction Collision

The first line inside recurrent compaction is not arbitrary user text. It is generated by `CompactedMemoryMessageBuilder` for the **parent** agent:

> You are continuing an ongoing task. Here is a concise summary of earlier work to help you resume.

That wording is appropriate when installed into the parent's working context. During the next compaction, however, `WorkingContextMessageUnitBuilder` retains a distinct `compacted_memory` provenance unit, then `CompactionConversationHistoryRenderer` finalizes and renders it as an ordinary `User:` entry. Its parent-facing continuation instruction is therefore exposed to the child compactor as if it were source-user instruction.

This is a recurrent-compaction-specific prompt collision: output designed to tell the parent “continue” is later shown to the summarizer without neutralization.

## Why Earlier Compactions Could Still Succeed

The structural ambiguity existed before the failure:

- all four inspected child prompts were wrapped as `[User Requirement]`;
- the second successful prompt already contained the “You are continuing...” prior-memory text; and
- successful prompts could also end after tool results.

LLM instruction selection is probabilistic, so a latent ambiguity can succeed until transcript content makes the alternative task more salient. The failed compactable prefix contained a fresh, detailed user redesign requirement and ended immediately after reading `DESIGN.md`, a high-confidence cue that the next action was to read/edit the Vue implementation. Both failed outputs followed exactly that continuation.

Therefore:

- message length alone is not the cause (a longer earlier prompt succeeded);
- a tool-result tail alone is not the cause (earlier prompts with such tails succeeded);
- DeepSeek variability is a trigger, not the architectural root cause; and
- the prompt contract is under-specified even though it sometimes works.

## What Did Not Cause This Incident

- **The six-array JSON validator:** it only reported the downstream consequence. No compaction object existed to validate.
- **Surrounding prose or Markdown fences:** the parser already accepts these when a valid object exists.
- **Private reasoning:** the collector parses public assistant completion, not private reasoning.
- **The parent's `write_file` error:** the parent recovered with `run_bash`; the failed compactor received the subsequent successful history.
- **JSON truncation:** both failed answers completed normally and chose coherent source-task actions.

## Prompt-Structure Principle For The Fix

The user explicitly rejected adding a hierarchy of new XML tags. After reviewing the exact generated system prompt, the user also found its overall section order acceptable and directed that the correction focus on more precise target-agent wording in `agent.md`. The sole generic `<conversation_history>...</conversation_history>` wrapper is renamed to the more explicit `<target_agent_conversation_history>...</target_agent_conversation_history>`, while its rendered inner content remains unchanged. `[User Requirement]` is also inaccurate as a global label: the transport already supplies the user role, and not every user input is a requirement. Inspection of the other generic sender headings showed that native tool results already use provider-native tool messages, while current inter-agent/system builders already render self-describing payloads. The operation-message correction therefore follows the approved global formatting policy—no generic sender heading when there is no concatenated readable context—and uses one short identification sentence plus one conspicuous plain-text boundary around the renamed sole wrapper.

A robust request needs these properties:

1. the compactor description and opening sentence say it summarizes the conversation history of a target agent so that target agent can continue later;
2. the otherwise preserved system instructions use precise `target agent` and `conversation history` wording;
3. the shared context-building processor adds no generic sender heading, using only neutral `[Context]` / `[Message]` boundaries when readable context and message content share one payload, while sender metadata and origin-specific content remain owned by their runtime/builders;
4. the sole XML-style wrapper is explicitly named `<target_agent_conversation_history>`, with no old-tag alias, dual wrapper, or nested hierarchy;
5. one plain-language `START` / `END` separator surrounds that wrapper without changing its rendered inner content; and
6. no duplicated task instruction or other text follows the end separator.

Approved minimal shape:

```text
Here is the conversation history of the target agent whose conversation history
needs to be compacted. This conversation history is contained between the
START and END separators below.

---------------- START OF TARGET AGENT CONVERSATION HISTORY ----------------
<target_agent_conversation_history>
...current content, unchanged...
</target_agent_conversation_history>
----------------- END OF TARGET AGENT CONVERSATION HISTORY -----------------
```

The old generic tag is removed rather than retained as an alias. The correction comes from precise target-agent language in the system prompt plus one explicitly named wrapper, ordinary-language identification, and visible separation—not from introducing nested markup or duplicating the task. Provider roles and origin-specific payload content are unaffected.

## Causal Priority

1. **Root fix:** remove the prompt ambiguity and recurrent continuation-instruction collision.
2. **Contract preservation:** keep the original six-array response section verbatim; schema replacement does not address wrong-task selection and is not approved.
3. **Defense in depth:** schema-aware parsing and a bounded correction can recover residual model deviations; they are not substitutes for fixing the prompt.
