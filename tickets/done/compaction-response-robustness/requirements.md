# Requirements Doc

## Status (`Draft`/`Design-ready`/`Refined`)

`Refined — REQ-001–REQ-017 and all intended-behavior supplements approved by the user on 2026-08-14/15; strict fail-closed/manual-retry, non-user deferral, provider-safe Unicode rendering, and a bounded memory-owned compaction-configuration refactor for non-recursive compactor leaf execution approved after live verification; preserved six-array response and typed memory contract remain the current implementation basis`

## Goal / Problem Statement

Make automatic memory compaction reliably perform the compaction task even when the enclosed conversation resembles an unfinished agent workflow, while preserving the original six-array model response contract and atomic memory persistence. User verification additionally requires trigger-aligned single-pass reduction, correct runner-versus-response failure classification, and strict fail-closed recovery: a failed required compaction stops the current target-agent turn, remains pending, and is tried again only from a distinct user-authored turn such as `continue`. Agent-authored and system-authored inputs must not become autonomous retry signals or be lost while that user gate is active.

Live verification on 2026-08-15 additionally proved that provider-facing compaction text must be well-formed Unicode. The derived middle-omission renderer split the valid shield emoji `🛡️` at a UTF-16 surrogate boundary, and DeepSeek rejected `messages[1].content` with HTTP 400 before inference. Raw traces must remain exact; only the derived provider-facing copy is normalized and truncated safely.

The first successful Unicode-safe retry exposed a separate lifecycle and ownership defect: the built-in Memory Compactor inherited the global 20% automatic-compaction policy and compacted its own already-wrapped one-shot task. A Memory Compactor child is a specialized leaf worker, not a long-running target agent. Its agent-creation composition must carry an explicit disabled automatic-compaction configuration, while normal agents receive the existing enabled policy and current strategy dependency. The provider/model request capacity remains independent and continues to govern whether the one-shot request fits.

The reported failure was not caused by Markdown fences or harmless commentary around valid JSON. Two later compactor runs misunderstood the quoted conversation as an active CER/Vue task, emitted source-task `run_bash` calls, and returned no compacted memory object. The target behavior must fix that task/evidence ambiguity, tolerate benign response formatting, recover once from invalid output, and never accept unrelated prose as canonical memory.

## Investigation Findings

- The parent run was `daily_assistant_2a39c68eb96443ada6f5af9f4f81acef`, using strategy `structured-json` and model `deepseek-v4-flash`.
- Earlier compactor runs `memory_compactor_da3d2793f9244876b0c9bc81e95e5be9` and `memory_compactor_d305bed6091947f1984e2159f285e789` returned valid six-array summaries and committed successfully.
- Later runs `memory_compactor_506ea3c502f34687a3f6004a08364364` and `memory_compactor_e1f5d8b1cc884f66a4d4c9918639ba30` received the same 71,043-character input. Both output commentary continuing the CER/Vue task and DSML `run_bash` invocations; neither output contained a compaction object.
- The failed input was prefixed `**[User Requirement]**`, then contained the history, and ended with a normal source-task tool result followed by `</conversation_history>`. `WorkingContextCompactionPromptBuilder` adds no task directive after that boundary. The processed system prompt separately tells the zero-tool compactor to use Bash and perform workspace/file operations.
- The current parser accepts exact JSON, fenced JSON, and prose around a valid object. It fails when an unrelated valid object precedes the intended object because it returns the first parseable object before schema validation.
- The model response structure is transient. Host code, not the model, owns persistent identities, timestamps, salience, lineage, exact trace archival, working-context replacement, and the final Markdown projection.
- Free-form Markdown would be too weak: it could accept the exact wrong-task prose/tool-call output as memory. The user explicitly chose to preserve the original six-array schema because its detailed category explanations are already clear and the authored `agent.md` should receive only minimal wording changes.
- The screenshot's `write_file` failure is a separate normal-agent configuration error and was immediately recovered through `run_bash`; it did not cause compaction failure.
- User verification at 20% exposed a trigger/selection mismatch: trigger threshold 123,148 tokens versus a fixed planner suffix target of approximately 215,510 tokens. Three successful operations were requested in one parent turn before context finally fell to 8,755 tokens.
- After the agent later grew back to 123,520 tokens, a new compaction trigger was correct. Four child attempts across two parent turns failed before a usable response and recorded no token usage; the host misreported them as JSON extraction failures and reran the unchanged pending operation after `continue`.
- Architecture review then traced a supported non-user path into the same unconditional pending executor: `InterAgentMessageReceivedEvent -> AgentTurnRunner -> AgentInputPipeline -> LlmPhase -> LLMRequestAssembler`. Production server routing also wraps direct/team agent deliveries in `UserMessageReceivedEvent` with `SenderType.AGENT`, so event class alone is not a sufficient user-authorization boundary.
- In the later 371,352-token reproduction, trigger/planning behavior was correct, but `ReadableValueRenderer` split the valid shield emoji in a source tool result at its 2,000-character middle-omission boundary. The malformed derived child prompt contained one lone U+D83D and DeepSeek returned HTTP 400 before inference. The new runner path correctly classified it and launched no JSON repair, but retrying the unchanged renderer would reproduce the same local defect.
- The Unicode-safe retry then succeeded, but its outer Memory Compactor inherited the global 20% policy. At 176,655 prompt tokens it recursively launched another Memory Compactor. The nested task contained two START/END pairs because it wrapped a shortened copy of the outer compactor's already-wrapped task; this was deterministic local recursion, not model confusion. The intended Daily Assistant operation still completed and the next actual parent observation was 73,102 tokens, below the 123,148 trigger.

## Recommendations

1. Remove the generic sender-heading map from the shared context-building processor. Use raw message content when no readable context is concatenated and neutral `[Context]` / `[Message]` sections when both share one payload. Preserve `senderType` as runtime metadata, provider-native tool messages, and origin-specific wording owned by tool/inter-agent/system payload builders. For compaction, also make only minimal target-agent/conversation-history wording refinements in the otherwise preserved `agent.md`, preserve the current history block verbatim, and add only a short identification sentence plus one plain-text start/end separator.
2. Preserve the original six-array response instructions verbatim, including every category explanation, empty-array rule, and complete JSON example.
3. As defense in depth, make parsing schema-aware across all exact, fenced, and balanced-object candidates using the preserved six-array schema; accept one distinct valid object and reject zero or multiple valid objects.
4. As defense in depth, make one automatic corrective attempt for invalid/misdirected output, then fail once with actionable attempt metadata.
5. Keep generic `write_file` and arbitrary Markdown out of this fix; retain host-owned validation and atomic commit.
6. Bump the prompt contract to version 3 without rewriting existing persisted memory.
7. Make the sender-heading replacement clean-cut: remove the obsolete heading map and old rendering expectations rather than retaining a feature flag, compatibility branch, alias, or dormant fallback.
8. Pass the active trigger target into planning and make the estimated post-compaction target strictly lower with headroom; remove the independent fixed-35%-above-trigger behavior for low ratios. After accepted success, require an actual below-threshold provider observation before rearming the same crossing; one at/above observation yields bounded inadequate-reduction suppression instead of another proactive operation.
9. Return typed child-run failures before parsing; reserve the single correction child for usable but invalid assistant output.
10. Preserve the failed pending operation as an explicit pre-dispatch gate. On any final compaction failure, stop the current target-agent turn and schedule no automatic provider retry; one distinct later user-origin turn explicitly invokes one new attempt, and target-agent dispatch occurs only after that attempt succeeds.
11. Stamp authoritative `user` / `agent` / `system` origin on turn-start inbox entries before any input conversion. While the failed-pending gate awaits a user retry, keep agent/system entries in the existing FIFO queue and let the scheduler select the earliest user entry behind them. Do not add a second deferred store, drop messages, or allow non-user events to execute the pending operation.
12. Make compaction-history and accepted-summary truncation Unicode-safe. Preserve raw traces unchanged, normalize only the derived provider-facing copy, remove non-useful unsafe control characters while preserving newline/tab, and assert a well-formed completed task prompt before launching the child. Do not strip all emoji or reduce multilingual/code content to ASCII.
13. Refactor automatic-compaction composition without adding speculative abstractions. Add one discriminated memory-compaction configuration owned by `MemoryManager`: disabled, or enabled with the single existing `CompactionPolicy` and current strategy runner. Agent creation supplies it; normal server agents get the enabled default, while the canonical Memory Compactor gets disabled and does not invoke the runner factory. Remove the fragmented top-level runner field and factory-created policy. Keep the existing strategy registry and sole `structured-json` registration; do not add ratio/capacity policy subclasses, a new controller hierarchy, a persisted flag, or chunking in this task.

## Scope Classification (`Small`/`Medium`/`Large`)

`Medium`. The changes are bounded but span global input formatting, the compaction task boundary, parser candidate selection, retry lifecycle, turn-start admission, memory-owned automatic-compaction composition, built-in runtime provisioning, diagnostics, tests, documentation, and lineage versioning on a production-critical path. The model response schema itself remains unchanged, and the ownership refactor deliberately keeps one current policy and one current strategy implementation.

## In-Scope Use Cases

- **UC-001:** Automatic recurring compaction succeeds on the first model response without continuing an enclosed source task.
- **UC-002:** A valid response remains acceptable when fenced or surrounded by commentary, or when unrelated JSON-like content is also present.
- **UC-003:** An invalid/misdirected first output is corrected automatically by one repair attempt.
- **UC-004:** Two invalid outputs fail safely with one final user-visible failure and actionable operational evidence.
- **UC-005:** Successful output continues to populate typed current memory, lineage, Memory Inspector categories, and the final continuation projection.
- **UC-006:** Runs with existing prompt-contract-v1/v2 lineage and memory continue without migration.
- **UC-007:** Lowering the trigger ratio below an already-valid prompt triggers one target-aligned compaction rather than a rapid chain.
- **UC-008:** A child provider/runner failure is reported as that failure and does not consume the response-contract correction attempt.
- **UC-009:** A final compaction failure stops the current target-agent turn without an autonomous retry loop; a distinct later user-origin turn explicitly retries the retained pending compaction before target-agent dispatch.
- **UC-010:** Agent/system messages received while the pending operation awaits user retry remain queued without starting a turn or retry; the earliest user entry can authorize one retry, after which queued non-user work resumes in order only if compaction succeeds.
- **UC-011:** A conversation containing long multilingual/tool content and supplementary-plane Unicode is rendered, omitted, serialized, sent, and later projected without a truncation-created lone surrogate or provider request rejection.
- **UC-012:** A parent compaction child whose one-shot prompt crosses the configured proactive or hard-cap trigger completes as a leaf and returns its original response without evaluating or launching compaction against itself; a response-correction child is a separate sibling leaf, never a descendant.

- Building an isolated file-backed compaction provider.
- Adding unbounded retries, automatic provider/model fallback, or human approval during automatic compaction.
- Changing memory category semantics, salience policy, exact-trace archival policy, Memory Inspector information architecture, or the user-configured trigger ratio. The planner behavior needed to honor that ratio is now in scope.
- Rewriting existing memory or lineage solely to match the new transient response contract.
- Adding a persistent deferred-message store, delivery migration, retry timer, background scheduler, or special queue solely for compaction recovery; existing runtime turn-start queue and shutdown semantics are reused.
- Rewriting or sanitizing stored raw traces, archived traces, existing memory, or lineage; Unicode repair is limited to derived provider-facing/prompt-projection copies.

- Activating the separately discussed future split in which conversation compaction returns one unstructured continuation summary and episodic/semantic memory is distilled from raw/work traces. That product-contract redesign requires its own explicit approval and clean-cut design; it is not implied by the focused REQ-016 Unicode fix.

- Introducing alternative ratio-threshold/capacity-pressure policy classes, a general policy hierarchy, a new compaction controller layer, or a second strategy implementation. Preserve the active `senderType` metadata model and existing source-specific payload rendering. Preserve provider-native tool-call/result messages and the rule that a text-only `SenderType.TOOL` continuation produces no additional LLM user message; a media/context continuation may still produce the auxiliary user/media carrier required by the provider, using its builder-owned self-describing content rather than a generic wrapper. Refine the Memory Compactor description and opening wording so they state that the compactor summarizes the conversation history of a target agent so the target agent can continue later. Preserve the remaining authored compactor instructions except for corresponding minimal references from generic `agent`/`history` wording to `target agent`/`conversation history`; do not add prohibitive instructions about continuing tasks or performing actions. Rename the sole outer history wrapper from `<conversation_history>...</conversation_history>` to `<target_agent_conversation_history>...</target_agent_conversation_history>` and preserve the rendered inner history content and other rendering rules; update delimiter-collision escaping for the renamed tag. Do not retain the old tag as an alias or second wrapper. Add only the approved concise sentence identifying the block as the conversation history of the target agent whose conversation history needs to be compacted and saying that this conversation history lies between the following separators. Surround the renamed block with one plain-text `START OF TARGET AGENT CONVERSATION HISTORY` / `END OF TARGET AGENT CONVERSATION HISTORY` separator pair. Add no task restatement after the end separator. Preserve the current generated system-prompt section order and common sections. The complete approved text in `memory-compactor-prompt-spec.md` is authoritative and must be applied exactly; implementation must not invent, paraphrase, or reorder the prompt wording.
- **REQ-002 — Preserve the original structured response:** Preserve verbatim the original `agent.md` response section beginning `Return one JSON object with these fields:` through its complete six-array JSON example. The required fields remain `episodes`, `critical_issues`, `unresolved_work`, `durable_facts`, `user_preferences`, and `important_artifacts`; episode entries retain `summary`, fact-category entries retain `fact`, every array remains required, and at least one non-empty episode remains required. Do not introduce an `items`/`kind`/`text` contract.
- **REQ-003 — Benign-format tolerance:** Response handling must accept one valid envelope when it is the whole response, inside a Markdown JSON fence, or surrounded by visible prose; unrelated parseable JSON objects must not mask it.
- **REQ-004 — Semantic validation:** A successful response must contain all six required arrays and at least one nonblank `episodes[].summary`; the five fact categories retain `fact` entries. Multiple distinct schema-valid compaction objects must be rejected; blank/non-string entries may be discarded when the required episode invariant still holds; harmless extra fields must not cause failure.
- **REQ-005 — Bounded repair:** When the first output contains no unambiguous valid envelope or fails semantic validation, the same pending operation must make exactly one automatic corrective attempt and must not commit the first output.
- **REQ-006 — Coherent lifecycle and diagnostics:** A repair success must produce one completed operation without an intermediate user-visible failed lifecycle. Exhausted repair must produce one final failed lifecycle that identifies the validation stage and both attempt run IDs when available.
- **REQ-007 — Atomic safe failure:** No failed attempt may archive selected raw traces, add or change episodic/semantic rows, append lineage, replace working context/snapshot, or clear the pending compaction. A successful operation must use the existing accepted-compaction commit boundary and commit exactly once.
- **REQ-008 — Preserve typed memory outcome:** The parsed six-array response must continue producing the existing typed internal result so current normalization, deduplication, category ordering/salience, IDs/timestamps, Memory Inspector categories, and final Markdown-like continuation message remain behaviorally unchanged.
- **REQ-009 — Preserve least authority:** The compactor must remain tool-free for this change, and ordinary agent tool policy must not be changed as a side effect.
- **REQ-010 — Version and stored-data compatibility:** New successful lineage must record prompt contract version 3; normal lineage reading must accept versions 1, 2, and 3; existing canonical memory and lineage must remain directly usable without migration.
- **REQ-011 — Trigger-aligned planning:** The working-context planner must consume the active trigger threshold (not only the full input budget) and choose a retained-context target that leaves explicit estimated headroom below that threshold after accounting for protected content and the replacement summary. A fixed retention target that can exceed the configured trigger is invalid.
- **REQ-012 — Bounded threshold-crossing lifecycle:** A supported threshold crossing may request one parent compaction operation. A normal successful operation must satisfy the trigger-aligned reduction postcondition and must not immediately cause another operation without an intervening below-threshold observation and later crossing. If required/protected content or inadequate reduction makes the target unattainable, terminate with one coherent diagnostic outcome rather than a rapid or unbounded chain of successful model compactions.
- **REQ-013 — Typed runner-versus-response failure:** The child-run boundary must distinguish a usable public assistant response from provider, transport, response-ingestion, timeout, interruption, tool-approval, and other runner failures. Only a usable assistant response that fails extraction or semantic validation is eligible for the one response-contract correction attempt. A runner failure must bypass that correction, preserve its original classification/message and child run ID, and never be parsed or reported as model-authored invalid JSON.
- **REQ-014 — Fail-closed, user-initiated recovery:** Any final compaction failure—including runner/provider failure, exhausted response repair, planning failure, or precommit budget failure—must report one truthful terminal error, retain the pending compaction and selected source traces in an `awaiting_user_retry` attempt state, perform no additional target-agent LLM dispatch or tool phase in that turn, and schedule no background or same-turn compaction retry. The failed turn ends, but the agent runtime remains active and able to accept queued/new inputs. A distinct later turn whose authoritative turn-start origin is `user` (for example, a user-entered `continue`) is the explicit retry signal: before dispatching that message to the target agent, execute the retained pending compaction no more than once for that turn. If it succeeds, clear the pending operation and continue normal dispatch; if it fails, report the new failure, retain the gate, and stop that turn again. This policy applies whether pressure began at the proactive trigger or at the hard input cap. The only automatic second child allowed is the existing one correction attempt for usable but response-invalid model output under REQ-005; runner/provider failure never consumes it. A newly requested operation still receives one automatic initial execution regardless of the originating turn type; only attempts after a final failure require user authorization.
- **REQ-015 — Authoritative origin gate and non-user preservation:** Classify every supported external turn-start entry as `user`, `agent`, or `system` before `InterAgentMessageReceivedEvent` conversion or other input processing. A `UserMessageReceivedEvent` authorizes retry only when its original `AgentInputUserMessage.senderType` is `SenderType.USER`; `InterAgentMessageReceivedEvent`, `SenderType.AGENT`, and `SenderType.SYSTEM` never authorize a failed-pending retry. While an operation is `awaiting_user_retry`, non-user entries must remain unclaimed in the existing turn-start queue: they start no turn, execute no compactor, create no repeated compaction error, and reach neither target LLM nor tools. Queue selection must be able to claim the earliest eligible user entry behind them without moving, copying, or dropping the retained non-user entries. If the authorized retry fails, those entries remain queued. If it succeeds, the user turn proceeds first; when that active turn settles, ordinary FIFO scheduling resumes over the retained entries in their original relative order. With no failed-pending gate, normal FIFO behavior is unchanged. Existing runtime shutdown/drain treatment applies to retained entries; no persistent queue/schema or migration is introduced.
- **REQ-016 — Provider-safe Unicode rendering:** Every completed conversation-history task prompt sent to a compactor child must be a well-formed Unicode string. Preserve raw trace/tool payload/canonical-memory source values unchanged and operate on a derived copy. Middle and end truncation used by compaction presentation must never split a UTF-16 surrogate pair; omission accounting and configured limits must use the actual safe boundaries. Normalize any pre-existing lone surrogate in derived text to U+FFFD and remove non-useful C0/DEL controls while preserving normalized newlines and horizontal tabs. Apply the shared safe end-truncation primitive to episode/fact text clamps that can enter a later provider prompt. Valid multilingual text, paths, code, mathematical symbols, and emoji must remain valid rather than being broadly stripped or converted to ASCII. Enforce the completed operation-prompt invariant before child launch; if safe construction cannot be completed, report one typed local input-construction failure without a provider call, correction child, target-agent dispatch, source mutation, or canonical-memory mutation.
- **REQ-017 — Memory-owned configuration and non-recursive Memory Compactor leaf:** Automatic compaction must be composed at agent creation through one explicit discriminated memory-compaction configuration and owned by `MemoryManager`, not inferred from a top-level nullable runner while a separate factory always creates a policy. The disabled variant contains neither an automatic-compaction policy nor a strategy runner. The enabled variant contains the single existing `CompactionPolicy` and the current strategy runner dependency; the existing pluggable strategy registry and sole `structured-json` registration remain the `how` boundary. Omitted direct-core `AgentConfig` or `MemoryManager` construction resolves to the complete disabled variant. Production server composition is explicit: select disabled for the canonical built-in `autobyteus-memory-compactor` on create and restore and do not invoke the runner factory for it; normal server agents receive enabled configuration, and runner-factory failure/null fails their creation rather than silently disabling compaction. The generic LLM phase must ask the memory boundary for the configuration and, when disabled, skip automatic-compaction policy application, pending execution, post-response evaluation, lifecycle reporting, and strategy construction. A Memory Compactor child must therefore never create pending self-compaction or launch a descendant, even when its prompt usage exceeds the global proactive threshold or would classify as a policy hard cap. Provider/model input capacity, output reserve, and ordinary request safety remain independent of automatic-compaction enablement: send the parent-owned one-shot task directly when it fits, otherwise return the existing truthful planning/pre-launch or typed runner failure without recursively rewriting the child instruction/history. One optional response-contract correction remains a parent-owned sibling leaf. Remove the fragmented top-level `AgentConfig.compactionAgentRunner` field and unconditional `AgentFactory` policy construction cleanly; do not add multiple policy classes, a new controller hierarchy, a ratio hack, prompt-only instruction, persisted opt-out, historical cleanup, schema change, migration, or chunking strategy.
