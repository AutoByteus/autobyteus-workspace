## Target Selection Algorithm / Interface Boundaries
1. Preserve complete explicit PRISMA_QUERY_ENGINE_LIBRARY + PRISMA_SCHEMA_ENGINE_BINARY precedence exactly, without requiring metadata or reinterpreting operator paths. Existing partial-env behavior remains: a resolved automatic pair replaces both; with no pair, base env (including any partial value) remains while operational DATABASE_URL wins.
2. Inspect the same local JS entrypoint that getPrismaCommand prefers: appRoot/node_modules/prisma/build/index.js. Resolve its realpath. With node:module createRequire(realCliPath), resolve @prisma/engines/package.json. Resolve that manifest's realpath, anchor another createRequire there and resolve @prisma/engines-version/package.json. Read JSON's prisma.enginesVersion as the expected nonempty40-hex native revision. No JS package execution, CLI --version, ensureBinariesExist, download/copy, directory guessing or recursive ancestor/store scanning.
3. Private narrow metadata value {engineDir, engineRevision}; engineDir is the associated real engine manifest's directory. Missing local JS/package resolution, unreadable/malformed metadata or unknown revision yields null automatic discovery; never parse a pnpm directory/package semver as substitute. Leave getPrismaCommand JS→.bin→pnpm selection unchanged. For .bin/pnpm-only layouts with no proven local CLI identity, let that CLI resolve normally rather than guess its native revision.
4. Resolve a complete platform pair ONLY within associated engineDir using existing native filename/suffix and getPrismaRuntimeTargetPreference contract. Preserve source bundled/sourcePath shape. Do not scan other @prisma/engines installations even if their files look newer or native.
5. If own bundle has no complete runtime pair, consider ONLY cacheRoot/engineRevision. Reuse current target-token/preference/file-existence semantics within that revision; prefer stable sorted directory order for equivalent targets, not cache revision mtimes. Cache result still uses libquery-engine + schema-engine and source cache. Do not inspect all cache revision folders; never combine files across package/revision/target boundaries. No match → null.
6. Keep buildPrismaCommandEnv base-env spread plus authoritative supplied databaseUrl and both resolved paths. Keep runPrismaCommand logging/exec and runMigrations schema/deploy/P3005/genuine-error path. No engine discovery exception becomes successful migration or skips required schema work.

| Boundary | Explicit subject / responsibility | Allowed callers / forbidden bypass |
| --- | --- | --- |
| runMigrations({appRoot,databaseUrl}) | Deployment into caller's canonical DB with common engine inputs | Existing startup/standalone/importer only; no caller directly selects caches or mutates ledger |
| resolvePrismaEnginePair(appRoot,baseEnv,cacheRoot) | Pair or null; existing exported shape retained | Internal env assembly/tests; metadata mechanism remains private, not public registry |
| Private installed metadata resolver | Real CLI-bound engineDir/revision | Existing migrations owner only; no process-global cached identity or optional unrelated fields |
All singular responsibilities and explicit identity shapes; selector ambiguity Low. Names retain existing domain terms. No new public interface/dependency package. Helpers remain small in the existing coherent file; no general engine-service layer.

Genuine migration errors must stay visible. Native fixture/image build failure cannot be labeled source success. New public image is not implicit; current temporary pin remains lost on future recreation until a separately deployed corrected image is used.
