# Design Spec

## Current-State Read

AutoByteus currently has a run-scoped Agent Tools MCP surface:

```text
/mcp/agent-tools/:sessionId
```

That endpoint is generated by AutoByteus-managed runtime materializers for active AgentRuns/members. It can safely expose AutoByteus internal tools because the session has a real run owner, sender context, configured agent tool exposure, runtime kind, workspace/memory context, and lifecycle revocation.

AutoByteus also already imports external MCP servers through MCP Server Management. Discovered remote MCP tools are registered in the shared tool registry as `ToolOrigin.MCP` definitions with `metadata.mcp_server_id`. Current run-scoped Agent Tools MCP can expose selected MCP-origin tools for an agent run by delegating through the existing registry-created MCP tool / MCP proxy path.

The gap is a stable external MCP gateway endpoint for clients such as Cursor, Antigravity, Claude Code, or other AI CLIs. The gateway should not pretend to be an AgentRun and should not expose AutoByteus internal agent tools.

## Intended Change

Add a new stable external MCP gateway endpoint and minimal frontend discovery UI:

```text
/mcp/gateway
```

This endpoint exposes only registered MCP-origin tools (`ToolOrigin.MCP`) from the AutoByteus tool registry and delegates calls through the existing MCP Server Management proxy path. The frontend should surface this in Settings -> MCP Servers using tabs (`MCP Servers`, `MCP Gateway`) similar to the Nodes page tab pattern.

The existing internal run-based endpoint remains unchanged:

```text
/mcp/agent-tools/:sessionId
```

- Change posture (`Feature`/`Bug Fix`/`Behavior Change`/`Refactor`/`Cleanup`/`Performance`/`Larger Requirement`): Feature / Boundary Addition
- Current design issue found (`Yes`/`No`/`Unclear`): Yes, if trying to reuse run-scoped MCP as a general gateway; avoided by adding a separate MCP-origin-only gateway boundary.
- Root cause classification (`Local Implementation Defect`/`Missing Invariant`/`Boundary Or Ownership Issue`/`Duplicated Policy Or Coordination`/`File Placement Or Responsibility Drift`/`Shared Structure Looseness`/`Legacy Or Compatibility Pressure`/`No Design Issue Found`/`Unclear`): Boundary Or Ownership Issue avoided by explicit endpoint/tool-category split.
- Refactor needed now (`Yes`/`No`/`Deferred`/`Unclear`): Limited yes. Add a new gateway route/executor and, if required, tighten MCP proxy execution identity. Do not refactor internal run MCP behavior.
- Evidence: Current session model requires run identity and sender context; external gateway needs no run context if it exposes only `ToolOrigin.MCP` tools.
- Design response: Two surfaces: run-scoped Agent Tools MCP for internal AutoByteus runtimes; general MCP Gateway for external clients and MCP-origin tools only.
- Refactor rationale: Separate endpoint avoids optional run/profile fields and prevents accidental exposure of internal AutoByteus agent tools.
- Intentional deferrals and residual risk, if any: Gateway profiles/per-client subsets and token management UI are deferred. First version is all registered MCP-origin tools through the simplest configured gateway access mode.

## Terminology

- Run-scoped Agent Tools MCP: existing internal AutoByteus runtime bridge at `/mcp/agent-tools/:sessionId`.
- General MCP Gateway: new external MCP client endpoint at `/mcp/gateway`.
- MCP-origin tool: a registry tool definition with `origin === ToolOrigin.MCP`, imported from configured external MCP servers.
- Internal AutoByteus agent tool: server-owned/run-dependent tools such as `send_message_to`, task delegation, media, browser, `publish_artifacts`; these are excluded from `/mcp/gateway`.

## Legacy Removal Policy (Mandatory)

- Policy: `No backward compatibility; remove legacy code paths.`
- Required action: Do not emulate AgentRun sessions for gateway clients. Do not introduce fake run ids.
- Treat removal as first-class design work: no current route removal is needed; this is additive with strict boundary separation.
- Decision rule: `/mcp/gateway` must never call internal AutoByteus agent-tool adapters in this first version.

## Ownership Map

- General MCP Gateway owns `/mcp/gateway`, authentication for that endpoint, MCP-origin filtering, and gateway result mapping.
- MCP Server Management owns external MCP server configs, remote transport clients, proxy execution, connection reuse, and cleanup.
- Agent Tools MCP Run Session owns `/mcp/agent-tools/:sessionId`, run-scoped sessions, run-selected tool exposure, and AutoByteus internal tool adapters.
- Tool Registry owns registered tool definitions and origin metadata.

## Ownership Boundaries

- `/mcp/gateway` owns only external MCP gateway behavior and only exposes `ToolOrigin.MCP` tools.
- `/mcp/agent-tools/:sessionId` owns internal AutoByteus runtime tool projection and may expose server-owned tools because it has run context.
- MCP Server Management remains the only owner of remote MCP server configuration and transport execution.
- Tool Registry remains the authority for current tool origin and metadata; gateway must re-read current definitions when listing/calling.

| Authoritative Boundary | Internal Owned Mechanism(s) It Encapsulates | Upstream Callers That Must Use The Boundary | Forbidden Bypass Shape | If Boundary API Is Too Thin, Fix By |
| --- | --- | --- | --- | --- |

| MCP Server Management | managed MCP server clients/proxy | Gateway executor and run MCP-origin adapter | Gateway directly opening raw MCP transports | Extend proxy API |
| `/mcp/agent-tools/:sessionId` Run MCP | run session registry, run catalog, internal adapters | AutoByteus runtime materializers | Gateway trying to create run sessions | Keep separate endpoint |

## Dependency Rules

- Gateway may depend on Tool Registry and MCP Server Management.
- Gateway must not depend on AgentRunManager or team/member runtime context for normal operation.
- Gateway must not import/call server-owned internal agent tool adapter providers.
- Existing run MCP may continue depending on run/member services.
- MCP Server Management must not depend on gateway route/auth internals.

## Frontend UI Design

Use the existing Settings -> MCP Servers section as the entrypoint, but split its content into tabs following the Nodes page pattern.

Target shape:

```text
Settings
  -> MCP Servers
      [MCP Servers] [MCP Gateway]
```

- `MCP Servers` tab: existing `McpServerList`, add/edit/delete/bulk import/discover/view tools behavior.
- `MCP Gateway` tab: new minimal panel showing the stable endpoint `/mcp/gateway`, copyable MCP config guidance, and currently exposed MCP-origin tool count/list.

Implementation guidance:

- Add `McpManagementTabs.vue` or equivalent, modeled after `NodeManagerTabs.vue` (`role=tablist`, `aria-selected`, tab panels).
- Add `McpGatewayPanel.vue`.
- Keep Settings sidebar unchanged: one `MCP Servers` item only.
- Do not add token generation/rotation/revocation UI in this version.
- Reuse existing `tools(origin: MCP)` query/store data for exposed tool count/list where practical.

## Migration / Refactor Sequence

1. Add `src/mcp-gateway` with route/access/catalog/executor skeleton.
2. Register `/mcp/gateway` in server runtime before/alongside existing MCP route registration.
3. Implement the simplest configured gateway access mode; do not add profile/token CRUD.
4. Implement `tools/list` by filtering registry definitions to `ToolOrigin.MCP`.
5. Implement `tools/call` with current-definition origin check and existing registry tool execution.
6. Add/adjust MCP proxy execution identity only if current `agentId` requirement would create misleading fake run semantics.
7. Add frontend tabs inside Settings -> MCP Servers following the Nodes page pattern: `MCP Servers` and `MCP Gateway`.
8. Add `McpGatewayPanel` showing endpoint/config guidance and current MCP-origin tool count/list using existing `tools(origin: MCP)` data where possible.
9. Add integration tests with MCP SDK Streamable HTTP client against `/mcp/gateway`.
10. Run existing Agent Tools MCP tests to prove `/mcp/agent-tools/:sessionId` did not regress.
11. Update long-lived docs after implementation.

## Key Tradeoffs

- No profiles/token CRUD first: simpler and matches 'make gateway work', but cannot restrict clients to subsets yet.
- MCP-origin-only: much safer and simpler, but external clients cannot use AutoByteus internal tools through the general gateway.
- Separate endpoint: slightly more code, much clearer ownership.

## Risks

- Gateway access config source may need small product/implementation decision.
- Tool registry listing API may need inspection if it does not expose all definitions conveniently.
- MCP proxy identity may require a small cross-package change.
- External gateway docs/UI must clearly distinguish MCP-origin tools from AutoByteus internal run tools.

## Guidance For Implementation

Implement the gateway as a narrow, explicit MCP-origin-only endpoint. Do not modify run-scoped Agent Tools MCP except for extracting shared helpers if that is low-risk. Prefer a small, easy-to-review first slice over profile/token-management systems. The architecture and UI should make it obvious that `/mcp/gateway` is for external MCP tools and `/mcp/agent-tools/:sessionId` is for AutoByteus run-scoped internal/runtime tools. In the frontend, use tabs inside Settings -> MCP Servers rather than a second sidebar item or a mixed card above the server list.
