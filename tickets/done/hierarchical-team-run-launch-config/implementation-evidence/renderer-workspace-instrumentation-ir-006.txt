Diagnosis and selected correction
---------------------------------
useTeamRunRuntimeCatalogSync watched collectRuntimeKinds(configRef.value), which
returned a fresh array for every immutable Team config replacement. Vue therefore
re-ran catalog synchronization after workspace-only canonicalization even though
the runtime set had not changed. setRuntimeModelCatalogLoading intentionally
removed the ready catalog; the panel's duplicated post-preparation readiness gate
then observed MODEL_CATALOG_PENDING and returned before the existing launch owner.
This is a concrete full-renderer invalidation sequence, not a generic Pinia delay
and not a reason to add nextTick/timing machinery.

The durable correction is:
- watch a sorted runtime-kind-set signature, so workspace/model/workspace-metadata
  replacements with the same runtime set retain ready catalogs;
- after successful workspace preparation, pass the exact current selected draft
  directly and exactly once to agentTeamRunStore.launchDraft;
- keep readiness/admission/create inside that owner, which already reconciles
  topology, admits the exact snapshot, evaluates readiness from the snapshot and
  current catalogs, and establishes in-flight duplicate protection synchronously.
