# Design Spec

## Current-State Read

This ticket is based on latest `origin/personal` at `9a27e3d2 chore(ticket): record mobile chat flow finalization`.

The current AutoByteus mobile/remote-access path is already structurally sound for this request:

- Desktop Phone Access in `autobyteus-web/components/settings/PhoneAccessCard.vue` owns enable/disable, reachable URL selection, manual private URL entry, QR/link creation, and paired-device revocation/listing.
- `autobyteus-server-ts/src/api/rest/remote-access.ts` and `autobyteus-server-ts/src/remote-access/services/remote-access-pairing-service.ts` own remote-access status, pairing sessions, pairing exchanges, and paired device records.
- The QR/link generated by the backend points to `/mobile?pairing=<payload>` where the payload contains the selected `serverBaseUrl`, short-lived pairing code, expiry, and server name.
- `autobyteus-web/components/mobile/MobileRemoteAccessShell.vue` and related mobile components own the phone UI after `/mobile` loads.
- `autobyteus-web/stores/mobileNodeSessionStore.ts` owns mobile pairing/session lifecycle on the web side. It exchanges the pairing code, stores the returned `MobileNodeSession` through `mobileCredentialStorage`, and derives the node context from the paired base URL.
- `autobyteus-web/utils/remoteAccess/mobileCredentialStorage.ts` currently stores the mobile session in browser `localStorage`, which is origin-scoped.
- `autobyteus-web/docs/remote_access.md` already documents that native wrappers can reuse the same pairing and transport protocol later.

The current gap is not backend capability and not mobile run/chat behavior. The gap is packaging and connection journey:

- There is no Android app project, Gradle setup, or Android manifest.
- There is no native first-run connection profile UX that can remember a Tailscale/MagicDNS/Serve URL.
- There is no Android WebView navigation/security wrapper around the existing `/mobile` shell.
- There is no native recovery surface for Tailscale/offline/split-tunnel failures.
- There is no explicit mobile web PWA manifest/app-install metadata.
- Current docs do not yet give the exact recommended travel journey: pair using the same stable Tailscale URL that the user expects to use while away.

Target constraints:

- Keep backend, agent, team, runtime, run, chat, file, and tool core behavior unchanged.
- Keep existing `/mobile` web shell authoritative for AutoByteus product behavior.
- Use Android only as a shell/launcher/diagnostic wrapper.
- Treat Tailscale as private-network reachability, not authorization. Phone Access credentials remain required.
- Prefer stable HTTPS Tailscale Serve URL for travel. Allow private HTTP only with explicit user acknowledgement.
- Avoid WebView boundary bypasses: Android may own shell state and navigation policy; the mobile web owns AutoByteus application state.

## Intended Change

Add a new Android app-shell package plus small mobile web/docs app-shell refinements:

1. Add `autobyteus-android/` as a standalone Android project.
2. Implement a native first-run connection screen with:
   - scan QR;
   - paste pairing link;
   - enter server/mobile URL;
   - saved node list/reset.
3. Implement a native `SavedNodeStore` that persists stable node profiles such as `https://desktop.tailnet.ts.net/mobile`.
4. Implement a native URL normalizer/validator that can accept either a base node URL or `/mobile` URL, validate `/rest/remote-access/status`, and then save/load the normalized mobile URL.
5. Implement a `WebView` host that loads only the saved AutoByteus mobile origin and opens unrelated external links in the system browser.
6. Load the existing desktop-served `/mobile` shell in WebView. Do not bundle/execute a separate copy of the AutoByteus UI as local Android assets for normal operation.
7. Preserve existing web-side pairing/session behavior. MVP credentials may remain in WebView localStorage; a native secure credential bridge is optional and must be origin-restricted if implemented.
8. Add native diagnostics for unreachable saved URL, likely Tailscale disconnected/split-tunnel exclusion, Phone Access disabled, revoked/expired credential, and WebSocket failure.
9. Keep the healthy WebView state full-screen/immersive for the existing `/mobile` shell: do not render a persistent native title/URL/action toolbar above the web content. Edit Node, Retry, Browser/Open externally, and Tailscale recovery actions belong in diagnostic overlays, the connection screen, or a compact overflow/bottom-sheet affordance that does not reserve vertical layout space during normal use.
10. Add minimal mobile web PWA manifest/app-shell metadata for browser installability, without offline service-worker caching.
11. Update docs/copy to recommend stable Tailscale Serve/MagicDNS pairing before travel and explain origin-scoped credentials.

- Change posture (`Feature`/`Bug Fix`/`Behavior Change`/`Refactor`/`Cleanup`/`Performance`/`Larger Requirement`): Feature / app-shell packaging and connection journey.
- Current design issue found (`Yes`/`No`/`Unclear`): No core design issue found in Phone Access/mobile shell. The Android packaging surface is missing.
- Root cause classification (`Local Implementation Defect`/`Missing Invariant`/`Boundary Or Ownership Issue`/`Duplicated Policy Or Coordination`/`File Placement Or Responsibility Drift`/`Shared Structure Looseness`/`Legacy Or Compatibility Pressure`/`No Design Issue Found`/`Unclear`): No Design Issue Found for existing core; Boundary Or Ownership Issue is the risk to avoid if implementation duplicates mobile/core behavior in Android.
- Refactor needed now (`Yes`/`No`/`Deferred`/`Unclear`): No core refactor needed now.
- Evidence: Existing Phone Access pairing, `/mobile` shell, status endpoint, mobile session store, and finalized mobile configure-then-chat behavior already provide the required product functionality once loaded from a reachable URL. No Android package currently exists.
- Design response: Add an Android shell boundary around the existing mobile web owner. Add only narrow docs/PWA app-shell seams to the web. Keep backend and mobile core behavior unchanged. After user review of the implemented shell, refine the Android UI requirement so native recovery controls do not become permanent browser-like chrome over a healthy mobile web experience.
- Refactor rationale: Refactoring core run/chat/Phone Access would increase risk and violate the user's stated principle. The right design is additive packaging plus strict boundary containment.
- Intentional deferrals and residual risk, if any: Native secure credential storage can be deferred if MVP keeps credentials in WebView localStorage. Residual risk: origin-scoped localStorage means users should pair through the stable travel URL; switching origins may require re-pairing. Healthy-state WebView actions may use a minimal overflow/bottom-sheet affordance, but must not push content down with a permanent header.

## Terminology

- `Android shell`: the native Android package that owns first-run/saved-node UX, WebView hosting, navigation policy, diagnostics, and build/package concerns. It must stay visually subordinate to the mobile web shell once content is healthy.
- `Mobile web shell`: the existing AutoByteus Nuxt mobile experience served under `/mobile`; owns AutoByteus application behavior.
- `Saved node profile`: Android-owned metadata for a reachable AutoByteus node/mobile URL. It is not the Phone Access credential unless a secure bridge is explicitly implemented.
- `Stable travel URL`: the URL the user expects to use both at pairing time and while traveling, preferably a Tailscale Serve HTTPS URL.

## Legacy Removal Policy (Mandatory)

- Policy: `No backward compatibility; remove legacy code paths.`
- Required action: There is no existing Android implementation to remove. The design explicitly rejects compatibility layers that would duplicate core behavior or preserve multiple Android launch paths.
- Treat removal as first-class design work: if implementation prototypes create Android-native run/chat/pairing clones or broad bridge adapters, remove them before delivery.
- Decision rule: the design is invalid if it depends on Android-side backend/runtime behavior, a duplicated native mobile UI, arbitrary-origin WebView loading, or dual credential authorities.

## Return Or Event Spine(s) (If Applicable)

- Pairing success return: `RemoteAccess Pairing Exchange -> MobileNodeSessionStore -> mobileCredentialStorage(localStorage) -> Mobile Shell active state`. Android does not need to intercept this in MVP because future launches load the same origin and the web session restores itself.
- WebView load failure return: `WebViewClient error/status callback -> WebViewErrorMapper -> ConnectionDiagnosticMapper -> Recovery UI`.
- QR scan result return: `Android QR Scanner Activity Result -> PairingLinkParser -> SavedNodeStore + WebViewHost.load(pairingUrl)`.
- App resume return: `Android lifecycle onResume -> AndroidAppShellViewModel -> optional saved URL validation -> WebView remains active or recovery UI`.

## Bounded Local / Internal Spines (If Applicable)

- Parent owner: Android app-shell state owner.
  - `NoSavedNode -> AwaitingInput -> ValidatingNode -> OpeningWebView -> WebViewActive -> RecoverableError -> AwaitingInput/Retry`
  - Why it matters: prevents blank WebView states and ensures unreachable Tailscale/desktop issues become product recovery states.
- Parent owner: Trusted Navigation Policy.
  - `Navigation Request -> Parse URI -> Validate scheme -> Validate host/origin -> Classify path -> Allow WebView / Open External / Block + Diagnostic`
  - Why it matters: WebView security depends on exact scheme/host validation, not string contains/startsWith checks.

## Ownership Boundaries

- Android Shell boundary: native setup, saved profiles, reachability diagnostics, WebView containment. It may call public remote-access status for validation but must not own AutoByteus application behavior.
- Mobile Web Shell boundary: all product screens and actions after `/mobile` loads, including pairing exchange, session restore, run/chat/files/tools behavior.
- Remote Access backend boundary: pairing/session/credential/device authorization. Android must not create a parallel credential authority.
- Tailscale boundary: network reachability. AutoByteus Android may deep-link/open Tailscale or provide instructions, but must not implement or manage the VPN.

## Dependency Rules

Allowed:

- Android Connection Screen may call PairingLinkParser, NodeUrlNormalizer, ConnectionValidator, SavedNodeStore, and WebViewHost.
- Android ConnectionValidator may call only public `/rest/remote-access/status` on the selected node.
- Android WebViewHost may load saved `/mobile` URLs and same-origin AutoByteus paths only after TrustedNavigationPolicy approval.
- Existing mobile web may continue calling existing REST/GraphQL/WebSocket endpoints with its stored credential.
- Desktop Phone Access may update copy/docs and continue creating QR/link through existing backend.

Forbidden:

- Android app must not call agent/team/runtime/run APIs directly except as web content inside existing `/mobile` does.
- Android app must not implement a second pairing exchange/credential lifecycle unless a secure storage bridge is separately designed and origin-restricted.
- Android app must not bypass TrustedNavigationPolicy by loading arbitrary URLs.
- Android app must not read official Tailscale app private data/device list.
- Backend core must not special-case Android app clients for run/chat semantics.
- PWA support must not add offline caching of authenticated content in this ticket.

## Key Tradeoffs

- Native WebView shell vs TWA: WebView requires more security work but supports user-selected private URLs and native recovery UX. TWA does not fit the private-tailnet product shape.
- WebView localStorage credentials vs native secure storage: localStorage reuses current mobile behavior and avoids a risky bridge; native secure storage is stronger but must be origin-restricted and carefully designed.
- Tailscale Serve HTTPS vs raw tailnet IP/HTTP: Serve is smoother and more secure for travel; HTTP tailnet URLs are easier to set up but create cleartext/WebView friction.
- Native URL validation vs letting WebView fail: validation adds code but produces a product-quality recovery journey instead of raw 403/network pages. Recovery actions should remain available without becoming permanent healthy-state chrome.
- Manifest-only PWA vs full PWA: manifest-only improves installability without cache/auth risks; full PWA/offline behavior should be separate.

## Risks

- Pairing with the wrong origin: if the user pairs on LAN IP then travels via Tailscale HTTPS hostname, credentials may not restore. Mitigation: docs/copy and app setup should emphasize pairing through the stable travel URL.
- Cleartext HTTP: Android WebView/network security may block or warn on HTTP. Mitigation: prefer Tailscale Serve HTTPS; allow HTTP only intentionally.
- Tailscale split tunneling: user may exclude AutoByteus app from tailnet. Mitigation: diagnostic copy and open-Tailscale action.
- Desktop asleep/offline: Android cannot fix this. Mitigation: docs state desktop must be running/awake and connected.
- WebView bridge risk: any native bridge can expose sensitive data if not origin-restricted. Mitigation: no bridge in MVP, or bridge only with exact origin checks and tests.
- Android build ecosystem drift: new Gradle/Kotlin dependencies can create maintenance burden. Mitigation: keep app small and Android-only.
- Native wrapper chrome drift: Android utility controls can accidentally make the app feel like a browser and waste vertical space. Mitigation: healthy state is full-screen WebView; utility actions move to diagnostic/overflow/re-entry surfaces.

## Guidance For Implementation

- Treat this as Android shell packaging, not a core refactor.
- Start with the simplest working path: saved URL -> full-screen WebView `/mobile` -> existing mobile behavior.
- Use the stable Tailscale URL before pairing in demos/tests.
- Validate URI scheme/host with parsed URI objects, not string `contains`/`startsWith`.
- Keep `addJavascriptInterface` out of the first implementation unless secure credential storage is explicitly accepted; if added, scope it to the exact saved origin and test arbitrary-origin denial.
- Prefer `https://<machine>.<tailnet>.ts.net/mobile` in docs and examples.
- In healthy WebView state, do not show a permanent Android title/URL/action bar. The user should see the existing mobile web app using the available viewport. If native Edit Node / Retry / Browser controls are needed, expose them through a compact overflow/bottom sheet or only from diagnostic and connection screens.
- Validate the UX with a screenshot/UIAutomator check after opening a reachable saved node: no visible `EDIT NODE`, `RETRY`, or `BROWSER` header should push down the `/mobile` content.
- If implementation must touch `autobyteus-web` beyond docs/manifest/head metadata, explain why in the implementation handoff and prove no desktop/mobile regressions.
- Give API/E2E an explicit real-device validation path. If the user-provided Android phone is connected by USB, visible through `adb devices`, signed into Tailscale, and the desktop/server node is also signed into Tailscale, live E2E is achievable. Use pasted QR/link or manual stable URL for deterministic automation; treat camera QR scan as a manual smoke check if needed.
- Do not require Electron packaging for every Android E2E run. API/E2E can validate the Android wrapper against a development AutoByteus node that serves `/mobile` and remote-access endpoints. Require a packaged Electron smoke only when final release readiness includes packaged desktop behavior or when delivery provides a built desktop artifact.
- If implementation touches backend run/chat/runtime code, stop and raise a design-impact question; that is outside this ticket's intended boundary.
